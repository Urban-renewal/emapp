EMAPP · Decisions Log

Purpose: One place for every architectural decision worth more than 5 minutes of discussion. Each entry: what, when, why, alternatives, reversibility, revisit trigger.

How to use: When you make a decision, add an entry the same day (don't batch — see WORKFLOW.md §A.4). When someone asks "why did we do X?", point them here. When tempted to reverse a decision, read its entry first.

Format:

## D.NN — Title
Date · Decision · Alternatives · Why · Reversibility · Revisit trigger

Last updated: 2026-05-16 — D.16-D.20 propagated across all 9 planning docs (envelope, /api/v1/, 6 roles, status enum, national_id, Tenant→SMS).

D.01 — Stack: Neon + Railway + Cloudflare + Resend + Sentry

  • Date: 2026-05 (v2 architecture)
  • Decision: MVP runs on Neon (Postgres), Railway (BE + Worker containers), Cloudflare (R2 storage + Pages hosting), Resend (email), Sentry (monitoring). GitHub for code + CI.
  • Alternatives: AWS (RDS+ECS+S3+SES), Vercel+Supabase, Koyeb (was in v1), Render, Fly.io.
  • Why: Lowest operational overhead for a 2-person team; generous free tiers ($0-6/mo at MVP scale); each service swappable via the interface layer (Doc 02 §6). Neon's branching is excellent for migration testing. Railway's container model fits BE+Worker cleanly.
  • Reversibility: Medium (interface layer protects app code; infra config would change).
  • Revisit trigger: ~50 paying orgs (cost), or a provider degrades materially.
  • Ref: Doc 02 §4

D.02 — ORM: Drizzle (not Prisma)

  • Date: 2026-05
  • Decision: Drizzle ORM for all DB access.
  • Alternatives: Prisma, Kysely, raw SQL with pg.
  • Why: Generates readable SQL (no opaque engine binary), no runtime query-engine overhead, native-feeling TypeScript types, migrations are owned files. Prisma's engine binary added edge-deploy complexity.
  • Reversibility: Hard (ORM switch = rewrite all queries).
  • Revisit trigger: Drizzle abandons maintenance, or a blocking bug with no workaround.
  • Ref: Doc 02 §4.3, Doc 04a §2.6 C.01

D.03 — Auth: Better Auth (not Clerk/Auth0)

  • Date: 2026-05
  • Decision: Better Auth, self-hosted in our codebase.
  • Alternatives: Clerk, Auth0, Lucia, hand-rolled.
  • Why: Full control over the auth flow + data; no per-MAU pricing that punishes growth; MFA, magic links, sessions all supported; PII stays in our DB (important for Israeli privacy posture).
  • Reversibility: Hard (auth touches every request path).
  • Revisit trigger: Enterprise SSO/SAML demand that Better Auth can't meet (Phase 2+).
  • Ref: Doc 02 §4.4, Doc 07 §6

D.04 — Cache: PostgresCacheProvider in MVP (not Redis)

  • Date: 2026-05
  • Decision: ICacheProvider implemented with a Postgres cache_kv table in MVP. Upstash Redis deferred to Growth.
  • Alternatives: Upstash Redis from day 1, self-hosted Redis, Memcached.
  • Why: Minimal Runtime principle — one fewer service. Postgres handles MVP cache load (~10k ops/sec) easily. Interface lets us swap to Upstash with no app-code change.
  • Reversibility: Easy (swap the ICacheProvider implementation).
  • Revisit trigger: ~10 paying orgs, or cache_kv p95 > 10ms.
  • Ref: Doc 02 §4.5, §14.4, Doc 04a §2.6 C.02

D.05 — Provider tier: separate DB role + table (not is_admin boolean)

  • Date: 2026-05
  • Decision: EMAPP-internal access is a structurally separate tier — provider_users table, provider_app_role DB role with BYPASSRLS, withProvider() wrapper, MFA mandatory, all access audited.
  • Alternatives: is_admin boolean on users; a "superadmin" org; impersonation.
  • Why: A boolean flag is one bug away from privilege escalation. Structural separation means a customer JWT can never reach provider data even if RBAC has a bug. Defense in depth.
  • Reversibility: Hard (schema + auth + RLS all depend on it).
  • Revisit trigger: Never (this is foundational).
  • Ref: Doc 02 §10, Doc 07 §11, Doc 04c P1.3, Doc 04a §2.6 C.03

D.06 — PII encryption: pgcrypto field-level (not disk-only)

  • Date: 2026-05
  • Decision: national_id and phone and signature_blob encrypted at the field level via pgcrypto, with a separate PII_HASH_KEY for HMAC search. Two distinct keys.
  • Alternatives: Disk encryption only (Neon default), app-level encryption, no encryption.
  • Why: Disk encryption doesn't protect against a leaked connection string. Field-level means a DB dump without the key is useless. HMAC enables search without decryption.
  • Reversibility: Hard (re-encryption ceremony required — Doc 07 §14).
  • Revisit trigger: Never routinely. Only on confirmed key compromise.
  • Ref: Doc 07 §5, §14, Doc 04c P1.5

D.07 — Soft delete: archivedAt (not deletedAt)

  • Date: 2026-05 (v2 rename)
  • Decision: Soft delete uses archived_at timestamp. UI verb is "ארכוב" (archive), never "מחיקה" (delete). Hard delete is a Provider-only audited operation.
  • Alternatives: deleted_at (v1 name), hard delete, status enum.
  • Why: "Archive" communicates recoverability to users; legal/audit requirements forbid true deletion of signature/owner data; the rename from v1 avoids the implication that data is gone.
  • Reversibility: Easy (it's a naming + UX convention).
  • Revisit trigger: Never expected.
  • Ref: Doc 04c §4, Doc 05 §16, Doc 06 §16

D.08 — Buildings/Owners: single table with enum (not CTI)

  • Date: 2026-05 (v2 simplification)
  • Decision: One buildings table with a type enum; one owners table with a type discriminated union. No Class-Table-Inheritance child tables.
  • Alternatives: v1's CTI (residential_buildings / mixed_use_buildings / commercial_buildings; individual_owners / company_owners / inheritance_owners).
  • Why: CTI added join complexity and bug surface for marginal modeling benefit at MVP scale. Single table + enum + Zod discriminated union is simpler and faster.
  • Reversibility: Medium (could split later if a type's fields diverge significantly).
  • Revisit trigger: A building/owner type accumulates many type-specific columns.
  • Ref: Doc 04c §4, Doc 06 §16.1

D.09 — RLS: ENABLE + FORCE on all multi-tenant tables

  • Date: 2026-05
  • Decision: Every multi-tenant table has ENABLE ROW LEVEL SECURITY + FORCE ROW LEVEL SECURITY. app_user is not the table owner. Org context set via SET LOCAL app.organization_id.
  • Alternatives: App-level WHERE filters, separate schema per tenant, separate DB per tenant.
  • Why: RLS is enforced by Postgres even if app code has a bug. FORCE ensures it applies even to the table owner. The single highest-leverage tenant-isolation control.
  • Reversibility: Hard (the entire tenancy model depends on it).
  • Revisit trigger: Never (foundational). Tested by T1.5 (CI gate).
  • Ref: Doc 07 §10, Doc 04c P1.11

D.10 — API versioning: /api/v1/ from day 1

  • Date: 2026-05
  • Decision: Every endpoint is prefixed /api/v1/. v2 only for genuinely breaking changes, runs parallel during deprecation.
  • Alternatives: Unversioned /api/, header-based versioning, no versioning.
  • Why: Retrofitting a version prefix later is a breaking change for every client. The cost now is one line (app.setGlobalPrefix('api/v1')).
  • Reversibility: Hard once clients exist (that's the point of doing it now).
  • Revisit trigger: Never reverse. v2 prefix added when a true breaking change is unavoidable.
  • Ref: Doc 06 §5.1

D.11 — Hebrew collation: ICU he_il_icu per-column

  • Date: 2026-05
  • Decision: CREATE COLLATION he_il_icu (provider=icu, locale='he-IL-x-icu'). Applied per-column / per-query on Hebrew name fields, not as the DB default.
  • Alternatives: DB-level LC_COLLATE, app-side sort with Intl.Collator, no collation (byte order).
  • Why: Byte-order sorting makes Hebrew name lists nonsense. Per-column keeps English fields sorting by English rules. DB-default would be a one-way global decision.
  • Reversibility: Easy (it's additive — add/remove COLLATE clauses).
  • Revisit trigger: If full-text Hebrew search is added (Phase 2), revisit alongside pg_trgm.
  • Ref: Doc 04c P1.10

D.12 — Signature format: SVG, encrypted, inline (not R2)

  • Date: 2026-05
  • Decision: Signatures captured as SVG, encrypted with pgcrypto (same PII_ENCRYPTION_KEY), stored inline as bytea in signatures. 50KB max. Plus a documentHash (SHA-256) for tamper detection.
  • Alternatives: PNG, raw points; storage in R2; unencrypted.
  • Why: SVG is vector (scales for print), small (~5-15KB). Inline keeps the encryption story identical to other PII and avoids a second round-trip for small, tightly-coupled data.
  • Reversibility: Medium (format column allows future PNG; storage move is a migration).
  • Revisit trigger: If wet-ink scan upload is needed (would add PNG/JPG path).
  • Ref: Doc 04c P1.8

D.13 — Cookie consent: no banner in MVP (Israeli law)

  • Date: 2026-05
  • Decision: No cookie banner in MVP. Disclosure in Terms/Privacy page. Only 4 essential cookies. Banner becomes required only when analytics are added (Phase 2) or on EU expansion.
  • Alternatives: EU-style banner from day 1, no disclosure at all.
  • Why: Israeli privacy law (חוק הגנת הפרטיות) doesn't mandate the EU banner; essential cookies need no consent. A banner without legal need is pure friction.
  • Reversibility: Easy (add banner when analytics land).
  • Revisit trigger: Adding analytics (Phase 2), or non-trivial EU user base.
  • Ref: Doc 07 §6.14

D.14 — First-org bootstrap: self-serve signup

  • Date: 2026-05
  • Decision: Self-serve signup. POST /api/v1/auth/signup → magic link → creates org + user + manager membership + audit. Always returns 202 (anti-enumeration). No external approval. Provider Admin can also manually onboard.
  • Alternatives: Manual onboarding only (Provider creates every org), invite-only, payment-gated.
  • Why: 0-3 pilot customers; an "await approval" gate creates 30%+ drop-off. Accept the duplicate-org trade-off (Provider Admin can merge — Phase 6).
  • Reversibility: Easy (can add approval gate later).
  • Revisit trigger: Spam signups, or when billing is added (Phase 2).
  • Ref: Doc 03 Phase 2

D.15 — Worker scope: SSE + cleanup + retry only (MVP)

  • Date: 2026-05
  • Decision: The Worker container does exactly three things in MVP: SSE push for notifications, hourly cleanup of expired tokens, 5-min retry of failed email/storage calls. Nothing else.
  • Alternatives: Run jobs inside the BE container; a full job-queue system (BullMQ); more background jobs.
  • Why: Separation keeps BE stateless and deployable without dropping SSE clients. Three jobs is the genuine MVP need; more is speculation.
  • Reversibility: Easy (add jobs as needed).
  • Revisit trigger: Real need for digests/analytics/OCR background work (Phase 2).
  • Ref: Doc 02 §5.8

D.16 — JSON envelope: { data } wrapper + page object

  • Date: 2026-05-16
  • Decision: Every response wraps in { "data": ... }. Lists add { "data": [...], "page": { "limit", "cursor", "has_more" } }. Errors: { "error": { "code", "message", "details?" } }. Unpermitted Contractor fields are absent (not null).
  • Alternatives: Bare entity + { items, nextCursor } (our v1 draft).
  • Why: Adopted the partner's envelope — it's a consistent, evolvable REST pattern; the explicit has_more boolean is cleaner than inferring from a null cursor; the field-absence rule serves the Contractor permission model well.
  • Reversibility: Hard (every endpoint + adapter + mock depends on it).
  • Revisit trigger: Never expected; this is the locked wire contract.
  • Ref: Doc 06 §5.5, §4.9 (RECONCILIATION.md Delta 1)

D.17 — MVP core roles = 6 (Manager/Agent/Viewer/Contractor/Tenant/Provider Admin)

  • Date: 2026-05-16 (revised same day after user decision)
  • Decision: MVP has SIX roles, not five. The user confirmed BOTH Viewer AND Tenant are MVP needs. Canonical set: Manager, Agent, Viewer, Contractor, Tenant (resident, SMS OTP), Provider Admin. "Provider Admin" is the canonical name (not "Admin/Super-admin").
  • Alternatives: (a) Our v2 draft: 5 roles, Tenant Portal deferred to Phase 2. (b) Partner's draft: 5 roles with Tenant but no Viewer.
  • Why: User has customers needing read-only access (Viewer) in MVP, AND residents who need portal access from day one (Tenant). Both are real MVP needs, not Phase 2. Resolving the confusion: it was never "which 5" — it's 6.
  • Reversibility: Hard. Tenant adds an identity model + SMS auth + portal screens + tenant-scope RLS. This is a material scope expansion, consciously accepted.
  • Revisit trigger: None — this is the locked MVP role set.
  • Ref: Doc 01 §5, Doc 02 §10, Doc 06 §16.2 (supersedes RECONCILIATION.md Delta 3)

D.20 — Tenant in MVP → SMS OTP in MVP (Israeli SMS provider, not Twilio)

  • Date: 2026-05-16
  • Decision: Because Tenant (D.17) is MVP, SMS OTP authentication is MVP — pulled forward from Phase 2. MVP uses an Israeli SMS provider (019 / Inforu / similar) behind the existing ISMSProvider interface, NOT NoopSMSProvider, NOT Twilio.
  • Alternatives: (a) Twilio (more expensive for Israeli numbers, worse local deliverability). (b) Email magic link for tenants (rejected — many elderly owners in urban renewal have no active email; SMS is universal in Israel).
  • Why: Residents in תמ"א 38 / פינוי-בינוי are often elderly and email-averse; SMS is universal. An Israeli provider is materially cheaper per-SMS for +972 numbers and has better local deliverability. The ISMSProvider interface (designed in Doc 02 §6) means this is a provider swap, not an architecture change — the interface layer paying off exactly as intended.
  • Reversibility: Easy (provider swap behind interface). The decision to have Tenant at all (D.17) is the hard part; the SMS provider choice is soft.
  • Revisit trigger: SMS costs become significant (>~₪500/mo) → reevaluate providers; or international expansion → add Twilio alongside.
  • Ref: Doc 02 §6 (ISMSProvider), Doc 06 §16.2, OPEN_ITEMS.md (SMS moved from Phase 2 → MVP)

D.21 — Auth architecture: full ownership (argon2id + domain-DB sessions), Better Auth removed as orchestrator

  • Date: 2026-05-18
  • Decision: Own the entire authentication stack. Password hashing via argon2id (OWASP params). Credentials, sessions and refresh tokens live in the domain database (RLS-aware), not in a separate Better Auth store. Signup is a single atomic transaction (org + user + membership + credential + audit) via the audited withProvider bootstrap. Refresh tokens are stored hashed (SHA-256) with rotation-on-use and reuse-detection (replay ⇒ revoke all sessions + audit). Better Auth is removed from the request path (it was used only for password hashing behind a custom JWT + manual-refresh hybrid). The locked stack entry "Auth: Better Auth" (CLAUDE.md) is hereby superseded by this decision.
  • Alternatives: (a) Keep Better Auth, full adoption — rejected: its HTTP/session model does not satisfy the locked wire contract (stateless JWT with mandated claims, opaque hashed refresh in a sessions table, {data} envelope, /api/v1 prefix, RLS via withTenant), and the domain bootstrap would still span its store + ours non-atomically. (b) Patch the hybrid per-finding — rejected: orphaned-account / non-atomic-signup / plaintext-refresh / logout-not-revoking are all symptoms of the two-store hybrid; point fixes are plasters that retain the unsafe topology.
  • Why: A single store + single transaction makes the orphaned-account class of bug structurally impossible rather than "fixed". It is the only option that satisfies auth invariant #1 (atomic signup). The surface lost from Better Auth is password hashing only — replaced by a vetted argon2id library. For a 2-dev team facing security review (ISO 27001 A.8.5/A.8.24/A.8.25/A.8.26), a fully-understood auth module is more defensible than a library fighting the spec contract.
  • Risk & acceptance: Hand-written auth carries hand-rolled-auth risk. Contained by: black-box invariant contract suite written before the code; @security-reviewer on the diff pre-commit; argon2id not hand-rolled; rate-limit/lockout at the framework layer. Residual risk accepted by the product owner on this date as the lower-risk path versus shipping the broken hybrid.
  • Reversibility: Hard. Auth touches schema, sessions, and every guarded route. Treated as a one-way door — hence this record + Gate 6.
  • Revisit trigger: A managed auth provider (WorkOS/Auth0) is adopted org-wide, or the contract invariants change materially.
  • Ref: Doc 07 §6, Doc 08, GATES.md (Gate 6), Phase 2 audit + black-box conformance (PROGRESS.md)

D.22 — Production security-design hardening backlog (interim risk acceptance + remediation plan)

  • Date: 2026-05-18
  • Decision: A principal-level design review (docs-only) found four DESIGN-level gaps that are NOT code bugs and that a reckless mid-hardening rebuild would only turn into plasters. They are formally ACCEPTED as interim MVP risk with a dated remediation plan, per ISO 27001 risk-treatment governance, rather than rebuilt now:
    1. (A) Encryption-key blast radius. PII_ENCRYPTION_KEY is injected as a readable GUC (SET LOCAL app.encryption_key) on every withTenant tx and is process-resident. An app-level compromise (SQLi defeating Drizzle params, errant RAISE, current_setting readback) exposes the key for ALL tenants — the "DB dump is useless" claim holds only for cold-leak, NOT app-compromise. Remediation (own workstream, before enterprise/BYOK or first external pentest): move decrypt into an explicit-GRANT SQL function so the key is never a readable GUC; design envelope encryption / per-tenant DEK. Interim control: Drizzle parameterization everywhere (enforced), no raw SQL in app code (ESLint), key never logged (pino redaction).
    2. (B) Audit log not tamper-evident. Append-only via withheld DELETE grant stops the app role only; anyone with the Neon connection string / console can DDL. Not STRIDE-R / ISO-repudiation grade. Remediation: hash-chain rows + periodic external WORM mirror (later phase). Interim: the "cannot erase their tracks" claim is hereby DOWNGRADED to "the application cannot erase tracks"; infra-level access is covered by Neon access control + Infisical.
    3. (D) Neon connection/pooling model undecided. SET LOCAL×2–3 round-trips/request + scale-to-zero on the login path; ~100 req/s ceiling at the guessed 20-conn direct pool. Remediation (before Gate 5): pin pooled-transaction (PgBouncer) vs direct, validate SET LOCAL-in-tx under it, size the pool against measured concurrency. Tracked as a Gate-5 pre-launch checklist item.
    4. (F) No server-side idempotency key on legally-weighty POSTs. /auth/signup is effectively idempotent on the unique email + anti-enum neutral duplicate path + tight throttle (acceptable). /signatures (Phase 5, not yet built) MUST get an idempotency key — recorded here as a hard Phase-5 requirement so a network partition cannot double-sign.
    (C) secrets-model doc contradiction and (E) D.21 doc-incoherence were NOT deferred — they were FIXED 2026-05-18: Doc 07 §5.5/§15 reconciled to Infisical-only; D.21 propagated to CLAUDE.md + Doc 07 §6.2/§6.3 banner.
  • Why: ISO 27001 does not require zero risk — it requires every risk identified, owned, treated or consciously accepted with a plan. Rebuilding Phase-1 pgcrypto / audit tamper-evidence inside Phase-2 hardening would be high-blast-radius scope creep and itself the "plaster" anti-pattern. Documented acceptance + dated plan is the correct, defensible posture.
  • Risk & acceptance: Product owner accepts A, B, D, F as interim MVP risk on 2026-05-18; none is a launch blocker for a 0–100-org pilot, ALL are pre-scale / pre-enterprise / pre-external-pentest blockers and are now tracked.
  • Reversibility: Each remediation is its own gated workstream; this entry is the tracking anchor.
  • Revisit trigger: first enterprise/BYOK demand, first external pentest, >100 orgs, or Gate 5 (pre-launch) — whichever first.
  • Ref: Principal design critique (PROGRESS.md), Doc 02 §5.4/§8, Doc 07 §5/§8, Doc 08 §5, GATES.md (Gate 5)

D.23 — No separate packages/ui; shared UI lives in apps/web/src/components/ui (single-FE MVP)

  • Date: 2026-05-18
  • Decision: P0.3 named three empty packages: shared-types, config, ui. shared-types and config exist and are real. A separate packages/ui is intentionally NOT created — there is exactly ONE frontend (apps/web), and shadcn/ui's own convention places primitives in apps/web/src/components/ui/. A shared UI package only earns its keep with ≥2 consumers; creating an empty/contrived one now is YAGNI and adds a build edge for zero benefit. apps/web/src/components/ui/ is the canonical shared-UI location for the MVP.
  • Alternatives: (a) create packages/ui and move button.tsx there — rejected: single consumer, pure overhead, complicates the FE-component handoff flow (BUILD_LAYER_2 §2.3) which expects components inside the Next.js app. (b) Leave it undocumented — rejected: a named P0.3 deliverable cannot silently vanish before an ISO-bound phase; this entry is the audit-trail record.
  • Why: matches shadcn convention + the partner-component handoff (components land in the Next.js app, not a package), keeps the build graph minimal. Revisit only if a second FE (e.g. native/admin) appears.
  • Reversibility: Easy — extracting packages/ui later is mechanical if a second consumer ever exists.
  • Revisit trigger: a second frontend/consumer of shared components.
  • Ref: BUILD_LAYER_4 P0.3, BUILD_LAYER_2 §2.3, pre-Phase-3 verification (PROGRESS.md)
