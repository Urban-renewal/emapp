01 · Overview

Why This Matters

A professional Claude Code setup is not a one-time chore. It's a system that compounds value over time.

Without setup, every Claude Code conversation starts from zero: explaining the stack, repeating coding rules, fighting inconsistent decisions. With proper setup, Claude has persistent context. It knows you use Drizzle (not Prisma), that every DB query goes through withTenant(), that tests come before code. The cumulative time saved over 12 months is measured in weeks.

1.1 What This Document Covers

Three interlocking systems that together form a sustainable development environment:

🤖Claude Code Configuration

CLAUDE.md files, slash commands, hooks, and prompt templates. The contextual brain Claude uses every time you open a session.

🌿Version Control Workflow

Branching strategy, conventional commits, semantic versioning, automated CHANGELOG, GitHub release tagging. The discipline that keeps the codebase auditable and revertible.

🔄Long-term Maintenance

Team collaboration patterns, how to update setup as the project grows, handoff between team members, context window management.

1.2 Setup Order

Build it in this order. Each layer builds on the previous. Skipping ahead creates friction:

  • Root CLAUDE.md — without this, nothing else makes sense to Claude.
  • Branching strategy + conventional commits — establishes git discipline before there's much code to lose.
  • Slash commands (3-5 essential) — automates the most repetitive tasks first.
  • Hooks — adds enforcement of rules that were previously voluntary.
  • Per-package CLAUDE.md — added as you create each package during Phase 0.
  • CHANGELOG + release process — set up before first release, not after.
  • Prompt templates — internalized as you discover patterns, not predefined.

1.4 The Junior Framing — How to Think About Claude

The single biggest predictor of whether a team gets value from Claude Code or fights it is one mindset choice: treat Claude like a capable Junior developer. Not as an oracle. Not as a search engine. Not as a black box. A Junior who happens to have read enormous amounts of code, who can implement at speed, and who needs the same things any Junior needs.

What a Junior developer needs:

  • Clear context. The codebase conventions, the stack, the "why" behind decisions. A Junior who doesn't know you use Drizzle (not Prisma) will reach for Prisma. That's CLAUDE.md's job — give the Junior the orientation no one re-explains every conversation.
  • Specific tasks, not abstract goals. "Implement the user service" produces 5 different things from 5 different attempts. "Implement UsersService.create(orgId, input) following the pattern in ProjectsService.create, with Zod validation on input, withTenant wrapping the DB call, and a unit test mirroring projects.spec.ts" produces one consistent thing every time.
  • Review of output, not blind acceptance. You wouldn't merge a Junior's PR without reading it. Don't accept Claude's diff without reading it either. The Junior will sometimes invent APIs, miss edge cases, or imitate the wrong file. Reading the diff catches this.
  • Pushback when the task is wrong. A good Junior says "that's not what I'd build — here's why." Claude does this too if you set the expectation. When Claude suggests an alternative, take it seriously. It's not insubordination; it's craftsmanship.
  • Permission boundaries. A new Junior doesn't deploy to prod on day one. Same for Claude — the "Actions requiring explicit approval" section in CLAUDE.md (Section 2.4) is exactly this: the operations Claude needs to ask about before doing.

What this framing rules out:

  • Treating Claude as infallible. ("It said so, must be right.") — No. Read the diff.
  • Treating Claude as useless. ("It'll get it wrong; I'll write everything myself.") — No. A Junior who can implement 200 lines an hour is valuable; you just review their work.
  • Treating Claude as a search engine. ("How do I do X?") — Sometimes fine, but Claude shines when given tasks, not questions.
  • Treating Claude as a contractor needing zero context. ("Just build it.") — No. Give the same orientation you'd give any new team member.

This framing shapes every choice in this document — from the structure of CLAUDE.md (orientation for a Junior) to slash commands (recipes a Junior can follow) to the approval-required list (what a Junior doesn't decide alone).

1.5 The 150-Rule Ceiling

CLAUDE.md grows over time as the team learns. A new rule after every bug, a new convention after every refactor, a new "don't" after every mistake. This is fine — until the file becomes so long that Claude's actual instructions get diluted.

Practical ceiling: ~150 rules per CLAUDE.md file. Empirically, above this:

  • Claude's attention to any individual rule degrades — instructions far down the file get less weight than instructions at the top
  • The team stops reading the file; rules drift from reality
  • Contradictions creep in as the file grows without a global audit
  • Token cost per session grows linearly with file size

What to do when approaching the ceiling:

  • Split by scope. Move package-specific rules to packages/<name>/CLAUDE.md. Claude picks up the nearest CLAUDE.md by directory. This naturally shards the rules.
  • Promote rules to enforcement. If a rule is consistently followed, encode it: ESLint rule, hook, type system, code review checklist. Then remove it from CLAUDE.md (you don't need to remind Claude of things the tooling enforces).
  • Demote rules to learnings. Some "rules" are actually one-off learnings ("we hit X bug once"). Move to learnings.md (see Section 2.6) — not part of every session, but available when relevant.
  • Move design rationale to constraints.md. Big architectural choices ("why we chose Drizzle over Prisma") belong in their own document. CLAUDE.md says what to do; constraints.md says why we decided this way.
⚠ The Anti-Pattern
A CLAUDE.md with 300 rules feels comprehensive but performs worse than a CLAUDE.md with 80 rules. Counterintuitive, but real. Quality > quantity. When you hit ~150, audit and shard — don't keep adding.
02 · CLAUDE.md Files

Project Context Files

CLAUDE.md is the single most important file for Claude Code productivity. It loads into every conversation.

2.1 The Hierarchy

Claude Code reads CLAUDE.md files at multiple levels:

  • Root /CLAUDE.md — Project-wide context, stack, hard rules, and conventions. Loaded for any conversation about the project.
  • Per-package /packages/<name>/CLAUDE.md — Loaded when Claude works in that subdirectory. Contains package-specific patterns.
  • Per-app /apps/<name>/CLAUDE.md — Same as packages, for the application code.

Together these create a layered context system: general project knowledge plus specific local knowledge.

2.2 Root CLAUDE.md — Full Template

This is the foundation. Keep it under 200 lines. Update it as the project evolves.

CLAUDE.md (project root)
# Urban Renewal SaaS — Project Context

## What this project is
SaaS platform for managing urban renewal projects in Israel (תמ"א 38, פינוי-בינוי).
Multi-tenant B2B for small-medium real estate developers (SMB).
Hebrew + English UI from day one. Arabic and Russian planned.

## Critical priorities (in order — when in doubt, refer to this)
1. Security — sensitive PII (national IDs, signatures, deeds, contracts)
2. Performance — API p95 < 200ms, imports < 30s
3. Portability — no vendor lock-in, can migrate any component

## Repository structure
Monorepo: Turborepo + pnpm workspaces.
```
apps/
  api/           — NestJS 11 backend
  web/           — Next.js 15 frontend
packages/
  shared-types/  — Zod schemas (source of truth, used by FE+BE)
  db/            — Drizzle schema, migrations, RLS, withTenant
  config/        — T3-env validation, constants
  validators/    — Israeli ID Luhn, business rules
```

## Stack (final, do not suggest alternatives)
- Backend: NestJS 11 + Fastify adapter
- ORM: Drizzle ORM (NOT Prisma)
- Validation: Zod (everywhere — FE, BE, DB)
- Database: PostgreSQL 16 + RLS + pgcrypto (PostGIS + pgvector deferred to Phase 2)
- DB hosting: Neon (Free in MVP, Launch when ~10 orgs)
- Auth: Better Auth (NOT Clerk, NOT Auth0); MFA mandatory for Provider tier
- Cache: PostgresCacheProvider (cache_kv table) in MVP; Upstash Redis in Growth phase
- Storage: Cloudflare R2 via AWS SDK (S3-compatible)
- Frontend: Next.js 15 App Router + shadcn/ui + TanStack Query
- Backend hosting: Railway (Hobby $5 in MVP — BE container + Worker container)
- Frontend hosting: Cloudflare Pages
- Email: Resend (via IEmailProvider interface)
- Monitoring: Sentry
- Monorepo: Turborepo + pnpm

## Identity model (6 roles, 3 tiers — see Doc 02 §10): Manager, Agent, Viewer, Contractor, Tenant (SMS OTP), Provider Admin
- Tier 1 (org users): Manager / Agent / Viewer — table `users` + `memberships` (M:N)
- Tier 2 (external): Contractor — table `contractors` + `shares` (JSONB permissions)
- Tier 3 (provider): Provider Admin — table `provider_users` + DB role `provider_app_role` with BYPASSRLS

## Hard rules (non-negotiable)

RLS Rule:
Every database read goes through `withTenant(orgId, fn)` (customer code) or
`withProvider(providerUserId, reason, fn)` (support tooling).
Direct `db.query.X` is forbidden. ESLint will reject it.

Type Safety Rule:
No `any`. No `unknown` without `z.parse()`. Use `noUncheckedIndexedAccess`.

Validation Rule:
Every endpoint receives a DTO that passed Zod parse. No raw `body.x` access.

Schema Rule:
Every API schema lives in `packages/shared-types/`. Never duplicate types in apps/.

Index Rule:
Every column with `organization_id` gets a composite index `(organization_id, ...)`.
Never single-column index on org_id alone.

Storage Rule:
Every file goes through presigned URL. Backend never proxies file uploads/downloads.

Secrets Rule:
No hardcoded secrets. All env vars go through `packages/config/env.ts` (T3-env).

PII Rule:
National IDs are encrypted via pgcrypto. Logs use pino with PII redaction.

Commit Rule:
All commits follow Conventional Commits (feat:, fix:, chore:, docs:, etc.).
See .commitlintrc.json for enforcement.

Branch Rule:
Never commit directly to main. Always feature branch + PR.

## Testing approach
- Unit tests: Vitest
- Integration tests: Vitest with real Postgres + RLS
- E2E tests: Playwright
- All tests must pass before commit
- Coverage target: 70% for services
- The RLS isolation test (T1.5) is the most critical — never skip

## Actions requiring explicit approval
DO NOT do these without asking me first:
- Modify `packages/db/schema/` (existing tables)
- Modify `packages/shared-types/` (existing types)
- Delete files
- `git push --force` (forbidden on main)
- Modify `.env*` files
- Add new dependencies
- Run migrations against any environment
- Modify CI/CD config
- Create release tags or GitHub releases

## Code style
- TypeScript strict mode
- ESLint + Prettier (config in repo)
- Imports: external first, then internal (`@app/*`)
- Comments only when "why", not "what"
- Function names: verbs (`createProject`, not `project`)
- File names: kebab-case (`create-project.ts`)
- Test files: `*.spec.ts` for unit/integration, `*.e2e.spec.ts` for E2E

## When you don't know something
- Ask. Don't guess.
- Reference this file or other CLAUDE.md files in subdirectories.
- If a decision is needed, present options with trade-offs. I decide.

2.3 Per-Package CLAUDE.md Examples

Each packages/* and apps/* directory gets a focused CLAUDE.md (under 50 lines). Add these as you create each package during Phase 0.

apps/api/CLAUDE.md

apps/api/CLAUDE.md
# API — Backend Service (NestJS 11 + Fastify)

## Module structure
Each domain entity gets its own module under `src/modules/<entity>/`:
- `<entity>.service.ts` — business logic, calls withTenant
- `<entity>.controller.ts` — HTTP endpoints, guards, validation
- `<entity>.module.ts` — NestJS module
- `<entity>.spec.ts` — integration tests including RLS isolation

## Required guards on every endpoint
```ts
@UseGuards(AuthGuard, TenantGuard)
@UseInterceptors(ZodValidationPipe)
```

## Service pattern
```ts
async create(orgId: string, userId: string, data: CreateInput) {
  return await withTenant(orgId, async (db) => {
    const result = await db.insert(table).values(data).returning();
    await db.insert(auditLog).values({
      organizationId: orgId,
      actorUserId: userId,
      action: 'entity.created',
      resourceType: 'entity',
      resourceId: result[0].id,
    });
    return result[0];
  });
}
```

## Never
- Call `db` directly in controllers
- Skip Zod validation
- Return raw DB errors to client
- Log JWT tokens or PII
- Catch errors silently

packages/db/CLAUDE.md

packages/db/CLAUDE.md
# Database Package — Drizzle Schema + RLS

## RLS policy template (for every multi-tenant table)
```sql
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;
ALTER TABLE <table> FORCE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON <table>
  FOR ALL
  USING (organization_id = current_setting('app.organization_id')::uuid)
  WITH CHECK (organization_id = current_setting('app.organization_id')::uuid);
```

## withTenant pattern (always use this)
```ts
return await withTenant(orgId, async (db) => {
  return await db.query.projects.findMany();
});
```

## Critical: SET LOCAL vs SET
ALWAYS use SET LOCAL inside transactions. SET persists across pooled connections,
causing cross-tenant data leaks.

## Index rules
- Every FK gets an index (Drizzle auto-creates these)
- Every (organization_id, X) for filtered queries
- Use partial indexes for soft delete: `WHERE deleted_at IS NULL`
- Order by selectivity: most selective first

packages/shared-types/CLAUDE.md
# Shared Types — Zod Schemas (source of truth)

## Purpose
This package defines all data shapes used by both Backend and Frontend.
ZOD SCHEMAS are the source of truth. TypeScript types are inferred.

## Pattern for every entity
```ts
import { z } from 'zod';

export const ProjectSchema = z.object({
  id: z.string().uuid(),
  organizationId: z.string().uuid(),
  name: z.string().min(1).max(200),
  // ...
});

export const CreateProjectInput = ProjectSchema.omit({
  id: true,
  organizationId: true, // injected by guard
  createdAt: true,
  updatedAt: true,
});

export const UpdateProjectInput = CreateProjectInput.partial();

export type Project = z.infer<typeof ProjectSchema>;
export type CreateProject = z.infer<typeof CreateProjectInput>;
export type UpdateProject = z.infer<typeof UpdateProjectInput>;
```

## Re-export from index
Every new schema must be exported in `src/index.ts`.

2.4 When to Update CLAUDE.md

CLAUDE.md is not static. Update it when:

  • You make a new architectural decision (add new pattern, retire old one)
  • You discover a pattern Claude keeps getting wrong (codify the correction)
  • You change the stack (rare, but important to update immediately)
  • You add a new package (add per-package CLAUDE.md)
  • You complete a phase (add what you learned, update common pitfalls)

Don't update for: one-off issues, personal preferences, things that didn't reproduce, things you're not sure about.

⚠️ Avoid the bloat trap
CLAUDE.md should never grow beyond ~150 rules / ~250 lines. If it's getting too long, split into per-package files (Section 2.2) or promote rules to ESLint/hooks (Section 1.5). Long CLAUDE.md files cause Claude to skim, missing important rules. The single most damaging anti-pattern in Claude Code use.

2.5 Sub-Agents — Invoking with @agent-name

For tasks that need a fresh context window (heavy review, deep refactor, focused audit), sub-agents let you launch Claude in a dedicated session without polluting your main conversation. You invoke them with @agent-name at the start of a message.

Sub-agents are defined as files in .claude/agents/. Each file is a small markdown document — name, when to use, system prompt, allowed tools. A reasonable initial set for EMAPP:

.claude/agents/security-reviewer.md
---
name: security-reviewer
description: Reviews a diff for security issues — PII handling, RLS coverage, auth checks. Use after any change that touches owners, signatures, or auth code.
tools: Read, Grep, Glob, Bash
---

You are a focused security reviewer for the EMAPP backend.

Your job: read the provided diff (or files), and identify security issues, ranked
by severity. Focus on:

- PII handling: does anything log national_id, phone, signatures?
- RLS coverage: are all multi-tenant tables ENABLED + FORCED?
- withTenant/withProvider: is every DB call wrapped? Any direct `db.query.X`?
- Audit: does every state-changing operation create an audit log entry?
- Encryption keys: are PII_ENCRYPTION_KEY and PII_HASH_KEY ever logged?
- Error messages: do any leak internal details to the client?

Report format:
1. CRITICAL issues (must fix before merge) — with file:line and exact fix
2. HIGH issues (fix this sprint) — with rationale
3. MEDIUM issues (track for next refactor) — brief mention

Reference Doc 07 (Security Playbook) §9 for the full threat catalog (T01-T10).
Be specific. Be concise. No padding.

Other sub-agents worth defining early:

  • @perf-auditor — runs EXPLAIN ANALYZE on queries, checks RLS subqueries have indexes, flags N+1
  • @test-author — given a service, writes the missing integration tests in the established pattern
  • @migration-reviewer — checks Drizzle migrations for backward-compat, ENABLE+FORCE RLS, index coverage
  • @docs-updater — when a phase completes, updates CLAUDE.md and the relevant Doc to reflect the new state

Usage in main conversation:

main chat
I just finished P1.5 (Owners + PII). Before I commit:

@security-reviewer review the diff at HEAD vs main, focusing on
the new owners.ts schema and pii.ts encryption helpers.

The sub-agent runs in its own fresh context, returns a focused report, and the main conversation continues. No context pollution.

💡 When to use sub-agents vs slash commands
Slash commands (Section 3): you run them, they execute a script-like recipe in your current context. Good for: commits, deploy preparation, repetitive tasks.

Sub-agents (this section): Claude delegates to a fresh session with different instructions. Good for: reviews, audits, deep refactors that would derail the main conversation. Use them when you want a second perspective without losing your place.

2.6 Companion Files — constraints.md and learnings.md

CLAUDE.md says what to do. Two companion files capture the surrounding context:

constraints.md — "Why we decided this way"

The architectural decisions that took hours of debate and shouldn't be re-litigated. Each entry has the decision, the alternatives considered, and the reasoning. Not loaded into every session (it's long), but referenced when an alternative is suggested.

constraints.md (excerpt)
# EMAPP Architectural Constraints

## C.01 — Drizzle ORM, not Prisma

**Decision**: Use Drizzle for all DB access.
**Alternatives considered**: Prisma, Kysely, raw SQL with pg.
**Why Drizzle wins for us**:
- Generates queries we can read — no opaque "Prisma engine" binary
- No runtime overhead from Prisma's query engine
- TypeScript types feel native (Prisma types feel generated)
- Migrations are versioned files we own
**Why Prisma was tempting**:
- Better-known in the Node ecosystem
- Slightly nicer query builder API
**Why we said no anyway**:
- The Prisma engine binary added complexity for our edge deployment scenarios
- The runtime cost matters at our scale
**Reversibility**: Hard. ORM switch = rewrite all queries.

## C.02 — Postgres cache_kv in MVP, not Redis

**Decision**: ICacheProvider has PostgresCacheProvider implementation in MVP.
**Alternatives**: Upstash Redis (managed), self-hosted Redis, Memcached.
**Why Postgres in MVP**:
- Minimal Runtime principle — one fewer service to operate
- Postgres handles ~10k cache ops/sec easily for our access patterns
- The interface (ICacheProvider) lets us swap to Upstash in Growth phase
**When to reconsider**: ~10 paying orgs, or cache_kv p95 exceeds 10ms.

## C.03 — Two DB roles, not one with code-level filters
[...]

Pattern: When someone says "why don't we use Prisma?", you point to constraints.md C.01. Done in 5 seconds.

learnings.md — "What we discovered along the way"

Bugs that bit you, surprises in the stack, gotchas that aren't obvious from the docs. Chronologically ordered. Each entry brief — date, situation, lesson.

learnings.md (excerpt)
# EMAPP Learnings Log

## 2026-02-15 — SET vs SET LOCAL is not interchangeable

**Situation**: A withTenant block worked in tests but leaked tenant context
in production. Investigation: we used `SET app.organization_id = ...`
instead of `SET LOCAL`. SET persists on the pooled connection across
requests. The next request inherited the wrong org.
**Lesson**: SET LOCAL is mandatory. Tests with a single connection (no pool
contention) won't catch this. The CI test T1.5 now uses a pool of 2 to
force connection reuse and surface this class of bug.

## 2026-02-22 — Drizzle's `with` is not lazy

**Situation**: A list endpoint that did `.with({ apartments: true })`
was slow for projects with many apartments. We thought `with` was lazy
like JPA. It's not — it does the join eagerly.
**Lesson**: For lists, return projects only. Apartments are loaded on detail
view. Document the convention in packages/db/CLAUDE.md.

When updating: add new entries at the top (newest first), so the file reads like a journal. Old entries don't disappear — they become institutional memory. New team members read learnings.md to catch up on the war stories.

2.7 Repomix — Sharing Code Context with Other Tools

Sometimes you need to give a complete code snapshot to a non-Claude tool — for a security audit, a consultant review, a model with a smaller context window, or your own offline review. Repomix packages your entire repo (or any subtree) into a single markdown file optimized for LLM consumption: file tree, then each file with syntax-highlighted code blocks, with token counts.

Install once:

install
npm install -g repomix

Use:

terminal
# Pack the whole repo (default output: repomix-output.xml or .md)
repomix

# Pack only packages/db (the database package)
repomix --include "packages/db/**"

# Pack everything except tests and dependencies
repomix --ignore "**/*.spec.ts" --ignore "node_modules/**"

# Output as markdown (better for some tools)
repomix --style markdown

Add a config file at repo root to standardize what gets packed:

repomix.config.json
{
  "output": {
    "filePath": "repomix-output.md",
    "style": "markdown",
    "removeComments": false,
    "showLineNumbers": true
  },
  "include": ["packages/**/src/**", "apps/**/src/**"],
  "ignore": {
    "customPatterns": [
      "**/*.spec.ts",
      "**/*.e2e.spec.ts",
      "**/migrations/**",
      "node_modules/**",
      "dist/**",
      ".turbo/**"
    ]
  }
}
⚠ Never publish a Repomix output
The output contains your entire codebase including secrets if they're in non-gitignored places, business logic, and PII handling code. Treat the output the same as your git repo: never share publicly, never paste into an untrusted system. Add repomix-output.md to .gitignore.
03 · Slash Commands

Custom Commands for Repetitive Tasks

Slash commands transform multi-step workflows into single invocations. Build them for tasks you do 3+ times.

3.1 What Slash Commands Are

A slash command is a markdown file in .claude/commands/ that you invoke with /command-name. Claude reads the file and executes the instructions. Commands can take arguments via $ARGUMENTS.

3.2 The 7 Essential Commands

These cover ~90% of repetitive workflows. Add more only when you spot a clear pattern after using them for weeks.

.claude/commands/new-entity.md
# Create a new entity (full vertical slice)

Create a new entity with full backend support. Entity name: $ARGUMENTS

Execute these steps in order. DO NOT SKIP any step.

## Step 1: Zod schema
Create `packages/shared-types/src/<entity>.ts`:
- <Entity>Schema (full)
- Create<Entity>Input (omit id, timestamps, organizationId)
- Update<Entity>Input (Create.partial())
- Export type from inferred schema
- Add export to `packages/shared-types/src/index.ts`

## Step 2: Drizzle table
Create `packages/db/src/schema/<entity>.ts`:
- pgTable with all fields from Zod schema
- organizationId UUID NOT NULL FK to organizations
- createdAt, updatedAt timestamptz with defaults
- archivedAt timestamptz nullable (soft delete — v2 renamed from deletedAt)
- Composite indexes: (organizationId, ...) for common queries
- Add to `packages/db/src/schema/index.ts`

## Step 3: Migration
Generate via Drizzle: `pnpm db:generate`
Verify the SQL includes:
- CREATE TABLE
- ENABLE ROW LEVEL SECURITY
- FORCE ROW LEVEL SECURITY
- CREATE POLICY tenant_isolation
- All indexes

## Step 4: NestJS module
Create `apps/api/src/modules/<entity>/`:
- `<entity>.module.ts` — NestJS module
- `<entity>.service.ts` — uses withTenant for ALL queries
- `<entity>.controller.ts` — has @UseGuards(AuthGuard, TenantGuard)
- `<entity>.spec.ts` — integration test including RLS isolation
- Register module in `apps/api/src/app.module.ts`

## Step 5: Verify
Run in order:
1. `pnpm typecheck` — must pass

04 · Hooks

Automation Hooks

Hooks run automatically before or after Claude takes actions. They enforce rules without you having to remember.

4.1 What Hooks Do

Hooks are scripts that Claude Code runs at specific lifecycle points: before using a tool, after editing a file, before writing content. They can:

  • Reject changes that violate rules (e.g., editing forbidden files)
  • Run automatic checks (typecheck, lint) after every edit
  • Block dangerous operations (force push, secret commits)
  • Format code automatically

4.2 The 5 Recommended Hooks

Hook 1: Block edits to protected files

.claude/hooks/pre-tool-use.sh
#!/bin/bash
# Block edits to files that need explicit approval

set -e

PROTECTED_PATTERNS=(
  "packages/db/migrations/"
  ".env"
  ".env.local"
  ".env.production"
  "package-lock.json"
  "pnpm-lock.yaml"
  ".github/workflows/"
)

if [[ "$CLAUDE_TOOL_NAME" == "Edit" || "$CLAUDE_TOOL_NAME" == "Write" ]]; then
  TARGET="$CLAUDE_TOOL_FILE_PATH"
  for pattern in "${PROTECTED_PATTERNS[@]}"; do
    if [[ "$TARGET" == *"$pattern"* ]]; then
      echo "❌ BLOCKED: Cannot modify $TARGET without explicit approval"
      echo "Ask the user first: 'I need to modify $TARGET. Approve?'"
      exit 1
    fi
  done
fi

exit 0

Hook 5: Validate commit message format

.claude/hooks/validate-commit.sh
#!/bin/bash
# Validate commit message follows conventional commits

set -e

if [[ "$CLAUDE_TOOL_NAME" == "Bash" ]]; then
  COMMAND="$CLAUDE_TOOL_COMMAND"

  if echo "$COMMAND" | grep -qE 'git\s+commit\s+.*-m'; then
    # Extract the message
    MSG=$(echo "$COMMAND" | grep -oE -- '-m\s+["\047][^"\047]+["\047]' | sed -E 's/-m\s+["\047]([^"\047]+)["\047]/\1/')

    # Check format: type(scope): subject OR type: subject
    if ! echo "$MSG" | head -1 | grep -qE '^(feat|fix|chore|docs|style|refactor|perf|test|build|ci)(\([a-z-]+\))?: .+'; then
      echo "❌ BLOCKED: Commit message does not follow Conventional Commits format"
      echo "Expected: <type>(<scope>): <subject>"
      echo "Example:  feat(api): add project endpoints"
      echo ""
      echo "Got: $MSG"
      exit 1
    fi
  fi
fi

exit 0

4.4 Decision Point: Strict or Lenient Hooks?

💡 Decision Point
Question: Should the typecheck hook block on every error, or just warn?

Strict (block): Faster feedback, prevents accumulation. Annoying with WIP code that has temporary errors.
Lenient (warn): Less interruption. Risk of accumulating errors silently.

Recommendation: Start lenient, switch to strict if errors accumulate. The branch protection at PR level (CI) catches what hooks miss locally.

06 · Branching Strategy

Trunk-Based Development with PRs

A simple but disciplined branching strategy that scales from 2 developers to 20 without rework.

6.1 The Strategy

We use trunk-based development with short-lived feature branches. Why not GitFlow? GitFlow is overkill for our team size and creates bottlenecks. Why not pure trunk? Direct main commits without review create scary situations during incidents.

The result: simple, fast, reviewable.

main  ●─────●─────●─────●─────●─────●─────●  (always deployable)
            \         \         \         /
             \         \         \       /
              feat/owners  fix/import  feat/sigs
                  \         \         \
                   ● ● ●     ● ●       ● ● ●
                   commits     commits     commits

Workflow:
1. Create branch off main: feat/<description>
2. Commit incrementally with conventional commits
3. Open PR when ready
4. CI runs (typecheck, lint, test, security audit)
5. Self-review or partner review
6. Squash merge to main
7. Branch deleted automatically

6.2 Branch Naming Conventions

Branch names follow this format: <type>/<short-description>

PrefixUse forExample
feat/New feature or capabilityfeat/owner-management
fix/Bug fixfix/import-encoding
chore/Tooling, deps, buildchore/upgrade-drizzle
refactor/Internal refactorrefactor/with-tenant-cleanup
docs/Documentation onlydocs/migration-runbook
test/Adding teststest/rls-edge-cases
perf/Performance workperf/import-streaming

Description rules:

  • Lowercase, hyphen-separated
  • 2-4 words max
  • Describes the goal, not the implementation
  • No issue numbers (use commit body for that)

6.3 Branch Lifecycle

01
Create from main

git checkout main && git pull && git checkout -b feat/<description>

02
Commit incrementally

Small, focused commits. Each one passes typecheck and lint locally. Conventional commits format (see section 7).

03
Push regularly

git push -u origin feat/<description>

Don't wait days. Pushing daily protects your work.

04
Sync with main when needed

git checkout main && git pull && git checkout feat/X && git rebase main

Rebase, don't merge. Keeps history linear.

05
Open PR

When work is ready (not necessarily complete — drafts are fine). PR template guides you to fill in: what, why, how to test, screenshots if UI.

06
CI runs

Typecheck, lint, tests, security audit, build. All green required to merge.

07
Review

Self-review your own diff first (catch obvious things). Then partner review for non-trivial changes. Both can use /security-check on the diff.

08
Squash merge

Merge to main with squash. The PR title becomes the squash commit message. Branch is auto-deleted.

6.4 Branch Lifetime Limits

Long-lived branches are dangerous. Set limits:

  • Feature branches: max 5 days. Beyond that, split into smaller PRs.
  • Sync from main daily if branch lives more than 1 day.
  • Use feature flags for incomplete features that need to land in main.

6.5 Main Branch Protection

Configure on GitHub Settings → Branches:

  • Require pull request before merging
  • Require status checks to pass: typecheck, lint, test, build, security-audit
  • Require branches to be up to date before merging
  • Do not allow bypassing the above settings (even for admins)
  • Restrict force pushes
  • Restrict deletions
⚠️ Never bypass branch protection
It's tempting "just this once" during emergencies. Don't. The discipline of always going through PRs, even for hotfixes, is what creates the audit trail you'll need when something goes wrong.

6.6 Emergency Hotfixes

Rare but inevitable. Process:

  1. Create branch fix/hotfix-<description> from main
  2. Make minimal fix (the smaller the better)
  3. Open PR with "HOTFIX" in title
  4. CI must still pass — no exceptions
  5. Self-merge after CI green (partner review post-incident)
  6. Tag a patch release (e.g., v1.2.3 → v1.2.4)
  7. Document in .claude/incidents/YYYY-MM-DD-summary.md

  • subject (required): short description of the change.

  • footer (optional): breaking changes, issue references.

7.8 Why This Matters Long-term

Conventional commits look like overhead. They aren't. The benefits compound:

  • CHANGELOG generates automatically. No manual writing.
  • Version bumps are deterministic. No arguments about "is this a major or minor?".
  • Git log is searchable. "git log --grep='^feat(api)'" shows all API features.
  • PR descriptions write themselves. Squash merge uses commit message.
  • Onboarding is easier. New devs can read git log and understand the project.
  • Bisecting is faster. When something breaks, conventional commits help locate the cause.
08 · Semantic Versioning

Versioning Discipline

SemVer is a contract with users. Even before you have users, the discipline matters.

8.1 The Format

Every version is MAJOR.MINOR.PATCH:

  • MAJOR — Breaking changes. Existing users must update their code/integration.
  • MINOR — New features. Backward compatible. Existing users continue to work.
  • PATCH — Bug fixes. Backward compatible. Existing users get fixes.

Your project goes through these versioning stages:

RangeStageMeaning
0.0.xPre-MVPInternal development. Anything can change. No promises.
0.x.0MVP / AlphaReady for first users. Breaking changes possible but documented.
1.0.0StablePublic commitment. Breaking changes follow strict rules.
1.x.0MatureActive development. Frequent minor releases.
2.0.0+Major rewriteSignificant breaking changes warranted by major improvements.

8.3 When to Bump Each

PATCH bump (1.2.3 → 1.2.4)

  • Any commit with fix:
  • Performance improvement (commits with perf:)
  • Security patch (still fix: with appropriate scope)
  • Documentation fixes that affect users

MINOR bump (1.2.3 → 1.3.0)

  • Any commit with feat:
  • New configuration options (with backward-compatible defaults)
  • New API endpoints (existing endpoints unchanged)
  • Substantial UI additions (existing flows unchanged)

MAJOR bump (1.2.3 → 2.0.0)

  • Any commit with BREAKING CHANGE: in footer
  • Any commit with ! after type (e.g., feat!:)
  • Removing a feature or endpoint
  • Changing data structure that requires migration
  • Changing default behavior in user-visible ways

8.4 Pre-1.0 Considerations

While in 0.x.y, you have flexibility. The convention is:

  • 0.x.0 = minor + breaking changes (treat as MAJOR for users)
  • 0.x.y where y > 0 = patches and small features

Example:

  • 0.1.0 — First demo to beta users
  • 0.2.0 — Major changes after beta feedback
  • 0.2.1 — Bug fixes from beta
  • 0.3.0 — Phase 2 features (AI extraction)
  • 1.0.0 — First paying customer commits to stable API

  • Production releases: v1.2.3
  • Pre-releases: v1.2.3-rc.1 (release candidate), v1.2.3-beta.1
  • Phase milestones: v0.1.0-phase1 (special tag for our internal milestones)

In our monorepo, all packages share the same version (synchronized release strategy). Update them together:

For an internal monorepo with one product, synchronized versioning is simpler. If you ever publish individual packages to npm, switch to independent versioning with changesets. For now, synchronized is the right call.

9.6 Pre-Release Checks

Before creating a release, verify:

  • Working directory is clean (git status)

  • CHANGELOG.md is up to date
  • No secrets in repo (git log --all -p | grep -iE 'api_key|password' | head)

9.7 Rollback Strategy

If a release goes bad, you need a clear rollback path. Document it in RUNBOOK.md:

  • Identify the bad release. Sentry alerts, customer complaints, or your own monitoring.
  • Roll back deployment first. Re-deploy the previous tag. This stops the bleeding.
  • If DB migration was bad: Use Neon's PITR (Point-in-Time Recovery) to a moment before the migration. This is why PITR is critical in production tier.
  • Revert in git. Create a revert PR (don't force-push). Tag a hotfix release.
  • Document. Write up what happened in .claude/incidents/YYYY-MM-DD-summary.md. Update CLAUDE.md if there's a pattern to learn.
⚠️ Migrations are forever
DB migrations cannot be reverted by tagging an old version. They run forward only. This is why migrations need extra care: PR review, staging deployment, PITR backup before production migration. Never roll back schema migrations — roll forward with a fix.

11.2 Context Window Management

Claude Code conversations can grow long. Long context = Claude makes more mistakes. Manage it:

  • One task = one session. When task is done, start fresh session.
  • Daily log helps continuity. Use the End-of-Day prompt template. Saves to .claude/daily-log/.
  • Reset when confused. If Claude is making weird suggestions, the context is probably bloated. Start fresh.
  • Reference, don't repeat. Instead of pasting all context, point to docs: "Per Doc 04b section 5.3, ..."

11.3 When CLAUDE.md Stops Working

Symptoms that your CLAUDE.md is failing:

  • Claude keeps suggesting Prisma when you use Drizzle
  • Claude forgets the withTenant pattern
  • Claude adds dependencies without asking
  • Claude commits without conventional commits format

What to do:

  • Check that CLAUDE.md is being loaded (it should appear in Claude's context).
  • If yes, the rule probably isn't prominent enough. Move it to the top, make it bolder.
  • If the rule is buried in a long file, split into per-package CLAUDE.md.
  • If still failing, add a slash command or hook for enforcement.

11.4 Adding New Team Members

If a 3rd developer joins (rare, but plan for it):

  • Onboarding doc — README plus the 5 docs (01-05). Quick start in 15 minutes.
  • Pair on first PR — voice call with existing dev for first PR. Establishes patterns.
  • CODEOWNERS update — add new dev to relevant areas.
  • CLAUDE.md works for them too — that's the point. No re-onboarding for Claude.

11.5 Documentation Hygiene

Docs decay if not maintained. Keep them honest:

  • Each doc has a version (we have v1.0). Bump when meaningful changes.
  • Phase boundary = doc review. Are docs still accurate?
  • Out-of-date doc > no doc, but only by a little. Mark stale sections.
  • Delete obsolete sections rather than archive them. Git history preserves everything.

11.6 Tool Upgrades

Dependencies will get out of date. Plan for it:

  • Dependabot enabled — automatic PRs for security updates. Merge promptly.
  • Quarterly dep review — non-security updates. Read CHANGELOGs of major deps. Plan upgrades.
  • Major framework upgrades — treat as a feature: own branch, full testing, careful PR. Never rush.
  • Free Tier provider changes — providers change limits, plans, pricing. Recheck quarterly.

11.7 The Recovery Mindset

Things will break. The setup should make recovery faster, not prevent breaks entirely.

  • Phase tags — reset to v0.1.0-phase1 if Phase 2 work breaks something.

  • Sentry alerts — know about errors before customers.
  • Audit log — every action is recorded. You can see who did what.
  • Incident log — write up what happened. Future you will thank you.
