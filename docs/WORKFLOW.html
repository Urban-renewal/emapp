Part A — Pre-Implementation Workflow (Planning, No Code)

The work before opening Claude Code. This is where most teams get lost — they either skip planning (and pay later) or over-plan (and never start). The pattern below is calibrated for a 2-person team building MVP fast.

A.1 The Pre-Flight Checklist (Before Each Phase)

Run through this list before starting Phase N. ~30 minutes investment, hours saved.

[ ] Re-read the phase's specific section in the relevant Doc
    - Phase 0 → Doc 04b
    - Phase 1 → Doc 04c (the deep one — 432KB; budget 2-3 hours first read)
    - Phase 2-9 → Doc 03 (section per phase) + reference back to Doc 02 for architecture

[ ] Verify the previous phase's "Done When" is genuinely true
    - Don't move forward if even one item is "mostly done"
    - "Mostly done" before T1.5 (RLS isolation) = production data leak in 3 months

[ ] Check OPEN_ITEMS.md — has anything been deferred that this phase needs?
    - If yes: decide now (build it, or formally defer with date)

[ ] Update CLAUDE.md if patterns from the previous phase exposed gaps
    - "Always use withTenant" became obvious in Phase 1 → add it to root CLAUDE.md
    - Don't batch — update now while context is fresh

[ ] Identify which sub-agents you'll invoke this phase
    - Any PII work → @security-reviewer after the PR
    - Any migration → @migration-reviewer before merge
    - Performance-sensitive queries → @perf-auditor

[ ] Estimate the phase budget
    - Doc 03 gives estimates per phase (e.g., Phase 1 = ~8 days)
    - Add 30% for unknown unknowns; if you blow past estimate by 2x, stop and re-plan

A.2 The Phase Decomposition Pattern

All phases follow the same structure (already done in Doc 04c P1.1-P1.14):

Phase N: <Goal>
├── PN.1: First atomic task
│   ├── Goal (1 sentence)
│   ├── Files affected
│   ├── Dependencies (PN.X completed first)
│   ├── Tests required (TN.X)
│   └── Definition of Done (3-5 bullets, checkable)
├── PN.2: Second atomic task
├── ...
└── Phase Done When: <list of cross-task criteria>

For new work not yet in docs (e.g., when you start Phase 2 and need to decompose): use this format. Add tasks to a phase-specific markdown file (docs/phase-2-tasks.md) or directly extend Doc 03.

Rule of thumb: Each P*.X task = 0.5-1 day of work. If it's 3 days, it's not atomic; split.

A.3 The Test Gate System

Three test tiers, each with different CI behavior:

Tier When Speed Blocks merge?
Smoke Every PR push <1 min Yes
Integration Every merge to main 2-5 min Warning only
Critical Every PR push <30 sec Yes — hard block

Critical tests (the hard blockers):
- T1.5 RLS Isolation (Doc 07 §10)
- T1.6 Provider tier separation (Doc 07 §11)
- T1.7 Multi-org membership context (Doc 07 §11)

These three never fail silently. If any one goes red, the entire pipeline stops. Treat them as sacred.

A.4 Decision Capture As You Go

The single most leveraged habit after testing. Every decision worth more than 5 minutes of discussion gets a row in DECISIONS.md.

Format:

## D.NN — Short title
**Date:** YYYY-MM-DD
**Decision:** What we decided (1 sentence)
**Alternatives considered:** A, B, C
**Why we chose this:** 1-2 sentences
**Reversibility:** Easy / Medium / Hard
**Trigger to revisit:** When/if this should be reconsidered

When to add an entry:
- Picking a library when there are 2+ reasonable options
- Schema choice between 2+ designs
- Naming convention that will be repeated
- Trade-off accepted (cost / time / risk)

When NOT to bother:
- "Use Tailwind for styling" — already in Doc 02, not novel
- One-off naming (a variable name doesn't deserve a DECISION entry)

Doc 02 §13 already has 8 "portability rules" — those should seed the first 8 entries of DECISIONS.md when you create it.

A.5 Document Updates as a First-Class Output

When implementation reveals that a doc is wrong, update the doc as part of the same PR.

Examples:
- Phase 1 implementation reveals that pg_trgm is needed → update Doc 04c P1.10 to add it
- Phase 3 implementation finds that nextCursor should be null not undefined → update Doc 06 §5.5

Anti-pattern: "I'll batch doc updates at end of phase." This produces docs that drift from reality. Trust me — update now, in the same PR.

Part B — Implementation Workflow with Claude Code

Where the work actually happens. The patterns below assume you're using Claude Code (CLI or VS Code extension) for most implementation, with the docs as the source of truth.

B.1 Session Granularity

One Claude Code session per phase, not per day.

Pattern Why
Session-per-phase Context fresh from the doc; phase boundaries match natural commit boundaries
Session-per-day Yesterday's mistakes pollute today's context
Session-per-task Loses cross-task context (e.g., Phase 1 schema decisions span 14 tasks)
Single mega-session Context window fills up; Claude starts forgetting

When to end a session:
- Phase complete (all P.X tasks done, all T.X tests pass)
- Context window getting full (Claude starts losing details from earlier in the session)
- Big architectural pivot (start fresh with new framing)
- End of day (don't pause mid-task; finish the current commit, then end)

B.2 The Standard Work Loop

For each P*.X task:

1. OPEN
   - Point Claude at the doc:
   - "Read /docs/04c-phase-1-database.html, find task P1.3 (Provider tier).
      Also read /mnt/skills/public/db/SKILL.md if applicable.
      Propose the first commit."

2. PROPOSE
   - Claude proposes implementation plan (not code yet)
   - You review the plan: Does it match the doc? Are dependencies correct?
   - If not: push back. Don't accept a plan that's 80% right.

3. IMPLEMENT
   - Claude writes the code
   - You review the diff — line by line for security/PII, scan for everything else
   - You're the Junior's manager: catch what they miss

4. TEST
   - Run the relevant tests (TN.X for this task)
   - Failures: Claude fixes, loop back to step 3
   - Pass: continue

5. COMMIT
   - Use semantic commits: feat, fix, test, refactor, chore, docs
   - Format: type(scope): short description
   - Example: feat(db): add Provider tier table and RLS policy (P1.3)

6. UPDATE
   - If you learned a new pattern: add to CLAUDE.md
   - If you hit a surprising bug: add to learnings.md
   - If a doc was wrong: update the doc in same PR

7. NEXT
   - Move to next P*.X task OR end session if phase done

B.3 Sub-Agent Usage

Sub-agents (defined in .claude/agents/ — see Doc 04a §2.5) run with fresh context. Use them to get a "second opinion" without polluting your main session.

When to invoke each:

Agent Trigger Doc reference
@security-reviewer After ANY P1.5 (PII), P1.11 (RLS), Phase 2 (auth), or any code that touches owners/signatures Doc 07 §9 threat catalog
@perf-auditor Query feels slow; adding indexes; reviewing list endpoints Doc 04c P1.12
@migration-reviewer Before ANY Drizzle migration PR Doc 04c P1.1 + P1.11
@test-author Service exists but no test coverage; or you want comprehensive edge case tests Phase-specific T*.X
@docs-updater Phase completion; need to sync the doc with what was actually built All docs

Invocation pattern:

[main session, mid-Phase 1]
"I just finished P1.5 (Owners + PII). Before I commit:
 @security-reviewer review the diff at HEAD vs main, focusing on 
 the new owners.ts schema and pii.ts encryption helpers."

The sub-agent runs in a fresh context, returns a focused report, main conversation continues without context pollution.

B.4 Slash Commands

Define these in .claude/commands/ for repeatable operations:

Command What it does When to use
/commit Generate semantic commit message for current diff Every commit
/new-entity <name> Scaffold Drizzle schema + Zod + tests + RLS + adapter Adding any new MVP entity
/deploy-prep Final pre-deploy checklist (tests, lint, type-check, no console.log, no any, secrets not in repo) Before deploying
/audit Cross-doc consistency check (Hebrew collation present, withProvider not withSystem, archivedAt not deletedAt, etc.) Weekly, before phase handoff
/repomix-pack Generate Repomix output for external sharing When sending code to auditor/consultant

B.5 CLAUDE.md Hygiene

CLAUDE.md grows. Patterns to maintain:

Update when:
- A rule emerges from 2+ similar bugs ("we forgot withTenant in three services")
- A convention is now established across the team
- A constraint becomes operational (not just architectural)

Don't update when:
- One-off rule for one feature
- Personal preference (those go in .editorconfig or your IDE)
- Things already enforced by ESLint/TypeScript/CI

Pruning:
- At ~150 lines (Doc 04a §1.5), audit the file
- Move "why" reasoning to constraints.md
- Move historical learnings to learnings.md
- Promote consistent rules to enforcement (ESLint, hooks)

B.6 Repomix for External Sharing

When you need to share code with a non-Claude tool (security audit, consultant review, sending to a smaller LLM):

# Whole repo (creates repomix-output.md)
repomix

# Just the backend
repomix --include "apps/api/**" --include "packages/**"

# Excluding tests for cleaner audit view
repomix --ignore "**/*.spec.ts"

Doc 04a §2.7 has the full config. Treat the output like the source code itself — never publish, never share without NDA.

B.7 Critical CI Gates

The merge cannot happen without:

✓ TypeScript: pnpm typecheck
✓ Lint: pnpm lint
✓ Tests (Smoke): pnpm test --reporter=verbose
✓ Critical Tests:
    ✓ T1.5 RLS isolation
    ✓ T1.6 Provider tier separation  
    ✓ T1.7 Multi-org context
✓ Build: pnpm build
✓ No secrets in repo: gitleaks scan
✓ No console.log in production code: ESLint rule
✓ No `any` or unchecked `unknown`: TypeScript rule

Add these to .github/workflows/ci.yml as required checks on main branch protection.

B.8 Phase Handoff Protocol

When Phase N is done and you're moving to Phase N+1:

1. All P*.X tasks completed
2. All T*.X tests green
3. Definition of Done verified (re-read it; don't trust memory)
4. CLAUDE.md updated with new patterns
5. learnings.md has any war stories from the phase
6. DECISIONS.md has any new decisions (don't skip — they're freshest now)
7. Doc updated if implementation diverged
8. PR merged to main, tagged: v0.N-phase-N-complete
9. Sleep on it. Next morning: start Phase N+1 prep checklist

Part C — Secrets & API Key Management

The security-first approach. Three principles:

  1. Defense in depth — secrets stored in multiple places, each with different access
  2. Least privilege — only the system that needs the secret has it
  3. Recoverable — losing one storage location doesn't mean losing the secret

C.1 The Secret Categories

EMAPP has 4 categories of secrets. Each has different rotation and access rules.

Category 1: Cloud Provider Tokens

Provider What Used by
Neon Project API token + connection string Railway env vars
Railway Project token GitHub Actions (deploy)
Cloudflare Global API token + R2 access keys Railway (R2 access), Pages (deploy)
Resend API key Railway (BE container)
Sentry DSN (FE) + DSN (BE) + API key Pages (FE), Railway (BE), CI (releases)
GitHub PAT for CI GitHub Actions

Category 2: Application Secrets (Self-Generated)

Secret Purpose Rotation
PII_ENCRYPTION_KEY pgp_sym_encrypt for owners.national_id, phone, signatures NEVER routinely (Doc 07 §14)
PII_HASH_KEY HMAC for owners.national_id_hash (search) NEVER routinely
BETTER_AUTH_SECRET JWT signing On compromise only
JWT_REFRESH_SECRET Refresh token signing (if separate) On compromise only

These are SACRED. Treat differently from other secrets.

Category 3: Database Connection Strings

Variable Role Permissions
DATABASE_URL app_user Standard, RLS enforced
DATABASE_URL_PROVIDER provider_app_role BYPASSRLS — Provider tier only

Generated by Neon dashboard. Rotate by regenerating from Neon (changes the password component only).

Category 4: Third-Party Service Keys

Currently: Resend API key (already in Category 1).
Phase 2+: Twilio (SMS), Stripe (billing), maybe analytics provider.

C.2 Storage Tiers (Defense in Depth)

Tier 1 — Primary: 1Password Business

Source of truth for all secrets. Where the original values live.

Structure:

1Password Business Vault Structure:
├── EMAPP-Production (vault)
│   ├── Neon (Production DB)
│   ├── Railway (Production tokens)
│   ├── Cloudflare (Production R2 + Pages)
│   ├── Resend (Production API key)
│   ├── Sentry (Production DSNs + API)
│   ├── App Secrets (PII_ENCRYPTION_KEY, PII_HASH_KEY, BETTER_AUTH_SECRET)
│   └── GitHub PAT (CI)
│
├── EMAPP-Staging (vault)
│   └── Same structure, different values
│
└── EMAPP-Dev (vault)
    └── Same structure, dev-tier values

Each item must have:
- Value (the actual secret)
- Last-rotated date
- Owner (which founder is responsible)
- Rotation procedure URL (link to Doc 07 §14 for PII keys)
- Recovery contact (other founder)

Cost: ~$8/user/month. Worth it. Alternative: Bitwarden Business (~$5/user/month) — fewer features but solid.

Tier 2 — Runtime: Environment Variables

Where secrets actually run:

Platform What Set how
Railway BE + Worker container env Railway dashboard or railway variables CLI
Cloudflare Pages FE build-time env CF dashboard
GitHub Secrets CI/CD pipeline GitHub Actions settings

Rule: When 1Password says X, all three runtimes must have X. Drift between 1Password and runtime = source of bugs.

Tier 3 — Local Development: .env.local

Per-developer .env.local file (in .gitignore):

# .env.local — copy from EMAPP-Dev 1Password vault
DATABASE_URL=postgresql://...
DATABASE_URL_PROVIDER=postgresql://...
BETTER_AUTH_SECRET=...
PII_ENCRYPTION_KEY=...
PII_HASH_KEY=...
S3_ENDPOINT=...
S3_ACCESS_KEY_ID=...
S3_SECRET_ACCESS_KEY=...
S3_BUCKET=emapp-dev-...
RESEND_API_KEY=re_dev_...
SENTRY_DSN_API=https://...
NODE_ENV=development
LOG_LEVEL=debug
PORT_API=3000
PORT_WEB=3001

Never commit this file. git status should never show .env.local as staged. If it does, abort and check .gitignore.

Per-developer copies: Each founder maintains their own .env.local. Different values are OK for dev (different test data). Only production values must match across the team.

C.3 Rotation Policy

Secret Category Frequency Trigger Procedure
API keys (Resend, Sentry, GitHub PAT) Yearly Calendar reminder Jan 1 Generate new in provider dashboard → update 1Password → update Railway env → deploy → verify → revoke old
Database creds Quarterly (or when team changes) Neon dashboard Rotate password in Neon → update 1Password → update Railway → no app restart needed (connection pool handles)
BETTER_AUTH_SECRET On compromise OR yearly Suspicion of leak Generate new (32+ char) → update 1Password → update Railway → all sessions invalidated on deploy
PII_ENCRYPTION_KEY NEVER routine Confirmed compromise only Re-encryption ceremony — Doc 07 §14
PII_HASH_KEY NEVER routine Same as above Same — invalidates all hash searches; re-hashing required
Cloudflare global token Yearly Calendar reminder Generate scoped tokens with minimum permissions → swap → revoke old

The PII_ENCRYPTION_KEY ceremony (when it MUST rotate)

Triggers:
- Key confirmed leaked (e.g., in a public log, in a stolen laptop with .env.local)
- Insider threat with key access has been off-boarded

Procedure (~4-6 hours of focused work):

1. Two-person ceremony required (both founders present)
2. Schedule maintenance window (announce 24h before)
3. Generate NEW_PII_ENCRYPTION_KEY (cryptographically random, 32+ chars)
4. Store NEW key in 1Password (don't overwrite OLD yet)
5. Deploy migration that:
   - Decrypts all PII columns with OLD key
   - Re-encrypts with NEW key
   - Verifies round-trip
   - Updates only if successful (transaction)
6. Update Railway env vars: PII_ENCRYPTION_KEY=<new>
7. Deploy app with new key
8. Verify decrypts work in production (smoke test)
9. After 7 days of stable operation: discard OLD key
10. Document in incident log (learnings.md)

If PII_HASH_KEY is rotated, HMAC search breaks until ALL hash values are recomputed. Same ceremony, same caution.

The terrifying scenario: KEY LOST (no compromise, just gone)
- All PII unrecoverable
- All signatures invalid
- Affected customers must be notified (Israeli privacy law disclosure)
- This is why printed backup of PII keys is mandatory (1Password recovery codes + physical safe)

Who has access to what

Resource Founder A Founder B
1Password EMAPP-Production Read+Write Read+Write
1Password EMAPP-Staging Read+Write Read+Write
1Password EMAPP-Dev Read+Write Read+Write
Neon dashboard Owner Admin

2FA / MFA mandatory for

  • All cloud provider dashboards (Neon, Railway, Cloudflare, Resend, Sentry)
  • GitHub
  • Provider Admin login (schema-enforced in DB — Doc 07 §6.6)

The "two-person rule" for PII operations

For any operation involving PII keys in production:
- Both founders agree (Slack DM with "approved" + separate channel confirmation)
- Action logged in provider_audit_log with both signatures

C.5 Recovery Scenarios

Scenario 1: 1Password locked out (forgot master password)

Prerequisite: Each founder has a printed Recovery Code in a physical safe (separate from each other).

Procedure:
1. Use Recovery Code on 1Password.com
2. Reset master password
3. All devices need re-authentication

If both founders lose Recovery Codes:
- 1Password Business plan supports company-recovery via Account Recovery groups
- Otherwise: secrets accessible only via runtime environments (Railway/Cloudflare/etc.); re-create 1Password vault from those

Scenario 2: Cloud provider account compromised (e.g., Cloudflare token leaked)

Within 24 hours:

1. Rotate the specific token in provider dashboard
2. Audit access logs for unauthorized usage
3. Update Railway env vars
4. Force redeploy (kills any active sessions using old token)
5. Document incident in learnings.md

Scenario 3: Founder loses access (lost laptop, account hacked)

Other founder:

1. Deactivate user in 1Password (Owner action)
2. Revoke their access to all cloud provider dashboards
3. Rotate any secrets they had personal access to
   (in MVP — none, since all secrets are team-shared)
4. Re-enroll them with new account after device recovery

Scenario 4: PII_ENCRYPTION_KEY confirmed compromised

See C.3 ceremony above. ~4-6 hours of focused work.

Scenario 5: PII_ENCRYPTION_KEY LOST (worst case)

  • Restore from printed backup (1Password recovery + physical safe)
  • If no backup: PII data is permanently unrecoverable
  • National IDs, phones, signatures all unreadable
  • Customer notification required
  • This is why printed backup is mandatory at production launch

C.6 Day-to-Day Hygiene

Daily checks (~30 seconds each)

  • git status shows .env.local is not staged
  • No secrets in git log -p (use gitleaks periodically)
  • No secrets in PR descriptions or commit messages
  • Logs don't contain secrets (Pino redact config catches this — Doc 04b)

Monthly checks (~10 minutes)

  • 1Password vault audit: any items with rotation date > 1 year?
  • All cloud provider dashboards: any unused/orphan tokens?
  • GitHub: any old PATs that should be revoked?
  • Test that 1Password Recovery Codes still work (have one founder test on a fresh device)

Yearly checks (~2 hours)

  • Rotate all Category 1 secrets (API keys)
  • Review Provider Admin access list (still both founders? add/remove as team changes)
  • Backup test: restore Neon to staging environment from PITR, verify data integrity
  • Update this document if process has evolved

C.7 What NOT to Do

Hard rules with painful exceptions. Don't ever:

❌ Commit secrets to git. Even in a private repo. Even temporarily. Even "I'll delete it after." Once committed, assume leaked.

❌ Send secrets via email or Slack. Use 1Password sharing or in-person hand-off.

❌ Print secrets except for ceremonial backup. And then: physical safe, separate locations for each founder, audited.

❌ Use the same secret across environments (dev/staging/prod). Different values per environment, always.

❌ Use personal cloud accounts for production. EMAPP needs its own organization-level accounts at every provider.

❌ Log secrets, ever. Pino redaction config catches this for known keys. Be paranoid about new ones.

❌ Rotate PII keys without ceremony. This is the single fastest way to lose all your PII data.

❌ Skip 2FA "for now." "Now" becomes "ever."

❌ Reuse the master password. 1Password master password is unique to 1Password. Never typed elsewhere.

❌ Auto-generate PII_ENCRYPTION_KEY in CI. It's manually generated, stored in 1Password, and injected at runtime. Never derived from anything.

Appendix B: Anti-Patterns to Avoid

Patterns that look productive but destroy velocity:

Anti-pattern Why it fails Replace with
"Just one more rule in CLAUDE.md" 300-line CLAUDE.md gets ignored by Claude Promote to ESLint/hook, or move to constraints.md
"I'll batch doc updates" Docs drift; never get updated Update doc in same PR as code
"T1.5 is annoying, let me skip it once" RLS leak = legal liability + customer disclosure T1.5 is sacred; never skip
"I'll plan the whole phase upfront" Over-planning before learning Plan one PN.X ahead; let learning drive the rest
"Single Claude session for the whole week" Context bloat; old mistakes pollute new work New session per phase
"Let me just commit this secret temporarily" Once committed, always leaked Use 1Password; rotate the secret if mistake happens
"I'll review the diff later" Bugs ship Review every diff, every time
"Let me run all tests at end of phase" Test failures cascade Run tests per task; fail fast
