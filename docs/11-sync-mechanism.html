מנגנון הסנכרון מקצה-לקצה

5 הרגליים · איך נשארים מסונכרנים
EMAPP · Sync Mechanism

מה זה: התשובה המלאה לשאלה "איך צד הלקוח הוא שכבה עצמאית ובכל זאת מסונכרנת עם ה-backend". זה המסמך שמסביר את המכניזם, לא רק את המסמכים.

למי: לך (להבין את התמונה), לשותף + FE (לעבוד לפיו), Claude Code (לבנות את ה-5 הרגליים).

1. התובנה המרכזית

מסמכים לבדם לא יוצרים סנכרון. הם מתעדים אותו. הסנכרון האמיתי נשען על 5 רגליים שחייבות להתקיים יחד:

        מה שגורם לסנכרון אמיתי
┌─────────────────────────────────────────────┐
│ 1. shared-types   (קוד — Zod schemas)        │ ← הלב
│ 2. Adapter layer  (FE — api/ + SAMPLE_*)     │ ← העצמאות
│ 3. Stubs          (BE — endpoint דמה)        │ ← הגישור
│ 4. המסמכים        (06,08,09,10 — קריאה לאדם) │ ← ההבנה
│ 5. משמעת שינוי    (schema קודם, אז קוד)      │ ← המניעה מסחף
└─────────────────────────────────────────────┘

אם רגל אחת חסרה — הסנכרון נשבר. המסמכים הם רגל 4 בלבד.

2. רגל 1 — shared-types (הלב)

חבילת קוד אחת: packages/shared-types/. מכילה Zod schemas לכל ישות (ProjectSchema, OwnerSchema, MeSchema...).

packages/shared-types/
├── project.ts      → export const ProjectSchema = z.object({...})
├── owner.ts         → export const OwnerSchema = z.object({...})
├── auth.ts          → LoginSchema, MeSchema...
└── index.ts         → re-export הכל

איך זה יוצר סנכרון:
- ה-BE מוודא כל תשובה נגד ה-schema (ProjectSchema.parse(data) לפני שמחזיר). אם החזיר משהו לא תקין — נכשל ב-dev.
- ה-FE גוזר טיפוסים מאותו schema (type Project = z.infer<typeof ProjectSchema>). ה-mock data (SAMPLE_*) חייב לעבור ProjectSchema.parse — אז ה-mock תמיד בצורה הנכונה.
- שניהם קוראים את אותו קובץ. אי אפשר להיסחף — שינוי ב-schema נראה מיד בשני הצדדים (TypeScript נשבר אם לא התאמת).

הוראה ל-Claude Code: packages/shared-types נבנה ב-Phase 0 (P0.3) ומורחב בכל Phase. כל endpoint חדש מוסיף/משנה schema שם קודם, אז ב-controller, אז ב-FE. ה-schema הוא ה-source of truth של צורת הנתונים.

3. רגל 2 — Adapter Layer (העצמאות של ה-FE)

השותף כבר בנה את זה — שכבת api/ שכל קריאת "שרת" עוברת דרכה ומחזירה SAMPLE_*.

UI component  →  api/projects.ts  →  [mock mode]  SAMPLE_PROJECTS
                                  →  [live mode]  fetch /api/v1/projects

איך זה יוצר עצמאות: ה-UI לא יודע אם זה mock או אמיתי. החלפת mode = שינוי implementation אחד ב-api/, אפס שינוי ב-UI. השותף עובד full speed בלי לחכות ל-backend.

הכלל: ה-SAMPLE_* חייב לעבור Schema.parse (רגל 1). כך ה-mock תמיד בצורה שה-API האמיתי יחזיר. אם ה-schema השתנה וה-mock לא — TypeScript/הטסט נשבר. זה מה שמונע מ-ה-FE לבנות מול צורה ישנה.

4. רגל 3 — Stubs (הגישור בין הצדדים)

כש-ה-BE עדיין לא מימש endpoint, הוא מספק stub: controller שמחזיר נתוני דמה בצורת ה-schema הנכונה, מאחורי ה-path האמיתי.

@Get('projects')
@StubEndpoint('list projects')
async list() {
  return { data: [ProjectSchema.parse(MOCK)], page:{...} };
}

איך זה גושר: ה-FE יכול לעבור מ-mock mode ל-live mode מול ה-stub — ולגלות בעיות אינטגרציה (CORS, cookies, צורת תשובה) לפני שהלוגיקה האמיתית קיימת. כשהלוגיקה מוכנה — מחליפים את גוף ה-stub, ה-path וה-schema לא זזים.

הוראה ל-Claude Code: לכל endpoint שעדיין לא מומש אבל ה-FE צריך — ספק stub (Doc 06 §6). ה-stub מחזיר Schema.parse(mock) כדי שגם הוא מאומת מול ה-source of truth.

5. רגל 4 — המסמכים (ההבנה)

מסמך נותן לצד הלקוח
Doc 06 הפילוסופיה: 3 העמודים, מי בעלים של מה, אנטי-פטרנים
Doc 08 זרימות auth/API צעד-אחר-צעד + אבטחה בכל שכבה
Doc 09 API Reference — כל endpoint (מיוצר מ-schema, §0.4)
Doc 10 מה ה-FE חייב/אסור לעשות מבחינת אבטחה
Doc 11 (זה) איך כל הרגליים מתחברות

המסמכים = קריאה לאדם. הם משקפים את הקוד (רגל 1), לא מחליפים אותו. במקרה סתירה — ה-schema גובר. לכן Doc 09 §0.4 מורה ל-Claude Code לייצר את Doc 09 מה-schema אוטומטית — שלא יהיה פער.

6. רגל 5 — משמעת שינוי חוזה (המניעה מסחף)

הכלל המקודש: שינוי בחוזה = עדכון schema + מסמך קודם, אז קוד. לא הפוך.

צריך שדה חדש / שינוי צורה?
  1. עדכן את ה-Zod schema ב-packages/shared-types
  2. ה-CI מריץ gen:api-reference → Doc 09 מתעדכן אוטומטית
  3. ה-CI בודק: schema ↔ Doc 09 ↔ stubs מסונכרנים? לא → build נכשל
  4. רק עכשיו — מימוש ב-BE + שימוש ב-FE
  5. שני הצדדים מקבלים את השינוי מאותו commit

❌ האנטי-פטרן שהורג סנכרון: מישהו משנה צורת תשובה ישירות בקוד ה-BE בלי לעדכן schema. ה-FE לא יודע. שבועיים אחר כך — באג אינטגרציה. המנגנון מונע את זה כי ה-CI נכשל אם הקוד והschema לא תואמים.

הוראה ל-Claude Code: ה-CI חייב 3 בדיקות (Phase 0 P0.10 + Phase 2): (א) כל תשובת endpoint עוברת Schema.parse בטסט; (ב) gen:api-reference רץ ו-Doc 09 מעודכן; (ג) SAMPLE_* ב-FE עוברים את ה-schemas. כשל באחת = build אדום.

7. התרחיש המלא — איך זה עובד ביום-יום

שבוע 1:
  Claude Code  → בונה packages/shared-types (P0.3): ProjectSchema
  Claude Code  → stub GET /projects שמחזיר ProjectSchema.parse(mock)
  השותף        → api/projects.ts מחזיר SAMPLE_PROJECTS (עובר ProjectSchema)
  השותף        → מעצב מסך רשימת פרויקטים מול ה-mock — לא תלוי ב-BE

שבוע 2:
  השותף        → מחליף ל-live mode מול ה-stub. מגלה: cookies עובדים,
                  צורת { data, page } נכונה. אפס הפתעות.
  Claude Code  → מממש את הלוגיקה האמיתית מאחורי אותו path/schema

שבוע 3 — שינוי:
  צריך שדה stats.refused_count חדש
  Claude Code  → מוסיף ל-ProjectSchema. CI מריץ gen → Doc 09 מתעדכן.
  TypeScript   → נשבר אצל השותף (ה-SAMPLE חסר את השדה) → הוא רואה מיד
  השותף        → מוסיף לשדה ל-SAMPLE + למסך. שני הצדדים מסונכרנים שוב.
  ← הסחף נמנע כי ה-schema אחד וה-CI אוכף

8. התשובה הישירה לשאלה שלך

"אם לצד לקוח יש את המסמכים — זה אומר ששכבת הלקוח עצמאית ומסונכרנת?"

עצמאית — כן, כבר עכשיו. ה-adapter + SAMPLE_* (שהשותף בנה) נותנים עצמאות מלאה. הוא לא מחכה ל-backend לשום דבר.

מסונכרנת — כן, בתנאי ש-3 הדברים האלה קיימים (Claude Code בונה אותם ב-Phase 0-2):
1. packages/shared-types כחבילת קוד משותפת ✅ (P0.3)
2. ה-SAMPLE_* עוברים את ה-schemas ✅ (כלל ב-CI)
3. ה-CI אוכף schema ↔ doc ↔ stub ✅ (P0.10 + P2)

המסמכים (06,08,09,10) הם רגל ההבנה — חיונית אבל לא מספיקה לבד. מה שבאמת גורם לסנכרון הוא ה-schema המשותף + המשמעת + ה-CI. זה בדיוק מה ש-Claude Code בונה בשלבים הראשונים, ולכן כשתגיע ל-Gate של Phase 2 — תאשר את זה מפורשות.

מקורות: Doc 06 (3 העמודים), Doc 09 §0.4 (אוטו-יצור), Doc 10 (אבטחת FE). זה המסמך שמאחד את כולם למכניזם אחד. הרגליים נבנות ב-Phase 0 (shared-types, CI) ו-Phase 2 (gen:api-reference, stubs מלאים).
