זרימות Auth & API — צד לקוח וצד שרת

9 זרימות · כל צעד · האבטחה בכל שכבה
EMAPP · Auth & API Flows

מה זה: התשובה המדויקת ל"לחצתי התחברות — מה קורה?". כל זרימה כרצף: מה הדפדפן עושה, מה השרת עושה, ומה האבטחה בכל צעד.

למי: לך (להבין), ל-Claude Code (לממש מדויק), ולשותף (להבין מה ה-UI צריך לשלוח/לקבל).

מבוסס על: Doc 02 §10 (tiers), Doc 06 §5 (contract), Doc 07 (security pipeline). זה המסמך שמחבר את שלושתם לרצף אחד.

0. העקרונות שמתחתם הכל

לפני הזרימות — 5 כללי אבטחה שחלים על כל בקשה:

  1. Zero trust בצד לקוח. כל מה שמגיע מהדפדפן נחשב עוין עד שאומת בשרת. הדפדפן אף פעם לא מקבל החלטת הרשאה — רק מציג.
  2. Tokens ב-httpOnly cookies, לא ב-localStorage. JavaScript לא יכול לקרוא אותם → XSS לא יכול לגנוב אותם. Secure + SameSite=Lax → עמיד ל-CSRF.
  3. Access token קצר (15 דק'), Refresh token ארוך (30 יום) עם rotation. כל refresh מנפיק זוג חדש. אם refresh token נגנב ומשמש פעמיים — המערכת מזהה ומבטלת הכל.
  4. 9 שכבות trust boundary. כל בקשה עוברת: דפדפן → Cloudflare (WAF/rate-limit) → Railway → Auth middleware → Tenant middleware → Zod validation → Service (הרשאות) → Drizzle (parameterized) → Postgres (RLS). כל שכבה מסננת.
  5. הסיסמה אף פעם לא נשמרת. רק hash (Better Auth, argon2/bcrypt defaults). אף פעם לא ב-logs, אף פעם בתשובת API, אף פעם בהודעת שגיאה.

1. זרימה: התחברות (Manager / Agent / Viewer)

מה המשתמש רואה

מסך /login: שדה אימייל, שדה סיסמה, כפתור "התחברות".

צד לקוח — צעד אחר צעד

1. המשתמש מקליד אימייל + סיסמה, לוחץ "התחברות".
2. ה-UI עושה ולידציה בסיסית (אימייל תקין? שדות מלאים?) —
   זו ולידציית UX בלבד, לא אבטחה. השרת יבדוק שוב.
3. ה-UI שולח:
   POST /api/v1/auth/login
   Content-Type: application/json
   Body: { "email": "...", "password": "..." }
   credentials: 'include'   ← קריטי: כדי שה-cookie יחזור וייקלט
4. ה-UI נכנס למצב "submitting" (כפתור disabled + spinner).
5. ממתין לתשובה. לא עושה שום החלטת הרשאה בעצמו.

צד שרת — צעד אחר צעד

[שכבה 2 — Cloudflare] 
  - Rate limit: אם >10 ניסיונות login מאותו IP ב-15 דק' → 429.
  - מסנן בוטים/DDoS לפני שזה בכלל מגיע לשרת.

[שכבה 3 — Railway / Helmet]
  - בודק CORS allowlist (רק הדומיין שלנו מורשה).
  - מוסיף security headers (CSP, X-Frame-Options, HSTS).

[שכבה 4 — Auth Middleware / Better Auth]
  - זה endpoint ציבורי (login) — אין token עדיין, מדלג על אימות token.

[שכבה 6 — Zod Validation]
  - LoginSchema.parse(body): email הוא email תקין? password string
    באורך סביר? אם לא → 400 { error: { code:"validation_failed" }}.
    זה עוצר injection דרך שדה email/password.

[שכבה 7 — AuthService.login()]
  a. שולף את המשתמש לפי email מה-DB (parameterized query).
  b. אם אין משתמש כזה — עדיין מריץ hash compare דמה
     (constant-time) כדי שלא יהיה הבדל זמן בין "אין משתמש"
     ל"סיסמה שגויה" → מונע user enumeration.
  c. Better Auth משווה password מול ה-hash השמור (argon2/bcrypt).
  d. אם לא תואם → 401 { error: { code:"invalid_credentials",
     message:"אימייל או סיסמה שגויים" }}.
     ⚠️ הודעה גנרית בכוונה — לא מגלה אם האימייל קיים.
  e. אם תואם:
     - יוצר Access Token (JWT, TTL 15 דק') עם claims:
       { userId, activeOrgId, role, type:"access" }
       חתום עם הסוד של השרת (HS256/RS256).
     - יוצר Refresh Token (אקראי 256-bit, TTL 30 יום),
       שומר אותו ב-DB (טבלת sessions) — revocable.
     - רושם ב-audit_log: login event (userId, IP, timestamp).

[התשובה]
  Set-Cookie: access_token=<jwt>;  HttpOnly; Secure; SameSite=Lax; Max-Age=900
  Set-Cookie: refresh_token=<rnd>; HttpOnly; Secure; SameSite=Lax; Max-Age=2592000; Path=/api/v1/auth/refresh
  Body: { "data": { "user": { id, name, role, avatar_color,
          organization, capabilities } } }
  ← הגוף לא מכיל את ה-tokens. הם רק ב-cookies.

צד לקוח — אחרי התשובה

6. הדפדפן קולט את ה-cookies אוטומטית (כי credentials:'include').
   ה-JS לא רואה אותם — וזה בכוונה.
7. ה-UI קורא את { data: { user } }, שומר ב-state (לא ב-storage).
8. גוזר את ה-UI מ-user.capabilities (מה להציג בתפריט).
9. מנווט ל-dashboard.
10. מכאן כל בקשה הבאה — ה-cookie נשלח אוטומטית ע"י הדפדפן.

תרשים תמציתי

משתמש        UI (דפדפן)              Cloudflare      שרת (NestJS)           DB
  │ לחיצה      │                        │              │                   │
  ├───────────▶│ POST /auth/login       │              │                   │

2. זרימה: בקשת API מאומתת (כל בקשה אחרי login)

דוגמה: המשתמש פותח את רשימת הפרויקטים.

צד לקוח

1. ה-UI קורא:
   GET /api/v1/projects?limit=25
   credentials: 'include'   ← הדפדפן מצרף את access_token cookie לבד
2. אין צורך להוסיף Authorization header ידנית — ה-cookie עושה זאת.

צד שרת — 9 השכבות

[2] Cloudflare       → rate-limit per-user, WAF.
[3] Railway/Helmet   → CORS, security headers.
[4] Auth Middleware  → קורא access_token מה-cookie.
                       מאמת חתימת JWT. בודק תוקף (לא פג? 15 דק').
                       אם פג → 401 (ה-UI יעשה refresh, ראה §3).
                       מחלץ { userId, activeOrgId, role }.
[5] Tenant Middleware→ מזריק את activeOrgId לקונטקסט הבקשה.
                       מכאן כל query אוטומטית מסונן ל-org הזה.
[6] Zod Validation   → query params (limit, cursor) נבדקים.
[7] Service Layer    → ProjectsService.list(orgId, user):
                       בדיקת הרשאה — האם role רשאי? Agent רואה
                       רק assigned. Viewer רק קריאה.
[8] Drizzle ORM      → query פרמטרי (אין string concat → אין SQLi).
                       SET LOCAL app.organization_id = <activeOrgId>
[9] Postgres + RLS   → ה-RLS policy על הטבלה מסנן פיזית לפי
                       app.organization_id. גם אם השכבות מעל
                       טעו — ה-DB עצמו לא יחזיר נתונים של org אחר.
                       זו רשת הביטחון האחרונה (Doc 07 T1.5).

[התשובה]
  Body: { "data": [ ...projects ],
          "page": { "limit":25, "cursor":..., "has_more":bool } }

הנקודה הקריטית: ההרשאה נאכפת ב-3 שכבות בלתי תלויות — Service (role), Drizzle (org injection), Postgres (RLS). זו "defense in depth": טעות בשכבה אחת לא דולפת נתונים.

3. זרימה: רענון Token (אוטומטי, שקוף למשתמש)

ה-Access token חי רק 15 דק'. מה קורה כשהוא פג והמשתמש עדיין עובד?

צד לקוח

1. בקשה רגילה (למשל GET /projects) חוזרת 401
   { error: { code:"token_expired" }}.
2. ה-UI (interceptor ב-api adapter) תופס את ה-401:
   a. לא מציג שגיאה למשתמש עדיין.
   b. שולח: POST /api/v1/auth/refresh  credentials:'include'
      (ה-refresh_token cookie נשלח אוטומטית).
   c. אם הצליח → חוזר ושולח את הבקשה המקורית שוב, שקוף.
   d. אם נכשל (refresh גם פג) → מנקה state, מנווט ל-/login.

צד שרת — /auth/refresh

[4] Auth Middleware → קורא refresh_token מה-cookie.
[7] AuthService.refresh():
   a. מחפש את ה-refresh token ב-DB (sessions).
   b. אם לא קיים / פג / כבר שומש (rotation) →
      ⚠️ אם token שכבר סובב משמש שוב = סימן לגניבה →
      מבטל את כל ה-sessions של המשתמש, 401, רושם ב-audit.
   c. אם תקין → מנפיק זוג חדש (access + refresh),
      מסמן את הישן כ-used, שומר את החדש.
[התשובה] Set-Cookie x2 חדשים. Body { data:{ ok:true }}.

למה rotation: אם תוקף גנב refresh token, ברגע שאו הוא או המשתמש האמיתי משתמש בו פעם שנייה — המערכת מזהה שימוש כפול ומנתקת הכל. הגניבה מתגלה.

4. זרימה: התחברות דייר (Tenant) — SMS OTP

שונה מ-1: דייר אין לו אימייל/סיסמה. רק טלפון.

שלב א' — בקשת קוד

לקוח: משתמש מקליד טלפון ב-/portal/login, לוחץ "שלח לי קוד".
      POST /api/v1/auth/otp/request { phone }

שרת: [2] Cloudflare rate-limit — קריטי כאן: max 3 בקשות OTP
        לאותו טלפון ב-15 דק' (אחרת תוקף מציף ב-SMS = עולה כסף
        + מטריד אנשים).
     [6] Zod: phone בפורמט +972 תקין?
     [7] OtpService.request():
        a. מחפש tenant לפי phone. אם אין — מחזיר { data:{sent:true}}
           בכל מקרה (לא מגלה אם המספר רשום — מונע enumeration).
        b. אם יש — מייצר קוד 6 ספרות אקראי, שומר hash שלו ב-DB
           עם TTL 5 דק' + מונה ניסיונות.
        c. שולח דרך ISMSProvider (ספק ישראלי — D.20).
        d. audit: otp_requested.
     תשובה: { data: { sent: true }}

שלב ב' — אימות קוד

לקוח: משתמש מקליד 6 ספרות ב-/portal/otp, לוחץ "אישור".
      POST /api/v1/auth/otp/verify { phone, code }

שרת: [2] rate-limit: max 5 ניסיונות אימות לקוד. אחרי 5 → הקוד
        נשרף, צריך לבקש חדש (מונע brute-force על 6 ספרות).
     [7] OtpService.verify():
        a. שולף את ה-OTP hash מה-DB לפי phone.
        b. פג תוקף (>5 דק')? → 401 "הקוד פג, בקש חדש".
        c. השוואת hash (constant-time). לא תואם →
           מגדיל מונה, 401 "קוד שגוי".
        d. תואם → מוחק את ה-OTP (חד-פעמי!), מנפיק
           access+refresh tokens (כמו §1, אבל role=tenant,
           scope=הרשומה של הדייר בלבד).
        e. audit: tenant_login.
     תשובה: Set-Cookie x2 + { data: { tenant }}

ההבדל הקריטי בצד שרת: ל-Tenant ה-JWT מכיל tenant_id ולא activeOrgId. ה-RLS policy לדייר (Doc 02 §10) מסנן ל-tenant_id של המבקש — דייר פיזית לא יכול לשלוף רשומה של דייר אחר, גם אם ינסה לשנות את ה-URL.

5. זרימה: הרשמה (Signup — bootstrap ארגון ראשון)

לקוח: /signup — שם ארגון, שם, אימייל, סיסמה. "צור ארגון".
      POST /api/v1/auth/signup { org_name, name, email, password }

שרת: [6] Zod: password עומד במדיניות (אורך מינ', מורכבות)?
        email תקין? — נכשל → 400 עם הודעות שדה בעברית.
     [7] AuthService.signup() — בטרנזקציה אחת:
        a. בודק email פנוי. תפוס → 409 "האימייל כבר רשום".
        b. יוצר organization.
        c. יוצר user עם role=manager, משייך לארגון.
        d. Better Auth hash לסיסמה (אף פעם לא plaintext).
        e. audit: org_created + first_manager.
        f. commit. (אם משהו נכשל באמצע — rollback מלא,
           לא נשאר ארגון חצי-בנוי.)
        g. מנפיק tokens כמו §1.
     תשובה: Set-Cookie x2 + { data:{ user, organization }}

6. זרימה: התנתקות (Logout)

לקוח: לוחץ "התנתקות". POST /api/v1/auth/logout credentials:'include'

שרת: [7] AuthService.logout():
        a. מבטל את ה-refresh token ב-DB (מוחק/מסמן revoked).
           → גם אם מישהו העתיק אותו, הוא חסר ערך מעכשיו.
        b. audit: logout.
     תשובה: Set-Cookie access_token=; Max-Age=0  (מוחק)
            Set-Cookie refresh_token=; Max-Age=0
לקוח: מנקה state, מנווט ל-/login.

למה ביטול בשרת ולא רק מחיקת cookie: מחיקת cookie בלקוח לא מספיקה — אם מישהו כבר העתיק את ה-refresh token, הוא עדיין תקף. רק ביטול ב-DB באמת מנתק.

7. טבלת ה-Tokens (סיכום)

Access Token Refresh Token
מה JWT חתום מחרוזת אקראית 256-bit
TTL 15 דקות 30 יום (Provider: 4 שעות, Contractor: 7 ימים)
איפה httpOnly cookie httpOnly cookie, Path מוגבל ל-/auth/refresh
נשמר ב-DB? לא (stateless) כן (revocable)
מה מכיל userId, activeOrgId/tenant_id, role כלום (רק מפתח חיפוש ב-DB)
גניבה חסר ערך אחרי 15 דק' מתגלה ב-rotation (שימוש כפול)

9. מה זה אומר לכל אחד

ל-Claude Code (backend): ממש את §1-6 בדיוק כך. ה-pipeline (9 שכבות) הוא לא אופציונלי. כל endpoint עובר Zod → Service (הרשאה) → Drizzle (parameterized) → RLS. tokens תמיד httpOnly cookies, אף פעם לא בגוף התשובה.

לשותף (UI): כל קריאה צריכה credentials:'include'. אף פעם אל תשמור token ב-localStorage/state. תפוס 401 → קרא ל-/auth/refresh → נסה שוב. גזור UI מ-capabilities, לא מ-role ישירות.

לך: האבטחה לא "feature בסוף" — היא ב-9 השכבות שכל בקשה עוברת. ה-gates ב-GATES.md (RLS, PII, Tenant SMS) הם בדיוק הנקודות שבהן טעות פה עולה ביוקר — שם Claude Code עוצר ומראה לך לפני שממשיך.

מקורות: Doc 02 §10 (tiers + RLS), Doc 06 §5 (response contract), Doc 07 (trust boundaries, threat model, token policy). מסמך זה מאחד אותם לרצף ביצוע. במקרה של סתירה — Doc 07 גובר לאבטחה, Doc 06 לחוזה.
