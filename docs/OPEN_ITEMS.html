1. Tier 3 Operational Gaps (4 items)

These were identified in the audit, classified as defer-OK, and explicitly not closed in Option C.

1.1 Backup testing / DR drill schedule

  • What: A documented schedule for actually restoring from Neon backups (not just having them). Quarterly drill recommended at scale.
  • Where it would live: Doc 07 §13 (Incident Response) or a new §15 "Operations Runbook"
  • When to revisit: After 5 paying organizations, OR before any compliance audit (SOC 2 Phase 4)
  • Why deferred: Neon Free tier PITR is automatic; without paying customers, drill has no real-world stakes. The first drill should coincide with the first production deploy.
  • What we have today: Backup mechanism documented (Neon Launch = 7d PITR, Neon Pro = 30d); restoration procedure is one CLI command in Neon dashboard. We just haven't run the drill.

1.2 Rate limiting matrix per endpoint

  • What: A table mapping every endpoint to its specific rate limit (currently only /auth/login has explicit 5/min documented).
  • Where it would live: Doc 07 §6.x or Doc 06 §5.x (API spec)
  • When to revisit: Phase 6 (Hardening + Production), or immediately if abuse is detected
  • Why deferred: Default 100 req/min/IP global rate limit (set in apps/api/src/main.ts) is sufficient for MVP traffic. Per-endpoint tuning is premature without real traffic patterns.
  • What we have today:
  • Global: 100 req/min/IP (NestJS Throttler)
  • Login: 5/min/IP (explicit, Doc 07 §6.11)
  • Password reset: 3/email/hour + 10/IP/hour (explicit, Doc 07 §6.12.2)
  • What's missing: Specific limits for create-signature, upload-document, list endpoints (these may need higher limits for bulk operations).

1.3 Provider Admin production onboarding procedure

  • What: A step-by-step procedure to add a new Provider Admin to production (different from the initial bootstrap script in Doc 04c P1.3).
  • Where it would live: Doc 07 §14 (Secret Rotation) extension, or a new runbook
  • When to revisit: When EMAPP team grows beyond 2 people (i.e., we hire support/ops staff)
  • Why deferred: With 2 founders, no other people will have Provider access in MVP. The dev setup script in Doc 04c P1.3 handles the initial case.
  • What we have today: Bootstrap SQL script that creates the first provider_users entry with MFA enabled. No documented procedure for the second admin.
  • Open questions when revisited:
  • Who approves a new Provider Admin? (Both founders? CTO alone?)
  • Hardware token (Yubikey) or TOTP-only?
  • Vetting period before granting full access?
  • Offboarding procedure when someone leaves?

1.4 Hebrew full-text search

  • What: Postgres full-text search configured for Hebrew tokenization (e.g., search "אבי" finds "אבי כהן", "אבישי", etc.)
  • Where it would live: Doc 04c new task (P2.x or P3.x), Doc 02 §15 (Data Model)
  • When to revisit: When a single org reaches ~1000+ owners and the basic ILIKE pattern starts being too slow (likely Phase 2 of product)
  • Why deferred: Postgres ILIKE + the he_il_icu collation (just added in P1.10) handles MVP-scale search (~100 owners per org) fine. Hebrew tokenization is non-trivial and not free; premature.
  • Options when revisited:
  • pg_trgm extension (trigram matching — works OK for Hebrew, no tokenizer needed)
  • pg_search / paradedb (proper full-text search)
  • External: Meilisearch or Typesense

  • When to create: Before bringing on any third party (consultant, contractor, advisor)
  • Why deferred: Doc 01 + Doc 02 already cover this for the founding team. A condensed version is only valuable once someone external needs to understand the project quickly.

  • One paragraph: how to navigate the docs (01 → 02 → 04c → 07 path)

  • Why deferred: The decisions are currently spread across Doc 02 §13 (8 portability rules) and inline in each doc. Centralizing them is valuable for future reference but isn't blocking.
  • Sketch of contents (first 10-15 entries):

  • D.05 Provider tier: separate DB role + table (not is_admin boolean) — Doc 02 §10
  • D.06 PII encryption: pgcrypto field-level (not column-level disk encryption only) — Doc 07 §5
  • D.07 Soft delete: archivedAt (not deletedAt) — Doc 04c §4
  • D.08 Buildings/Owners: single table with enum (not CTI) — Doc 04c §4
  • D.09 RLS strategy: ENABLE + FORCE on all multi-tenant tables — Doc 07 §10
  • D.10 API versioning: /api/v1/ from day 1 — Doc 06 §5.1
  • D.11 Hebrew collation: ICU he_il_icu per-column — Doc 04c P1.10
  • D.12 Signature format: SVG, encrypted inline (not R2) — Doc 04c P1.8
  • D.13 Cookie consent: no banner in MVP (Israeli law) — Doc 07 §6.14
  • D.14 First-org bootstrap: self-serve signup — Doc 03 Phase 2
  • D.15 Worker scope: SSE + cleanup + retry only in MVP — Doc 02 §5.8

2.3 constraints.md

  • What: Long-form rationale for the most important architectural constraints (the "why we won't change this even when tempted").
  • Where it would live: Repo root, referenced from CLAUDE.md
  • When to create: Start with empty file in Phase 0; grow organically as decisions get challenged
  • Why deferred: Doc 04a §2.6 already shows the format with 3 starter examples (C.01 Drizzle, C.02 Postgres cache, C.03 Two DB roles). The actual file just needs to be created in the repo.

3. Phase 2+ Scope (Explicitly Excluded from MVP)

These are documented as out-of-scope in the v2 docs, but listed here for visibility so they don't surprise us later.

3.1 Tenant Portal — MOVED TO MVP (decisions D.17 + D.20)

  • Status: NO LONGER deferred. The user decided (2026-05-16) that Tenant is an MVP role.
  • What: Portal where residents/owners log in via SMS OTP to view their own record, project status, and sign documents.
  • MVP scope: tenants identity table + tenant-scope RLS land in Phase 1; SMS OTP auth in Phase 2; portal screens in Phase 8.
  • SMS provider: Israeli vendor (019/Inforu) behind ISMSProvider — D.20. NoopSMSProvider is dev-only.
  • Reflected in: Doc 01 Persona 3, Doc 02 §6.6 + §10, Doc 06 §16.2, Doc 07 §6.5, DECISIONS.md D.17/D.20.

3.2 SMS OTP (Twilio swap)

  • What: Real SMS implementation behind ISMSProvider interface (currently NoopSMSProvider).
  • Why excluded from MVP: No tenant portal in MVP = no SMS needed. Manager/Agent use email + password.
  • When to revisit: Same as Tenant Portal trigger.
  • Mentioned in: Doc 02 §6 (Interface Layer), Doc 02 §14.4 (Growth tier)

3.3 Field tasks + photo capture (Phase 2 of product)

  • What: Agent in the field receives tasks on mobile, photographs apartments / IDs, uploads from the road.
  • Why excluded from MVP: Web-first MVP. Mobile-optimized capture is its own product surface.
  • When to revisit: After basic project management is proven; likely Phase 2.

3.4 Chat between Manager / Agent / Contractor

  • What: In-app real-time chat (not just notifications).
  • Why excluded from MVP: Notifications + email cover the MVP coordination need. Real chat requires WebSocket infrastructure beyond SSE.
  • When to revisit: When users start asking for it; likely Phase 2.
  • Implication: IRealtimeProvider would need to swap from SSE to Pusher/WebSocket.

3.5 SSO / SAML for enterprise customers

  • What: Single Sign-On via SAML for large organizations using Active Directory.
  • Why excluded from MVP: SMB target customers don't use SSO.
  • When to revisit: First enterprise prospect that asks. Not before.

3.6 AI / RAG features (Phase 3 of product)

  • What: Document summarization, suggestion engine for next steps, semantic search across project history.
  • Why excluded from MVP: Premature without baseline data. Also: pgvector deferred (was in v1 stack).
  • When to revisit: Phase 3 of product (after 10-20 customers).

3.7 OCR for Israeli ID cards (Phase 3)

  • What: Agent photographs an ID card, system extracts name/number/photo automatically.
  • Why excluded from MVP: Big UX win but requires real OCR service (Google Vision, AWS Textract, or self-hosted). Adds cost and complexity.
  • When to revisit: When data entry pain is the #1 complaint.

3.8 Advanced analytics

  • What: Manager dashboard showing time-to-signature, refusal rate, conversion funnel, project velocity.
  • Why excluded from MVP: Basic counts (X owners, Y signatures) are enough until projects have history.
  • When to revisit: Phase 3.

3.9 Multi-language UI (English + Arabic + Russian)

  • What: Full UI translation beyond Hebrew + minimal English.
  • Why excluded from MVP: Israeli SMB market is Hebrew-first. English exists for backend dev tools and docs.
  • When to revisit: When a customer specifically requests it. Hebrew RTL design already in place.

3.10 Public API for integrations

  • What: API key based access for customer's own systems to integrate with EMAPP data.
  • Why excluded from MVP: Premature. The internal API is the only API.
  • When to revisit: When an enterprise customer asks. /api/v1/ structure (already decided) makes adding a public v1 layer straightforward.

3.11 SOC 2 Type II / external pentest / bug bounty

  • What: Compliance frameworks needed for enterprise sales.
  • Why excluded from MVP: ~$5-15K each, only valuable when revenue justifies it.
  • When to revisit: When pursuing enterprise deals (50+ orgs).
  • Mentioned in: Doc 02 §16.3 Phase 4

3.12 Multi-region deployment

  • What: Running EMAPP outside Israel for international customers.
  • Why excluded from MVP: Israeli market is the focus. Single region = simpler ops.
  • When to revisit: When non-Israeli customers exist.

3.13 Billing / payment integration

  • What: Stripe or Paddle integration for self-serve payment + subscriptions.
  • Why excluded from MVP: 0-3 pilot customers = manual billing. No friction needed.
  • When to revisit: Before scaling beyond ~10 customers.
  • Implication for first-org bootstrap (Doc 03 Phase 2): Currently signup creates a free account; add trial/payment when relevant.

3.14 Account deletion / data export (GDPR-style)

  • What: User-initiated full data export + account deletion.
  • Why excluded from MVP: Israeli law doesn't require these for our use case yet. Implementation is non-trivial (multi-table cascades, R2 cleanup, audit retention rules).
  • When to revisit: Before any EU customer expansion, or if Israeli law strengthens.
  • Mentioned in: Doc 07 §12.9 ("no deletion on user request for audit data")

4. Open Questions Not Yet Resolved

These came up in audit but weren't categorized as gaps — they're decisions that could go either way.

4.1 Analytics provider for Phase 2

  • Question: When we eventually add analytics, which provider? PostHog? Plausible? Self-hosted?
  • Why not decided: Phase 2 timing.
  • Implications: Cookie consent banner UX depends on choice. Plausible is cookieless (no banner needed); PostHog needs consent.

4.2 PDF generation strategy (for contracts)

  • Question: Eventually we'll need to generate PDFs from templates (rendered contracts ready to sign). What library? puppeteer? @react-pdf/renderer? Server-side or client-side?
  • Why not decided: Phase 5 (Signatures) is when this matters. MVP may not need it if signatures attach to existing PDFs.
  • Implications: If server-side, Worker container has another responsibility. If client-side, FE bundle grows.

4.3 Mobile app future

  • Question: Will EMAPP ever have a native mobile app, or stay web-only (PWA)?
  • Why not decided: PWA is sufficient for Phase 1-2. Native makes sense only if mobile features (camera, offline) become critical.
  • Implications: Affects API design (would push toward more RESTful + better caching headers).

4.4 Audit log UI for customers

  • Question: Should Managers see their org's audit log in the UI? If so, how filtered?
  • Currently: Doc 07 §12.11 mentions "Manager UI (Phase 2)" for activity page.
  • Why not decided: UX research needed. May raise privacy concerns from Agent users ("Manager can see everything I did").

4.5 Soft delete cleanup policy

  • Question: Currently archivedAt is permanent (no hard-delete after N days). Do we want a cleanup job?
  • Why not decided: Storage cost minimal in MVP. Audit log retention rules (Doc 07 §12.9) already cover the legal angle.
  • Implications: If we ever add it, must be Provider-only, audited, and excluding audit_log.
