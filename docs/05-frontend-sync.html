02 · Project Context (TL;DR)

What You're Building

If you only read one section, read this one.

2.1 The Product in Three Sentences

Urban Renewal SaaS is a multi-tenant platform for Israeli real estate developers running urban renewal projects. Each project involves dozens to hundreds of property owners who must sign agreements, share documents, and coordinate over 1-3 years. Today, developers manage this with Excel + WhatsApp + paper folders. We replace that mess with a single system.

2.2 The Core Workflows

Five workflows that drive the product. Almost everything you build supports one of these:

  • Owner Management. Developer imports a list of all property owners (often from Excel). System tracks contact info, ownership shares, and signature status for each owner.
  • Document Distribution. Developer uploads a contract or notice. System sends it to all relevant owners (or a subset) and tracks who opened it.
  • Digital Signatures. Owner clicks a link in an email, sees the document, signs on a canvas (or types name), submits. System records the signature with audit trail.
  • Project Dashboard. Developer sees overview of project: how many owners signed, progress timeline, recent activity, blockers.
  • Reports & Exports. Developer generates PDF/Excel reports for legal filings, investor updates, or owner communications.

2.3 The User Personas

You're designing for two distinct users:

👨‍💼
The Developer
Real estate company, project manager

Primary user. Logs in daily during active projects. Manages multiple projects. Hebrew speaker, RTL native. Comfortable with software but expects efficiency. Pays the subscription.

👤
The Owner
Property owner being signed

Public user. Receives email link. Doesn't log in. Opens link, signs document, leaves. Mixed tech comfort — could be 25 or 75. Often uses phone, not computer. Doesn't pay anything.

2.4 Key Constraints That Shape Your UI

  • RTL by default. Hebrew is the primary language. Layouts flow right-to-left. Mirror everything.
  • Multi-language from day one. Hebrew + English at MVP. Arabic + Russian later. Build for i18n from the first component.
  • Accessibility matters. Some owners are elderly. Big enough fonts, high contrast, keyboard navigation, screen reader support.
  • Mobile-first for owner-facing. Owners click email links on phones. Sign on phones. The signature flow must work flawlessly on mobile.
  • Desktop-primary for developer-facing. Developers use real screens. Optimize for tablet+ for the dashboard.
  • Performance under Israeli network conditions. 4G mobile signal in older buildings is slow. Don't ship 2MB JavaScript bundles.

2.5 What Success Looks Like

By the end of MVP (~4 weeks of part-time work):

  • A developer can sign up, create a project, import 50 owners, send a document, and see signatures come back — without calling support
  • An owner can sign on phone in under 2 minutes — without creating an account
  • The whole experience feels native to Israeli users (RTL, Hebrew, familiar UX patterns)
  • The product is fast enough that nobody complains about loading times

3.4 The Async-First Principle

You and your partner work on different schedules. The default is async:

  • What's planned this week (each)
  • Any blockers (each)
  • Anything in shared territory needing alignment

That's it. No daily standups. Most communication happens through code.

💡 The Conflict Resolution Rule
When you disagree on shared territory (e.g., a Zod schema design), the rule is: whoever needs it first owns the decision, but documents the trade-off. The other can revisit later if it doesn't work in practice. Don't get stuck in design debates. Ship something, learn, iterate.

06 · RTL & i18n Setup

Hebrew First, English Second, Arabic + Russian Later

RTL and i18n aren't features added later — they're foundational. Build with both in mind from your first component.

6.1 The Setup

Phase 0 (P0.5) sets this up. Here's what's already in place when you start:

  • html lang="he" dir="rtl" on the root layout
  • Heebo font via next/font/google (loaded as --font-heebo CSS variable)
  • Tailwind RTL plugin: tailwindcss-rtl
  • next-intl configured for HE + EN
  • Locale prefix in URLs: /he/projects, /en/projects

6.2 Writing RTL-Aware Tailwind

Tailwind RTL plugin gives you logical properties:

RTL-aware Tailwind classes
// ❌ Wrong: hard-coded direction
<div className="ml-4 pl-2 text-left">...</div>

// ✓ Right: logical direction
<div className="ms-4 ps-2 text-start">...</div>
// ms = margin-start (right in RTL, left in LTR)
// ps = padding-start
// text-start = right-aligned in RTL, left in LTR

// Some things stay literal — those are fine
<div className="mt-4 pb-2">...</div>  // top/bottom doesn't flip

6.3 The Logical Properties Cheat Sheet

6.4 Icons That Need Mirroring

Some icons should flip in RTL (arrows pointing in directions). Others should not (search, mail, settings):

Icon RTL handling
// ❌ Wrong: chevron points the same way regardless of direction
<ChevronRight />  // In RTL, this still points right (visually wrong)

// ✓ Right: rotate based on locale
import { ChevronLeft, ChevronRight } from 'lucide-react';
import { useLocale } from 'next-intl';

const locale = useLocale();
const ChevronForward = locale === 'he' ? ChevronLeft : ChevronRight;

<ChevronForward />  // Points "forward" relative to text direction

// Or use Tailwind's rtl: variant
<ChevronRight className="rtl:scale-x-[-1]" />

Don't mirror these icons even in RTL: ✉ mail, 🔍 search, ⚙ settings, 👁 eye, ✓ check, ✕ close.

Do mirror: arrows (→ ←), chevrons (› ‹), play buttons (▶), back/forward navigation icons.

6.6 Number and Date Formatting

Use Intl APIs through next-intl for locale-aware formatting:

Locale-aware formatting
import { useFormatter } from 'next-intl';

export function ProjectCard({ project }: Props) {
  const format = useFormatter();
  return (
    <div>
      <p>{format.dateTime(project.createdAt, 'short')}</p>
      <p>{format.number(project.budget, { style: 'currency', currency: 'ILS' })}</p>
      // In Hebrew: ‎15/03/2026 and 1,250,000.00 ₪
    </div>
  );
}

6.7 Hebrew-Specific Considerations

  • Numbers stay LTR. "15/03/2026" reads left-to-right even in Hebrew text. Browsers handle this automatically with dir="rtl" on the parent.
  • Mixed Hebrew + English. User types "I love NestJS" — the English flows LTR within Hebrew RTL context. Use &lrm; or &rlm; Unicode marks if direction breaks.
  • Israeli ID validation. 9 digits. Use isValidIsraeliId from @app/validators. Format with leading zeros if user types 8 digits.
  • Phone numbers. Israeli format: 050-1234567 or +972-50-1234567. Display normalized.
💡 Test RTL early and often
Don't develop in English then "fix RTL later". Build in Hebrew from day one. Switch to English to verify logical properties work both ways. Test with the locale switcher.

Start with primitives. Build composites as needed. Don't try to design everything upfront — design emerges from real screens.

7.3 The Theme

Pick the theme during Phase 0. Keep it simple. Two recommendations:

  • Neutral / Slate — professional, B2B-feeling. Recommended for our developer-facing UI. Easy to read in long dashboards.
  • Brand color accent — pick one accent (blue, teal, or green) for primary actions. Avoid bright reds (associated with errors).

Configure in tailwind.config.ts via CSS variables. shadcn provides templates.

7.4 Spacing & Typography Scale

Use Tailwind's default scale. Don't customize unless necessary:

  • Spacing: 4px increments (p-1 = 4px, p-4 = 16px, p-8 = 32px)
  • Font sizes: text-sm (14px) for body, text-base (16px) for emphasized, text-2xl (24px) for headings
  • Line height: leading-relaxed for body text (Hebrew reads better with more space)

7.6 The "Don't Reinvent" Rule

If shadcn has a primitive for it, use shadcn. Don't write your own button, input, dialog. Reasons:

  • Accessibility built in (a11y is hard to get right)
  • Keyboard navigation built in
  • Consistency across the app
  • Less code to maintain

You can customize the shadcn copy in your repo. That's the whole point of shadcn — you own it.

7.7 Empty States, Loading States, Error States

Every list, every async data view, every form needs three states beyond the happy path:

  • Loading. Skeleton or spinner. Don't show a blank page during fetches.
  • Empty. "No projects yet" with a CTA to create the first one. Empty states are a designed state, not a default.
  • Error. "Couldn't load. Retry?" with a retry button. Generic but actionable.

TanStack Query gives you isLoading, isError, and data states. Use them.

💡 Design as you go
Don't try to design the entire system before building. Build a screen, see what feels off, refine. Build the next screen, notice patterns, extract components. Real designs emerge from real screens — regardless of which design tool produces them.

7.8 Choosing Your Design Workflow

You have multiple paths to producing UI code. The choice is yours. The contract with backend (Doc 06) is identical regardless of which path you choose.

Option A: Figma + Claude Design (recommended starting point)

Use Figma to plan the high-level structure: which screens exist, how they connect, basic wireframes. Then use Claude Design for the actual visual design and code generation.

  • Figma is for thinking. Sketch flows, explore variants, share with stakeholders for feedback.
  • Claude Design is for production. Generates polished UI code that uses shadcn primitives, follows your design tokens, handles RTL.
  • Hand-finishing is normal. Whatever Claude Design produces, you'll likely refine it. That's the point — you own the code.

Option B: Claude Design only

Skip Figma. Go directly from idea to UI through Claude Design. Faster for screens that are well-understood (a standard form, a list view).

  • Works for screens with clear patterns from the existing app
  • Less suited for novel UX (signature canvas, complex wizards) — Figma exploration helps there
  • Iterate by re-prompting Claude Design with what you want changed

Option C: Direct coding with shadcn

Skip both design tools. Build directly in code with shadcn primitives. Fastest for trivial screens (settings page, terms of service, simple forms with one field).

  • Best when you know exactly what you want
  • Best for tiny changes to existing screens
  • Always available as a fallback

Mixing and matching

You'll likely use different paths for different screens:

  • Dashboard layout — Figma to plan, Claude Design to build
  • Owner form — Claude Design directly (it's a standard form)
  • Settings page — Direct coding (trivial)
  • Signature canvas — Figma exploration first (novel UX), then code by hand or with Claude Design

What every path must produce

Regardless of which tool you used, the resulting code must:

  • Import types from @app/shared-types (not redefined)
  • Use react-hook-form + zodResolver for forms
  • Use TanStack Query for API calls
  • Use shadcn primitives (don't reinvent Button, Input, Dialog)
  • Use logical Tailwind properties (ms/me, not ml/mr)
  • Externalize all strings via next-intl
  • Pass the FE Definition of Done in Doc 06 section 13

If Claude Design produces code that violates these — refine it. The DoD is the truth, the tool is a means.

Switching tools mid-project

You can change approaches anytime. The contract doesn't care. Backend doesn't care. Switch when the current tool isn't working for the screen you're on, or when a new tool becomes more capable.

✓ Tool-agnostic code is the goal
If someone reads your code 6 months from now, they shouldn't be able to tell whether it came from Figma + manual coding, Claude Design, or hand-typed shadcn. The code should look the same — clean, conventional, schema-driven. The tool is a delivery mechanism for code; the code is what matters.
08 · shared-types Contract

The Single Source of Truth

The shared-types package is the formal contract between you and your backend partner. Treat it with care.

Every entity in the system has a Zod schema in packages/shared-types/. The schema defines the shape, validates input, and generates TypeScript types. Both FE and BE use the same schemas. When the schema changes, both sides update.

8.1 Why This Matters

In a typical FE/BE split, each side has its own type definitions. They drift. FE expects { id, name }, BE actually returns { id, displayName }. Bugs.

By sharing Zod schemas:

  • Forms get validation for free — same rules as backend
  • API responses are typed automatically — no manual TypeScript interfaces
  • Schema changes are visible — single PR shows what changed and who's affected
  • Errors match — when BE rejects bad input, FE shows the same error message
💡 For full protocols on shared-types
This section gives you the FE-side view. Document 06 sections 4 and 8 cover the formal contract: how to add new schemas, how to safely change existing ones (additive vs tightening vs breaking), and the coordination protocols with your backend partner.

8.2 The Pattern

Every entity has one file in packages/shared-types/src/:

packages/shared-types/src/owner.ts
import { z } from 'zod';
import { isValidIsraeliId } from '@app/validators';

// Enums first
export const OwnerTypeEnum = z.enum(['individual', 'company', 'inheritance']);
export type OwnerType = z.infer<typeof OwnerTypeEnum>;

// Full schema (for reads)
export const OwnerSchema = z.object({
  id: z.string().uuid(),
  organizationId: z.string().uuid(),
  type: OwnerTypeEnum,
  displayName: z.string().min(1).max(200),
  phone: z.string().nullable(),
  email: z.string().email().nullable(),
  address: z.string().nullable(),
  notes: z.string().nullable(),
  createdAt: z.coerce.date(),
  updatedAt: z.coerce.date(),
  archivedAt: z.coerce.date().nullable(),
});

// Input schema for individual owner (for forms)

8.4 Using Schemas to Parse API Responses

When you call the API, parse the response with the schema. This catches contract drift early:

apps/web/src/lib/api/projects.ts

If the BE returns something unexpected, the parse throws — better to fail loudly here than silently elsewhere.

8.5 Modifying Shared Types

When you need to add or change a schema:

  • Discuss first. Ping your partner. Quick chat about why and what.
  • One person opens a PR. Whoever needs it first.
  • The PR title says it clearly: feat(shared-types): add owner inheritance schema
  • Both review. Check that the schema matches BE reality and FE expectations.
  • Merge before either side uses it. Don't reference the new type in code that lands first — that creates type errors elsewhere.

8.6 Common Patterns

📋 Pattern: Read schema vs Input schema
Read schemas (e.g. ProjectSchema) include all fields the API returns: id, timestamps, organizationId. Input schemas (CreateProjectInput) omit those — id is generated, organizationId is injected by BE, timestamps are server-set.
📋 Pattern: Discriminated unions for polymorphic types
Owners are individuals, companies, or inheritances. Each has different fields. Use z.discriminatedUnion('type', [...]) for type-safe handling. TypeScript narrows correctly based on the type field.
📋 Pattern: z.coerce.date() for timestamps
JSON sends dates as strings. Use z.coerce.date() on read schemas to auto-convert. Without coerce, you get a string where TypeScript thinks it's a Date.
📋 Pattern: nullable vs optional
z.string().nullable() means the field exists but value can be null. z.string().optional() means the field might not be in the object. For DB nullable columns, use .nullable(). For form fields the user might skip, use .optional().
⚠️ The Shared Types Stability Rule
Once a schema is in main and used by both sides, breaking changes need explicit coordination. Don't rename fields casually. Don't tighten validation without checking impact. Add new optional fields freely, but reshape carefully.
09 · API Integration Pattern

How You Talk to the Backend

TanStack Query + fetch + shared-types. A simple, modern, predictable pattern.

9.1 The Layers

Three layers between your component and the backend:

  • API client functions in lib/api/. Plain async functions that call fetch and parse responses.
  • TanStack Query hooks in hooks/. Wrap API functions in useQuery / useMutation for caching, refetching, optimistic updates.
  • Components. Use the hooks. Don't call fetch directly.

9.2 The API Client Pattern

apps/web/src/lib/api/client.ts
// Base fetch wrapper with error handling and credentials
const API_BASE = process.env.NEXT_PUBLIC_API_URL ?? 'http://localhost:3000';

export class ApiError extends Error {
  constructor(public status: number, message: string, public body?: unknown) {
    super(message);
  }
}

export async function apiFetch<T>(
  path: string,
  options: RequestInit = {},
): Promise<T> {
  const res = await fetch(`${API_BASE}${path}`, {
    ...options,
    credentials: 'include',  // Send cookies for auth
    headers: {
      'Content-Type': 'application/json',
      ...options.headers,
    },
  });

  if (!res.ok) {
    const body = await res.json().catch(() => null);
    throw new ApiError(res.status, body?.message ?? res.statusText, body);
  }

  return await res.json() as T;
}

9.4 The TanStack Query Pattern

import { useQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { listProjects, createProject } from '@/lib/api/projects';
import type { CreateProject } from '@app/shared-types';

// Query key factory — consistent keys for cache invalidation
export const projectKeys = {
  all: ['projects'] as const,
  lists: () => [...projectKeys.all, 'list'] as const,

};

export function useProjects() {

    queryKey: projectKeys.lists(),

}

export function useCreateProject() {

  return useMutation({
    mutationFn: (input: CreateProject) => createProject(input),
    onSuccess: () => {
      // Invalidate the projects list so it refetches
      queryClient.invalidateQueries({ queryKey: projectKeys.lists() });
    },
  });
}

9.6 Optimistic Updates

For actions where the user expects instant feedback (toggle, like, mark done), use optimistic updates:

Optimistic update pattern
export function useUpdateProject() {
  const queryClient = useQueryClient();

  return useMutation({
    mutationFn: updateProject,
    onMutate: async (newProject) => {
      // Cancel in-flight queries
      await queryClient.cancelQueries({ queryKey: projectKeys.detail(newProject.id) });

      // Snapshot previous value
      const previous = queryClient.getQueryData(projectKeys.detail(newProject.id));

      // Optimistically update
      queryClient.setQueryData(projectKeys.detail(newProject.id), newProject);

      return { previous };
    },
    onError: (err, newProject, context) => {
      // Rollback on error
      queryClient.setQueryData(projectKeys.detail(newProject.id), context?.previous);
    },
    onSettled: (data, err, newProject) => {
      // Refetch to ensure server state
      queryClient.invalidateQueries({ queryKey: projectKeys.detail(newProject.id) });
    },
  });
}

9.7 Error Handling Strategy

  • Network errors — TanStack Query auto-retries 3x. After that, show error state.
  • 4xx errors — show specific message from API. Don't retry.
  • 5xx errors — generic "Something went wrong, try again" message. Log to Sentry.
  • 401 unauthorized — redirect to login. Clear local state.
  • Validation errors (400) — display field-level errors in the form.

9.8 The Adapter Pattern — Insulate UI from API Shape

The shared-types schemas are the contract with the backend. But the shape that's optimal for an API response is rarely the shape that's optimal for rendering a UI. The adapter pattern sits between them: it takes the wire shape (validated by Zod against shared-types) and returns the UI shape that components actually want.

Why this matters:

  • Backend schema changes don't ripple into 50 components. When the backend renames nationalIdEncrypted to nationalId on the wire (because PII is decrypted server-side before sending), the adapter changes; components don't.
  • The UI shape is what the UI needs, not what the DB has. The DB has archived_at: Date | null. The UI wants isArchived: boolean. The adapter does the translation in one place.
  • Computed fields live in adapters, not components. "Display name" might be firstName + ' ' + lastName for an individual owner but the company name for a corporate owner. That logic lives in the adapter, runs once, and components just render owner.displayName.
  • Multiple sources of truth become one shape. If we have owners and contractors from different endpoints but the UI shows them in the same list, the adapter normalizes both to a common PersonViewModel.

9.8.1 The Pattern

Three types per entity:

  • Wire type — what the API returns. Lives in @app/shared-types. Validated with Zod.
  • View Model — what components consume. Lives in apps/web/src/models/<entity>.vm.ts.
  • Adapter — pure function from Wire to ViewModel. Lives in apps/web/src/adapters/<entity>.ts.

9.8.2 Where the Adapter Runs

Right in the TanStack Query hook, with select:

apps/web/src/hooks/use-projects.ts
import { useQuery } from '@tanstack/react-query';
import { listProjects } from '@/lib/api/projects';
import { toProjectViewModels } from '@/adapters/project';

export function useProjects() {
  return useQuery({
    queryKey: ['projects'],
    queryFn: listProjects,
    select: toProjectViewModels,  // adapter runs here, only on change

}

TanStack Query's select memoizes by reference, so the adapter runs only when the underlying data changes — not on every render.

9.8.3 When You Don't Need an Adapter

Not every entity needs an adapter. Heuristic:

SituationAdapter needed?
UI shows raw fields as-isNo — use the Wire type directly
UI shows enum labels in HebrewYes — adapter maps enum → label
UI shows computed fields (progress %, days remaining)Yes — computation lives in adapter
UI normalizes 2 different shapes into 1 listYes — each shape has its own adapter to the unified VM
UI shows dates in relative form ("3 days ago")Yes — adapter formats the date
Form input/output (write path)No — use shared-types CreateXInput directly
💡 Adapter rules of thumb
Adapters are pure functions. No fetch, no side effects, no hooks inside. Input → Output. Easy to test.

Adapters don't mutate the wire type. The Zod-validated Project stays exactly as the contract defines. The adapter produces a new shape next to it.

Adapters live in the FE only. The backend has no concept of ProjectViewModel — that's UI-specific. Don't add adapters to shared-types.

Start without them; add when needed. Don't pre-build adapters for every entity. Add the adapter the first time a component needs translation. Pre-mature abstraction is a real cost.

10.7 Mock-First Anti-Patterns

Things to avoid:

  • Don't ship mocks to production. Use env var to gate. CI should fail if MSW is enabled in build.
  • Don't make mocks too elaborate. A few realistic items per endpoint is enough. Don't simulate the entire backend.
  • Don't let mocks drift from schemas. If you change a Zod schema, update the mocks. Otherwise tests pass against fake data, fail against real backend.
  • Don't keep mocks indefinitely. When the real endpoint is ready, switch and remove the mock.
✓ Why this works
Mock-first development means you're never blocked. Your partner ships endpoints when they ship. You build UI continuously. When endpoints come online, integration is just toggling a flag — because the contract (Zod schemas) was right from day one.
