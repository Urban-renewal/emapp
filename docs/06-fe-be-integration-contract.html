01 · Why This Document

The Tool-Agnostic Contract

Tools change. Tastes change. Frameworks evolve. The contract between frontend and backend should not.

This document is read by both developers. It defines the formal contract between the frontend and backend layers — the rules, protocols, and ceremonies that allow two part-time developers to work in parallel without blocking each other and without breaking each other's work.

1.1 Who Reads This

  • The backend developer — to understand what the FE expects and how to deliver it without breaking things
  • The frontend developer — to understand what the BE provides, how to consume it safely, and how to work productively before endpoints exist
  • Future team members — to onboard onto the integration model in 30 minutes

1.2 What This Is, What This Isn't

1.3 The Tool-Agnostic Principle

The frontend developer might choose to:

  • Sketch screens in Figma, then implement with shadcn primitives
  • Use Claude Design to generate complete UI, then refine in code
  • Skip design tools and code directly with shadcn
  • Use a different design tool entirely (Penpot, Sketch, etc.)
  • Switch tools mid-project

None of this changes the contract. Whatever produces the final UI code, that code:

  • Imports types from @app/shared-types (not redefined locally)
  • Uses Zod schemas for form validation (not custom validation)
  • Follows the API integration pattern (TanStack Query + parsed responses)
  • Respects the API stubs the backend provides
  • Works against both real endpoints and mocks

The contract is what makes parallel work possible. The tools are how each developer chooses to honor the contract.

1.4 The Cost of Skipping This

Without an explicit contract, integration breaks down in predictable ways:

  • Schema drift. FE assumes the API returns { id, name }. BE actually returns { id, displayName }. Bug in production.
  • Blocked work. FE can't build features because the API doesn't exist. BE can't ship the API because they're not sure what FE needs.
  • Repeated re-work. Schema changes break FE. FE rebuilds. BE realizes the change was wrong, reverts. FE rebuilds again.
  • Slow handoffs. "Is endpoint X ready?" "I think so?" Endless back-and-forth with no clear definition.
  • Lost trust. When integration repeatedly breaks, developers stop trusting each other's work. Communication overhead increases. Velocity drops.

This document prevents all of those by formalizing the contract once.

✓ The compounding benefit
A tight contract isn't bureaucracy — it's leverage. Two developers with a clear contract ship more than three developers without one. Every minute spent enforcing the contract saves an hour debugging integration issues.
02 · The Three Pillars

What Makes the Contract Work

Three load-bearing mechanisms. Remove any one of them, and parallel work becomes impossible.

The integration contract rests on three pillars. They reinforce each other. Together they enable parallel work; individually, none is sufficient.

2.1 Pillar 1: shared-types as Single Source of Truth

Every entity in the system has a Zod schema in packages/shared-types/. Both the backend and the frontend import from this package. The Zod schema defines:

  • The shape of the entity (fields, types, constraints)
  • Validation rules (min length, format, enums)
  • Input variants (Create, Update) derived from the base schema
  • TypeScript types inferred from the schema

When the schema changes, both sides see the change. TypeScript catches mismatches at compile time. Runtime parsing catches mismatches at the boundary.

Without this pillar: types drift, fields get renamed without coordination, validation rules diverge between FE and BE.

2.2 Pillar 2: Mocks and Stubs Enable Independence

The frontend developer should never block on the backend developer to build a feature. The mechanism: mocks and stubs.

  • API stubs — the backend developer provides a stub endpoint before the real implementation. The stub returns realistic mock data that matches the schema. FE wires up against the stub.
  • FE mocks (MSW) — the frontend developer creates client-side mocks that intercept fetch calls during dev. Useful when the BE stub doesn't exist yet, or for offline work.

Both mechanisms produce data that conforms to the shared-types schemas. When the real endpoint ships, the FE switches over with zero code changes — only a config toggle.

Without this pillar: every FE feature waits for the BE feature. Sequential work. 2x the calendar time.

2.3 Pillar 3: Clear Communication Protocols

Two part-time developers cannot afford ambiguous communication. The protocols are explicit:

  • Schema change protocol — how to safely modify shared-types
  • Endpoint handoff protocol — when an endpoint is officially "ready for FE"
  • Breaking change protocol — how to roll out incompatible changes without downtime
  • Conflict resolution protocol — what to do when developers disagree
  • Definition of Done — when a feature is genuinely complete on each side

Each protocol is a short, repeatable script. Not a meeting. Not a debate. A defined sequence of steps.

Without this pillar: every integration moment becomes a discussion. Discussions take time. Time is scarce.

03 · Working in Parallel

The Operating Model

How the day-to-day works. The default mode is async, autonomous, and unblocked.

3.1 The Daily Reality

You and your partner are part-time developers. You have day jobs. Your schedules don't align. Some days one of you ships three commits, the other ships none. Some days you both ship. Some days neither does. This is normal.

The operating model accepts this reality and is designed for it:

  • Async by default. No daily standup, no required real-time communication. PRs are the main artifact.
  • Autonomous within scope. Each developer makes decisions in their own territory without asking permission.
  • Unblocked by design. If FE needs something from BE that doesn't exist yet, FE mocks it and continues.
  • Coordinated at boundaries. Shared territory (shared-types, env config, CLAUDE.md) requires explicit coordination.

3.2 The Ownership Map

3.3 The Three Modes of Work

At any given moment, each developer is in one of three modes:

Mode A: Independent Work

Working entirely within owned territory. No coordination needed. Examples:

  • BE writing a database migration in packages/db/
  • FE building a form in apps/web/
  • Either developer fixing a typo in their own files

Most work is in this mode. The default. Just ship.

Mode B: Pre-Integrated Work

Building something that consumes shared types or interacts with the other side. The work is independent but the result will integrate. Examples:

  • FE building a feature against a stub or mock
  • BE shipping an endpoint with mock data
  • Either developer using shared types in their own code

Coordination is implicit (via the contract), not explicit (via meetings).

Mode C: Boundary Work

Modifying shared territory. Requires explicit coordination:

  • Adding or changing a Zod schema in shared-types
  • Modifying root CLAUDE.md conventions
  • Changing CI workflows that affect both apps
  • Adding a dependency to a shared package

Mode C is rare but high-stakes. Follow the protocols.

3.4 The Bandwidth Model

Communication has cost. The model minimizes it:

3.5 The Weekly Pulse

Once a week, a 15-minute sync. Not optional, but disciplined:

Weekly pulse template
## Last week (each)
- What got done (with PR/commit links)
- Tests added
- Blockers hit and how resolved

## This week (each)
- Planned tasks
- Expected sync points (handoffs, schema changes)

## Coordination items
- Anything in shared territory needing alignment
- Open issues blocking either developer
- Decisions needed on architecture

## Done
End of meeting. Total time: 15 minutes max.

If the pulse runs long, that's a signal you need a separate decision meeting. Schedule it. Don't extend the pulse.

3.6 The Anti-Patterns

Things that look like coordination but actually destroy parallel work:

  • Daily standups. 10 minutes/day = 50 min/week. Replace with weekly pulse.
  • "Just run it by me first" culture. Each developer is autonomous in their territory. Ask permission only for boundary work.
  • Real-time chat for non-urgent items. WhatsApp pings interrupt deep work. Use issues.
  • Pair programming on routine work. Two part-time developers can't afford pair programming on most tasks. Reserve it for genuinely complex problems.
  • Long PR reviews. Review within 48 hours. If a PR sits longer, it blocks integration.
  • Verbal agreements. If it's important, write it down in an issue or PR.
💡 The autonomy principle
Within their own territory, each developer makes decisions without asking permission. The other developer can comment in PR review. They cannot block routine work. Only boundary work (shared types, infrastructure) requires explicit alignment.
04 · shared-types

The Single Source of Truth

The most important file structure in the entire project. If you read only one section of this document, read this one.

Every entity has a Zod schema in packages/shared-types/. The schema defines shape, validation rules, and TypeScript types. Both backend and frontend import from this package. When the schema changes, both sides see the change.

4.1 Why Zod Schemas (not TypeScript interfaces)

TypeScript interfaces vanish at runtime. They cannot validate. They cannot tell you the shape of incoming JSON. They are documentation, not enforcement.

Zod schemas exist at runtime. They validate. They parse JSON into typed objects. They generate TypeScript types automatically. They are documentation and enforcement.

One source, two outputs:

  • Compile time: TypeScript types inferred from the schema
  • Runtime: Validation that catches API drift, malformed input, unexpected nulls

4.2 The File Structure

Each entity has one file. Files are flat (no subdirectories per domain).

4.3 The Anatomy of a Schema File

Every schema file follows the same structure. This consistency is intentional — Claude Code can generate new schemas reliably with /new-entity.

packages/shared-types/src/project.ts (template)
import { z } from 'zod';

// 1. Enums (if any)
export const ProjectTypeEnum = z.enum(['tama38_1', 'tama38_2', 'pinui_binui']);
export type ProjectType = z.infer<typeof ProjectTypeEnum>;

export const ProjectStatusEnum = z.enum([
  'planning', 'gathering_signatures', 'approved', 'in_construction', 'completed', 'cancelled',
]);
export type ProjectStatus = z.infer<typeof ProjectStatusEnum>;

// 2. Full schema (what the API returns on read)
export const ProjectSchema = z.object({
  id: z.string().uuid(),
  organizationId: z.string().uuid(),
  name: z.string().min(1).max(200),
  description: z.string().max(2000).nullable(),
  type: ProjectTypeEnum,
  status: ProjectStatusEnum,
  address: z.string().min(1).max(500),
  city: z.string().min(1).max(100),
  targetSignaturePct: z.number().min(0).max(100),
  metadata: z.record(z.unknown()).default({}),
  createdAt: z.coerce.date(),
  updatedAt: z.coerce.date(),
  archivedAt: z.coerce.date().nullable(),  // soft delete pattern in v2
});

// 3. Input schemas (what the API accepts on write)
export const CreateProjectInput = ProjectSchema.omit({
  id: true,
  organizationId: true,  // injected by guard, not user input
  createdAt: true,
  updatedAt: true,
  archivedAt: true,
});

export const UpdateProjectInput = CreateProjectInput.partial();

// 4. Type exports (for consumers)
export type Project = z.infer<typeof ProjectSchema>;
export type CreateProject = z.infer<typeof CreateProjectInput>;
export type UpdateProject = z.infer<typeof UpdateProjectInput>;

4.4 How Backend Uses It

The backend imports schemas to validate incoming requests:

apps/api/src/modules/projects/projects.controller.ts
import { Controller, Post, Body } from '@nestjs/common';
import { CreateProjectInput, type CreateProject } from '@app/shared-types';
import { ZodValidationPipe } from '../common/zod-validation.pipe';

@Controller('projects')
export class ProjectsController {
  @Post()
  async create(
    @Body(new ZodValidationPipe(CreateProjectInput)) data: CreateProject,
  ) {
    // `data` is now validated and typed
    return await this.service.create(data);
  }
}

If the request body doesn't match the schema, the pipe rejects with 400 Bad Request. Validation errors include field names and reasons.

4.5 How Frontend Uses It

The frontend imports schemas for forms (validation) and API responses (parsing):

apps/web/src/components/forms/project-form.tsx

apps/web/src/lib/api/projects.ts
import { z } from 'zod';
import { ProjectSchema, type Project } from '@app/shared-types';

export async function listProjects(): Promise<Project[]> {
  const res = await fetch('/api/projects');
  const data = await res.json();
  // Parse the response — throws if shape doesn't match
  return z.array(ProjectSchema).parse(data);
}

4.6 The Common Patterns

Pattern: Read schema vs Input schema

Read schemas (ProjectSchema) include all fields the API returns: id, timestamps, organizationId. Input schemas (CreateProjectInput) omit those — id is generated by DB, organizationId is injected by guard from the auth token, timestamps are server-set.

Pattern: Discriminated unions for polymorphic types

Owners are individuals, companies, or inheritances. Each has different fields. Use z.discriminatedUnion('type', [...]) for type-safe handling. TypeScript narrows correctly based on the type field.

Discriminated union example
export const CreateOwnerInput = z.discriminatedUnion('type', [
  z.object({
    type: z.literal('individual'),
    firstName: z.string().min(1),
    lastName: z.string().min(1),
    nationalId: z.string().refine(isValidIsraeliId),
  }),
  z.object({
    type: z.literal('company'),
    companyName: z.string().min(1),
    companyId: z.string().min(1),
  }),
  z.object({
    type: z.literal('inheritance'),
    deceasedName: z.string().min(1),
    heirsCount: z.number().int().positive(),
  }),
]);

Pattern: z.coerce.date() for timestamps

JSON sends dates as strings. Use z.coerce.date() on read schemas to auto-convert. Without coerce, you get a string where TypeScript thinks it's a Date.

Pattern: nullable vs optional

z.string().nullable() means the field exists but value can be null. z.string().optional() means the field might not be in the object at all. For DB nullable columns, use nullable(). For form fields the user might skip, use optional().

4.7 The Stability Rule

⚠️ Stability rule for shared-types
Once a schema is in main and used by both sides, breaking changes need explicit coordination via the protocol in section 9. Don't rename fields casually. Don't tighten validation without checking impact. Adding new optional fields is always safe. Reshape carefully.

05 · API Spec

How Endpoints Are Specified

The API specification is the agreement on what endpoints exist, what they accept, and what they return.

5.1 API Versioning — /api/v1/ prefix from day 1

Decision: Every endpoint is prefixed with /api/v1/. From the very first endpoint, never an unversioned /api/ path.

Why bake this in now:

  • Adding versioning later is breaking. Migrating all clients from /api/projects to /api/v1/projects requires coordinated FE/BE/contractor/CI/Postman/everything updates. With one developer doing this part-time, it's painful enough to never get done. Better to pay the 0-minute cost now.
  • v2 is for breaking changes, not bug fixes. Most API evolution happens additively (new optional fields, new endpoints) — no version bump needed. v2 appears only when we genuinely break a contract that mobile clients (Phase 2 of product) or contractor integrations can't follow.
  • NestJS supports this trivially. app.setGlobalPrefix('api/v1') in main.ts. Zero per-controller cost.
  • Generated OpenAPI reflects it automatically. The /api/v1/docs route serves the spec.
apps/api/src/main.ts
const app = await NestFactory.create<NestFastifyApplication>(
  AppModule,
  new FastifyAdapter(),
);

app.setGlobalPrefix('api/v1');  // every route gets /api/v1/ prefix

await app.listen(env.PORT_API);

When does v2 happen?

Only for genuinely breaking changes that can't be expressed within v1 (e.g., reshaping a core response in ways adapters can't bridge). v2 = a new prefix (/api/v2/), runs in parallel with v1 for a deprecation window. The expand-then-contract rule (Section 8) applies: add v2 endpoints first, migrate clients, then sunset v1.

💡 Internal Provider routes are versioned the same way
Provider Admin endpoints (Section 10 in Doc 02) use the same prefix: /api/v1/provider/*. They're not on a separate version track. The Provider tier is an authentication boundary, not an API contract boundary.

5.2 The Source of Truth

The API spec lives in two places:

  • Inline specifications in the controller code (NestJS decorators). The code is the truth.
  • Generated OpenAPI spec at /api/v1/docs in dev. Auto-generated from controllers + Zod schemas.

There is no separate spec document that can drift from reality. The OpenAPI is generated from the code, every commit.

The "absent key" rule for Contractor permissions

When a Contractor's share.permissions does not grant a field, that field is entirely absent from the response object — not null, not "". The FE treats "key missing" as "not permitted to see," distinct from "key present but null" (= permitted, no value). This was the partner's design and is adopted as-is.

//                                          ↑ key present, value null

5.7 The Idempotency Rule

For operations that the FE might retry (create, update), the BE should be idempotent or accept an idempotency key:

  • Read operations (GET) are inherently idempotent. Safe to retry.
  • Update operations (PATCH) should be idempotent — applying the same patch twice yields the same state.
  • Create operations (POST) are not idempotent by default. The FE should not retry POSTs blindly. Use TanStack Query's mutation behavior (no auto-retry on POST).
  • Delete operations (DELETE) are idempotent (deleting an already-deleted resource returns 204 or 404 — both acceptable).

5.8 The Discoverability Rule

The OpenAPI documentation is the discoverability mechanism. In dev:

terminal

# Then open: http://localhost:3000/api/docs

Swagger UI shows every endpoint, every schema, every response. FE developer should browse this when starting work on a feature.

💡 The OpenAPI is for humans, the schemas are for code
Don't generate FE types from OpenAPI. Use the Zod schemas directly. OpenAPI is for browsing and learning; the type-safe contract is shared-types. Two different uses, two different mechanisms.
06 · API Stub Protocol

How Backend Unblocks Frontend

An API stub is a real endpoint that returns mock data. It has the right URL, right shape, right schema validation — but the implementation is fake.

The stub protocol is the most important mechanism for parallel work. The BE provides stubs before the real implementation. The FE wires up against stubs immediately. When the real implementation is done, the FE switches to it without code changes.

6.1 What an API Stub Is

An API stub is:

  • A real NestJS controller route
  • With the right path and method
  • With the right Zod validation on input
  • With response data that matches the shared-types schema
  • With realistic-looking mock data (not just empty arrays)
  • Marked clearly as a stub (so it doesn't ship to production)

An API stub is not:

  • A real implementation that calls the database
  • A placeholder that returns 501 Not Implemented
  • Production-ready (it intentionally isn't)

6.2 When Backend Provides a Stub

The protocol:

1
BE
Schema for the entity is in shared-types and merged to main
2
BE
Creates the controller with the right routes and decorators
3
BE
Implements stub responses returning realistic mock data validated by the schema
4
BE
Marks the controller methods with @StubEndpoint() decorator (custom)
5
BE
Opens issue: "STUB-READY: <feature>" with the endpoint paths and example responses
6
FE
Builds against the stub. Reports schema mismatches as comments on the issue.

6.3 The Stub Decorator Pattern

The @StubEndpoint() decorator is custom and serves two purposes: documentation and a CI guard against shipping stubs to production.

apps/api/src/common/stub-endpoint.decorator.ts
import { SetMetadata } from '@nestjs/common';

/**
 * Marks an endpoint as a stub (not real implementation).
 * Throws on startup if NODE_ENV=production and stubs exist.
 */
export const STUB_ENDPOINT_KEY = 'isStubEndpoint';

export const StubEndpoint = (note?: string) => {
  if (serverEnv.NODE_ENV === 'production') {
    throw new Error(`STUB endpoint not allowed in production: ${note ?? ''}`);
  }
  return SetMetadata(STUB_ENDPOINT_KEY, { stub: true, note });
};

6.5 Why Stubs Are Worth the Effort

It's tempting to skip stubs and have the FE use only client-side mocks (MSW). Why bother with stubs?

  • Validation is real. The stub uses the same Zod validation as the real endpoint. The FE catches input errors against real validation logic, not its own mocks.
  • Auth flow is real. The stub goes through AuthGuard and TenantGuard. The FE tests its auth wiring early.
  • HTTP semantics are real. Status codes, error responses, headers — all real.
  • Two-step verification. When the real implementation replaces the stub, only the body changes. The contract was already proven.
  • Backend gets early feedback. If FE finds the stub awkward to use, BE can fix the API design before implementing the real thing.

6.6 The Stub-to-Real Transition

When BE replaces a stub with a real implementation:

1
BE
Implements real database queries, business logic, audit logging
2
BE
Removes @StubEndpoint() decorator
3
BE
Adds integration tests including RLS isolation
4
BE
Comments on the original "STUB-READY" issue: "REAL-READY"
5
FE
Pulls main, tests against real endpoint, reports any behavior differences

The key property: the FE code does not change. Same URL, same shape, same validation. The transition is invisible to the FE consumer.

✓ The stub-first principle
Stub-first development is a learnable habit. The first few stubs feel unnecessary. After two phases, you'll wonder how you ever worked without them. The compounding effect of unblocked parallel work is enormous.

7.8 The Mock Drift Risk

⚠️ Mocks must match the schema
When a Zod schema changes, the mocks must update. Otherwise tests pass against fake data but fail against real backend. The mitigation: parse mock data with the schema (ProjectSchema.parse(mockData)). If the mock doesn't match, tests fail at setup time.

7.9 Removing Mocks

As real endpoints come online, remove the corresponding handlers. The mock layer should shrink over time. By production:

  • All real endpoints exist
  • Mocks remain only for: test-only scenarios, error simulation, offline dev
  • The CI build fails if NEXT_PUBLIC_USE_MOCKS=true in a production env

08 · Schema Changes

Modifying shared-types Safely

Most schema changes are additive and harmless. Some are subtly dangerous. This protocol distinguishes the two and handles each correctly.

8.1 The Three Categories of Change

Every change to a shared-types schema falls into one of three categories. The protocol differs for each.

CategoryExamplesRiskProtocol
Additive (safe)New optional field, new enum value, new schema entirelyLowJust merge. Notify in PR description.
Tightening (medium)Make optional → required, narrow string length, restrict enumMediumCoordinate timing. Roll out BE first, then FE.
Reshaping (high)Rename field, split entity, change type, remove fieldHighUse the breaking change protocol (section 9).

8.2 Additive Changes — The Default Path

~80% of schema changes are additive. The protocol is short:

1
EITHER
Open a PR titled feat(shared-types): add <field/schema>
2
EITHER
PR description explains: what's added, why now, who's the immediate consumer
3
OTHER
Reviews within 48 hours. Approves if shape makes sense.
4
EITHER
Merges. Both sides can now use the new field/schema.

No coordination call needed. No timing concerns. Additive changes can't break anyone.

8.3 Tightening Changes — Coordinate Timing

Tightening means making the schema more restrictive. Existing data and code might violate the new rules.

Examples:

  • Field was nullable, now required
  • String had no max length, now max(200)
  • Enum had 5 values, now restricted to 3
  • Number was any integer, now min(1).max(100)

The protocol:

1
BE
Audits existing data: any rows that violate the new constraint?
2
BE
If yes: writes data migration to fix offending rows BEFORE tightening
3
FE
Audits client code: any forms or inputs that allow the now-forbidden values?
4
FE
Updates client validation to match new constraint
5
BOTH
Coordinate the schema PR — merge after data migration and FE updates are in main

The order matters: tighten last. Otherwise existing data fails validation and the app breaks.

8.4 Reshaping Changes — See Section 9

Renames, splits, removals, type changes — these are breaking changes. They require the formal breaking change protocol in section 9.

8.5 The Schema Change Checklist

Before merging any shared-types PR, the author verifies:

  • The change category is identified (additive / tightening / reshaping)
  • If tightening: data audit done, migration written if needed
  • If reshaping: breaking change protocol started (don't merge to main yet)
  • The index.ts re-exports are updated for new schemas
  • Both BE and FE typecheck pass
  • The PR description names the immediate consumer
  • Reviewer (the other developer) is requested

8.6 Common Pitfalls

Pitfall: "I'll make it required, it'll only affect new data"

Wrong. Existing reads also validate through the schema. If existing data has null where you now require a value, every read fails. The fix: data migration first, then schema tightening.

Pitfall: Renaming a field as "additive"

Renaming is not additive. name → displayName means the old field is gone. Existing code referring to name breaks. Use the breaking change protocol.

Pitfall: Adding a required field

Adding a required field looks additive but isn't — every existing payload that doesn't include the new field fails validation. Either:

  • Add it as optional (additive — safe)
  • Add it as required + provide a default (additive — safe)
  • Add as required without default + migrate existing data (tightening — see protocol)

Pitfall: Changing an enum value

Renaming 'tama38_1' to 'tama_38_strengthen' breaks every existing record. Use the breaking change protocol — possibly add the new value, migrate data, remove the old value across multiple deploys.

💡 The "expand then contract" rule
For risky changes, expand first (add the new shape alongside the old), migrate data, then contract (remove the old shape). Two deploys, zero downtime, zero broken consumers. This is the foundation of the breaking change protocol.
09 · Breaking Changes

Rolling Out Incompatible Changes

Sometimes you have to break the contract. The protocol minimizes the damage and keeps both sides working through the transition.

9.1 What Counts as Breaking

A change is breaking if existing code on either side will fail after the change:

  • Renaming a field (consumers reference the old name)
  • Removing a field (consumers might depend on it)
  • Changing a field's type (string → number, etc.)
  • Splitting one entity into two (consumers fetched the merged shape)
  • Merging two entities into one (consumers fetched separate shapes)
  • Changing endpoint paths or methods
  • Removing endpoints

9.2 The "Expand, Migrate, Contract" Pattern

Every breaking change uses the same three-phase pattern:

01
Expand: Add the new shape alongside the old

Both old and new exist. No consumer breaks because old still works. New consumers can adopt the new shape.

02
Migrate: Move all consumers to the new shape

FE updates to use the new field/endpoint. BE serves both old and new. Time passes (days or weeks).

03
Contract: Remove the old shape

Once no consumer uses the old shape, remove it. The migration is complete.

9.3 Example: Renaming a Field

Suppose Project.name should be renamed to Project.displayName. Walk through the protocol:

Phase 1: Expand

PR 1: Add displayName alongside name
export const ProjectSchema = z.object({
  id: z.string().uuid(),
  name: z.string().min(1).max(200),         // Keep for now
  displayName: z.string().min(1).max(200),  // New, mirrors name
  // ...
});

// Backend: when creating/updating, populate both fields with same value
// On read: return both fields (mirrored)
// On write: accept either field, write to both

Both sides now have access to displayName without losing access to name.

Phase 2: Migrate

Over days/weeks:

  • FE replaces every reference to project.name with project.displayName
  • FE forms send displayName instead of name
  • BE accepts both but logs warnings when name is used (helps find stragglers)

Phase 3: Contract

PR 3: Remove name field
export const ProjectSchema = z.object({
  id: z.string().uuid(),
  displayName: z.string().min(1).max(200),  // Single source of truth now
  // name field removed
});

Migration complete. The codebase is clean.

9.4 The Breaking Change Protocol

1
EITHER
Opens an RFC issue: "BREAKING: <change>". Describes current state, desired state, why.
2
BOTH
Discuss in issue. Agree on the migration plan and timeline (typically 2-4 weeks).
3
BE
Phase 1 PR: expand. Both old and new shapes exist.
4
FE
Audit work: list every place the old shape is used. Plan migration.
5
FE
Phase 2: migrate consumer-by-consumer over multiple PRs. Tag with the RFC issue.
6
BE
Monitor logs/audit: any consumer still using old shape? If yes, contact FE.
7
BE
Phase 3 PR: contract. Removes old shape. Closes the RFC issue.

9.5 The "Just Do It" Exception

For very early-stage code (Phase 0-1, no real users yet), the expand-migrate-contract overhead may not be worth it. The shortcut:

  • Both developers are aware
  • The change happens in a single PR
  • Both sides update simultaneously
  • No deploy in between

This works when there's no production data and no real users. Not a long-term pattern. Switch to expand-migrate-contract once Phase 9 (production) is approached.

9.6 Common Pitfalls

Pitfall: Skipping Phase 2

Going straight from expand to contract without verifying all consumers migrated. The FE silently breaks because some references to the old shape were missed. Mitigation: BE logs every use of deprecated fields; review logs before contracting.

Pitfall: No timeline

Expand happens. Then no migration. Then a year later, the codebase has both old and new shapes everywhere. Mitigation: every breaking change RFC has a timeline. If the timeline slips, escalate in weekly pulse.

Pitfall: Treating database changes the same way

This protocol is for shared-types and API. Database changes have a similar but distinct protocol (see Doc 04c on migrations). Don't confuse them.

⚠️ Breaking changes are expensive
Even with this protocol, breaking changes cost time and attention. Avoid them when possible. Most apparent "breaks" can be reframed as additive: instead of renaming name to displayName, just add displayName if it's truly different. Live with the legacy name unless there's a strong reason to change it.
10 · Endpoint Handoff

When an Endpoint Is "Ready for FE"

Ambiguity around "is it done?" is the biggest source of integration friction. The handoff protocol eliminates it.

10.1 The Handoff Definition

An endpoint is ready for FE when ALL of these are true:

  • The endpoint exists in code (controller + service + tests)
  • The Zod schemas it uses are merged in shared-types
  • It's deployed to the dev environment (FE can call it from localhost)
  • Auth and tenant guards are wired (or explicitly noted as not applicable)
  • It returns the documented shape, validated by the read schema
  • It rejects invalid input with the documented error format
  • Either: real implementation passes integration tests, OR it's a stub clearly marked

If any item fails, the endpoint is not ready. Don't claim it is.

10.2 The Handoff Issue Template

BE creates an issue when an endpoint is ready. The template:

10.3 The FE Acknowledgment

FE responds to the handoff issue within 48 hours with one of:

  • "Picked up" — FE is now wiring against the endpoint
  • "Queued, will start <date>" — FE saw it but is on something else
  • "Schema mismatch" — comments specifically what doesn't match expectation
  • "Behavior question" — asks for clarification on a specific scenario

10.4 The Verification Checklist

When FE picks up a handoff, they verify the endpoint actually works as advertised:

  • Call the endpoint from curl or Postman with a valid request — gets expected response
  • Call with invalid input — gets 400 with proper error format
  • Call without auth — gets 401
  • Call with another tenant's ID — gets 404 (RLS isolation)
  • Response shape parses cleanly with the Zod schema
  • Performance is reasonable (under 500ms for simple operations on Free tier)

If anything fails, FE comments on the issue with the specific failure. BE fixes. Repeat until verification passes.

10.5 The Handoff Closing

The issue is closed when:

  • FE confirms the endpoint works as expected
  • FE has merged code that wires up against the endpoint
  • FE has switched off any client mocks for that endpoint

The closer is whoever does the last action — usually FE on merging the wiring PR.

10.6 The Stub-to-Real Re-Handoff

When BE replaces a stub with the real implementation, a new handoff issue is opened:

Title format
FE-Ready: <feature> (real implementation)

FE re-verifies. Often the real implementation has different performance characteristics, or surfaces issues the stub didn't (e.g., the stub returned 5 items, the real DB has 10,000 — pagination becomes critical).

10.7 The Anti-Handoff

Things that look like handoff but aren't:

  • "It's working on my machine" — works locally for BE, but not deployed to dev
  • "The schema's almost right" — almost is not ready. Finish first.
  • "The auth might not be wired yet" — uncertain auth = not ready
  • "You can probably mock it" — that's not a handoff, that's a punt

If any of these phrases appear, the handoff is premature. BE should keep working until ALL handoff criteria are met.

10.8 The Bulk Handoff

For features with many related endpoints (e.g., projects CRUD), one handoff issue can cover all 5 endpoints. The table format in the template handles this naturally.

For features with multiple unrelated endpoints, separate issues are clearer. Rule of thumb: if it's all one feature, one issue.

✓ The handoff discipline pays off
The first few handoffs feel slow. After 3-4 features, the rhythm clicks. FE knows exactly when to pick up. BE knows exactly when to call something done. The ambiguity that kills small teams is gone.
11 · Conflict Resolution

When Developers Disagree

Disagreements are normal. Stuck disagreements are deadly. The protocol gets you unstuck quickly.

11.1 The Three Categories of Disagreement

TypeExampleProtocol
Owned territory"I think the API endpoint should return X"The owner decides. Other developer can comment but not block.
Shared territory"This shared-type field should be named X"Discussion → decision → document trade-off.
Strategic"We should use a different framework"RFC issue → discussion → joint decision.

11.2 Owned Territory: The Owner Decides

If FE wants the API to return data in a specific shape, FE can request it. But BE owns the API and decides how to deliver. Constraints:

  • The owner must serve the consumer's needs (not "I won't do it because I don't feel like it")
  • The owner can choose the implementation approach
  • The consumer can flag if the chosen approach genuinely doesn't work
  • The owner has 24 hours to respond — silence is not OK

11.3 Shared Territory: The Decision Protocol

For shared-types, env config, root CLAUDE.md — the decision needs alignment. The protocol:

1
EITHER
Open a PR or issue with the proposal. State the trade-off clearly: "I want X because Y, the alternative is Z which has problem W."
2
OTHER
Responds within 48 hours: agree, suggest alternative, or ask for clarification
3
BOTH
If still disagreeing after one round of discussion, schedule a 30-minute call
4
BOTH
After the call, the proposer makes the final call AND documents the decision (trade-offs, rationale) in the PR or an ADR

11.4 The 30-Minute Rule

⚠️ Don't get stuck
If a discussion has gone 30 minutes without reaching a conclusion, stop. Pick the simpler option. Document the trade-off. Move on. You can revisit in 2 weeks if the chosen approach doesn't work in practice. Stuck conversations destroy small teams.

11.5 The "Disagree and Commit" Pattern

Sometimes you'll disagree with a decision your partner makes. The healthy response:

  • State your disagreement clearly, once. With reasoning.
  • If your partner still wants to proceed, support it.
  • Don't sabotage the decision afterward. No passive-aggressive PRs that work around it.
  • If it turns out wrong, that's data — bring it up calmly when revisiting.

"I disagree but I'll support your decision" is a complete sentence. Use it.

11.6 Strategic Disagreements: RFC Process

For decisions affecting the whole project (framework choices, major refactors, architecture changes):

.github/ISSUE_TEMPLATE/rfc.md
---
name: RFC
about: Propose a significant change to the project
title: 'RFC: <change>'
labels: ['rfc']
---

## Summary
One sentence describing the change.

## Motivation
Why is this needed? What problem does it solve?

## Proposed change
Detailed description of what would change.

## Alternatives considered
What other approaches did you think about?

## Trade-offs

## Migration plan
How do we get from current state to proposed state?

## Timeline
How long would this take?

RFC sits open for at least 1 week. Both developers comment. If aligned, proceed. If not aligned after a week, postpone — likely not urgent enough to force.

11.7 When to Escalate to a Third Party

Two-developer projects sometimes hit fundamental disagreements that aren't resolving. When to seek outside input:

  • You've discussed for 2+ weeks without convergence
  • The disagreement is blocking other work
  • The decision is large and reversal would be expensive
  • You're personally getting frustrated (signal of strain)

Options for outside input:

  • Ask a senior developer you both respect — quick chat, fresh perspective
  • Time-box an experiment — try one approach for a week, evaluate
  • Ask AI — Claude can help frame the trade-offs without bias toward either of you
  • Take a break — sometimes 48 hours of distance changes the picture

11.8 The Goodwill Bank

You and your partner are working long-term. Every interaction either deposits or withdraws goodwill:

  • Deposits: reviewing PRs promptly, acknowledging good work, supporting decisions you disagreed with, doing your share of unglamorous tasks
  • Withdrawals: ignoring messages for days, blocking PRs over taste, second-guessing past decisions, taking credit for joint work

When goodwill is high, conflicts resolve quickly. When goodwill is low, every conversation is harder. Pay attention to the bank balance.

💡 The shared goal
You both want to ship a good product. Disagreements are means to that end, not battles to win. When stuck, ask: "What's best for the product, regardless of who suggested it?" Most disagreements look small from that angle.

✓ Browser DoD

13.11 The "Real Test" — Try It Yourself

Beyond all checkboxes, the final test: use the feature yourself, like a real user. If it feels awkward, frustrating, or unclear — it's not done. Polish it.

Specific scenarios to walk through:

  • The empty state — first-time user, no data yet. Does the page tell them what to do?
  • The error path — backend returns 500. Can the user recover or are they stuck?
  • The slow network — Chrome DevTools throttle to slow 3G. Does the loading state appear quickly enough? Does the user know something's happening?
  • The mobile owner — for owner-facing flows, simulate the actual user: clicking an email link on a 5-year-old phone with weak signal. Does it work?

13.12 The Frontend DoD Bottom Line

💡 The two-pass approach
First pass: build it, get it functional, ship to staging. Second pass: walk through every state with fresh eyes, find the rough edges, polish them. The first pass takes 80% of the time. The second takes 20% but contributes 50% of the perceived quality.
14 · Common Scenarios

Day-to-Day Situations and How to Handle Them

Concrete situations both developers will face. The recommended response is in the protocol — not a debate.

When you hit one of these scenarios, follow the playbook. Don't reinvent. The patterns below are what works in practice for two-developer SaaS teams.

🚀
Scenario 1: FE needs an endpoint that doesn't exist yet
FE is starting a new feature. The endpoint they need has no stub, no implementation, nothing.
FE Action
  1. Open issue: "BE-Request: <feature>". Describe the data shape needed and one suggested API path.
  2. Create a client-side mock in apps/web/src/mocks/handlers/ that matches the schema you wish existed.
  3. Build the FE feature against the mock.
  4. When BE delivers a stub or real endpoint, switch off the mock and verify.
BE Action
  1. Within 48 hours: respond to the issue. Either accept the proposed shape, or counter-propose.
  2. When able: ship a stub first (matches schema, returns mock data). Open FE-Ready issue.
  3. When able: ship real implementation. Open another FE-Ready issue.
Outcome
FE was never blocked. BE got clear requirements. Integration was incremental.
🔧
Scenario 2: Schema needs a new field
FE needs to display "last login" on the user profile. Current schema doesn't have it.
FE Action
  1. Open PR: feat(shared-types): add lastLoginAt to User schema.
  2. Mark as nullable since existing users don't have one yet.
  3. Request review from BE.
BE Action
  1. Review the PR within 48 hours.
  2. If makes sense: approve. Then in a follow-up, add the column to DB schema and start populating it.
  3. If not aligned: comment with concerns, propose alternative.
Outcome
Schema change is additive (nullable). No coordination dance needed. Both sides update independently.
⚠️
Scenario 3: BE finds the schema is wrong after building real endpoint
BE was about to ship the real implementation of a stubbed endpoint. Found that address should really be split into street, city, zip for Israeli addresses.
BE Action
  1. Don't change the schema unilaterally. Don't ship the real implementation with a different shape than the stub.
  2. Open RFC issue: "BREAKING: split address into street/city/zip".
  3. Explain motivation, propose migration, ask FE to discuss.
Joint Action
  1. Discuss in the issue. If aligned, follow expand-migrate-contract from section 9.
  2. BE expands schema to include both address (deprecated) and street/city/zip (new).
  3. FE migrates forms to use new fields over the next few PRs.
  4. BE contracts: removes deprecated address.
Outcome
Schema evolved cleanly without breaking FE. BE caught the design flaw early thanks to having to write a stub before the real thing.
🔍
Scenario 4: FE finds the API behaves differently than expected
FE wired up against the real endpoint. The schema says status: 'gathering_signatures' but BE returns status: 'GATHERING_SIGNATURES' (different casing).
FE Action
  1. Don't add a workaround in FE code. The schema is the truth.
  2. Comment on the FE-Ready issue with specifics: "Endpoint returns ACTIVE but schema says active. Test reproduces: [paste curl command]".
  3. Wait for BE fix. Continue with mocks if blocked.
BE Action
  1. Reproduce the issue.
  2. Decide: was the schema right, or was the implementation right?
  3. If schema right: fix the implementation to match.
  4. If implementation right: open shared-types PR to update schema, follow change protocol.
Outcome
The contract is upheld. No workarounds in FE that mask BE bugs.
🔁
Scenario 5: Both developers want to modify shared-types simultaneously
FE wants to add a nickname field to Owner. BE wants to add a preferredLanguage field. They open PRs at the same time.
First-Mover Action
Whoever opens PR first: review the other's PR within 48 hours. Approve if no conflict.
Second-Mover Action
After your partner's PR merges, rebase your branch on main. Resolve any conflicts. Push and merge.
Outcome
Two non-conflicting additions both land. Each is additive, neither requires coordination beyond review.
⏰
Scenario 6: BE PR sits in review for too long
BE opened a PR. 4 days have passed. FE hasn't reviewed.
BE Action
  1. Send a polite ping in WhatsApp: "Hey, PR #X is up. Could you review when you have time?"
  2. If the change is clearly self-contained (e.g. a refactor that doesn't affect FE), self-merge after another 24 hours with a note: "Self-merging — change is internal to api/. Happy to revert if you have concerns post-hoc."
FE Action
Acknowledge the ping. Provide a realistic timeline ("I'll get to it tomorrow morning"). Stick to it.
Outcome
No PR rots. Communication is direct without being pushy.
🤝
Scenario 7: Disagreement on API design
FE wants GET /api/projects?include=buildings,owners. BE prefers separate endpoints /api/projects/:id/buildings and /api/projects/:id/owners.
Discussion
  • FE argues: fewer requests, simpler client code, atomic page load
  • BE argues: caching is harder, response size grows unpredictably, separate endpoints are RESTful
Resolution Protocol
  1. BE owns the API. BE makes the call.
  2. BE says "let's go with separate endpoints, but if FE finds it actually slow in practice, we'll add the include parameter".
  3. FE accepts. Documents the discussion in PR/issue.
  4. If 2 weeks later FE has data showing real performance issues: revisit.
Outcome
Decision made in 30 minutes. Trade-off documented. Path to revisit if needed.
🐛
Scenario 8: Production bug, no clear owner
A user reports: "I can't see my project after creating it." Bug crosses both BE and FE.
First Responder
Whichever developer sees the report first opens an issue with: reproduction steps, what user expected, what happened, browser/device.
Triage
  1. Check Sentry on both apps. Look for related errors at the user's session time.
  2. Check API logs for the user's organization.
  3. One of two emerges:
    • Backend issue (e.g., RLS policy bug, cache stale) → BE owns
    • Frontend issue (e.g., cache invalidation, render bug) → FE owns
Outcome
Owner fixes within 24 hours (urgent). Other developer is informed. Lesson captured if it relates to the contract.
🎨
Scenario 9: FE switches design tools mid-project
FE was using Figma + manual coding. Decides to try Claude Design for the next feature.
FE Action
  1. Doesn't need to ask permission. Tool choice is FE's call.
  2. Builds the feature with the new tool.
  3. Result must still pass DoD: shared-types used, RTL works, accessibility good, tests written.
BE Action
Doesn't change anything. The contract is identical. BE's stubs and endpoints work the same.
Outcome
Tool change is invisible to BE. The contract proved its value: FE could swap implementation approaches without coordination.

16.1 Apartment vs Unit — the One That Causes Real Bugs

The most-confused pair in this project. Both refer to the same thing but mean it differently:
