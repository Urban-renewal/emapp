חלק 1 — היסודות

1.1 Base & גרסה

Production:  https://api.emapp.io/api/v1
Staging:     https://api-staging.emapp.io/api/v1

קידומת /api/v1/ חובה (D.10). שינוי גרסה = /api/v2/ חדש; v1 ממשיך לחיות.

1.2 מבנה תשובה — 3 צורות, אין רביעית

ישות בודדת:

{ "data": { "id": "...", "...": "..." } }

רשימה:

{ "data": [ {...}, {...} ],
  "page": { "limit": 25, "cursor": "eyJ...", "has_more": true } }

שגיאה:

{ "error": { "code": "machine_code",
             "message": "הודעה בעברית למשתמש",
             "details": { "fields": [ { "path": ["email"], "code": "taken" } ] } } }

code — מחרוזת קבועה (ה-FE מתנהג לפיה). message — עברית מוכנה להצגה. details — אופציונלי, מובנה (אף פעם לא טקסט חופשי).

1.3 טיפוסי בסיס (חלים על כל שדה)

טיפוס פורמט דוגמה ולידציה
uuid UUID v4 "a3f...9c" z.string().uuid()
timestamp ISO 8601 UTC "2026-04-24T14:32:00Z" תמיד UTC, תמיד Z
date ISO date "2026-04-24" ללא שעה
national_id string ממוסך "•••••••82" מלא רק ב-endpoint חשיפה. ולידציה ביצירה: 9 ספרות + Luhn ישראלי
phone E.164 "+972541234567" +972 + 9 ספרות
email RFC 5322 "a@b.co.il" z.string().email(), lowercase

nullable T \| null null null מפורש, אף פעם חסר

חלק 2 — קטלוג השגיאות (החור שהיה חסר)

כל error.code, מה גרם, ומה ה-FE מציג. ה-FE עושה switch(error.code) — אף פעם לא מנתח message.

2.1 שגיאות גלובליות (כל endpoint)

HTTP code סיבה מה ה-FE מציג/עושה
400 validation_failed קלט לא עבר Zod שגיאת שדה מ-details.fields ליד כל שדה
401 unauthorized אין token redirect /login
401 token_expired access פג /auth/refresh → retry שקוף
401 invalid_refresh refresh פג/נגנב clear state, /login + "התחבר מחדש"
403 forbidden אין הרשאה toast "אין לך הרשאה לפעולה זו"
404 not_found לא קיים/לא בארגון empty / מסך 404
409 conflict התנגשות מצב message ספציפי
422 business_rule חוקיות עסקית message (עברית מוכנה)
429 rate_limited יותר מדי בקשות "יותר מדי ניסיונות, נסה בעוד דקה" + disable זמני
500 internal_error באג שרת "משהו השתבש, נסה שוב" + Sentry (בלי PII)
503 service_unavailable תחזוקה "המערכת בתחזוקה"

2.2 שגיאות ספציפיות ל-endpoint

Endpoint code מה ה-FE מציג
signup email_taken ליד אימייל: "האימייל כבר רשום"
signup weak_password ליד סיסמה: details מפרט מה חסר
login invalid_credentials מעל הטופס: "אימייל או סיסמה שגויים" (גנרי)
login account_locked "החשבון ננעל זמנית"
otp/request phone_not_found לא מוצג — השרת מחזיר {sent:true} בכל מקרה. ה-FE תמיד עובר למסך הקוד
otp/verify invalid_code "הקוד שגוי, נסה שוב" + מנקה שדות
otp/verify code_expired "הקוד פג, בקש חדש" + כפתור שליחה
otp/verify too_many_attempts "יותר מדי ניסיונות" + נועל קלט
projects POST limit_reached "הגעת למכסת הפרויקטים בתוכנית"
owners PATCH ownership_sum_invalid "סך הבעלויות בדירה חייב 100%"
shares POST contractor_invalid "כתובת הקבלן לא תקינה"
contractor GET share_revoked "הגישה בוטלה" → redirect החוצה
signatures POST already_signed "כבר נחתם — לא ניתן שוב"
documents upload file_too_large "הקובץ גדול מ-50MB"
documents upload mime_not_allowed "סוג קובץ לא נתמך (PDF/JPG/PNG/DOCX)"
provider/* mfa_required מסך הזנת קוד MFA
provider orgs/:id reason_required "חובה לציין סיבת גישה"

2.3 מבנה details

"details": { "fields": [
  { "path": ["email"], "code": "taken", "message": "כבר רשום" },
  { "path": ["password"], "code": "too_short", "message": "מינ' 12 תווים" }
] }

ה-FE ממפה path → שדה בטופס, מציג message לידו, code ללוגיקה.

חלק 4 — עיבוד JSON בצד לקוח (הרצף המלא)

מה קורה לכל תשובה מה-fetch ועד התצוגה. זה הקוד ב-adapter (api/).

4.1 הרצף — 7 צעדים, לכל קריאה

1. fetch(url, { credentials:'include', headers })
       │
2. בדיקת status:
   ├─ 2xx → צעד 3
   ├─ 401 token_expired → refresh → retry once (Doc 08 §3) → צעד 1
   ├─ 401 אחר → clear state, redirect /login → עצור
   └─ 4xx/5xx → parse error envelope → throw ApiError(code,message,details)
                → ה-UI תופס, מציג לפי קטלוג §2 → עצור
       │
3. const json = await res.json()
   └─ נכשל (לא JSON) → throw ApiError('internal_error') → עצור
       │
4. ולידציית schema:
   const parsed = ResponseEnvelope(EntitySchema).parse(json)
   └─ נכשל (השרת החזיר צורה לא צפויה) →
       ⚠️ באג חוזה. dev: throw בקול. prod: Sentry +
       ApiError('internal_error'). אף פעם לא מציגים JSON גולמי.
       │
5. חילוץ:
   ├─ ישות: data = parsed.data
   └─ רשימה: items=parsed.data ; cursor=parsed.page.cursor ;
              hasMore=parsed.page.has_more
       │
6. adapter → ViewModel (הטרנספורמציה היחידה המותרת):
   - timestamp UTC → Asia/Jerusalem ("לפני 3 ימים")
   - enum → תווית עברית + צבע
   - national_id ממוסך → נשאר ממוסך
   - שדה נעדר (Contractor) → "אין הרשאה", לא קורס
   - null → "—" לתצוגה, לא "null"
       │
7. ה-UI מקבל ViewModel נקי. אף פעם לא JSON גולמי, אף פעם
   לא parsing בעצמו, אף פעם לא fetch ישיר.

4.2 הכללים המוחלטים

  1. כל תשובה עוברת Schema.parse. לא "אני סומך". parse נכשל = באג חוזה, לא להציג למשתמש.
  2. adapter הוא המקום היחיד שממיר. components מקבלים ViewModel. אין JSON.parse/toLocaleDateString ב-component.
  3. תאריך: השרת UTC → ההמרה לישראל רק ב-adapter, פעם אחת.
  4. enum → label במקום אחד (STATUS_LABELS). enum לא מוכר → "לא ידוע" + log, לא קורס.
  5. נעדר ≠ null ≠ "". נעדר=אין הרשאה. null=אין ערך→"—". ""=ריק אמיתי. שלושתם שונים.
  6. שגיאה לפי code (§2), אף פעם לפי message.

4.3 ApiError — מה כל שגיאה הופכת אליו

class ApiError {
  code: string       // §2 — ה-FE עושה switch על זה
  message: string    // עברית מוכנה — הצגה ישירה
  details?: object
  httpStatus: number
}

ה-adapter תמיד זורק ApiError. ה-UI תמיד תופס ומחליט לפי .code (toast / שדה / redirect / מסך).

חלק 5 — מה כל צד עושה עם המסמך

ה-FE dev: ה-adapter מממש בדיוק §4.1. כל endpoint מ-§3 → פונקציה ב-adapter (fetch→parse→ViewModel). שגיאות לפי §2. אף component לא נוגע ב-fetch/JSON.

השותף (Claude Design): מעצב מסך לכל מצב מ-§2 — לא "error" גנרי. מסך ל-validation_failed, forbidden, not_found, rate_limited, internal_error. הקטלוג §2 נכנס לפרומפט (ראה PARTNER_SCREEN_PROMPTS המעודכן).

Claude Code: מממש endpoints בדיוק לפי §3 + קודי §2. בונה gen-api-docs (§1.4) ב-Phase 2.
