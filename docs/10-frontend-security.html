מדריך אבטחת Frontend

מה צד הלקוח חייב לעשות נכון
EMAPP · Frontend Security

מה זה: האבטחה היא לא רק בצד שרת. ה-FE יכול לחשוף את כל המערכת אם יממש לא נכון. המסמך הזה = ה-checklist המחייב של מה ה-FE חייב/אסור לעשות.

למי: ה-FE dev, השותף (חלק מזה משפיע על העיצוב), Claude Code (כשבונה את ה-FE ב-Phase 8).

העיקרון: ה-FE לא "מאבטח" — השרת מאבטח. אבל ה-FE יכול לדלוף או להחליש אבטחה אם לא נזהר. זה מה שמונעים כאן.

1. ניהול Tokens — הכלל החשוב ביותר

✅ חובה

  • Tokens חיים רק ב-httpOnly cookies שהשרת מציב. ה-FE אף פעם לא נוגע בהם ישירות.
  • כל קריאת API: fetch(url, { credentials: 'include' }) — הדפדפן מצרף את ה-cookie לבד.

❌ אסור (כל אחד מאלה = פרצה)

  • ❌ לשמור token ב-localStorage / sessionStorage — נגיש ל-XSS, כל סקריפט זדוני קורא אותו.
  • ❌ לשמור token ב-state גלובלי / Redux / context — נשאר בזיכרון, דולף ב-error reports.
  • ❌ לשים token ב-URL / query param — נשמר ב-history, ב-logs של שרתים, ב-Referer.
  • ❌ להוסיף Authorization: Bearer ידנית — אם אתה עושה את זה, סימן שהחזקת token איפשהו (טעות).

למה: XSS אחד שמצליח לקרוא localStorage = גניבת חשבון מלאה. cookie עם httpOnly — JavaScript פיזית לא יכול לקרוא אותו, גם אם יש XSS.

2. טיפול ב-401 / רענון (בלי לולאות אינסופיות)

ה-adapter layer (שכבת ה-api/ שכבר בנית) חייב interceptor אחד מרכזי:

on response:
  if status == 401 and code == "token_expired":
     if not already_refreshing:
        already_refreshing = true
        await POST /api/v1/auth/refresh   (credentials:'include')
        if refresh ok:
           already_refreshing = false
           retry the original request ONCE
        else:
           clear app state, redirect /login
     else:
        queue this request until refresh resolves, then retry
  if status == 401 and code == "unauthorized":
     redirect /login   (אין token בכלל)

❌ אסור: retry בלי גבול (לולאה אינסופית אם refresh נכשל), או refresh במקביל מ-5 בקשות (race → ביטול הדדי). חייב single-flight (refresh אחד, השאר מחכים לו).

3. ה-FE לא מקבל החלטות הרשאה — רק מציג

העיקרון

ה-capabilities מ-GET /me נועד להציג/להסתיר UI בלבד. הוא לא אבטחה — השרת אוכף הרשאות בכל בקשה (Doc 08 §2, 3 שכבות).

✅ נכון

if (user.capabilities.includes('projects.create'))
   render <CreateButton/>

זה UX — לא מציגים כפתור שיכשל ב-403.

❌ הטעות המסוכנת

לחשוב ש"הסתרתי את הכפתור = המשתמש לא יכול". משתמש יכול לשלוח את ה-POST ידנית. השרת חייב לדחות אותו ב-403 בכל מקרה. ה-FE מסתיר רק כדי לא לבלבל — לא כדי להגן.

❌ אסור מוחלט

לקבל מ-ה-API נתון רגיש ו"להסתיר אותו ב-CSS/JS". אם השרת שלח national_id מלא וה-FE רק לא מציג אותו — הוא בכל זאת ב-DOM/network tab. נתון רגיש שאסור למשתמש לראות — לא אמור להגיע ל-FE בכלל. (לכן השרת מחזיר ממוסך — Doc 09 §4.)

4. הצגת PII — מה ה-FE עושה עם נתון רגיש

נתון מה השרת שולח מה ה-FE עושה
national_id ממוסך (•••••••82) כברירת מחדל מציג ממוסך. "הצג" = קריאת API נפרדת + מסמן intent (לא נשמר ב-state)
phone / email מלא (אם מורשה) מציג. לא לוגג ל-console/Sentry
חתימה (SVG) רק כשצריך, מ-endpoint ייעודי מציג בקנבס, לא שומר ב-localStorage/cache
שדה לא-מורשה (Contractor) נעדר מהאובייקט לא להניח שהוא קיים. obj.phone → undefined = "אין הרשאה", לא "אין ערך". לא להציג שדה ריק

❌ אסור: לכתוב PII ל-console.log, ל-Sentry breadcrumbs, ל-analytics events, ל-localStorage, או ל-URL.

5. קלט משתמש — ה-FE מנקה לתצוגה, השרת מאמת לאמת

  • ולידציה ב-FE = UX בלבד (משוב מהיר). היא לא אבטחה — השרת מאמת הכל שוב ב-Zod.
  • ❌ אסור: dangerouslySetInnerHTML עם תוכן מהמשתמש/מה-API (XSS). אם חייבים — sanitize (DOMPurify).
  • קלט עברית/דו-כיווני: השתמש ב-<bdi>/unicode-bidi:isolate לשמות, ת"ז, טלפונים — לא רק עיצוב, גם מונע bidi-spoofing.
  • כל ערך מה-API שמוצג כ-HTML → דרך text binding של הפריימוורק (React מנקה אוטומטית), לא string concatenation.

6. בקשות שמשנות מצב (POST/PATCH/DELETE)

  • Idempotency-Key: ב-POST של יצירה — שלח Idempotency-Key: <UUID חדש לכל פעולה>. מונע יצירה כפולה בלחיצה כפולה / retry.
  • כפתור submit: disabled מרגע הלחיצה עד התשובה. מונע double-submit (גם UX וגם אבטחה).
  • פעולות הרסניות (ארכוב): confirm dialog. ה-verb בעברית "ארכוב" לא "מחיקה" (Doc 06 glossary).
  • CSRF: ה-cookies הם SameSite=Lax → הדפדפן לא שולח אותם בבקשות cross-site. ה-FE לא צריך CSRF token ידני, אבל חייב לוודא שכל בקשה משנת-מצב היא POST/PATCH/DELETE (לא GET) — GET לא אמור לשנות כלום.

7. סביבת הרצה (build/deploy)

  • ❌ אסור: סודות ב-FE bundle. אין API keys, אין secrets ב-NEXT_PUBLIC_*. כל מה שב-bundle = ציבורי.
  • CSP: ה-FE מוגש עם Content-Security-Policy הדוק (נקבע ב-Doc 07). לא להוסיף unsafe-inline/unsafe-eval כדי "שיעבוד".
  • תלויות: pnpm audit ב-CI. תלות עם CVE קריטי = build נכשל. לא להתקין חבילה לא מוכרת בשביל רכיב UI.
  • Source maps: לא לפרסם לציבור (חושף לוגיקה). רק ל-Sentry באופן מאובטח.
  • Error reporting: Sentry — אבל scrub PII לפני שליחה (national_id, phone, tokens אף פעם לא ב-error payload).

8. ה-Checklist (Definition of Done לאבטחת FE)

לפני שמסך עולה ל-production:
- [ ] שום token ב-localStorage/state/URL — רק httpOnly cookies
- [ ] כל קריאת API עם credentials:'include'
- [ ] interceptor 401 עם single-flight refresh (אין לולאה, אין race)
- [ ] UI gating מ-capabilities (תצוגה בלבד — לא מסתמכים על זה לאבטחה)
- [ ] שום PII ב-console/Sentry/analytics/localStorage/URL
- [ ] national_id מוצג ממוסך; חשיפה = פעולה מפורשת
- [ ] שדה נעדר (Contractor) מטופל כ-"אין הרשאה", לא קורס
- [ ] אין dangerouslySetInnerHTML עם תוכן לא-מסונן
- [ ] Idempotency-Key ב-POST יצירה; submit disabled עד תשובה
- [ ] אין סודות ב-bundle; CSP הדוק; pnpm audit נקי
- [ ] ערכי דו-כיווניות (<bdi>) על שמות/ת"ז/טלפון

9. החלוקה — מי אחראי על מה

צד שרת (Claude Code) צד לקוח (FE/שותף)
אכיפת הרשאות ✅ הבעלים (3 שכבות) ❌ רק מציג
אימות קלט ✅ Zod (האמת) ⚠️ UX בלבד
הצפנת PII ✅ pgcrypto ❌ לא נוגע
ניהול tokens ✅ מנפיק+מבטל ⚠️ רק שולח cookie
מיסוך PII ✅ מחזיר ממוסך ⚠️ לא חושף מיוזמתו
XSS prevention — ✅ הבעלים (sanitize, CSP)
double-submit ⚠️ Idempotency ✅ disable + key

השורה התחתונה: השרת מניח שה-FE עוין (Doc 07 §0). ה-FE מצדו לא מחליש את ההגנות של השרת ולא דולף את מה שהשרת הגן עליו. שני הצדדים = הגנה שלמה.
