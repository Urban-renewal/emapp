01 · WHY THIS DOCUMENT

The Foundation for Everything Else

This is not a checklist. It is the security architecture itself — explicit, written, and testable.

Most SaaS products bolt security on after launch. They patch holes when found. They run penetration tests once a year. They write incident reports after breaches. We do the opposite: security is the first thing designed and the last thing compromised.

1.1 Who Reads This

Both developers. Every commit. Every PR. Every deployment. This document is the source of truth for security decisions — not the code, not the comments, not the original architecture documents.

When a security question arises:

  1. Check this document first. If the answer is here, follow it.
  2. If not here, propose an addition. Don't make an ad-hoc decision and move on.
  3. Update this document when learning happens. Every breach, every near-miss, every "we should have caught this" becomes a section here.

1.4 The Threat Actors

We design defenses for four threat actor profiles. Each gets attention proportional to likelihood and impact:

  • Curious user (Organization member). An agent who tries to peek at another organization's data because the URL pattern looked guessable. Most common, lowest sophistication. RLS catches them every time.
  • Malicious contractor. An external user with legitimate access to one project trying to access another. Moderate sophistication, real motivation (competitive intelligence). Share permissions enforcement is critical here.
  • Compromised credentials. A legitimate user's password is leaked elsewhere. Attacker has valid login. Defense: rate limiting, MFA on provider tier, audit logs catch anomalies.
  • External attacker. Unauthenticated. Looking for SQL injection, auth bypass, exposed secrets, etc. Defense: input validation (Zod), parameterized queries (Drizzle), no secrets in code, WAF at edge.

    • We do not design for nation-state attackers. That's a different product category and a different budget.

    1.5 The Five Principles Applied to Security

    The five core principles from CORE_PRINCIPLES.md shape every choice below:

    PrincipleApplied as
    SOLIDAuth provider, encryption provider, storage provider — all interface-based. Swap implementations without touching consumers.
    SecurityThis entire document.
    PerformanceSecurity must not exceed budget. RLS adds <1ms. Encryption adds <5ms. Audit log writes are async. Every overhead measured.
    RuntimeEncryption keys held in memory, not re-fetched. Cache auth decisions for the request lifetime.

    ⚠ The First Rule
    When security and any other principle conflict, security wins. A 5ms latency cost to encrypt PII is not negotiable. A more complex code path to enforce RLS is not negotiable. Beauty, simplicity, performance — all yield. This is the only principle without exception.

    What We're Defending Against

    A threat model maps attackers to assets to defenses. This is ours, made explicit.

    In order of sensitivity:

    National IDs (ת"ז)Identity theft fuel, regulated PIICritical — legal liability, customer churn
    Phone numbersTargeted phishing/scamsHigh — direct harm to end users
    Signed contractsLegal documents, business intelHigh — competitive intel + legal complications

    User credentialsAccount takeover potentialMedium — limited blast radius if rotated

    2.2 The Attack Surface

    Every point where untrusted input enters the system:

    1. HTTP API endpoints. Largest surface. Every request body, query param, header, cookie is untrusted until validated.
    2. File uploads. Multipart streams to R2. Filename, content-type, size — all attacker-controlled.
    3. Auth flows. Login, magic link consume, password reset, SMS OTP (future). Email/phone inputs are attacker-controlled.
    4. JSONB share permissions. Manager-set, structurally complex. If parsing trusts shape without validating, attackers can inject keys.
    5. Webhooks (future). Inbound from external services — signature verification mandatory.
    6. WebSocket / SSE connections (Phase 2). Long-lived connections, auth must persist correctly.
    7. Direct DB access. Migration scripts, ad-hoc queries via Drizzle Studio. Smallest surface but highest privilege.

    2.3 Trust Boundaries

    Every boundary is a place where data crosses from less-trusted to more-trusted (or vice versa). At each boundary, something must be validated, transformed, or both:

    // Trust boundaries in EMAPP — outside (untrusted) to inside (trusted) [1] Browser/Client (zero trust) │ ▼ HTTPS, CSP, sanitized output [2] CDN/WAF (Cloudflare) (filters bot traffic, DDoS) │ ▼ Rate limiting, TLS termination [3] API Gateway/Container (Railway) │ ▼ Helmet headers, CORS allowlist [4] Auth Middleware (BetterAuth) │ ▼ JWT verification, session validity [5] Tenant Middleware (withTenant injection) │ ▼ organization_id extracted from JWT [6] Zod Validation (per endpoint) │ ▼ Shape, type, range checks [7] Service Layer (business rules) │ ▼ Permission checks (share, role) [8] Drizzle ORM (parameterized queries) │ ▼ SET LOCAL app.organization_id [9] Postgres + RLS + FORCE (final gate) │ ▼ Row policies + encrypted PII [10] Data at rest (Neon + pgcrypto)

    Each boundary either filters, validates, or enriches the request. A successful attack must defeat every boundary, not just one. This is the heart of defense in depth.

    2.4 The STRIDE Model Applied

    STRIDE is a Microsoft-derived framework that categorizes threats by type. Useful for verifying coverage:

    ThreatExample in our systemPrimary defense
    SpoofingAttacker uses another user's session tokenJWT signature verification, short TTL, refresh rotation
    TamperingModifying request body to escalate permissionZod validation, server-side permission re-check, no trust in client state
    RepudiationUser claims they didn't sign a contractAudit log with IP, UA, timestamp on every signature
    Information DisclosureCross-tenant data leak via APIRLS + FORCE, withTenant wrapper, share permissions enforcement
    Denial of ServiceOTP request flooding, large file uploadsRate limiting per IP+user, file size limits, async processing
    Elevation of PrivilegeAgent gains Manager rightsServer-side role validation per request, no client-side role decisions

    2.5 What We Do Not Defend Against (Explicit)

    Being explicit about gaps prevents pretending we have coverage we don't:

    • Cold cloud provider keys. If Cloudflare R2 is compromised at the provider level, we have no defense. We trust them.
    • Insider threats from EMAPP team. Provider tier users with audit but technical access — by design. Mitigated by audit logging and team integrity, not technical means.
    • Long-running session theft from a compromised device. If an attacker has full access to a logged-in laptop, they have access. MFA limits time window but doesn't eliminate.
    • End user's own device security. Phishing of credentials, malware on their machine — outside our scope.
    • Side-channel attacks. Timing attacks on bcrypt — we use the library defaults; not designed against state-actor sophistication.
    ⚠ Honesty about scope
    A threat model that claims to defend everything is lying. We defend everything reasonable for our scale (MVP → 100 organizations). For enterprise customers (1000+ orgs, government contracts), the model expands — and so does the budget and the team.
    03 · DEFENSE IN DEPTH

    Layered Defense, Not Single Line

    Every protection layer can fail. The next layer is the one that catches it.

    The principle is simple: assume any single defense layer will eventually fail, and design so that failure is contained. If application-level auth is bypassed, RLS catches it. If RLS is bypassed (e.g., bug in withTenant), encrypted PII limits the damage. If encryption keys are leaked, audit logs reveal the breach. Every layer is independent — and every layer is necessary.

    3.1 The Five Layers

    From outermost (filters traffic) to innermost (data at rest):

  • Edge (Cloudflare). Bot filtering, DDoS protection, WAF rules. Most attacks die here without ever reaching our app. Free tier provides basic protection; Pro tier ($20/mo) adds advanced rules for production.
  • Application gateway. Helmet HTTP headers (CSP, HSTS, X-Content-Type-Options, etc.), strict CORS allowlist, rate limiting via Upstash Redis or in-memory. The first line of code-level defense.
  • Authorization & validation. JWT verification, role check, Zod schema validation, share permission enforcement. By the time a request reaches business logic, every input is typed and every actor is known.
  • Database access pattern. withTenant wrapper sets app.organization_id per request. Direct DB access through db is forbidden by lint rule. There is exactly one path to data, and it is auditable.
  • Postgres + RLS + Encryption. The final wall. RLS FORCE on every multi-tenant table. PII columns encrypted with pgcrypto. Even with full DB access (e.g., backup leak), encrypted columns require the key to read.

    • 3.2 Defense Layer Properties

    Each layer is independent — they don't trust each other's checks:

    LayerIndependent ofCatches what others miss
    Edge (Cloudflare)App code, DBVolumetric attacks, malicious IPs, bot scrapers
    App gatewayBusiness logic, DBMissing headers, CORS violations, rate abuse
    Auth/validationDatabase, infrastructureType confusion, schema violations, role escalation
    DB access patternNetwork, infraForgotten tenant context, accidental cross-org queries
    Postgres + RLSApplication code entirelyApp bugs, dev mistakes, raw SQL slips

    3.3 The Critical Insight: Layer Independence

    If layers depend on each other ("RLS works because the app sets app.organization_id correctly"), they're not independent. They're a chain — break one, break the rest.

    True independence means: if the app code is fully compromised and runs arbitrary queries, the database still refuses cross-tenant data. That's what RLS FORCE provides. The app's correctness is not assumed.

    Example: app code attempts cross-tenant query
    // Compromised app runs this with no withTenant wrapper
const allUsers = await db.execute(sql`SELECT * FROM users`);

// Result: empty array, not data leak
// Reason: RLS is enabled + FORCE on users table
//   policy: USING (org_id IN (SELECT org_id FROM memberships WHERE user_id = current_setting('app.user_id')))
// No app.organization_id set + no app.user_id set = policy evaluates to FALSE = no rows visible

    This only works because RLS doesn't trust the application. The application can have any bug; the database stands its ground.

    3.4 What Each Layer Does NOT Defend

    Knowing what a layer doesn't catch tells you which other layer must catch it:

    LayerDoes NOT catchCaught by
    EdgeLogical attacks via valid-looking requestsAuth/validation
    App gatewayAuthorized but malicious user actionsService-level permission checks + RLS
    Auth/validationServer-side logic bugs that bypass checksRLS + audit log
    DB access patternDirect DB tampering (provider tier, admin)Audit log + key separation
    RLSEncrypted data being read with valid keysKey rotation + access control on keys

    Defense in depth has a cost. We track it explicitly so security and performance principles coexist:

    DefenseLatency costMemory costMitigation
    Cloudflare CDN/WAF~5ms (edge)NoneNet positive — caches static assets
    JWT verification<1msNegligibleCached public key

    Defense costs ~5% of our latency budget. Security is paid for; we know what we're paying.

    3.6 The Modular Defense Architecture

    The defense layers are plug-able. Following SOLID and modularity principles:

    • Cloudflare can be replaced with another CDN (Fastly, BunnyCDN) — DNS change, no code change.
    • Helmet can be replaced with another header middleware — same interface.
    • JWT verification logic is in an interface (IAuthVerifier) — can swap to opaque tokens later.
    • Zod is the validation library, but the validation pattern (parse-don't-validate) is the principle.
    • withTenant wrapper is our concept; we own it.
    • Postgres + pgcrypto is our DB choice; if migrated, encryption layer would be reimplemented at application layer with the same interface.

    This means: if any tool fails us, we replace it. No layer is bound to a vendor. The defenses are conceptual; the implementations are interchangeable.

    💡 The 80/20 of defense
    80% of attacks are caught by RLS + input validation. The other 20% are caught by the remaining layers, but those 20% are the ones that would otherwise become news headlines. Each layer's cost is justified by the breach it prevents — and the breach it prevents is usually the catastrophic one.

    04 · PII CLASSIFICATION

    What Counts as PII, and How We Treat It

    Not all personal data is equal. The strategy depends on the field, the sensitivity, and the use pattern.

    Personal Identifiable Information (PII) in this system flows from Israeli tenants whose data sits in our database. The Israeli Privacy Protection Law treats national IDs as the highest-sensitivity category — leakage carries legal liability, reputational damage, and contractual consequences with our customers. Encryption is not a "nice to have." It is the minimum bar.

    4.1 The Four Sensitivity Tiers

    Every field with personal data is classified into one of four tiers:

    TierExamplesStrategyStorage
    CRITICALNational ID (ת"ז), phoneEncrypted at rest + HMAC for lookupBYTEA + TEXT hash
    HIGHSignature blob, document scan pathsEncrypted at rest (no lookup needed)BYTEA
    MEDIUMEmail, name, addressPlaintext (search/display needs)TEXT
    LOWAvatar color, role, timestampsPlaintext (not PII)Standard types

    4.2 Field-by-Field Classification

    Every PII-bearing column in our 18-table schema, classified explicitly:

    TableColumnTierWhy this tier
    ownersnational_idCRITICALLegal/regulated identifier — direct identity theft fuel
    ownersphoneCRITICALTargeted phishing vector + direct user contact
    tenant_usersphoneCRITICALSame as owners — primary auth credential
    signaturessignature_blobHIGHVisual signature — legal evidence, no search needed
    usersemailMEDIUMLogin identifier — must search, low individual harm
    usersnameMEDIUMUI display, frequent read — encryption cost too high
    ownersnameMEDIUMSame as users.name
    ownersemailMEDIUMSame as users.email

    usersavatar_colorLOWCosmetic, not PII
    audit_logipLOWNetwork artifact, useful for security forensics

    4.3 The Decision Framework

    For new fields, this decision tree determines tier:

    // Decision tree for new PII fields Is the field a regulated identifier? (national ID, passport, SSN-equivalent) └─ YES → CRITICAL (encrypt + hash) └─ NO → continue Is it a direct contact channel for the person? (phone, personal email used for OTP, etc.) └─ YES → CRITICAL if it's the primary auth credential OR HIGH if it's secondary contact └─ NO → continue Is it a biometric or signature? └─ YES → HIGH (encrypt, no hash needed) └─ NO → continue Is it shown in the UI on every page load? (name, avatar, role) └─ YES → MEDIUM (plaintext — encryption cost exceeds benefit) └─ NO → continue Is it searchable by users via UI? (email for login, name in search) └─ YES → MEDIUM (plaintext) or CRITICAL with hash strategy └─ NO → LOW (plaintext, document why)

    4.4 Why Some PII Stays Plaintext

    The choice to keep email, name, and address in plaintext is deliberate, not lazy. The reasoning:

    • Functional necessity for email. Login by email requires fast lookup. Encrypting forces HMAC-hash strategy with the same lookup performance — but adds complexity for marginal benefit. Email leaks are mostly spam-fuel, not identity theft.
    • Display performance for name. Names appear in every list, every audit entry, every notification. Decrypting on every render adds measurable latency to common operations. The harm vector is mild (a name alone is not a credential).
    • Public record for address. Land registry addresses are public records. Encrypting them adds cost with no benefit.
    • Provider lock-in concern. Heavy encryption ties us to pgcrypto. We keep encryption surgical — only where the legal/harm vector justifies it.
    ⚠ Revisit at scale
    At 100+ organizations and certainly at enterprise scale, an enterprise customer may demand "encrypt everything." That requires us to either migrate fields to BYTEA (DB migration + app changes) or to implement application-layer encryption. We plan for this: the EncryptionService interface can support any field — adding a field is a configuration change, not a redesign.

    4.5 The Israeli Compliance Lens

    Israeli Privacy Protection Law (חוק הגנת הפרטיות) and related regulations have specific requirements for personal data handling. We don't pretend to be lawyers; we implement defensible defaults:

    • Reasonable technical measures. Encryption of high-sensitivity fields is industry-standard "reasonable."
    • Access controls. RLS + role-based authorization restrict who sees what.
    • Audit trails. Every PII access by provider tier is logged (Section 12).
    • Data subject rights preparation. Schema supports "find all data about person X" via HMAC hash + decryption with audit.
    • Data deletion on request. Soft delete is the default; hard delete is a documented procedure (Section 13).

    This is the defensible baseline. Enterprise customers may demand more (encryption-at-rest beyond fields, data residency in Israel, specific deletion timelines) — those are deferred to enterprise scale.

    4.6 The Performance Budget for PII Operations

    Encryption isn't free. Every encrypted field adds cost. We track the budget explicitly:

    OperationTarget latencyMitigation
    Encrypt single field (write)< 2mspgcrypto with cached key
    Decrypt single field (read)< 2msSame as encrypt
    HMAC hash for lookup< 1msSHA-256 with HMAC key
    Search by hashed field (lookup)< 5msIndex on hash column
    Bulk decrypt (list view, 50 rows)< 50msAvoided — list views don't show ת"ז
    Total PII overhead per request< 10msSurgical encryption (only CRITICAL fields)

    The strategy of encrypting only CRITICAL fields (and not names/emails) is what makes this budget achievable. If we encrypted every field, list views would take 200ms+ and the user experience would suffer.

    💡 The trade-off, made explicit
    More encryption = more security at the cost of performance and complexity. Less encryption = more performance and simplicity at the cost of security. Our strategy: encrypt where the harm vector justifies the cost (CRITICAL fields), leave plaintext where harm is bounded and cost is real. This is not a permanent answer — it's the right answer for this stage. At enterprise scale, the answer changes.
    05 · ENCRYPTION IMPLEMENTATION

    How PII Encryption Actually Works

    The mechanism behind the strategy. Postgres-native, performant, replaceable.

    We use pgcrypto — Postgres's built-in cryptography extension — for symmetric encryption of CRITICAL fields. This choice keeps encryption close to the data, avoids round-trips, and uses battle-tested cryptography. We do not implement our own crypto.

    5.1 The Encryption Pattern

    Every CRITICAL field uses a two-column pattern:

    Drizzle schema: owners table (relevant columns)
    import { pgTable, uuid, text, customType } from 'drizzle-orm/pg-core';

// Custom type for encrypted BYTEA
const bytea = customType<{ data: Buffer; driverData: Buffer }>({
  dataType() { return 'bytea'; },
});

export const owners = pgTable('owners', {
  id: uuid('id').primaryKey().defaultRandom(),
  apartmentId: uuid('apartment_id').notNull(),

  // MEDIUM tier — plaintext
  name: text('name').notNull(),
  email: text('email'),

  // CRITICAL tier — encrypted + hashed
  nationalIdEncrypted: bytea('national_id_encrypted').notNull(),
  nationalIdHash: text('national_id_hash').notNull(),

  phoneEncrypted: bytea('phone_encrypted'),
  phoneHash: text('phone_hash'),

  // ... other columns
});

    5.2 Why Two Columns Per Encrypted Field

    Encryption alone breaks search. If national_id is encrypted with random salt, you cannot find an owner by their national ID without decrypting every row (a full table scan, catastrophic at scale).

    The solution: a second column with a deterministic HMAC hash. Same input always produces the same hash; same key always produces the same hash. You can search the hash column with an index, while the actual data lives encrypted.

    ColumnTypePurpose
    national_id_encryptedBYTEAThe data itself, encrypted with AES-256
    national_id_hashTEXTHMAC-SHA256 of the same data — searchable

    An attacker with database access sees the hash column but cannot reverse-engineer the national ID — HMAC is one-way. They cannot use the hash for anything except confirming "does this exact national ID exist?" — and only if they already know it.

    5.3 The Encryption Service Interface

    Following SOLID and modularity principles, encryption is hidden behind an interface:

    packages/db/src/providers/encryption.interface.ts
    export interface IEncryptionService {
  // Encrypt a string. Returns the BYTEA-compatible Buffer.
  encrypt(plaintext: string): Buffer;

  // Decrypt a BYTEA back to a string.
  decrypt(ciphertext: Buffer): string;

  // Compute the HMAC hash used for lookups.
  hash(plaintext: string): string;

  // Convenience: encrypt + hash in one call
  protect(plaintext: string): { encrypted: Buffer; hash: string };
}

export interface IEncryptionKeyProvider {
  // Returns the active encryption key (32 bytes for AES-256).
  getEncryptionKey(): Buffer;

  // Returns the active HMAC key (separate from encryption key).
  getHmacKey(): Buffer;
}

    The interface allows multiple implementations:

    • PgcryptoEncryptionService — current MVP implementation. Uses pgcrypto functions via SQL.
    • NodeCryptoEncryptionService — fallback if we migrate off Postgres. Uses Node's crypto module.
    • KmsEncryptionService — enterprise scale option. Uses AWS KMS or similar for key management.

    The consumer (service code) never knows which is active. Replaceability is built in.

    5.4 The Encrypt/Decrypt Helper

    Service code never calls pgcrypto directly. It always goes through the helper:

    packages/db/src/providers/pgcrypto-encryption.service.ts
    import { sql } from 'drizzle-orm';
import { createHmac } from 'crypto';

export class PgcryptoEncryptionService implements IEncryptionService {
  constructor(private keys: IEncryptionKeyProvider) {}

  encrypt(plaintext: string): Buffer {
    // pgcrypto: pgp_sym_encrypt(text, key) returns BYTEA
    // In practice, this is computed via a DB function call in INSERTs.
    // At the app layer, we delegate to a stored function.
    throw new Error('Use SQL-level pgp_sym_encrypt in INSERT statements');
  }

  hash(plaintext: string): string {
    return createHmac('sha256', this.keys.getHmacKey())
      .update(plaintext, 'utf8')
      .digest('hex');
  }

  protect(plaintext: string): { encrypted: Buffer; hash: string } {
    // The actual encrypt happens at SQL level via Drizzle's sql tag.
    // This helper computes the hash; encryption is part of the INSERT.
    return { encrypted: Buffer.from(''), hash: this.hash(plaintext) };
  }
}

    The actual encrypt operation happens in SQL, using pgcrypto's pgp_sym_encrypt function. This is faster than encrypting at the application layer and ensures the plaintext never crosses the network in the wrong direction:

    SQL inside an INSERT (via Drizzle's sql tag)
    INSERT INTO owners (
  id, apartment_id, name, email,
  national_id_encrypted, national_id_hash
) VALUES (
  gen_random_uuid(),
  $1,            -- apartment_id
  $2,            -- name (plaintext)
  $3,            -- email (plaintext)
  pgp_sym_encrypt($4, current_setting('app.encryption_key')),  -- national_id encrypted
  $5             -- national_id_hash (computed in app)
);

    5.5 The Key Management Strategy

    Keys are the security model's foundation. If the encryption key leaks, the encrypted data is exposed. Key handling rules:

    • Two separate keys, always. Encryption key (for pgcrypto) and HMAC key (for hashes) are different. Compromising one does not compromise the other.
    • Keys come from environment, never code. PII_ENCRYPTION_KEY and PII_HASH_KEY are env vars loaded via T3-env, validated at startup, never logged.
    • Keys are injected into Postgres session. Via SET LOCAL app.encryption_key = $key inside transaction. Keys never appear in query logs.
    • Keys are 32 bytes (256-bit) random. Generated with openssl rand -base64 32. Stored ONLY in Infisical (environments: dev/staging/production), injected at runtime via infisical run -- / Infisical's CI integration. Railway/host env is populated from Infisical at deploy, it is not the source of truth.
    • Keys rotate, but not casually. See Section 14 for the procedure. Rotation requires re-encrypting all data.
    ⚠ The key handling failure modes
    Never: log encryption keys (even DEBUG), send them over unencrypted channels, store them in code or git history, share them via chat/email, reuse encryption keys across environments (dev / staging / prod), or treat the HMAC key as less sensitive than the encryption key — they're equally critical.

    5.6 The Session-Level Key Injection

    Encryption keys reach Postgres via session variables, just like the tenant context. The pattern mirrors withTenant:

    packages/db/src/wrappers/with-tenant.ts (excerpt)
    export async function withTenant<T>(
  orgId: string,
  fn: (db: Database) => Promise<T>
): Promise<T> {
  return pool.transaction(async (tx) => {
    // Set tenant context (RLS uses this)
    await tx.execute(sql`SET LOCAL app.organization_id = ${orgId}`);

    // Set encryption keys (pgcrypto functions use these)
    await tx.execute(sql`SET LOCAL app.encryption_key = ${env.PII_ENCRYPTION_KEY}`);

    // Run the user's code with both contexts active
    return fn(tx);
  });
}

    Why SET LOCAL inside a transaction:

    • Transaction-scoped. Keys are visible only for the current transaction. End of transaction = keys discarded from session.
    • Connection-pool safe. Pgcrypto session vars don't leak to the next request that reuses the connection.
    • Atomic with the tenant context. Both are set together; impossible to encrypt without the right tenant active.

    5.7 The Lookup Pattern

    To find an owner by national ID, the flow is:

    1. App computes hash. hmac.sha256(nationalId, hmacKey) = "abc123..."
    2. Query by hash. SELECT * FROM owners WHERE national_id_hash = 'abc123...'
    3. RLS filters by tenant. The query only returns owners in the current organization (RLS policy enforces this).
    4. Index makes it fast. Hash column has a btree index on (organization_id_via_join, national_id_hash).
    5. Decrypt if needed. Display name and other plaintext fields are returned directly. The encrypted column is decrypted via pgp_sym_decrypt only if the requesting context needs it (rarely — usually we have the input already).
    Service code: lookup by national ID
    async findOwnerByNationalId(orgId: string, nationalId: string) {
  return withTenant(orgId, async (db) => {
    const hash = encryptionService.hash(nationalId);

    const [owner] = await db
      .select()
      .from(owners)
      .where(eq(owners.nationalIdHash, hash))
      .limit(1);

    return owner; // null if not found
  });
}

    Notice: we never decrypt to compare. The hash comparison is the entire lookup. Decryption only happens when we actually need to display the value (rare in business flow; sometimes for audit or export).

    5.8 Common Mistakes to Avoid

    • Encrypting at the app layer instead of SQL. Sending plaintext across the network to encrypt then send back adds round-trip cost and increases exposure. pgcrypto in SQL is faster and safer.
    • Reusing the same key for encryption and HMAC. Same key = correlated weaknesses. We use two separate keys.
    • Storing the hash but not the encrypted value. Some teams think "we only need to search" and skip encryption. But search alone doesn't return the data — you still need the value for display, audit, export. Both columns are required.
    • Decrypting in bulk for list views. A list of 50 owners with all their national IDs decrypted is unnecessary and expensive. UI shouldn't show national IDs in list views — only in detail views where the cost is per-record and warranted.
    • Forgetting to rotate keys after a leak. If an env var is exposed (a developer's laptop compromised, a CI log leaked), the procedure in Section 14 is mandatory. Old encrypted data needs re-encryption with the new key.
    • Different encryption strategies per developer. All encryption goes through the IEncryptionService. If someone "improves" encryption locally with custom code, our consistency breaks.

    5.9 Testing the Encryption Layer

    Encryption code is tested with two categories of tests:

    • Round-trip tests (T1.8). Encrypt a value, decrypt it, expect equal. Hash a value twice, expect equal hashes. Hash two different values, expect different hashes. Boring but essential — proves the math is right.
    • Storage tests. Insert an owner, query the raw national_id_encrypted column, verify it's binary (not the original string). Query national_id_hash, verify it's a 64-char hex string. Proves the columns are populated correctly.
    • Key rotation tests. Encrypt with key A, attempt to decrypt with key B, expect failure. Proves the system rejects wrong keys (no silent fallback to plaintext).

    Tests live in packages/db/test/encryption.spec.ts and run on every CI build.

    5.10 The Migration Path to Stronger Encryption

    The current MVP uses symmetric AES-256 via pgcrypto with keys in env vars. This is industry-standard for the scale we operate at. Future evolution:

    StageStrategyWhy
    MVP (now)pgcrypto + env-var keysSimple, fast, sufficient for 1-100 orgs
    Growth (10-100 orgs)Same + Railway secrets manager + monitoringProduction hardening, no architecture change
    Scale (100+ orgs)Move keys to KMS (AWS/GCP), via IEncryptionKeyProviderHardware-backed key management, audit-grade key access logs
    Enterprise (1000+)Per-tenant encryption keys (BYOK option)Customer holds key — even EMAPP team cannot decrypt

    Each stage is a configuration change, not a rewrite. The IEncryptionService and IEncryptionKeyProvider interfaces remain stable; only the implementations change.

    ✓ The encryption invariants
    Three properties must hold at all times: (1) plaintext PII is never written to disk (database, logs, file system), (2) encryption keys never appear in logs or query history, (3) swapping encryption providers requires no service-code changes — only configuration. If any of these is violated, the security posture is broken.

    ⚠ SUPERSEDED BY D.21 (2026-05-18). Better Auth was REMOVED from the auth path.     2. Data ownership. Session tokens, OAuth states, MFA secrets all live in our database. No third party holds our customers' authentication data.

    6.3 Password Security

    For Manager, Agent, Provider Admin — password is the primary credential. Strict rules:

    • bcrypt with cost 12. Better Auth default. Adjustable as compute gets cheaper (rotate to cost 14 in 2027+).
    • Minimum 12 characters. Below 12 is too easy to brute-force in cloud.
    • Breached password check (recommended). Optional integration with haveibeenpwned API. Rejects passwords known to be in breach databases.
    • No password complexity rules. NIST 2020 guidance: long passphrases beat complex short passwords. Don't force special characters.
    • Password change requires current password. Always. Even when "logged in."
    • Password reset via email link. Token-based, single-use, 15-minute TTL.

    6.4 Magic Link Security

    For Contractor (primary) and Agent (optional). The flow:

    // Magic link flow — Contractor case [1] Contractor visits /auth/magic-link, enters email ▼ [2] Server validates email format (Zod) ▼ [3] Server looks up contractor record by email + active share ▼ [4] Generate cryptographically random token (32 bytes, base64url) ▼ [5] Store SHA-256 hash of token + expiry + email in magic_link_tokens table // We store the hash, not the token — token leak from DB ≠ token usable ▼ [6] Send email via Resend with link: app.url/auth/consume?token=<raw_token> ▼ [7] Contractor clicks link → server computes hash → looks up in table ▼ [8] If found + not expired + not used → mark as used + issue JWT // Single-use enforcement via "used_at" column.     6.5 SMS OTP Security (MVP — Tenant login, D.17+D.20)

    For Tenant login. This is MVP (D.17+D.20) — Tenant is an MVP role. SMS provider is a real Israeli vendor (019/Inforu) behind ISMSProvider:

    • Rate limit: 3 attempts per phone per 15 minutes. Brute force defense.
    • 6-digit code, cryptographically random. Not Math.random().
    • 5-minute TTL. Codes expire fast.
    • Single-use enforcement. Once consumed, the code is dead. Same as magic link.
    • Server stores hash of code, not plaintext. Same principle as magic link.
    • Phone normalization. All numbers stored as +972XXXXXXXXX (E.164). User input "050-1234567" normalizes server-side.
    • OTP audit. Every send + every verify (success or fail) goes to audit log with IP and timestamp.

    The ISMSProvider interface lets us swap providers without code changes. MVP ships with a real Israeli provider (019/Inforu — chosen for +972 cost & deliverability, D.20). Dev/test use NoopSMSProvider (logs the OTP, sends nothing) so tests don't burn real SMS.

    6.6 MFA (Multi-Factor Authentication)

    MFA is mandatory for Provider Admins and optional for everyone else. Implementation:

    • TOTP (Time-based One-Time Password). Standard RFC 6238. Compatible with Google Authenticator, Authy, 1Password, etc.
    • Secret stored encrypted. The TOTP secret is HIGH-tier PII — encrypted in provider_users.mfa_secret_encrypted.
    • Recovery codes generated at enrollment. 8 single-use codes printed once, hashed in DB.
    • 30-second window with ±1 step tolerance. Standard TOTP defaults.
    • MFA challenge on every login. Not just first time. For Provider Admins, every session.
    • SMS MFA explicitly NOT supported. SMS is vulnerable to SIM swap. We use TOTP only.

    6.8 JWT Claims — What's In, What's Not

    The JWT is signed and trusted, but only as a transport. The claims:

    JWT payload structure
    {
  // Standard claims
  "sub": "usr_01H...",           // user_id
  "iat": 1726492800,             // issued at
  "exp": 1726496400,             // expires
  "iss": "emapp",
  "aud": "emapp-api",

  // Application claims
  "role": "manager",             // auth role

    • NOT in JWT: email, name, national_id, phone, any PII
    • NOT in JWT: permissions (those come from DB on each request)
    • NOT in JWT: share_id or contractor-specific data (fetched server-side)
    • NOT in JWT: anything that can change without re-login

    Reasoning: JWTs are visible to anyone who has them, including the client. If we put email/name in the JWT, every browser request leaks them. We put only what's needed to identify the session and resolve the rest server-side.

    6.9 Multi-Org Session Handling

    A user can belong to multiple organizations (via memberships table). The session tracks one active org at a time:

    1. Login resolves to a default org. The user's primary membership (marked is_primary=true) is the default active org.
    2. JWT includes active_org_id. Every request reads this, every query scopes to it via withTenant.
    3. Switching orgs requires a new token. Endpoint: POST /auth/switch-org with org_id. Server verifies the user has membership, issues new JWT.
    4. Old token cannot reach new org. Token is bound to a specific active_org_id. Mid-session changes require explicit switch.

    This prevents a class of bugs where a user "leaks" data from one org to another by accidentally querying across them.

    6.11 Account Lockout Policy

    After repeated failed logins, accounts are temporarily locked:

    • 5 failed login attempts within 15 minutes. Account locked for 15 minutes.
    • Lockout is per-account, not per-IP. Otherwise attackers can lock out legitimate users by guessing wrong passwords from random IPs (denial-of-service-as-a-service).
    • Email notification on lockout. User gets "your account was locked due to failed logins" — alerts legitimate user to compromise attempt.
    • Provider Admin lockouts trigger an alert. 5 failed Provider Admin attempts = page the on-call engineer (eventually; in MVP, log + email).
    • Lockout doesn't apply to magic link or OTP. Those have their own rate limits (Section 6.4, 6.5).
    ⚠ Why not "lock forever after N failures"
    Permanent lockouts create a denial-of-service vector — an attacker who knows your email can permanently lock you out. Time-based lockouts (15 min) give the legitimate user a recovery path while making brute force economically painful. The trade-off is intentional.

    6.12 Password Reset Flow

    The password reset flow is its own attack surface: it accepts attacker-controlled input (email), it sends a token to that email, and a successful flow grants account access. Every step matters.

    6.12.1 The flow, step by step

    1. User requests reset. Submits email at /forgot-password. The form always returns "If an account exists, we sent you a link" — regardless of whether the email is in the system. Anti-enumeration: never reveal existence.
    2. Server generates reset token. 32 random bytes (256-bit), URL-safe base64-encoded. Stored in cache_kv with key pwreset:<token-hash> and value {userId, createdAt}. The token itself is NOT stored — only its SHA-256 hash. If cache_kv leaks, tokens can't be reversed.
    3. Email sent via Resend. Magic-style URL: https://app.emapp.io/reset-password?token=<raw-token>. Includes user's IP and approximate location of the request, plus "If you didn't request this, ignore this email."
    4. Token TTL: 1 hour. After 1 hour, the entry expires from cache_kv automatically. No grace period.
    5. User clicks link, lands on /reset-password. Frontend extracts token, sends to POST /api/v1/auth/reset-password with new password.
    6. Server validates token. Hashes received token with SHA-256, looks up pwreset:<hash>. If found and not expired: proceed. If not: 400 "Invalid or expired link."
    7. Single-use enforcement. On successful validation, immediately delete the entry from cache_kv. Even if request fails downstream (DB write failure), the token can't be reused.
    8. New password validated. Same rules as registration (Section 6.3): min length, breach check, no common passwords.
    9. Password updated. bcrypt hash stored, password_changed_at timestamp updated, all existing sessions for this user are invalidated (force re-login on other devices).
    10. Confirmation email sent. "Your password was changed at <time> from <IP>. If this wasn't you, contact support immediately."
    11. Audit log entry. action: 'auth.password.reset.completed', includes userId, IP, user agent. Failed attempts (invalid token, expired) also audited.

    6.12.2 Rate limiting on reset requests

    The "request reset link" endpoint is rate limited both by email and by IP:

    • Per email: 3 reset requests per hour. Beyond that → 429 "Too many requests; try again later." (Same generic message regardless of whether email exists.)
    • Per IP: 10 reset requests per hour. Prevents an attacker from enumerating emails or generating spam by submitting many emails.
    • Rate limit storage: ICacheProvider (Postgres cache_kv in MVP, Upstash later).

    6.12.3 Provider Admin password reset

    Provider Admin password resets do not use the standard flow. They are operated manually:

    • Another Provider Admin marks the account as "needs reset" (action recorded in provider_audit_log).
    • The target user must verify identity out-of-band (Slack DM with a separate code, phone call, in-person — whatever the team agrees on).
    • Second Provider Admin issues a one-time reset URL valid for 30 minutes.
    • On successful reset, MFA is forced to be re-registered (revoke old TOTP secret, require new enrollment).
    ⚠ The "self-service" trap for Provider Admin
    A regular user reset flow that an attacker can run = social engineering risk. If a Provider Admin's email is compromised, the attacker controls password resets. Mandating a second Provider Admin's involvement makes the attack require two compromises. Same reasoning as MFA — defense in depth.

    6.12.4 What's NOT done in MVP password reset

    • No security questions. "What's your pet's name" is worse than no protection — it's a low-entropy attack surface that legitimate users forget.
    • No SMS-based password reset for org users. SIM-swap is real. Tenant (MVP) uses SMS OTP as its primary auth by design (phone-first users), but Manager/Agent/Viewer password reset → email only.
    • No "remember this device" bypass. Reset is reset; no shortcuts.

    6.13 HTTP Security Headers — CSP, HSTS, and Friends

    HTTP response headers are the cheapest defense layer we have. They cost nothing to deploy, they break nothing legitimate, and they prevent entire classes of attacks before they reach our code. We enforce them at two layers: at the Cloudflare edge (defense-in-depth), and in the API/FE applications (always-correct fallback).

    The actual header configuration code lives in Doc 04b §main.ts (Helmet setup) — this section explains the rationale behind each header choice.

    6.13.1 Content Security Policy (CSP)

    CSP tells the browser exactly which sources can serve scripts, styles, images, and connections. Even if an attacker injects HTML (XSS), the browser refuses to execute scripts from unauthorized origins. The strictest viable CSP:

    DirectiveValueWhy this exact value
    default-src'self'Everything must be same-origin unless overridden. Whitelist model — explicit allows only.
    script-src'self'No inline scripts, no eval. React + Next.js handle this natively. No 'unsafe-inline' or 'unsafe-eval' ever.
    style-src'self' 'unsafe-inline'Tailwind injects inline styles for utility classes. Trade-off accepted: CSS injection is low-impact (cosmetic), and the alternative is rewriting our entire styling stack.
    img-src'self' https://*.r2.cloudflarestorage.com data:Document thumbnails and signature SVGs are served from R2 via signed URLs. data: for inline icons.
    connect-src'self' https://*.sentry.io https://api.resend.comFE makes XHR/fetch calls. Same-origin for our own API; Sentry for error reporting; Resend not directly from browser, but listed for completeness.
    font-src'self' https://fonts.gstatic.comGoogle Fonts. If we self-host fonts later, drop the external entry.
    object-src'none'No <object>, <embed>, or <applet> ever. Closes Flash-era attack vectors.
    frame-ancestors'none'EMAPP can't be embedded in an iframe by anyone. Prevents clickjacking. (X-Frame-Options also set as fallback for older browsers.)
    base-uri'self'Prevents <base href> injection from redirecting relative URLs to an attacker domain.
    form-action'self'Forms can only POST to our own origin. Prevents form-injection exfiltration.

    The 'unsafe-inline' trade-off for styles is explicit. If we ever migrate to a CSS-in-JS solution that doesn't require inline styles, this gets tightened. Tracked as a Phase 3 hardening item, not blocking.

    6.13.2 HTTP Strict Transport Security (HSTS)

    HSTS tells browsers "never connect to this domain over HTTP again." Prevents downgrade attacks and accidental cleartext leakage.

    HSTS configuration
    Strict-Transport-Security: max-age=31536000; includeSubDomains; preload
    • max-age=31536000 (1 year). Long enough to be meaningful; not so long that recovery from misconfiguration is painful.
    • includeSubDomains. Applies to api.emapp.io, app.emapp.io, all preview deploys.
    • preload. Eligible for inclusion in Chrome/Firefox preload lists. After verification on hstspreload.org, browsers refuse HTTP even on first visit.
    ⚠ HSTS is irreversible (sort of)
    Once a browser caches the HSTS header for your domain, it will refuse HTTP for the full max-age period — regardless of what the server now sends. If you accidentally break HTTPS (cert expired, wrong DNS, etc.), affected users cannot access the site at all until either the cert is fixed or 1 year passes. Mitigation: staging environment uses max-age=3600 (1 hour) for the same domain pattern until we're confident. Production goes to 1 year only after 30 days of stable HTTPS.

    6.13.3 Other Headers

    HeaderValueWhat it prevents
    X-Frame-OptionsDENYClickjacking via iframe embedding (redundant with CSP's frame-ancestors but covers older browsers).
    X-Content-Type-OptionsnosniffPrevents MIME-sniffing attacks where the browser tries to "guess" a different content type than what the server declared.
    Referrer-Policystrict-origin-when-cross-originLimits what URLs leak via the Referer header to other sites. Keeps full URL only for same-origin.
    Permissions-Policygeolocation=(), microphone=(), camera=()Disables browser APIs we never use. Reduces attack surface even if XSS occurs.
    X-Powered-ByremovedFastify removes by default. Prevents fingerprinting the server stack.

    6.13.4 Where headers are set — defense in depth

    Headers are set in two places, both of which return the same values:

    1. Cloudflare edge (recommended for prod): Page Rules + Transform Rules on the emapp.io zone. Headers added to every response, regardless of origin. Catches edge cases where the origin server is bypassed (e.g., direct R2 access).
    2. NestJS via Helmet middleware (always-on fallback): The API sets them per-response. Used in development, and as backup if Cloudflare config is misconfigured.

    If both layers disagree, the most restrictive wins (CSP is intersected, not union). Conflicts surface in Sentry as CSP violation reports — we monitor those to catch regressions.

    • EU expansion. If a non-trivial number of users access from the EU (even without us targeting them), GDPR applies. At that point: full banner with granular consent (essential vs. analytics vs. marketing buckets).

    07 · AUTHORIZATION LAYERS

    Who Can Do What

    Three layers of authorization, evaluated in order. Each one independent. Each one mandatory.

    Authentication says "you are user X." Authorization says "user X can do Y." We layer three independent checks, and every request passes through all three before touching data. One layer's failure is caught by the next.

    7.1 The Three Layers

  • Role-Based Access Control (RBAC). Coarse-grained. "Is this user allowed to call this endpoint at all?" Implemented as NestJS guards. Example: only Manager can POST /projects.
  • Share-based permissions (JSONB). Fine-grained, project-scoped. "For this specific project, what fields/actions can this Contractor see?" Implemented in service layer. Example: Contractor can see tenants.name but not tenants.phone for project X.
  • Row-Level Security (RLS). Database-enforced. "Even if everything above failed, can this row be returned to this tenant?" Implemented as Postgres policies. The final safety net.

    • 7.2 Layer 1: RBAC at the Endpoint

    Every NestJS controller method declares its allowed roles via decorator:

    Example: projects.controller.ts
    @Controller('projects')
@UseGuards(AuthGuard, RoleGuard)
export class ProjectsController {

  @Post()
  @Roles('manager')           // Only Manager can create
  create(@Body() dto: CreateProjectDto) { ... }

  @Get()
  @Roles('manager', 'agent')  // Manager and Agent can list
  list() { ... }

  @Get(':id')
  @Roles('manager', 'agent', 'contractor')  // Contractor too (filtered later)
  get(@Param('id') id: string) { ... }

  @Delete(':id')
  @Roles('manager')           // Only Manager can soft-delete
  archive(@Param('id') id: string) { ... }
}

    The RoleGuard reads the JWT, extracts role, and compares against the @Roles decorator. Request rejected with 403 if mismatch. This is the cheapest, fastest authorization check — runs before any business logic.

    7.3 Layer 2: Share-Based Permissions (Contractor Path)

    Contractor's access to a project is determined by the share record. The permissions JSONB column specifies what they can see and do:

    share.permissions structure (example)
    {
  "overview":   { "on": true },
  "tenants":    {
    "on": true,
    "fields": {
      "name":  true,       // always true — required
      "phone": false,
      "email": false,
      "national_id": false,
      "note":  true
    }
  },
  "documents":  {
    "on": true,
    "actions": { "download": true, "upload": false }
  },
  "signatures": { "on": true },
  "notes":      { "on": false, "actions": { "add": false } },
  "team":       { "on": false }
}

    When a Contractor calls GET /projects/:id/apartments, the service layer:

    1. Resolves the share. Looks up share by (project_id, contractor_id from JWT). If no share, 403.
    2. Checks revocation. If share.revoked_at is set, 403. The check is on every request — not cached.
    3. Reads the permissions. Validates the JSONB shape with Zod (defense against malformed permissions).
    4. Filters the response. Apartments are loaded, then transformed: fields with false permissions are removed from the response — not nulled, but absent (missing keys).
    5. Returns the filtered data. Contractor sees only what they're allowed to see.

    7.4 The Critical Pattern: Field Absence vs Null

    When a field is hidden by share permissions, it is absent from the response object, not set to null. The distinction matters:

    Wrong: nullable fields
    // BAD: Contractor sees null where data exists
{
  "id": "apt_01H...",
  "name": "דוד כהן",
  "phone": null,        // hidden — but contractor knows it exists
  "email": null         // also hidden — same info leak
}
    Right: missing fields
    // GOOD: Contractor sees only what they're allowed
{
  "id": "apt_01H...",
  "name": "דוד כהן"
  // phone, email simply not present
}

    Reasoning: a null field tells the attacker "this field exists and has a value, but you can't see it." That's information leakage. An absent field is opaque — the attacker can't even tell if the field is empty or simply hidden.

    7.5 Layer 3: RLS as Final Safety Net

    Both RBAC and share permissions are application code. Code has bugs. Code gets bypassed. RLS is the only layer that the database enforces regardless of what the application does:

    • RLS runs on every query, no exceptions. Even SELECT * FROM apartments with no WHERE clause is filtered.
    • RLS FORCE means superuser can't bypass. Even the database owner respects the policies (with FORCE ROW LEVEL SECURITY).
    • RLS doesn't trust the app. The policy reads current_setting('app.organization_id'), which is set by withTenant. If withTenant is forgotten, the setting is empty, the policy evaluates to false, no rows are returned.
    • RLS doesn't depend on join logic. The policy is on every row — no need to remember to filter.

    7.6 The Policy Pattern Per Table Type

    Three patterns cover all multi-tenant tables in the schema:

    PatternTablesPolicy condition
    Direct org_idprojects, contractors, tasks, audit_logorg_id = current_setting('app.organization_id')::uuid
    Via parentbuildings, apartments, owners, documentsJoin to parent table that has org_id; filter via subquery
    Via membershipusers, notificationsUser's org_id matches via memberships M2N — policy uses EXISTS subquery
    Example: apartments RLS policy
    ALTER TABLE apartments ENABLE ROW LEVEL SECURITY;
ALTER TABLE apartments FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON apartments
  USING (
    project_id IN (
      SELECT id FROM projects
      WHERE org_id = current_setting('app.organization_id')::uuid
    )
  )
  WITH CHECK (
    project_id IN (
      SELECT id FROM projects
      WHERE org_id = current_setting('app.organization_id')::uuid
    )
  );

    The USING clause filters reads. The WITH CHECK filters writes — preventing a tenant from inserting rows belonging to another tenant.

    7.7 The Layer Independence Test

    The strength of three-layer auth is that each layer is independent. We test this:

    • Test: RBAC only. Bypass share-filtering (mock the service). Confirm Contractor cannot call Manager-only endpoint. Catches: missing @Roles decorator.
    • Test: Share filtering only. Allow Contractor through RBAC, mock RLS. Confirm fields hidden by permissions are absent. Catches: missing filter logic in service.
    • Test: RLS only (T1.5). Bypass all app-layer checks. Set wrong tenant context. Confirm no rows returned. Catches: missing FORCE, weak policies.

    Each test simulates the case where the other layers have already failed. If all three tests pass, the system is robust against single-layer bugs.

    7.8 Authorization Errors: HTTP Codes

    Different auth failures get different status codes — useful for the client, useful for monitoring:

    CodeMeaningWhen
    401 UnauthorizedNot authenticatedNo JWT, invalid JWT, expired JWT
    403 ForbiddenAuthenticated, no permissionRBAC mismatch, share missing, share revoked
    404 Not FoundResource doesn't exist OR isn't visibleRLS filtered the row + appears as "not found"

    Note: RLS-filtered rows return 404, not 403. If a Manager of org A queries GET /apartments/<id-from-org-B>, they get 404. We don't tell them "this exists but you can't see it" — that's an information leak about cross-tenant entities.

    08 · PROVIDER TIER SECURITY

    When EMAPP Team Needs Access

    A separate identity tier with separate rules. Mandatory MFA, narrow scope, audit-heavy.

    Customer support sometimes needs to look at a customer's data to help them. Billing sometimes needs to update plan information. The EMAPP team — the people who build and run this product — needs a way in that customers cannot access, and that customers can trust. That way is the provider tier: a separate identity system with separate rules.

    8.1 Why Provider Tier Is Separate

    An obvious design would be to mark certain users as "admin" inside the existing users table. We reject this for security reasons:

    • Different threat model. Provider Admins are higher-value targets. A compromised Manager affects one organization; a compromised Provider Admin can affect all.
    • Different authentication requirements. MFA mandatory, shorter sessions, no magic links. Different defaults than regular users.
    • Different audit requirements. Every Provider action is logged with elevated detail (Section 12). Regular user actions get standard audit.
    • Different database access pattern. Provider queries cross-org by design. They use withProvider(), not withTenant(). Mixing patterns invites bugs.
    • Different revocation needs. A departing EMAPP team member needs all Provider access revoked instantly. Tying this to the normal user lifecycle invites mistakes.

    8.2 The Two-Tier Database Architecture

    Two Postgres roles, two access patterns:

    // Postgres roles in EMAPP app_user (connection role for normal app traffic) ├─ Uses withTenant(orgId, ...) ├─ RLS policies ENFORCED (FORCE row level security) ├─ Cannot bypass tenant boundaries └─ All API requests use this role provider_app_role (separate role for provider tier) ├─ Uses withProvider(providerUserId, ...) ├─ RLS policies BYPASSED (different role, different policies) ├─ Can query across all organizations └─ Every query writes to audit_log automatically

    This is the only way to do cross-tenant queries safely. The role separation means: even a bug in the app cannot accidentally use provider_app_role for regular requests — connection strings are different, configurations are different.

    8.3 The withProvider Wrapper

    Mirror of withTenant, with different guarantees:

    packages/db/src/wrappers/with-provider.ts
    export async function withProvider<T>(
  providerUserId: string,
  reason: string,                     // MANDATORY — written to audit
  fn: (db: Database) => Promise<T>
): Promise<T> {
  // Use the provider DB pool (different connection string, different role)
  return providerPool.transaction(async (tx) => {
    // Set provider context (separate session var from org)
    await tx.execute(sql`SET LOCAL app.provider_user_id = ${providerUserId}`);
    await tx.execute(sql`SET LOCAL app.access_reason = ${reason}`);

    // Write audit entry BEFORE the query
    await tx.execute(sql`
      INSERT INTO provider_audit_log (provider_user_id, reason, started_at)
      VALUES (${providerUserId}, ${reason}, NOW())
    `);

    // Run the user's code
    const result = await fn(tx);

    // Audit closes when transaction commits
    return result;
  });
}

    Three differences from withTenant:

    1. Reason is mandatory. Every Provider access has a stated purpose — "support ticket #1234", "billing reconciliation", "scheduled health check". The reason is in the audit log.
    2. Uses a different connection pool. providerPool connects with provider_app_role credentials. The pools are completely separate, so misuse is structurally hard.
    3. Audit happens before the work, not after. Even if the query fails, the access attempt is recorded.

    8.4 What Provider Tier Can and Cannot Do

    Even with elevated access, there are limits:

    OperationProvider can?Notes
    Read customer data (any org)YesAudited
    Modify customer dataYes (rare)Audited; usually only for support tickets with customer consent
    Delete customer dataRestrictedManager-initiated via Provider tooling; not direct DB writes
    Decrypt PII at scaleNoBulk decrypts trigger alerts; only individual records on demand
    Read encryption keysNoKeys are env vars; only the running app has them
    Disable RLS globallyNoProvider_app_role doesn't have DDL permissions on RLS settings
    Read audit logYesIncluding their own actions — transparency
    Delete from audit logNeverAudit is append-only at DB level (no DELETE permission)

    8.5 Provider Authentication Requirements

    Stricter than regular users:

    • MFA mandatory. Cannot disable. Enrollment is part of account creation.
    • Stronger password rules. Minimum 14 characters (vs 12 for regular).
    • Shorter session TTL. 30-minute access token, 4-hour refresh. Re-auth at least every 4 hours.
    • No magic links. Email-link auth is too easy to phish for elevated access.
    • IP allowlist (optional Phase 2). Provider logins from outside known IPs trigger MFA challenge plus alert.
    • Separate password reset flow. Cannot use the customer-facing reset; requires another Provider Admin to approve.

    8.6 The Provider Audit Standard

    Provider actions get richer audit than regular users. The schema:

    provider_audit_log (separate table)
    CREATE TABLE provider_audit_log (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  provider_user_id  UUID NOT NULL REFERENCES provider_users(id),
  reason            TEXT NOT NULL,        // from withProvider() call
  action_type       TEXT NOT NULL,        // "read", "write", "decrypt", etc.
  target_table      TEXT,
  target_record_id  UUID,
  affected_orgs     UUID[],            // which organizations' data was touched
  ip                INET NOT NULL,
  user_agent        TEXT,
  started_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  ended_at          TIMESTAMPTZ,
  query_count       INT,                  // approximate number of queries in session
  metadata          JSONB                 // extra context (ticket #, etc.)
);

    Every Provider session creates one row. The audit can answer: "On Monday at 14:30, which Provider user accessed organization X's data, and why?"

    8.7 Customer-Visible Provider Access

    Trust is built on transparency. Customers can see when Provider tier has accessed their data:

    • Dashboard widget (Phase 2). Organization Manager sees "EMAPP support accessed your data: 2 times this month."
    • Notification on access (optional Phase 2). Customer can opt-in to email notification when their org is accessed.
    • On request. Customer can ask for the audit log; we deliver the relevant entries within 48 hours.
    • Compliance reports (Enterprise). Quarterly summary of all Provider access for compliance-conscious customers.

    8.8 Provider Tier Failure Modes

    Things that go wrong with privileged access, and how we prevent them:

    • Compromised Provider account. Mitigated by MFA, short session, IP monitoring. If compromised, alert + force logout + key rotation.
    • Insider misuse. Audit log makes after-the-fact detection possible. Provider tier access is small and known — anomalies are visible.
    • Provider mistakes (wrong customer). The reason field in withProvider forces explicit thought. Production tools (when built) require selecting the specific organization, not free-form queries.
    • Stale Provider accounts. Monthly review of active provider_users. Anyone who hasn't logged in for 90 days gets disabled.
    • Provider audit log compromise. Audit log is append-only at DB level. provider_app_role has INSERT but not DELETE. Even Provider Admins cannot erase their tracks.

    8.9 Provider Tier in the MVP vs Later

    MVP scope (what's built):

    • provider_users table with id, email, role, mfa_secret_encrypted, recovery_codes_hashed
    • provider_app_role Postgres role created in migrations
    • withProvider() wrapper function
    • Basic Provider Admin role (full access)
    • provider_audit_log table with INSERT-only permissions
    • Login flow with password + MFA

    Phase 2 expansions:

    • Sub-roles within Provider: support, billing, readonly (less than full admin)
    • IP allowlist for Provider logins
    • Customer-visible Provider access widget
    • Provider tooling UI (currently: direct database queries via Drizzle Studio in audited fashion)
    • SSO for Provider tier (e.g., Google Workspace)

    8.10 The Trust Contract

    Provider tier represents a promise to customers: "We can help you when you need us, but we cannot betray your trust without leaving evidence." The technical mechanisms — separate role, mandatory audit, append-only logs, mandatory MFA — make that promise enforceable, not just stated.

    ⚠ The provider tier is the most sensitive surface
    A breach of Provider tier is catastrophically worse than a breach of any customer account. One Provider Admin with compromised credentials can access every customer. The MFA mandate, the short session, the per-action audit — these are not bureaucratic friction. They are the defense against a single-point catastrophe. Never weaken these requirements, even for convenience.
    09 · TOP 10 THREAT SCENARIOS

    The Specific Attacks We Defend Against

    Each scenario is concrete, plausible, and tested. The defense pattern for each is documented and enforced in code.

    A threat model in the abstract is useless. You defend against specific attacks. Here are the ten threats most likely to occur in our system, each with the attack vector, the defense layers that catch it, the test that proves the defense works, and the code patterns that make the defense automatic.

    T01
    Tenant sees another tenant's apartment
    Critical
    Attack Vector
    Tenant A (resident of project X) authenticates, then crafts a URL like GET /tenant/apartments/<id-from-project-Y> by guessing or scraping IDs. If the API doesn't verify ownership, Tenant A reads another resident's data.
    Defense Layers
    Layer 1 (RBAC): Tenant role can only call /tenant/me* endpoints — not /apartments/:id. The general endpoint is blocked at the controller.
    Layer 2 (Service): /tenant/me resolves apartment_id from JWT, not request params. There is no way for the Tenant to specify which apartment.
    Layer 3 (RLS): Even if layers 1-2 are bypassed, RLS on apartments filters by tenant_user_id = current_setting('app.user_id').
    Test
    T1.5 scenario 2: Create two Tenants in different projects. Authenticate as Tenant A. Attempt to read Tenant B's apartment via direct ID. Expected: 404 (not 403 — we hide existence entirely).
    T02
    Contractor accesses project without a share
    Critical
    Attack Vector
    Contractor with legitimate access to project X tries to access project Y by sending GET /projects/<Y-id>. The contractor's JWT is valid; the question is whether share verification catches the request.
    Defense Layers
    Layer 2 (Service): The first action in any Contractor-facing service method is resolveShare(projectId, contractorIdFromJwt). If no row in shares table matches, throw 403 immediately. If revoked_at is not null, throw 403.
    Layer 3 (RLS): RLS policies on tables like apartments, notes, documents include a condition: row's project must have an active share with the current contractor. No share → no rows visible.
    Test
    T1.5 scenario 4: Create contractor C with active share to project X only. Authenticate as C. Attempt to access project Y. Expected: 403 with code FORBIDDEN_NO_SHARE.
    T03
    Manager of org A reads data from org B
    Critical
    Attack Vector
    A user with a Manager role in org A — perhaps recently moved from org B — sends a request with JWT for org A but includes an ID known from org B. Or: a Manager with memberships in both orgs accidentally accesses cross-org data through stale session state.
    Defense Layers
    Layer 1 (Auth): JWT contains active_org_id, set explicitly when org was selected. Cannot change without new token issuance.
    Layer 2 (withTenant): Every query wraps in withTenant(active_org_id, ...). The org context is from JWT, not from request body.
    Layer 3 (RLS + FORCE): Policies use current_setting('app.organization_id'). If wrong (or empty) — zero rows.
    Architecture note: Multi-org users (memberships M2N) explicitly require token switching to access different orgs. There is no "shortcut."
    Test
    T1.5 scenario 1 (the canonical cross-tenant test): Create two orgs with separate users and data. Authenticate as Manager of org A. Set wrong organization_id in withTenant simulation. Verify: no rows from org B returned, even when querying tables directly.
    T04
    Agent sees projects they're not assigned to
    High
    Attack Vector
    Agent in org A is assigned to projects X and Y. Project Z exists in same org but Agent is not on its team. The Agent attempts to list or read Z. Same-org access can't be stopped by RLS (RLS keeps within org but not between projects).
    Defense Layers
    Layer 2 (Service): For Agent role, list endpoints filter by membership in project_assignments table. Detail endpoints check assignment exists before returning the project.
    RLS extension: A second RLS policy (in addition to org isolation) checks project_id IN (SELECT project_id FROM project_assignments WHERE user_id = current_setting('app.user_id')) when current role is 'agent'. This is the only same-org scoping done at DB layer.
    Note: Manager role bypasses the project-assignment check — Manager sees all projects in their org.
    Test
    T1.5 scenario 5: Create one org with three projects. Create an Agent assigned to projects X, Y. Authenticate as Agent. List projects. Expected: only X and Y returned. Direct access to Z expected: 404.
    T05
    PII leaks via logs, URLs, or JWT claims
    Critical
    Attack Vector
    Three sub-vectors:
    (a) National ID appears in URL: /owners/search?national_id=123456789. URL ends up in browser history, server access logs, CDN logs, monitoring tools — all unencrypted.
    (b) Pino logger inadvertently logs request body containing phone. Logs ship to Sentry/CloudWatch.
    (c) JWT payload includes "national_id": "..." for convenience. JWTs visible in browser dev tools and logged by middleware.
    Defense Layers
    (a) URL pattern: Search endpoints accept hash, not raw value. Endpoint signature: POST /owners/lookup with body { national_id }, body never in URL. App computes hash, queries by hash.
    (b) Pino redaction: Configured at startup with redact: ['*.national_id', '*.phone', '*.password_hash', 'authorization']. PII never reaches log output.
    (c) JWT claims policy (Section 6.8): Only id, role, active_org_id, session_id. Everything else fetched server-side.
    Test
    Unit test: pino logger configured + call logger.info({ phone: '+972541234567' }). Inspect output. Expected: phone replaced with [REDACTED]. Integration test: hit search endpoint with PII in body. Inspect access logs and Sentry. Expected: no PII in either.
    T06
    Signature lacks identity proof (forged or disputed)
    High
    Attack Vector
    An owner signs a tama 38 contract via the in-app signature flow. Later, they dispute it: "I never signed that. Or: it was signed under duress. Or: it was someone else who entered my credentials." If the signature record contains only the visual blob, we cannot defend the contract.
    Defense Layers
    Multi-fact audit at signature time: Every signatures row captures: signature_blob (visual), document_hash (SHA-256 of the doc bytes at signing time), signer_ip, signer_user_agent, signed_at (server timestamp, not client-supplied), authentication_method (how they logged in), session_id (correlates to their auth audit trail).
    Tamper detection: If the document is modified after signing, document_hash mismatch reveals it.
    Authentication freshness check: Signature flow requires re-authentication if session is older than 30 minutes. Forces fresh identity proof.
    Audit log entry: Separate audit_log row with all signature metadata + correlated session events.
    Test
    Test signature endpoint: create signature, fetch the row, assert all fields populated. Modify document, recompute hash, assert mismatch. Forensic test: given a disputed signature, the audit log should provide a complete timeline of the signer's session.
    T07
    Share permissions cached in UI lead to data exposure after revocation
    High
    Attack Vector
    Manager revokes Contractor's share at 14:00. Contractor's browser still has an active session at 14:05. The frontend caches permissions in memory or localStorage. Contractor continues making API calls, frontend says "you can see X, Y, Z." If the backend doesn't re-check, the Contractor sees stale data.
    Defense Layers
    Backend is the source of truth. Frontend never decides what data to show based on local state. Every request to a project's data triggers resolveShare() server-side, every time.
    Revocation effect is immediate: shares.revoked_at is checked on every request. No in-process cache.
    Stale frontend data: Server returns 403; frontend treats as "session is stale" and redirects to login. The user briefly sees stale data they already had — but cannot fetch new data.
    No client-side authorization: Lint rule forbids importing share permissions for routing decisions. Frontend uses backend responses to decide what to render.
    Test
    Integration test: Create share, give to Contractor, fetch some data with cached share_id. Revoke share. Same request with same token: expected 403. Verify no DB query was made that would return data (the share check fails first).
    T08
    Revoked or departed contractor retains valid token
    High
    Attack Vector
    Contractor's relationship with the Manager ends. Manager clicks "revoke share" — but the Contractor's JWT was issued 20 minutes ago and is valid for another 40 minutes. The Contractor still has all access until the token expires.
    Defense Layers
    Token TTL is short for Contractor (1h): Maximum exposure window is 1 hour. Refresh requires DB check against share status.
    Refresh checks share liveness: The refresh endpoint reloads the share. If revoked_at is set, refresh fails — Contractor cannot extend session.
    Manual revocation flow: If immediate cutoff is needed (suspicious activity), Manager can also click "force logout" which marks the contractor's refresh tokens as revoked. Next API call fails 401.
    Audit: Revocation writes audit row. Force-logout writes audit row.
    Test
    Integration: issue Contractor JWT, revoke share, attempt API call within token TTL window — expected: 403 (share check fails). Attempt refresh — expected: 401 (refresh fails). Force logout — verify refresh token cleared from DB.
    T09
    JSONB share.permissions corruption via injection
    High
    Attack Vector
    Manager creates a share with custom permissions. The request body contains malicious JSON: {"tenants": {"on": true, "fields": {"__proto__": {"admin": true}}, "all_orgs": true}}. If the backend stores the JSONB without validation, attacker-controlled keys end up in the database. If permission-checking code uses unsafe property access, prototype pollution or unintended keys grant unauthorized access.
    Defense Layers
    Zod schema on permissions input: The share creation endpoint validates the permissions JSONB against a strict Zod schema. Schema defines allowed top-level keys (overview, tenants, documents, signatures, notes, team), allowed sub-keys (on, fields, actions), and allowed field/action names. Anything else is rejected at parse time.
    Schema enforcement at read time too: When loading a share from DB, validate the JSONB. If the schema doesn't pass, treat as "no permissions" (default deny) and write an alert. Old corrupt rows fail closed, not open.
    Permission-check function uses explicit keys: No dynamic property access on the permissions object. Code reads permissions.tenants?.fields?.phone explicitly, not permissions[userInputKey].
    Test
    Fuzz test: send malformed permissions JSON to share creation. Expected: 400. Test malicious keys: __proto__, constructor, unexpected booleans. Expected: rejected. Schema drift test: a stored permission row with unknown fields — load it, expect default-deny behavior.
    T10
    Pre-signed file URL leaks or is shared externally
    Medium
    Attack Vector
    User downloads a contract PDF via a pre-signed Cloudflare R2 URL. The URL is valid for 15 minutes. They forward the email containing the URL to a friend. Or: the URL ends up in browser history of a shared computer. The friend opens the URL — and gets the file without authentication.

    Short URL TTL (15 minutes): Reduces exposure window. After 15 minutes, the URL is dead.
    URL generation is authenticated and audited: The endpoint that generates pre-signed URLs requires auth, checks share permissions, writes audit log: "user X downloaded document Y at time Z."
    Single-use option (optional, Phase 2): For highly sensitive documents (signed contracts), generate the URL with a single-use token that becomes invalid after first access.
    No URL caching headers: Server response sets Cache-Control: no-store on the redirect. Browsers don't cache the signed URL.
    Accept residual risk: Pre-signed URL leakage in a 15-minute window is the trade-off for direct R2 downloads (vs proxying through our backend). The risk is bounded; the performance gain is real.
    Test
    Time-based test: generate signed URL, wait 16 minutes, request — expected: R2 returns 403. Audit test: download a document, verify audit_log has entry with user, document, timestamp, IP.

    10 · CROSS-TENANT ISOLATION

    The Most Important Test in the Codebase

    If multi-tenant isolation fails, every other defense becomes irrelevant. This section is the deep-dive on why and how we prove it works.

    When a customer signs up for a multi-tenant SaaS, they make one fundamental assumption: my data is mine, and no other customer can see it. Violating that assumption is the worst kind of bug — not because the code failed, but because the trust contract failed. There is no acceptable rate of cross-tenant data leaks. The answer is zero, always.

    10.1 What "Tenant Isolation" Means

    In our system, "tenant" is the organization entity. A tenant boundary is the line around an organization's data. Inside the boundary: all the org's projects, users, apartments, owners, notes, documents, signatures, tasks. Outside: another organization's everything.

    Tenant isolation means:

    • No read of another org's data. Whether by query, by joining tables, by API endpoint, by anything.
    • No write to another org's data. Inserting a row "belonging" to another org is impossible; updating their rows is impossible.
    • No knowledge of another org's existence. The system shouldn't reveal "this org exists but you can't see it." Cross-tenant access returns 404, not 403.
    • No timing leaks. Querying a row that exists vs doesn't exist shouldn't take measurably different time, lest attackers infer existence.
    • No exception that contains data. Error messages from another org's data shouldn't include identifying information.

    10.2 The Layers Enforcing Isolation

    Multiple layers stack — each can catch what others miss:

    // Cross-tenant defense stack [1] JWT contains active_org_id // Set on login or org-switch; cannot be changed mid-session ▼ [2] Tenant middleware extracts it // Stored in request context, not request body ▼ [3] Service layer uses request context // Never trusts body/query for org_id ▼ [4] withTenant wraps every query // SET LOCAL app.organization_id = <jwt org> ▼ [5] RLS policy on every table // USING (org_id = current_setting('app.organization_id')) ▼ [6] FORCE ROW LEVEL SECURITY // Even the table owner respects the policy ▼ [7] app_user role has no superuser // Cannot DROP POLICY, cannot ALTER TABLE

    An attacker would need to defeat ALL seven layers to extract cross-tenant data. The seventh is structural — they would need direct database admin access, which is the provider tier's territory.

    10.3 The withTenant Pattern in Depth

    This wrapper is the only path to data in the codebase. It's the gate that ensures every query has tenant context:

    packages/db/src/wrappers/with-tenant.ts (complete implementation)
    import { sql } from 'drizzle-orm';
import { Database, pool } from '../client';
import { env } from '../env';

/**
 * Run a database operation in a tenant-scoped transaction.
 *
 * Sets app.organization_id and app.encryption_key for the duration
 * of the transaction. RLS policies and pgcrypto functions read these
 * via current_setting().
 *
 * IMPORTANT: This is the ONLY way to query data in this codebase.
 * Direct use of db.query.* is forbidden by ESLint rule.
 */
export async function withTenant<T>(
  orgId: string,
  fn: (db: Database) => Promise<T>
): Promise<T> {
  // Validate orgId is a UUID — defense against accidentally passing non-UUID
  if (!isUuid(orgId)) {
    throw new Error('withTenant requires a valid UUID orgId');
  }

  return pool.transaction(async (tx) => {
    // SET LOCAL — scoped to this transaction only
    // Cannot leak to other requests via connection pool
    await tx.execute(sql`SET LOCAL app.organization_id = ${orgId}`);

    // Also set encryption key in same context
    await tx.execute(sql`SET LOCAL app.encryption_key = ${env.PII_ENCRYPTION_KEY}`);

    // Execute caller's code with tenant context active
    return fn(tx);
  });
}

    Critical properties:

    • SET LOCAL, not SET. SET would persist across the connection lifetime; in pooled connections, that leaks to the next request. SET LOCAL is transaction-scoped and ends with COMMIT/ROLLBACK.
    • UUID validation at the gate. If orgId isn't a UUID — perhaps it's a string from misparsed request — throw immediately, before any query runs.
    • Transaction wraps everything. If anything in the callback throws, ROLLBACK happens, no partial writes.
    • The function is the only path. No "escape hatch" for "just this once." If you need cross-tenant access, you use withProvider instead — explicitly and audited.

    10.5 The RLS Policy Templates

    RLS is the last line of defense. Even with withTenant in place, the policies must be correct. Three template patterns cover every multi-tenant table:

    Template A: Direct org_id column

    Used for tables that have org_id directly: projects, contractors, tasks, audit_log, notifications.

    RLS template A
    ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
ALTER TABLE projects FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON projects
  USING (org_id = current_setting('app.organization_id', true)::uuid)
  WITH CHECK (org_id = current_setting('app.organization_id', true)::uuid);

    The true in current_setting('app.organization_id', true) means "return NULL if not set." Without it, no setting would cause an error — which we don't want (silent failure of policy is the bad case).

    Template B: Joined org_id via parent

    Used for tables that don't have org_id directly but reach it via a parent: buildings (parent: project), apartments (parent: building → project), owners (parent: apartment), documents, signatures.

    RLS template B
    ALTER TABLE apartments ENABLE ROW LEVEL SECURITY;
ALTER TABLE apartments FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON apartments
  USING (
    project_id IN (
      SELECT id FROM projects
      WHERE org_id = current_setting('app.organization_id', true)::uuid
    )
  )
  WITH CHECK (
    project_id IN (
      SELECT id FROM projects
      WHERE org_id = current_setting('app.organization_id', true)::uuid
    )
  );

    The subquery joins back to projects for the org_id check. Performance note: this adds a join cost per query. We index projects(org_id, id) and apartments(project_id) to keep this fast (sub-1ms).

    Template C: Membership-based (multi-org users)

    Used for users — a user has no org_id directly (they can belong to multiple). The check uses memberships:

    RLS template C
    ALTER TABLE users ENABLE ROW LEVEL SECURITY;
ALTER TABLE users FORCE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON users
  USING (
    EXISTS (
      SELECT 1 FROM memberships
      WHERE memberships.user_id = users.id
        AND memberships.org_id = current_setting('app.organization_id', true)::uuid
    )
  );

    A user is visible if they have a membership in the current org. A user with memberships in orgs A and B would be visible from either org's context — but only the org's own data about them, not the other org's.

    10.6 T1.5: The Critical Test

    T1.5 is the test that proves isolation works. It is the most important test in the entire codebase. Failure of T1.5 in CI must block all deployments, no exceptions.

    packages/db/test/rls-isolation.spec.ts (T1.5 — the canonical test)
    import { describe, it, expect, beforeAll } from 'vitest';
import { sql } from 'drizzle-orm';
import { withTenant, pool } from '../src';
import { createTestOrgWithData } from './factories';

describe('T1.5: RLS isolation across tenants', () => {
  let orgA: TestOrg;
  let orgB: TestOrg;

  beforeAll(async () => {
    orgA = await createTestOrgWithData({ name: 'Org A' });
    orgB = await createTestOrgWithData({ name: 'Org B' });
  });

  it('Scenario 1: SELECT cannot read across tenants', async () => {
    // Read from org A's context, expect only org A's data
    const projectsFromA = await withTenant(orgA.id, async (db) =>
      db.query.projects.findMany()
    );
    expect(projectsFromA).toHaveLength(orgA.projectCount);
    expect(projectsFromA.every((p) => p.orgId === orgA.id)).toBe(true);

    const orgBProjectIds = orgB.projects.map((p) => p.id);
    const spilledProjects = projectsFromA.filter((p) =>
      orgBProjectIds.includes(p.id)
    );
    expect(spilledProjects).toHaveLength(0);
  });

  it('Scenario 2: SELECT by specific ID returns 0 rows for cross-tenant', async () => {
    const orgBProjectId = orgB.projects[0].id;

    // Try to read org B's project from org A's context
    const result = await withTenant(orgA.id, async (db) =>
      db.query.projects.findFirst({ where: eq(projects.id, orgBProjectId) })
    );
    expect(result).toBeUndefined();
  });

  it('Scenario 3: INSERT into another org fails', async () => {
    // Try to insert a project belonging to org B while in org A context
    await expect(
      withTenant(orgA.id, async (db) =>
        db.insert(projects).values({
          orgId: orgB.id,  // Different org!
          name: 'Malicious cross-tenant project',
          type: 'tama38_1',
        })
      )
    ).rejects.toThrow();  // WITH CHECK clause blocks
  });

  it('Scenario 4: UPDATE of another org row is no-op', async () => {
    const orgBProjectId = orgB.projects[0].id;

    // Try to update org B's project from org A's context
    const result = await withTenant(orgA.id, async (db) =>
      db
        .update(projects)
        .set({ name: 'Hijacked' })
        .where(eq(projects.id, orgBProjectId))
        .returning()
    );
    expect(result).toHaveLength(0);  // No rows affected

    // Verify org B's project is unchanged
    const stillIntact = await withTenant(orgB.id, async (db) =>
      db.query.projects.findFirst({ where: eq(projects.id, orgBProjectId) })
    );
    expect(stillIntact?.name).not.toBe('Hijacked');
  });

  it('Scenario 5: DELETE of another org row is no-op', async () => {
    const orgBProjectId = orgB.projects[0].id;

    const result = await withTenant(orgA.id, async (db) =>
      db.delete(projects).where(eq(projects.id, orgBProjectId)).returning()
    );
    expect(result).toHaveLength(0);

    // Verify still exists
    const stillExists = await withTenant(orgB.id, async (db) =>
      db.query.projects.findFirst({ where: eq(projects.id, orgBProjectId) })
    );
    expect(stillExists).toBeDefined();
  });

  it('Scenario 6: No tenant context returns 0 rows', async () => {
    // Raw query without withTenant (simulating a bug)
    const result = await pool.execute(sql`SELECT * FROM projects`);
    expect(result.rows).toHaveLength(0);
  });

  it('Scenario 7: Multi-org user only sees current org context', async () => {
    // Create a user with memberships in both org A and org B
    const multiOrgUser = await createMultiOrgUser(orgA, orgB);

    // From org A's context: user is visible
    const fromA = await withTenant(orgA.id, async (db) =>
      db.query.users.findFirst({ where: eq(users.id, multiOrgUser.id) })
    );
    expect(fromA).toBeDefined();

    // From org B's context: user is also visible
    const fromB = await withTenant(orgB.id, async (db) =>
      db.query.users.findFirst({ where: eq(users.id, multiOrgUser.id) })
    );
    expect(fromB).toBeDefined();

    // But from a third org: not visible
    const orgC = await createTestOrgWithData({ name: 'Org C' });
    const fromC = await withTenant(orgC.id, async (db) =>
      db.query.users.findFirst({ where: eq(users.id, multiOrgUser.id) })
    );
    expect(fromC).toBeUndefined();
  });
});

    10.7 The Test Failure Protocol

    If T1.5 fails in CI:

    1. STOP all deployments. No code reaches staging or production until T1.5 passes.
    2. The PR that broke it is reverted. No "we'll fix it forward" — the previous green state is restored.
    3. Root cause investigated. Which change introduced the failure? Was it RLS policy, withTenant change, schema change, ESLint exception?
    4. The failing test is fixed. Not removed, not skipped — actually fixed.
    5. Postmortem written. Why did this almost reach production? What additional check could prevent it next time? Added to learnings.md.

    10.8 What Could Make T1.5 Pass Falsely

    A test that passes incorrectly is worse than a test that fails. Things that could give us false confidence in T1.5:

    • Test runs against a DB without RLS enabled. Mitigation: setup script explicitly verifies SELECT relrowsecurity FROM pg_class WHERE relname = 'projects' returns true before running.
    • Test creates both orgs but only adds data to org A. Mitigation: factories create symmetric data — every assertion that "org A sees N rows" has a parallel "org B sees M rows."
    • RLS policies use the wrong session variable name. Mitigation: integration test asserts that the variable name matches between policy DDL and withTenant code.
    • Test runs as superuser, which bypasses RLS. Mitigation: tests use app_user role explicitly, not the connection-string default.
    • FORCE is missing on some tables. Mitigation: separate assertion test that every multi-tenant table has both relrowsecurity and relforcerowsecurity set.

    Every RLS policy adds query overhead. Every withTenant wrapper adds a SET LOCAL. We track the cost:

    10.11 The Trust Argument

    Multi-tenant isolation is not "a feature." It is the entire reason customers can use a shared SaaS platform without owning their own server. When a customer signs up, they accept that their data lives next to their competitors' data — separated only by software.

    That separation must be technically real, not merely promised. The customer cannot inspect our code, but they can demand evidence that isolation works. T1.5 in CI, the seven-layer defense stack, the FORCE policies — these are the evidence. When a customer's security team asks "how do you guarantee my data is mine?", we point at this section and at the test suite. The argument is concrete.

    ⚠ The non-negotiable
    Of all the principles in this document, tenant isolation is the one with zero tolerance. A 3% slowdown to enforce it: acceptable. A complex code path to enforce it: acceptable. A schema migration to enforce it: acceptable. One missing FORCE on one table: not acceptable. One service that bypasses withTenant: not acceptable. There is no "edge case where it's OK." If isolation breaks, every other promise we make to customers breaks with it.

    11.7 Transaction Rollback Tests (T1.9)

    If anything throws inside withTenant or withProvider, the whole transaction must rollback. Otherwise we get partial writes — which can leak data or corrupt state:

    • Insert + throw → no row. withTenant inserts a project; immediately throws; verify no project row exists.
    • Update + throw → original value preserved. Update apartment.status; throw; verify status unchanged.
    • Audit on rollback. For withProvider: audit row inserted before fn() — when fn() throws, audit row still exists (committed via the same TX? or recorded as failed attempt?). Implementation: audit is part of the same transaction, so rollback also rolls back audit. The failed attempt is captured by Sentry, not by audit.

    11.11 What Tests Cannot Catch

    Some failure modes survive testing. We document them so we know what other defenses must catch them:

    • Business logic bugs. "Manager can revoke shares" — what if a Manager revokes their own share to themselves? Test the specific cases you can think of; some you can't.
    • Race conditions in concurrent updates. Tests run sequentially; production has many concurrent users. Mitigation: database constraints (UNIQUE, CHECK) catch many races; explicit locking where needed.
    • Time-based attacks. Tests run with mocked clocks. Real-world timing attacks (e.g., comparing hash duration) need production monitoring.
    • Third-party dependency vulnerabilities. npm audit catches known CVEs; novel vulnerabilities are missed.
    • Social engineering. No technical test catches "an attacker called the Manager and asked for the password."
    • Insider threats. Provider Admins are trusted by definition; audit catches misuse after the fact, not during.
    💡 Tests as living documentation
    When a test breaks, that's often the first signal of a real bug — not always a flaky test. Resist the temptation to "fix the test." First understand: what changed in the code that made the test fail? If the code is wrong, fix the code. If the test was wrong, fix the test — but understand why it was wrong, and update other tests with the same flaw.
    12 · AUDIT LOG STRATEGY

    The Permanent Record

    Every meaningful action gets recorded. The log is append-only, queryable, and authoritative.

    An audit log answers questions that nothing else can: "who did what when, and why?" It is the basis of trust between us and our customers — and the basis of accountability between EMAPP team members. If it's not in the audit log, it didn't happen. If we cannot answer who did something, we have an integrity problem.

    12.1 The Two Audit Logs

    We maintain two separate audit log tables for different concerns:

    TableScopeWho writesWho reads
    audit_logOrganization-scoped actionsAll app users (via service code)Manager of their org, Provider tier
    provider_audit_logProvider tier actionsProvider tier (via withProvider)Provider tier only (read-only after write)

    Separation matters: customer-facing audit (audit_log) is shared with customers on request. Provider audit (provider_audit_log) is internal — what EMAPP team did, for our own accountability. Mixing them would expose internal operations to customers.

    12.2 What Gets Logged to audit_log

    The principle: any action that changes meaningful state, plus reads of sensitive data. Not every API call — that's a load problem. But every state change matters.

    • Authentication events. Login success/failure, password change, MFA enrollment/disable, magic link issued/consumed, OTP request/verify, forced logout.
    • Authorization changes. Share created/updated/revoked, member added/removed from org, role changed.
    • Resource lifecycle. Project created/archived, building added, apartment status changed, owner added/removed/updated.
    • Document/signature events. Document uploaded/downloaded/deleted, signature created.
    • Sensitive reads. Owner's national_id decrypted (rare but happens — usually for export). Bulk export of any kind.
    • Notes and tasks. Note added, task assigned, task completed.
    • Administrative. Settings changes, integrations enabled/disabled.

    12.3 What Is NOT Logged

    • Routine reads. Listing projects, viewing apartments, scrolling notes — too high volume, too little signal.
    • UI interactions. Clicks, scrolls, page views — that's product analytics, not audit.
    • Background system actions. Auto-archive of old projects via cron — logged in system logs, not audit_log.
    • Failed requests due to validation. 400-level errors from typos in form data — captured in Sentry, not audit.

    12.4 The audit_log Schema

    audit_log table
    CREATE TABLE audit_log (
  id              UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  org_id          UUID NOT NULL REFERENCES organizations(id),
  actor_id        UUID,                    // users.id (null for system actions)
  actor_type      TEXT NOT NULL,             // 'user' | 'system' | 'provider'
  actor_email     TEXT,                    // denormalized — email at time of action
  action          TEXT NOT NULL,             // e.g., 'project.created', 'share.revoked'
  target_table    TEXT,                    // e.g., 'projects', 'shares'
  target_id       UUID,                    // the affected row's id
  before_state    JSONB,                   // snapshot of relevant fields before
  after_state     JSONB,                   // snapshot after (null for read events)
  ip              INET,
  user_agent      TEXT,
  session_id      UUID,                    // for correlation across multiple actions
  metadata        JSONB,                   // extra context (reason, source, etc.)
  created_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Indexes for the common query patterns
CREATE INDEX idx_audit_org_time ON audit_log(org_id, created_at DESC);
CREATE INDEX idx_audit_actor ON audit_log(actor_id, created_at DESC);
CREATE INDEX idx_audit_target ON audit_log(target_table, target_id);

-- Append-only at DB level: app_user role gets INSERT and SELECT, but NOT UPDATE or DELETE
GRANT INSERT, SELECT ON audit_log TO app_user;
REVOKE UPDATE, DELETE ON audit_log FROM app_user;

    12.5 The Audit Helper

    Service code writes to audit through a helper, never directly:

    packages/db/src/audit/audit.service.ts
    export class AuditService {
  async log(entry: AuditEntry, db: Database): Promise<void> {
    const context = getCurrentRequestContext();

    await db.insert(auditLog).values({
      orgId: entry.orgId,
      actorId: context.userId ?? null,
      actorType: context.actorType,         // 'user' | 'system' | 'provider'
      actorEmail: context.userEmail,
      action: entry.action,                  // e.g., 'share.created'
      targetTable: entry.targetTable,
      targetId: entry.targetId,
      beforeState: entry.before ?? null,
      afterState: entry.after ?? null,
      ip: context.ip,
      userAgent: context.userAgent,
      sessionId: context.sessionId,
      metadata: entry.metadata ?? {},
    });
  }
}

    Services call this within their existing withTenant transaction. The audit row is part of the same transaction as the state change, so they commit (or rollback) together. You can't have a state change without its audit entry — and you can't have an audit entry of a state that didn't change.

    12.6 The Action Naming Convention

    The action field follows a consistent resource.verb pattern:

    ResourceVerbs
    projectcreated, updated, archived, restored
    apartmentcreated, status_changed, archived
    owneradded, updated, removed
    noteadded
    documentuploaded, downloaded, deleted
    signaturecreated, verified
    sharecreated, updated, revoked
    authlogin_success, login_failed, password_changed, mfa_enrolled, magic_link_sent, magic_link_consumed, logout
    memberadded, removed, role_changed
    taskcreated, assigned, completed

    Consistent naming makes audit log queryable. "Show me all share revocations in the last month" becomes WHERE action = 'share.revoked'. Inconsistent naming (some entries "share_revoked", some "ShareRevoked", some "RevokeShare") makes the log useless.

    12.7 The before/after Snapshot Strategy

    For state-change actions, we capture relevant fields before and after. Not every field — that's wasteful. Just what matters:

    Example: share update
    {
  "action": "share.updated",
  "target_table": "shares",
  "target_id": "sha_01H...",
  "before_state": {
    "permissions": { /* old JSONB */ },
    "revoked_at": null
  },
  "after_state": {
    "permissions": { /* new JSONB */ },
    "revoked_at": null
  },
  "metadata": { "changed_by": "manager_email" }
}

    The snapshot includes only fields that change for that action type. For "share.updated", it's permissions and revoked_at. For "apartment.status_changed", it's just status. Keeping snapshots minimal prevents audit log bloat.

    12.8 Querying the Audit Log

    Common queries we support:

    Sample audit queries
    -- Who changed share X recently?
SELECT created_at, actor_email, action, before_state, after_state
FROM audit_log
WHERE target_table = 'shares' AND target_id = 'sha_01H...'
ORDER BY created_at DESC
LIMIT 20;

-- All actions by user X this week
SELECT created_at, action, target_table, target_id
FROM audit_log
WHERE actor_id = 'usr_01H...'
  AND created_at >= NOW() - INTERVAL '7 days'
ORDER BY created_at DESC;

-- Failed login attempts from same IP in last hour
SELECT created_at, actor_email, ip
FROM audit_log
WHERE action = 'auth.login_failed'
  AND created_at >= NOW() - INTERVAL '1 hour'
  AND ip = '1.2.3.4'
ORDER BY created_at;

-- Show me all share revocations in the last month for this org
SELECT created_at, actor_email, target_id, metadata
FROM audit_log
WHERE org_id = 'org_01H...'
  AND action = 'share.revoked'
  AND created_at >= NOW() - INTERVAL '30 days'
ORDER BY created_at DESC;

    12.9 Audit Log Retention

    Audit logs grow forever if we don't manage retention. The strategy:

    • MVP: keep all forever. Volume is small (~1K rows/day per org). At 100 orgs, ~100K rows/day = ~36M rows/year. Postgres handles this trivially with good indexes.
    • At scale (1000+ orgs): tiered retention. Recent 90 days in hot table; older moved to audit_log_archive partition. Same schema, slower queries acceptable for historical lookups.
    • Authentication events: longer retention. auth.* events kept indefinitely — they're small and forensically valuable.
    • Read events (sensitive decrypts): permanent retention. The fact that someone decrypted PII is itself important historical record.
    • No deletion on user request. Audit log is legally significant — we don't honor "right to be forgotten" requests for audit data. Customer is informed of this in TOS.

    12.10 The Append-Only Guarantee

    An audit log that can be modified is worse than no audit log — it gives false confidence. We make modification impossible at the database level:

    • app_user role lacks UPDATE/DELETE on audit_log. Even with full app-level access, the role cannot modify rows.
    • provider_app_role lacks UPDATE/DELETE on provider_audit_log. Same protection for provider tier.
    • No "edit" UI. The system doesn't expose any way to modify audit entries.
    • Schema migrations can technically modify audit. This is the only path. Documented as a sensitive operation requiring two-person approval.

    12.11 Customer Access to Audit Log

    Customers can see their own org's audit log:

    • Manager UI (Phase 2). "Activity" page shows recent audit entries for the org, filtered to non-sensitive events (no decrypt events shown to customer).
    • Export endpoint. Manager can request CSV export of their org's audit log for compliance reporting.
    • Customer support requests. "Who changed this?" — Manager-initiated; we respond within 48h with the audit trail.
    • Self-service forensics. Manager can answer "is this user logging in from unusual IPs?" via the audit view.

    12.12 Performance Considerations

    Audit writes are on the hot path — every state change includes one INSERT to audit_log. We optimize:

    ConcernOptimization
    Write latencyAudit INSERT runs in the same TX as the action — adds ~0.5ms, no additional round trip
    Index bloatThree targeted indexes (org_time, actor, target) cover all common queries without over-indexing
    JSONB sizebefore/after limited to changed fields; metadata under 1KB typical
    Read performanceQueries always include org_id (RLS enforced); index (org_id, created_at DESC) makes recent-N queries fast
    Bulk insertSystem actions (audit batching) use batch insert during off-peak
    ✓ The accountability foundation
    The audit log is not bureaucratic overhead. It is the single mechanism by which we can answer questions of accountability — to customers, to ourselves, to regulators. When something goes wrong (and it will), the audit log determines whether we can explain what happened. Build it well, fill it consistently, and never delete from it.
    13 · INCIDENT RESPONSE

    When Something Goes Wrong

    Incidents will happen. Preparation determines whether they become catastrophes or recoverable events.

    No security system is perfect. Eventually — through a vulnerability, a misconfiguration, a compromised credential, a successful phishing attack — something will go wrong. The question is not whether, but when, and how prepared we are. This section is the playbook for incidents: how to recognize them, contain them, recover from them, and learn from them. It is designed to be read in advance, used in panic.

    13.1 Severity Classification

    Not every incident is a five-alarm fire. We classify into four severity levels:

    SeverityExamplesResponse time
    SEV-1 CatastrophicConfirmed cross-tenant data leak, customer PII publicly exposed, production database breachImmediate, all hands
    SEV-2 CriticalCompromised provider admin account, signed-contract integrity broken, encryption key leakedWithin 1 hour
    SEV-3 HighSingle user account compromised, partial service outage, suspicious access patternsWithin 24 hours
    SEV-4 ModerateFailed CI security test, dependency vulnerability disclosed, audit log anomalyWithin 1 week

    13.2 The Incident Response Steps

    Five phases. In order. Don't skip — even under pressure:

  • Detect. Recognize that an incident exists. Sources: monitoring alerts, customer reports, internal observation, security researcher disclosure, news.
  • Triage. Quickly assess: is it real? What's the severity? What's the immediate risk? Decide who needs to act.
  • Contain. Stop the bleeding. Disable compromised accounts, revoke leaked tokens, block suspicious IPs, take service offline if necessary.
  • Eradicate. Remove the cause. Patch the vulnerability, rotate the credentials, fix the misconfiguration, deploy the corrected code.
  • Recover & Learn. Restore normal operation. Inform affected customers. Write postmortem. Add the lesson to learnings.md and to this document.

    • 13.3 SEV-1 Checklist: Suspected Cross-Tenant Data Leak

    The worst case. Customer data may have been seen by another customer. Steps in order:

    SEV-1 response — first 60 minutes
    [ ] 0:00  — Confirm or deny
       Reproduce the issue. Is data actually crossing tenants?

[ ] 0:05  — Take defensive action

       Unacceptable: leave the leak open while perfecting a fix.

       Which other customers accessed (potentially saw)?

[ ] 0:30  — Preserve evidence
       Snapshot relevant audit_log rows.
       Snapshot relevant provider_audit_log rows.
       Save Sentry events.
       Save Railway logs.

[ ] 0:45  — Plan customer communication
       Draft message: what happened, what was exposed, what we're doing.
       Identify the affected customers (Managers of leaked orgs).
       Identify the customers who accessed others' data (also affected — legally complex).

[ ] 1:00  — Deploy permanent fix + communicate
       Replace temporary block with the real fix.
       Send communications to affected customers.
       Brief Provider team.

    13.4 SEV-2 Checklist: Compromised Provider Admin

    An EMAPP team member's account was compromised. The attacker may have cross-tenant access. Steps:

    SEV-2 response — compromised Provider Admin
    [ ] 0:00  — Disable the compromised account
       UPDATE provider_users SET disabled_at = NOW() WHERE id = ...;
       Invalidate all refresh tokens for this user.
       The compromised session, if any, can no longer refresh.

[ ] 0:05  — Rotate provider credentials
       If multiple admins shared infrastructure access: rotate everything.
       Generate new MFA secrets if MFA app may have been compromised.

       SELECT * FROM provider_audit_log

    13.5 SEV-2 Checklist: Encryption Key Leaked

    The PII_ENCRYPTION_KEY or PII_HASH_KEY is exposed (e.g., in a public commit, in CI logs, on a developer's compromised laptop). All encrypted PII is at risk:

    SEV-2 response — encryption key leak
    [ ] 0:00  — Confirm the leak
       Verify the key is actually exposed.
       Check if it's the dev key or production key.

[ ] 0:05  — Generate new keys
       openssl rand -base64 32  # encryption key
       openssl rand -base64 32  # HMAC key
       Store in Railway secrets manager.

[ ] 0:10  — Begin key rotation
       Procedure in Section 14.
       Cannot do this instantly — re-encrypting all PII takes time.

[ ] 0:30  — Deploy double-key reading window
       App can decrypt with OLD or NEW key.
       New writes use NEW key.
       This minimizes service disruption during rotation.

[ ] 1:00 - 24:00  — Background re-encryption
       Worker process re-encrypts all rows.
       Use OLD key to decrypt, NEW key to encrypt.
       Update HMAC hash with NEW HMAC key.

[ ] 24:00+  — Remove OLD key support
       After all data re-encrypted: remove OLD key from app.
       OLD key is now useless (data no longer encrypted with it).
       Document: who had access to OLD key during exposure window?

[ ] Post-incident
       How did the key leak?
       Add detection rule (e.g., gitleaks check key patterns).
       Train team on secret handling.

    13.6 SEV-3 Checklist: Single User Account Compromised

    A Manager's password was leaked. Attacker has access to their org but not cross-org:

    SEV-3 response — compromised user account
    [ ] 0:00  — Confirm via affected user
       Call/email user, confirm: "did you log in from X at time Y?"

[ ] 0:05  — Force logout + password reset

       Send forced password reset link.

       Working with the customer Manager, identify and revert.

[ ] 1:00  — Update related controls if pattern
       Is this user one of many? IP geolocation suggests breach campaign?
       If yes: escalate to SEV-2.

    13.7 SEV-4 Checklist: Failed Security Test in CI

    T1.5 or related test failed in a PR. This is the cheapest incident — caught before deploy:

    SEV-4 response — failed CI security test
    [ ] 0:00  — Block the deploy
       PR cannot merge. CI is blocking.

[ ] 0:15  — Investigate

[ ] 0:30  — Decide:

    13.10 The Blameless Principle

    Postmortems are about systems, not people. Even if "a developer forgot withTenant," the question is: why does our system allow that mistake to reach production?

    • If code review missed it → add it to the checklist.
    • If the test didn't catch it → add a test that does.
    • If documentation was unclear → update this document.

    The developer who made the mistake is the one who knows best how to prevent it next time. Blaming them removes that knowledge from the team.

    14 · SECRET ROTATION

    Keys Get Rotated, Not Forgotten

    A secret that lives forever is a secret that eventually leaks. Rotation is part of operating, not a fire drill.

    Every secret in this system has a rotation procedure. Some rotations are scheduled — done as routine hygiene. Others are emergency — triggered by suspected compromise. The procedures differ in tempo, but not in care. The wrong rotation can take down production. The right rotation is invisible to customers.

    14.3 The PII_ENCRYPTION_KEY Rotation (Hardest Case)

    This is the most expensive rotation because all encrypted data must be re-encrypted. The procedure:

    PII_ENCRYPTION_KEY rotation procedure
    // PRE-WORK: Schedule a maintenance window. Notify on status page.
// Estimated time: 1-6 hours depending on DB size.

[ ] Step 1: Generate the new key
       NEW_KEY=$(openssl rand -base64 32)
       Store NEW_KEY in a password manager temporarily.

[ ] Step 2: Add the new key as a SECOND env var
       Railway env: PII_ENCRYPTION_KEY=<old>  (unchanged)
       Railway env: PII_ENCRYPTION_KEY_NEW=<new>  (added)
       Deploy: app now has access to both keys.

[ ] Step 3: Deploy app version that reads both keys
       withTenant sets both:
         SET LOCAL app.encryption_key = <OLD>
         SET LOCAL app.encryption_key_new = <NEW>
       Decryption: try NEW key first, fall back to OLD.
       Encryption (for writes): use NEW key.

[ ] Step 4: Run re-encryption job
       Background worker reads rows in batches:
         FOR each row WHERE encrypted_with_key_version = 'old':
           plaintext = pgp_sym_decrypt(encrypted, OLD)
           encrypted_new = pgp_sym_encrypt(plaintext, NEW)
           UPDATE row SET encrypted = encrypted_new, key_version = 'new'
       Use small batches (100 rows) with COMMIT between.
       Monitor: rows_remaining metric in Sentry.

[ ] Step 5: Verify completion
       SELECT COUNT(*) FROM owners WHERE key_version = 'old';
       Expected: 0.
       If non-zero: investigate before proceeding.

[ ] Step 6: Remove the OLD key
       Railway env: PII_ENCRYPTION_KEY=<new>  (was OLD, now NEW value)
       Railway env: PII_ENCRYPTION_KEY_NEW=<remove>
       Deploy.
       App no longer references OLD key.

[ ] Step 7: Confirm production is stable
       Smoke test: create new owner with PII, read it back.
       Check Sentry for decryption errors.

[ ] Step 8: Destroy the OLD key
       Remove from password manager.
       Document in audit: "PII_ENCRYPTION_KEY rotated on YYYY-MM-DD"

    Key properties of this procedure:

    • No downtime. The double-key window allows reads and writes during re-encryption.
    • Rollback-friendly. If something goes wrong before step 6, the OLD key is still available.
    • Progress is visible. Step 5's count query shows exactly where re-encryption stands.
    • Idempotent batches. If a batch fails, it can be re-run safely. key_version column tracks state.

    14.4 The PII_HASH_KEY Rotation

    Slightly different from encryption key: HMAC hashes are deterministic, so rotating the hash key invalidates all existing hashes. The procedure mirrors PII_ENCRYPTION_KEY:

    PII_HASH_KEY rotation procedure
    [ ] Step 1: Generate new HMAC key
       NEW_HASH_KEY=$(openssl rand -base64 32)

[ ] Step 2: Deploy app with both keys available
       Search by national_id:
         hash_old = HMAC(input, OLD_KEY)
         hash_new = HMAC(input, NEW_KEY)
         query: WHERE national_id_hash IN (hash_old, hash_new)

[ ] Step 3: Re-hash in background
       FOR each row:
         plaintext = pgp_sym_decrypt(encrypted, encryption_key)
         new_hash = HMAC(plaintext, NEW_HASH_KEY)
         UPDATE row SET national_id_hash = new_hash
       Indexes rebuild as hashes change. Monitor index bloat.

[ ] Step 4: Switch to NEW only after verification
       Same step-6/7/8 pattern as encryption key.

    Performance impact: during the rotation window, every search by hash queries with two values (old and new). This is roughly 2× the cost of a normal search. Not catastrophic but worth noting.

    14.5 The JWT_SIGNING_KEY Rotation

    Rotating the JWT signing key invalidates all existing tokens. Users must re-login. Less catastrophic than data re-encryption but disruptive:

    JWT_SIGNING_KEY rotation procedure
    // Option A: Hard rotation (forces all logout, simplest)
[ ] Generate new key.
[ ] Replace env var.
[ ] Deploy.
[ ] All users get 401 on next request → forced login.
[ ] Communicate via in-app banner: "Please log in again — security update."

// Option B: Graceful rotation (zero-disruption window)
[ ] Deploy app version that signs with NEW, verifies with OLD or NEW.
[ ] Wait for existing tokens to expire (max 30 days for refresh).
[ ] After 30 days, remove OLD verification capability.
[ ] All tokens now signed and verified with NEW only.

    For MVP: Option A is fine. The disruption is brief and acceptable. For mature production: Option B is friendlier to active users.

    Easiest case. Both Neon (the DB) and Railway (the app) support seamless rotation:

    DATABASE_URL rotation procedure
    [ ] In Neon dashboard: generate new password for app_user role.
       Old password remains valid for grace period (Neon's behavior).

    14.7 R2 + Resend Key Rotation

    14.9 The Detection Mechanisms for Compromise

    How do we know a secret might be compromised? Multiple sources:

    • GitHub secret scanning. If a key is accidentally committed, GitHub detects common patterns (AWS keys, etc.) and alerts. Configure repo-level alerts.
    • Gitleaks pre-commit hook. Catches secrets before they reach git. Configured in .husky/pre-commit.
    • CI log scrubbing. CI runs use masked env vars; failed builds shouldn't print secrets. Periodically audit CI logs for accidental exposure.
    • Sentry data scrubbing. Sentry config drops fields matching *_KEY, *_SECRET, etc. — even if accidentally logged.
    • Provider notifications. Cloudflare, Resend, etc. send alerts on suspicious API usage patterns.
    • Audit log monitoring. Unusual access patterns to high-sensitivity endpoints can suggest compromise.
    • Customer reports. Sometimes the first signal is a customer noticing something wrong.

    14.10 Documentation of Rotation Events

    Every rotation is logged. The log answers: "When was this key last rotated? By whom? Why?"

    Rotation log format (kept in repo as docs/security/rotations.md)

| Date | Secret | Reason | Rotated by | Next due |
|------|--------|--------|------------|----------|
| 2026-09-15 | JWT_SIGNING_KEY | Scheduled (annual) | Dev1 | 2027-09-15 |

    This log lives in the repo (not in audit_log) — it's a runbook artifact, not a customer-facing record.

    14.11 What Rotation Doesn't Fix

    Rotating a secret stops future use of the old secret. It doesn't undo damage from past use:

    • If PII was decrypted with the leaked key — data is exposed already; rotation prevents further exposure but not past.
    • If sessions were created with the leaked JWT key — tokens issued before rotation are still valid until expiry. To kill them, also revoke refresh tokens.
    • If R2 was accessed with the leaked key — files copied during the exposure window are out. Rotation prevents future access.

    This is why incident response (Section 13) goes beyond rotation: containment, customer communication, forensics. Rotation is one step among many.

    ⚠ The two-person rule for production secrets
    For production secret rotation (especially PII_ENCRYPTION_KEY): two team members are involved. One executes; the other observes and verifies. This catches mistakes (wrong env var name, wrong environment, copy-paste of old value) before they cause an outage. The friction is worth the safety. For staging and dev — one person is fine.
    15 · PRODUCTION CHECKLIST

    The Final Gate Before Customer Data Goes Live

    Before any organization's real data enters production, this list is verified. No exceptions.

    This is the last checkpoint between development and customer trust. Every item below must be ticked — verified, not assumed. Some items are obvious; some are subtle. All matter. If anything on this list is not done, customer data does not go live.

    15.1 Infrastructure Checklist

    • Neon Postgres production project created (separate from dev/staging)
    • Neon region set to closest available to Israel
    • Point-in-time recovery enabled (Neon Launch tier or above)
    • Railway production environment created (separate from staging)
    • Cloudflare R2 production bucket created (separate from dev)
    • R2 bucket has public access disabled
    • Cloudflare Pages production project linked to main branch
    • Custom domain configured with valid SSL certificate
    • DNS records: CAA records limit which CAs can issue certs for the domain
    • Cloudflare DDoS protection enabled
    • Cloudflare WAF rules configured (free tier or Pro)
    • Resend domain verified (SPF, DKIM, DMARC configured)
    • Sentry production project created
    • All secrets stored in Railway environment variables — never in code or repo

    15.2 Database Checklist

    • All migrations applied to production DB
    • All multi-tenant tables have RLS enabled (relrowsecurity = true)
    • All multi-tenant tables have FORCE row level security (relforcerowsecurity = true)
    • RLS policies present on every multi-tenant table (test with system table query)
    • app_user role created with appropriate permissions (no superuser, no DROP)
    • provider_app_role created separately with audit-related permissions
    • app_user has INSERT/SELECT on audit_log but NOT UPDATE/DELETE
    • provider_app_role has INSERT/SELECT on provider_audit_log but NOT UPDATE/DELETE
    • pgcrypto extension installed and tested
    • All indexes present (especially on org_id columns and hash lookup columns)
    • Connection pool configured with transaction-mode pooling
    • Connection limits set: ~50 connections per service (Neon Launch supports 100-200)

    15.3 Application Checklist

    • withTenant wrapper is the only data access path (verified by ESLint rule passing in CI)
    • withProvider wrapper handles cross-tenant access; requires reason parameter
    • All endpoints have @Roles decorator (or are explicitly public)
    • All request bodies validated by Zod schemas
    • All response bodies pass through serializers that respect share permissions
    • Hidden fields are absent from responses, not null
    • JWT signing key is production-grade (32 bytes random, not a placeholder)
    • JWT access token TTL: 1h for users, 30min for Provider
    • JWT contains no PII (verified by inspecting decoded production JWT)
    • Refresh tokens are opaque and stored in DB with rotation logic
    • Pino logger configured with PII redaction
    • Helmet middleware active with strict CSP
    • CORS configured with explicit allowlist (not wildcard)
    • Rate limiting active on auth endpoints, registration, password reset
    • File upload size limited at presigned-URL generation
    • Pre-signed URL TTL is 15 minutes max

    15.4 Authentication Checklist

    • bcrypt cost 12 configured (Better Auth default verified)
    • Minimum password length 12 enforced (14 for Provider)
    • Password reset flow tested end-to-end
    • Magic link flow tested with single-use enforcement
    • Magic link tokens stored as SHA-256 hashes (not plaintext)
    • Account lockout after 5 failed attempts in 15 minutes
    • Lockout is time-based (15 min), not permanent
    • Failed login attempts written to audit_log
    • MFA TOTP working for Provider Admin (mandatory)
    • MFA recovery codes generated and stored hashed
    • Session refresh rotates both access and refresh tokens
    • Forced logout endpoint works (revokes refresh tokens)
    • Provider Admin session TTL is 30 min access, 4h refresh

    15.5 Encryption Checklist

    • PII_ENCRYPTION_KEY generated with openssl rand -base64 32
    • PII_HASH_KEY generated separately (not the same value as encryption key)
    • Both keys stored in Railway secrets manager (not in code, not in repo)
    • Encryption keys differ between dev, staging, production
    • Production encryption keys never shared via email, chat, or screen-shared sessions
    • T3-env validates encryption keys are present at startup (app fails to start without them)
    • Test: encrypt a value, decrypt, expect original (T1.8)
    • Test: encrypted column in DB contains binary, not plaintext
    • Test: HMAC hash is deterministic for same input
    • Rotation calendar configured (PII keys every 24 months, others annual)

    15.11 The Final Approval

    Before flipping the production switch:

    1. Both developers sign off. Each verifies they've personally checked their assigned sections.
    2. Pilot customer briefed. They know they're pilot, they know what works and what doesn't, they have a direct line to us.
    3. First 48 hours have someone watching. Not 24/7 stare, but checking Sentry / audit logs / customer messages multiple times daily.
    4. Rollback plan documented. If something is catastrophically wrong, what's the path back? (Usually: revert deployment, restore DB from point-in-time backup, notify customer.)
    5. Date stamped on this checklist. Save a copy of the completed checklist in the repo under docs/security/launches/<date>-launch.md.

    15.12 What This Checklist Is Not

    This checklist verifies a baseline. It is not a guarantee:

    • It does not catch novel attack patterns.
    • It does not replace ongoing security work.
    • It does not certify compliance with any specific framework (SOC 2, ISO 27001) — those have their own checklists, more extensive.
    • It does not eliminate risk — only reduces known risks to acceptable levels.

    The checklist is the floor, not the ceiling. After launch: monitor, learn, expand.

    ✓ The discipline of pre-flight
    Pilots don't take off without running through their pre-flight checklist — even though they've done it hundreds of times. The reason isn't doubt; it's discipline. The cost of going through the list is low. The cost of forgetting one item could be catastrophic. This is the same discipline applied to launching customer-facing software. Every launch — even the small ones — goes through this list.
    ⚠ One last reminder
    Of everything in this document, one principle stands above all others: tenant isolation has zero tolerance for failure. Every other control can be improved iteratively. T1.5 cannot. If any item in this checklist is uncertain, that's a yellow light — proceed with caution. If T1.5 is uncertain, it's a red light — stop. Customer trust is rebuilt over years and broken in seconds. The list exists to make sure the second never happens.
