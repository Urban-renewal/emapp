המערכת ב-30 שניות

תמונה כללית של מה המערכת עושה, איך היא בנויה, ועם מה היא מתחברת.

EMAPP · URBAN RENEWAL SAAS
B2B SaaS לחברות התחדשות עירונית בישראל
מערכת לניהול פרויקטי תמ"א 38, פינוי-בינוי, וחיזוק מבנים — מהפגישה הראשונה עם בעלי הדירות ועד החתימה הסופית על החוזה. המערכת מנהלת את הפרויקטים, הדיירים, האחוזי בעלות, החתימות, המסמכים, השיתופים עם קבלנים, וקלנדר העבודה של הצוות.

1.1 מה המערכת עושה

EMAPP היא מערכת SaaS שמכוונת לחברות התחדשות עירונית בישראל. החברות הללו מנהלות פרויקטים מורכבים: עשרות בעלי דירות בכל בניין, אחוזי בעלות מסובכים, חוזים שדורשים רוב חתימות (לרוב 67% או 80%), שיתוף פעולה עם קבלנים חיצוניים, ותהליכים ארוכים של חודשים עד שנים.

המוצר נותן לחברות:

  • ניהול היררכי של פרויקטים — פרויקט מכיל בניינים, בניין מכיל דירות, דירה מכילה בעלים עם אחוזי בעלות.
  • מעקב סטטוס דירה-דירה — מי הסכים, מי סירב, מי בפגישה, מי לא בקשר. תמונת מצב בזמן אמת.
  • שיתוף בקרה עם קבלנים — הזמנת חברת הנדסה/עו"ד/קבלן לראות חלקים מהפרויקט עם הרשאות מדויקות לכל שדה.
  • חתימות דיגיטליות — חתימת בעל דירה על חוזה, עם הוכחת זהות, IP, וחותמת זמן.
  • קלנדר ומשימות — מנהל מקצה משימות לסוכנים, מתזמן פגישות, ועוקב אחר התקדמות.
  • תיעוד מלא — audit log של כל פעולה, מסמכים מקושרים לדירות, היסטוריית סטטוסים.

1.2 מי המשתמשים

חמישה סוגי משתמשים — בארבעה תפקידים בצד הלקוח + אחד פנימי ב-EMAPP. הפרק על Multi-tenancy (Section 10) מתאר את ההפרדה הטכנית; כאן זו תמונת המבט:

1.3 איך זה בנוי במשפט אחד

מונורפו TypeScript עם Next.js בקדמי, NestJS+Fastify בצד שרת, Drizzle ORM מעל Postgres עם Row-Level Security, פרוס על 5 ספקים: Neon (DB), Railway (containers), Cloudflare (R2 storage + Pages FE), Resend (email), Sentry (monitoring). עלות MVP: $0-6 לחודש.

1.4 מה התחדש בארכיטקטורה (v2)

הגרסה הזו של מסמך הארכיטקטורה כוללת שלושה עדכונים מהותיים מהגרסה הקודמת:

  • חמשת העקרונות המרכזיים (Section 2): SOLID, Security First, Performance, Minimal Runtime, Code Efficiency. כל החלטה ארכיטקטונית מתבססת על אחד או יותר מהם.
  • Provider tier נפרד מבחינה מבנית (Section 10): טבלת זהויות נפרדת (provider_users), DB role נפרד (provider_app_role), wrapper נפרד (withProvider) — לא דגל "is_admin" על משתמש רגיל.
  • שכבת Interfaces לכל תלות חיצונית (Section 6): IEmailProvider, IStorageProvider, IEncryptionService, ועוד. החלפת ספק = ימים, לא חודשים. הקוד העסקי לא יודע מי הספק.

בנוסף, ה-MVP גדל מ-14 טבלאות ל-18 טבלאות לקוח + 2 טבלאות Provider — נוספו tasks, task_assignees, notifications, project_assignments כדי לאפשר MVP אמיתי end-to-end (קלנדר, הקצאות, התראות).

02 · CORE PRINCIPLES

חמשת העקרונות שמכוונים כל החלטה

לפני כל בחירה — של ספק, של ספרייה, של מבנה — אנחנו שואלים: האם זה תואם את חמשת העקרונות? אם לא — נדחה. אם כן — נמשיך.

ארכיטקטורה טובה אינה רשימה של בחירות נכונות; היא שיטה להגיע לבחירות נכונות באופן עקבי. חמשת העקרונות הללו הם השיטה שלנו. הם לא מתחרים — הם משלימים. כל החלטה ארכיטקטונית מסוננת דרכם, וכל "למה זה ככה?" צריך להתחבר לפחות לאחד מהם.

SOLID

עקרונות SOLID

Single Responsibility — כל מודול, מחלקה ופונקציה אחראית על דבר אחד.
Open/Closed — פתוח להרחבה, סגור לשינוי (interfaces, לא ירושות).
Liskov — Implementation A יכול להחליף Implementation B ללא שינוי קוד צרכן.
Interface Segregation — interface צר עדיף על interface רחב; הצרכן לא תלוי בפונקציות שאינו משתמש בהן.
Dependency Inversion — קוד עסקי תלוי ב-interface, לא ב-implementation. NestJS DI מזריק את ה-implementation בהפעלה.

איך זה מתורגם בפועל: שכבת Interfaces לכל תלות חיצונית (Section 6); fakes לכל בדיקה; החלפת ספק = factory swap.
SECURITY FIRST

אבטחה היא דרישה בסיסית, לא פיצ'ר

כל פיצ'ר נשאל "איך זה נכשל בטוח?" לפני "איך זה עובד?" אבטחה מנצחת כשיש קונפליקט — תמיד.

איך זה מתורגם בפועל: RLS + FORCE על כל טבלה רב-לקוחית; הצפנת PII ב-pgcrypto עם מפתחות session-scoped; audit log append-only ברמת ה-DB (לא ברמת אפליקציה); 2 DB roles נפרדים (app_user + provider_app_role); MFA חובה ל-Provider tier; fail-closed ב-default. ראה Doc 07 לפרטים מלאים.
PERFORMANCE

latency נמוך מהיום הראשון

MVP אינו תירוץ לאיטיות. אם בנינו על תשתית איטית, נשבר ב-100 לקוחות. נבנה נכון מההתחלה.

היעדים: p95 API < 200ms, p99 < 500ms; p95 DB query < 5ms; First Contentful Paint < 1.5s; Time to Interactive < 3s.

איך זה מתורגם בפועל: Composite indexes לכל RLS subquery; connection pool עם statement_timeout; HTTP/2 + brotli; CDN edge למשאבים סטטיים; Drizzle (בקרת query מדויקת) במקום Prisma (מטא-טריקים מסתורים). ראה Section 9.
MINIMAL RUNTIME

פחות runtime, פחות סיכון

כל service, queue, cache, או runtime זר מוסיף תחזוקה, debugging, ו-failure modes. נשתמש בכמה שפחות.

איך זה מתורגם בפועל: Container-first (Railway), לא serverless עם cold starts; Postgres עושה כפול תפקיד (DB + Cache + Queue ב-pg-boss אם נצטרך); אין Redis ב-MVP (יבוא ב-Phase 2 דרך ICacheProvider); אין Kubernetes ב-MVP; אין message broker — pg-boss אם נצטרך queue.
CODE EFFICIENCY

DRY עם שכל — לא over-abstraction

הקוד הוא נכס. כל שורה מתחזקת, נקראת, ומבדק. נכתוב פחות שורות שעושות יותר.

איך זה מתורגם בפועל: סכמה מוצהרת פעם אחת ב-Drizzle, ה-TS types נגזרים אוטומטית; Zod DTOs נגזרים מ-Drizzle עם drizzle-zod; helpers משותפים (commonColumns, tenantColumns); אבל לא over-abstraction — כל abstraction חייב להצדיק את עצמו. כשיש 2 אפשרויות, נבחר את הפשוטה.

2.1 איך העקרונות פותרים קונפליקטים

לפעמים שני עקרונות לכאורה נוגדים. הסדר הוא:

  1. Security First מנצח תמיד. אם החלטה מקלה על ביצועים אך מסכנת אבטחה — נדחה. אם החלטה הופכת קוד פשוט אך משאירה PII בלוגים — נדחה.
  2. Minimal Runtime לפני Performance בהיקפים קטנים. ב-MVP, פוסטגרס כ-cache (איטי יותר מ-Redis) מנצח Redis (מהיר יותר אבל runtime נוסף). ב-100 לקוחות, נשקול.
  3. SOLID לפני Code Efficiency. Interface מוסיף קבצים, אבל עוזר ל-Liskov. הוספת קוד תמורת gainability נכון.
  4. Performance מנצח Code Efficiency בנקודות חמות. אם query עסקית רצה 1000 פעמים בדקה, אינדקס denormalized מוצדק גם אם הוא נראה כפילות.

אנחנו מתעדים כל החלטה ארכיטקטונית עם העקרון שמצדיק אותה. דוגמאות מה-Stack:

03 · SYSTEM LAYERS

חמש השכבות שבונות את המערכת

המערכת מחולקת לחמש שכבות, כל אחת עם אחריות מוגדרת. הקו ביניהן ברור; התקשורת ביניהן עוברת דרך חוזים מפורשים.

חלוקה לשכבות אינה תרגיל אקדמי — היא הדרך שלנו לוודא שכל מודול אחראי על דבר אחד (Single Responsibility), ושאפשר להחליף שכבה בלי לגרור שינויים ב-others. כשמישהו שואל "איפה הקוד הזה צריך לחיות?", התשובה מתחילה ב"באיזה שכבה הוא נמצא?"

L1 · UI

Frontend — Next.js App Router

ממשק משתמש. דפים בעברית RTL. רכיבים מ-shadcn/ui עם tailwind. State management ב-Zustand (לא Redux — minimal runtime). אינטראקציה עם השרת דרך React Query.
Next.js 15 · React 18 · TypeScript · shadcn/ui · Tailwind · Zustand · React Query · Cloudflare Pages
L2 · API

API Layer — NestJS + Fastify

שכבת HTTP. Controllers שמקבלים בקשות, מאמתים אותן עם Zod, ומעבירים ל-services. Auth middleware. Rate limiting. Error handling. אין כאן business logic — רק תרגום בין HTTP לבין שירותים.
NestJS · Fastify · Zod · Better Auth · @nestjs/swagger
L3 · SERVICES

שכבת השירותים — Business Logic

ה-logic האמיתי. שירות "ProjectsService" יודע מה זה פרויקט, איך יוצרים אותו, איך מוקצים אגנטים. השירות לא יודע על HTTP ולא על SQL ספציפי. מקבל DTOs, מחזיר DTOs. משתמש ב-withTenant / withProvider ב-DAL. משתמש ב-IEmailProvider / IStorageProvider דרך DI.
NestJS Injectable · withTenant · AuditService · IEmailProvider · IStorageProvider
L4 · DATA

שכבת הנתונים — Drizzle + Postgres

ה-DB עצמו ו-Drizzle schemas. הסכמה היא מקור האמת — כל ה-types נגזרים ממנה. RLS policies על כל טבלה רב-לקוחית. שתי connection pools (app_user + provider_app_role). שני wrappers (withTenant + withProvider) — היחידים שכותבים/קוראים מה-DB. ראה Doc 04c.
Drizzle ORM · pg pool · pgcrypto · Neon Postgres · RLS + FORCE
L5 · INFRA

שכבת תשתית — ספקים חיצוניים

Email, Storage, SMS, Monitoring. כל אחד מהם מוסתר מאחורי interface (Section 6). הספקים יכולים להתחלף; השכבה הקוד מעליהם לא משתנה.
Resend (email) · R2 (storage) · ספק SMS ישראלי (MVP — D.20) · Sentry (monitoring) · Postgres cache_kv (Phase 2 → Upstash)

3.1 חוקי התקשורת בין שכבות

חמישה כללים שמגדירים איך השכבות מדברות זו עם זו:

  • שכבה גבוהה מדברת עם שכבה נמוכה — לא להפך. UI מדבר עם API. API מדבר עם Services. Services מדברים עם Data. Data מדבר עם Infra דרך interfaces. אסור לרוץ אחורה.
  • כל שכבה חוצה את הגבול דרך חוזה מפורש. UI → API דרך REST + Zod. Services → Data דרך wrappers + Drizzle types. Services → Infra דרך interfaces.
  • אין שכבה שמדלגת על שכבה. UI אינו ניגש ישירות ל-DB. Controllers אינם ניגשים ישירות לספק חיצוני. אם נדמה לך שצריך לדלג — בדוק את התכנון.
  • DTOs נכתבים בגבול ה-API. ה-DB types (Drizzle) לא חוצים את ה-API החוצה. Services ממירים אותם ל-DTOs לפני שהם מחזירים ל-Controllers.
  • שגיאות מוגדרות בכל שכבה. NotFoundError ב-Service. HttpException ב-Controller. השכבה הגבוהה ממירה לפרוטוקול שלה (HTTP status, JSON shape).

3.3 הסיבה למבנה הזה

למה דווקא חמש שכבות, ולא ארבע או שש? המבחן הוא אחריות יחידה:

  • UI אחראי על המראה ועל התגובה למשתמש; לא יודע על מבנה DB
  • API אחראי על HTTP; לא יודע על business logic
  • Services אחראים על business logic; לא יודעים על HTTP או על pgcrypto
  • Data אחראי על persistence; לא יודע על business invariants ברמה הגבוהה
  • Infra אחראי על תקשורת עם העולם החיצוני; כל אחד מאחורי interface

כל שכבה אפשר להחליף או לבדוק בנפרד. החלפת ה-UI (React → Vue) לא מצריכה שינוי ב-Services. החלפת DB (Postgres → CockroachDB) דורשת שינוי ב-Data ובמשהו ב-Services (RLS-equivalents), אבל לא ב-API. החלפת ספק email מצריכה שינוי קובץ אחד במודול ה-Infra — כי ה-interface נשמר.

💡 איפה זה לא נכון להחיל
השכבות הן חזק עבור CRUD ועבור business logic סטנדרטי. עבור scripts (migration scripts, seed scripts, one-offs) — לא תמיד נדרשת חלוקה לחמש שכבות. הקפדה חיונית בקוד אפליקציה ראשי; פחות חיונית בקוד עזר.

5.3 הקשרים בין הספקים

איך הקופסאות בתרשים מדברות אחת עם השנייה:

  • User → Cloudflare Pages (Frontend): בקשת HTML/JS/CSS. Cloudflare CDN משרת מ-edge הקרוב. בישראל: POP בתל אביב, latency < 20ms.
  • Frontend → Railway BE (API): בקשות REST דרך api.emapp.io. Cookies לסשן. Railway חושף את ה-BE דרך custom domain.
  • BE → Neon (DB): Pool של 20 connections (app_user) + 5 connections (provider_app_role). Connection-string פרטי, לא חשוף ל-Frontend.
  • BE → R2 (Storage): שירות BE מייצר presigned URLs. הקליינט מעלה/מוריד ישירות מ-R2 (לא דרך BE) — חוסך bandwidth.
  • BE → Resend (Email): API call לכל email send. רק BE שולח; Frontend לא ניגש ל-Resend ישירות.
  • BE → Sentry: SDK מסתעף לכל error. Frontend גם שולח שגיאות שלו ל-Sentry (browser SDK).
  • Worker → Neon: אותו DB. Worker ב-Railway רץ במכולה נפרדת מ-BE, מתחבר ל-Neon כמו BE. משמש ל-scheduled jobs + SSE push.

5.6 Disaster Recovery (תקציר)

פירוט מלא ב-Doc 07. תמצית:

  • Neon backups: Daily snapshots, point-in-time recovery עד 7 ימים אחורה. ב-Pro plan: 30 ימים.
  • R2 files: Cloudflare מבטיח 99.999999999% durability (11 nines). אם נדאג: replication to S3 ב-Phase 2.
  • Railway containers: ללא state פנימי. Deploy חדש = פתרון.
  • Encryption keys: מאוחסנים ב-Railway env vars + גיבוי ידני ב-1Password של הצוות. אובדן = כל ה-PII הצפון אבוד.
  • Audit log: נמצא ב-Neon backups. אם DB נחרב, ניתן לשחזור מ-snapshot.
⚠ הסיכון הגדול ביותר: אובדן מפתחות הצפנה
אם PII_ENCRYPTION_KEY אובד, כל ה-PII (תעודות זהות + טלפונים) בלתי קריא לעולם. הגיבוי הפיזי של המפתחות הוא דרישה מנדטורית. ראה Doc 07 Section 14 לפרוצדורת ה-rotation וה-backup.

5.7 Timezone Strategy — Asia/Jerusalem ב-UI, UTC במערכת

החלטה: Postgres ושכבת ה-API עובדים UTC בלבד. UI מציג זמן ב-Asia/Jerusalem דרך Intl.DateTimeFormat. Scheduled jobs ב-Worker container רצים ב-UTC, ולוקחים את ה-DST בחשבון רק ברמת הקוד.

הזמן הוא נקודת כשל קלאסית. ישראל ב-UTC+2 בחורף ו-UTC+3 בקיץ (DST). בלי החלטה מפורשת, כל פיתוח חודש 4 חודשים פולש לבאגים: "למה החתימה הופיעה ביום אחרי?", "המייל יצא בארבע לפנות בוקר", "audit log אומר שזה קרה אתמול אבל זה קרה היום".

5.7.1 ההשלכות הקונקרטיות

ב-FE — כל הצגת תאריך/שעה דרך useFormatter מ-next-intl או Intl.DateTimeFormat עם locale he-IL ו-timeZone: 'Asia/Jerusalem'. אין conversion ידני, אין hard-coded "UTC+2".

ב-BE controllers — תאריך נכנס כ-ISO 8601 UTC; נאחסן כפי שהוא. תאריך יוצא כ-ISO 8601 UTC; FE ממיר.

ב-DB queries — אם יש WHERE על תאריך, עובדים ב-UTC. דוגמה: "פרויקטים שנוצרו היום" = WHERE created_at >= date_trunc('day', NOW() AT TIME ZONE 'Asia/Jerusalem') AT TIME ZONE 'Asia/Jerusalem'. זה הדגם היחיד שבו ה-DB יודע על Asia/Jerusalem — וזה רק לחישוב גבול היום של המשתמש.

ב-Worker scheduled jobs — cron expressions ב-UTC. "כל יום בשעה 9 בבוקר ישראל" = 0 7 * * * בחורף, 0 6 * * * בקיץ. הפתרון: שני יוצרי cron בקוד, או job rescheduling אוטומטי ב-DST switch (פעמיים בשנה). MVP = שני entries cron עם תיעוד שמסביר.

5.7.2 הטסטים שמגבים את ההחלטה

  • Test: יצירת רשומה ב-23:30 ישראל בחורף — created_at ב-DB צריך להיות 21:30 UTC, ה-UI מציג 23:30
  • Test: כפילות שעה DST (ב-26 באוקטובר 2026 השעה 03:00 חוזרת ל-02:00) — audit log עדיין מציג סדר נכון בגלל אחסון UTC
  • Test: בקשת "פרויקטים מהיום" ב-00:30 ישראל — מחזירה את היום הנכון
  • Test: scheduled job ב-Worker רץ פעם אחת ביום גם ב-DST switch (אסור פעמיים, אסור 0 פעמים)
💡 שני זמני התקלות הסבירים
1. סוף מרץ (DST in): השעה 02:00 קופצת ל-03:00. cron job ב-02:30 לא רץ ביום הזה.
2. סוף אוקטובר (DST out): השעה 03:00 חוזרת ל-02:00. cron job ב-02:30 רץ פעמיים.

5.8 Worker Container — מה הוא עושה ב-MVP

ה-Worker container ב-Railway הוא container שני, נפרד מ-BE, שמתחבר לאותו Neon DB. הוא לא מקבל HTTP requests — הוא רץ עם long-lived processes. ב-MVP הוא מבצע שלוש משימות בלבד:

2Cleanup של tokens פגי-תוקףכל שעה (cron)מחיקת rows מ-cache_kv עם expires_at < NOW(): magic link tokens שנשלחו ולא נצרכו, password reset tokens, אם יש

5.8.1 מה לא ב-Worker ב-MVP

  • Background analytics processing — Phase 2 (כשנוסיף analytics)
  • Document OCR — Phase 2 of product
  • Weekly digest emails — Phase 2
  • Backup-to-S3 of R2 — Phase 4 / Scale
  • Audit log archival ל-partition table — Phase 3 (כשהטבלה גדולה)

5.8.2 ההפרדה: למה לא לעשות הכל ב-BE container

אפשר להפעיל את ה-3 משימות מתוך ה-BE container עצמו. אבל לא בריא:

  • SSE צורך connections פתוחות ארוכות. אם BE container מטפל גם ב-HTTP requests וגם ב-SSE, restart לdeploy פוגע גם בlivecלקוחות שצופים. הפרדה = deploy ל-API ללא הפרעה ל-SSE clients
  • Cron jobs מערערים את ה-thread pool. ב-Fastify, ה-thread pool של BE מוקדש לבקשות. job ש-CPU-intensive (גם אם רק כל שעה) מאט תגובות בעלות עומס
  • Scaling differently. Phase 2: יכול להיות שנרצה 3 BE replicas מאחורי load balancer + 1 Worker. אם הכל באותו container, הקסקלה לא נקייה

$5/חודש נוספים על Railway = שווה את ההפרדה. ה-Worker container זול ומאפשר ל-BE להיות לחלוטין stateless.

06 · INTERFACE LAYER

שכבת ה-Interfaces — SOLID בפעולה

שש interfaces. שש implementations. החלפת ספק = ימים, לא חודשים. הקוד העסקי לא יודע מי הספק.

החלטה ארכיטקטונית מהותית: כל תלות חיצונית (ספק email, storage, SMS, cache, monitoring, real-time) מסתתרת מאחורי interface. שירותי business logic תלויים ב-interface (IEmailProvider), לא ב-implementation (ResendEmailProvider). NestJS DI מזריק את ה-implementation בעת הפעלה. ה-test code מזריק FakeEmailProvider. החלפת ספק = שינוי factory; שירות הקוד אינו זז.

import { Resend } from 'resend';
import { IEmailProvider } from './email.interface';

export class ResendEmailProvider implements IEmailProvider {
  constructor(private client: Resend, private defaultFrom: string) {}

  async send(message: EmailMessage): Promise<EmailDeliveryResult> {
    const result = await this.client.emails.send({
      from: message.from ?? this.defaultFrom,
      to: message.to,
      subject: message.subject,
      html: message.html,
      text: message.text,
    });
    return { id: result.data?.id ?? '', status: 'sent' };
  }

  async healthCheck(): Promise<void> {
    await this.client.domains.list();
  }
}

6.6 SMS Provider — ספק ישראלי ב-MVP (לא Noop, לא Twilio)

⚠ עודכן — החלטה D.20 (2026-05-16)
המסמך תכנן במקור NoopSMSProvider כי tenant portal היה Phase 2. אבל Tenant הוא עכשיו MVP (D.17), ולכן SMS OTP הוא MVP. ב-MVP משתמשים ב-ספק SMS ישראלי אמיתי (019 / Inforu / דומה) מאחורי ISMSProvider — לא Noop, ולא Twilio. הקטע למטה משקף את ההחלטה הסופית.

דיירים מתחברים ב-SMS OTP — אין להם אימייל/סיסמה. זה תפקיד MVP (פרסונה 3, Doc 01). ה-Auth flow קורא ל-ISMSProvider, וב-MVP ה-implementation הוא ספק ישראלי אמיתי.

למה ספק ישראלי ולא Twilio: דיירים בהתחדשות עירונית הם לרוב מבוגרים, עם מספרים +972. ספק ישראלי (019, Inforu) זול משמעותית למספרים ישראליים ובעל deliverability טוב יותר בארץ מ-Twilio. הכל מאחורי ISMSProvider — אם נצטרך Twilio (הרחבה בינלאומית) זו החלפת factory.

למה עדיין דרך interface: אם נחליף ספק SMS (מחיר, deliverability, הרחבה), שירות הקוד לא זז — רק ה-factory. בדיוק כמו שאר ה-providers. ב-dev אפשר להגדיר NoopSMSProvider (קורא OTP מ-logs) כדי לא לשרוף SMS אמיתיים בבדיקות — אבל ב-staging/production זה הספק הישראלי.

israeli-sms.provider.ts (MVP — production/staging)
export class IsraeliSMSProvider implements ISMSProvider {
  constructor(private http: HttpClient, private cfg: SmsConfig) {}

  async send(to: string, body: string): Promise<SMSDeliveryResult> {
    // to: E.164 (+9725...). Provider API per 019/Inforu docs.
    const res = await this.http.post(this.cfg.endpoint, {
      user: this.cfg.user, pass: this.cfg.token,
      to: toLocalIsraeli(to), msg: body,
    });
    return { id: res.messageId, status: res.ok ? 'sent' : 'failed' };
  }

  async healthCheck(): Promise<void> { await this.http.get(this.cfg.healthUrl); }
}

// dev only — reads OTP from logs, sends nothing
export class NoopSMSProvider implements ISMSProvider {
  async send(to: string, body: string): Promise<SMSDeliveryResult> {
    logger.warn({ msg: 'SMS (dev noop)', to: maskPhone(to), bodyPreview: body.slice(0, 30) });
    return { id: 'noop-' + Date.now(), status: 'sent' };
  }
  async healthCheck(): Promise<void> {}
}

6.9 דוגמאות לתרחישי החלפה

איך נראה מעבר בפועל, כשהאינטרפייס במקום:

  • R2 → S3. AWS SDK is the same — רק endpoint משתנה. S3StorageProvider קוד כמעט זהה ל-R2StorageProvider. זמן: שעות.
  • החלפת ספק SMS (אם צריך). כתיבת provider חדש, החלפה ב-factory, contract tests. זמן: יום. (ב-MVP: ספק ישראלי — D.20.)

✓ Reversibility כביטוח
שכבת ה-interfaces היא הביטוח על בחירות ה-Stack שלנו. אם Resend ייסגר מחר, יש לנו כלי לעבור ב-יום. אם Cloudflare תעלה מחירים ב-10x, יש לנו אופציה. אנחנו לא נעולים. ההחלטות שעשינו הן קונפיגורציה, לא ארכיטקטורה.
07 · DATA FLOWS

איך מידע זורם במערכת

חמש זרימות מרכזיות. מה קורה ב-request, איפה עוצרים, מה נכתב, מה נקרא.

הבנת זרימות נתונים היא הדרך לדבר על המערכת בלי לטבוע בפרטים. הזרימות הללו מופיעות עשרות פעמים ביום במערכת — והן זהות מבחינה מבנית, גם אם הנתונים שונים. פעם אחת מבינים אותן, ואז כל פיצ'ר חדש "נראה כמו אחת מהזרימות הללו, עם שינויים."

         if (user.role !== 'manager') throw ForbiddenError

  • Email אחרי commit — אם Resend נופל, המשתמש עדיין יצר את הפרויקט (best-effort)
  • RLS WITH CHECK — אם dto.orgId היה אחר, ה-INSERT היה נכשל ב-DB level (defense in depth)

7.3 זרימה C — קריאה של PII (Get Owner Details)

הזרימה הרגישה ביותר. מחזירה ת"ז וטלפון מוצפנים — דורש פענוח ב-DB session-scoped.

Flow C: GET /api/apartments/:id/owners (PII flow)
1.  Browser → BE: GET /api/apartments/<id>/owners
2.  Middleware: auth check + role check
3.  Controller: extract apartment_id from URL
4.  OwnersService.listForApartment(orgId, apartmentId, user):
       await withTenant(orgId, async (tx) => {
         // 4a. RLS scopes to org. SET LOCAL app.encryption_key set.

         // 4b. Fetch with decryption — pgcrypto runs IN the DB
         const rows = await tx.execute(sql`
           SELECT o.id, o.name, o.email,
             pgp_sym_decrypt(o.national_id_encrypted,
                             current_setting('app.encryption_key')) AS national_id,
             CASE WHEN o.phone_encrypted IS NOT NULL THEN
               pgp_sym_decrypt(o.phone_encrypted,
                               current_setting('app.encryption_key'))
             ELSE NULL END AS phone
           FROM owners o
           JOIN ownerships ow ON ow.owner_id = o.id
           WHERE ow.apartment_id = ${apartmentId}
             AND ow.ended_at IS NULL
         `)

         // 4c. Map to DTOs — never expose national_id_hash etc.
         return rows.map(mapToOwnerDto)
       })

6.  Browser: HTTPS-encrypted in transit; sensitive data displayed in UI

נקודות קריטיות:

  • Decryption ב-DB, לא ב-app code (Doc 04c P1.5)
  • Key הוא session var, נמסר דרך SET LOCAL ב-withTenant — לא משאיר עקבות בלוגים
  • Plaintext PII חוצה את ה-network רק פעם אחת (DB → BE → browser, מוצפן ב-TLS)
  • אין PII ב-logs — Pino redactors מסירים שדות רגישים (Doc 07)
  • Audit אופציונלי כאן — קריאת PII היא רגישה אבל לא state-changing. Doc 07 דן מתי לרשום audit ב-read.

כל הזרימות מצייתות לעקרון אחד: שום שכבה לא סומכת על השכבה מעל. ה-UI יכול לשלוח כל מה שירצה; ה-API מאמת. ה-API יכול לקרוא לכל service; ה-service בודק role. ה-service יכול לכתוב כל מה שירצה ל-DB; RLS מסנן. אם רק שכבה אחת עובדת, המערכת בטוחה. אם כל השכבות יחד נכשלות — ההצפנה של PII היא ה-last line.

8.1 הפילוסופיה — Defense in Depth

כל שכבה לבדה מספיקה. כל שכבה מניחה שהבאה אחריה תיכשל. אם כולן עובדות יחד — האבטחה הרבה יותר חזקה מהסכום.

SHIELD 1

Network & Edge — Cloudflare

DDoS protection, rate limiting ברמת ה-Edge, WAF rules בסיסיים. רוב הבוטים אינם מגיעים עד הסרבר. בנוסף, HTTPS (TLS 1.3) כברירת מחדל לכל ה-domains.
Cloudflare DDoS · WAF · TLS · Edge rate limiting
SHIELD 2

App-level — NestJS Middleware

Auth middleware (Better Auth): session validation, JWT verification. Role-based access (Manager/Agent/Viewer/Contractor/Provider). Rate limiting per-user. CSRF protection. Zod validation לכל body/query. Helmet headers (CSP, X-Frame-Options, etc.).
Better Auth · Zod · Helmet · per-user rate limit · CSRF tokens
SHIELD 3

DB role separation

שני DB roles נפרדים: app_user (קוד הלקוח, RLS אכוף) ו-provider_app_role (צוות EMAPP, BYPASSRLS + audit). אפילו אם קוד שירות נשבר, ה-DB role הוא הקיר. ל-app_user אין הרשאת UPDATE/DELETE על audit_log או על provider tables.
app_user · provider_app_role · GRANT/REVOKE · BYPASSRLS attribute
SHIELD 4

Row-Level Security (RLS)

Policy על כל טבלה רב-לקוחית: org_id = current_setting('app.organization_id')::uuid. אם withTenant לא נקרא, RLS מחזיר 0 שורות. אם ה-app code שוגה ושוכח filter — RLS מסנן. השכבה האחרונה לפני ה-data.
ENABLE RLS · FORCE RLS · current_setting · SET LOCAL
SHIELD 5

PII Encryption

תעודות זהות וטלפונים מוצפנים ב-BYTEA columns עם pgcrypto. גם אם הכל אחר נשבר — DB dump חשוף לעולם — ה-PII אינו קריא. ה-encryption key אינו ב-DB; הוא ב-Railway env vars, מועבר ל-session דרך SET LOCAL.
pgcrypto · pgp_sym_encrypt · HMAC for lookup · session-scoped key

8.3 הצפנת PII — מבט תמציתי

מודל ההצפנה (פרטים ב-Doc 04c §P1.5 ו-Doc 07 §5):

  • שני columns לכל שדה רגיש: national_id_encrypted (BYTEA) + national_id_hash (TEXT, HMAC). ההצפנה מסתירה; ה-hash מאפשר חיפוש.
  • הצפנה ב-DB: pgp_sym_encrypt(plaintext, key). הקוד אינו רואה plaintext מחוץ ל-INSERT הראשי.
  • HMAC ב-app: createHmac('sha256', hashKey).update(input). דטרמיניסטי — אותו קלט תמיד אותו hash.
  • שני מפתחות נפרדים: PII_ENCRYPTION_KEY (להצפנה) ו-PII_HASH_KEY (ל-HMAC). מובדלים כדי שאף אחד מהם לא יחשוף את השני.
  • Session-scoped: withTenant עושה SET LOCAL לשני המפתחות. הם מתפוגגים בסוף ה-transaction.

8.4 Provider Tier — תוסף קריטי

צוות EMAPP צריך לפעמים לגשת לנתוני לקוח (תמיכה, debugging). הגישה הזו אסור שתיראה כמו admin flag על משתמש רגיל. במקום, היא tier נפרד מבחינה מבנית:

  • זהות נפרדת: טבלת provider_users (לא users). MFA חובה ברמת ה-schema (column NOT NULL). Password חובה (אין magic links).
  • DB role נפרד: provider_app_role עם BYPASSRLS. שירותי לקוח אינם יכולים לכתוב כ-provider, ולהפך.
  • Audit נפרד וחזק: provider_audit_log עם reason חובה לכל גישה. INSERT only — אין UPDATE/DELETE.
  • Wrapper נפרד: withProvider(providerUserId, reason, fn). דוחה reason קצר מ-5 תווים. כותב audit לפני העבודה.
  • Session קצר: Provider session TTL = 30 דקות, לא 7 ימים. אי אפשר "להישאר מחובר" לאורך זמן.

הסיבה: פריצת חשבון Provider Admin היא קטסטרופלית פי כמה מפריצת לקוח (כל הלקוחות חשופים). השכבות הנוספות הללו אינן ביורוקרטיה — הן ההגנה מפני נקודת כשל יחידה.

8.5 Audit Log — מקור האמת על מה קרה

שני audit logs נפרדים:

  • audit_log — לכל פעולה ב-tier הלקוח. INSERT only. ניתן לקרוא ע"י Manager (פעולות שלו), Provider (לחקירת אירועים).
  • provider_audit_log — לכל גישת Provider Admin. INSERT only. ניתן לקרוא ע"י Provider Admins (התנהגות צוות פנים), אסור לקוחות.

שניהם append-only ברמת ה-DB GRANT — אין UPDATE, אין DELETE. גם אם attacker יקבל הרשאות מלאות של app_user — הוא לא יכול למחוק עקבות.

8.6 מה לא נכלל ב-MVP (אבל ב-roadmap)

  • SOC 2 Type II — אחרי ~10 לקוחות (Phase 4 של רוד-מאפ)
  • External pentest — אחרי שיהיו 5-10 לקוחות (תקציב)
  • Bug bounty program — אחרי SOC 2
  • HSM ל-encryption keys — Phase 3 (כרגע מספיק Railway env vars)
  • WAF advanced rules — Cloudflare Pro מהוסיף ב-Phase 2
  • SAML/SSO — לפי דרישת לקוחות (Phase 2 של מוצר)

ה-MVP מכוון לקבל חברה ישראלית קטנה-בינונית כלקוח ראשון. הוא אינו מכוון לבנק או חברת ביטוח (אלה יבואו אחרי SOC 2).

⚠ Security First — לא ניתן לפשרה
העקרון השני מבין החמישה. כל החלטה ארכיטקטונית שעלולה לפגוע באבטחה — נדחית. אם איזון בין performance לאבטחה — אבטחה מנצחת. אם איזון בין נוחות פיתוח לאבטחה — אבטחה מנצחת. הסיבה: לקוחות שלנו מחזיקים PII של עשרות אלפי דיירים. פריצה אחת = סוף הפרויקט.

9.2 איך אנחנו מגיעים לזה — DB layer

ה-DB הוא הצוואר. אם הוא איטי, הכל איטי. ה-techniques שלנו:

  • Composite indexes על כל RLS subquery. כל policy שבודק org_id חייב אינדקס שמתחיל ב-org_id. ראה Doc 04c P1.12 לרשימה המלאה (~45 אינדקסים).
  • Connection pool עם statement_timeout. 20 connections ל-app_user. statement_timeout = 30s. בקשה איטית לא תופסת חיבור לעולמים.
  • Drizzle ולא Prisma. Drizzle יוצר queries צפויות; ללא lazy loading; ללא runtime overhead. כל query גלוי בלוגים.
  • Denormalization מודעת. buildings.apt_count מתוחזק ע"י trigger — חוסך COUNT(*) בכל list. audit_log.actor_email denormalized — חוסך join ל-users בכל read.
  • JSONB עם indexes מתאימים. share.permissions כ-JSONB. אם נצטרך GIN index — נוסיף בנקודה הנכונה.
  • Partial indexes על דפוסים נפוצים. notifications WHERE read_at IS NULL — index קטן ומהיר ל-"unread" query.

9.3 איך אנחנו מגיעים לזה — API layer

  • Fastify ולא Express. Fastify מהיר ~2x מ-Express ל-throughput. אינו פתרון יחיד אבל קלאסי.
  • NestJS injection ברמת request, לא global. Services נוצרים פעם אחת; מצב חוצה-בקשה נמנע.
  • Streaming responses ל-list endpoints גדולים. במידת הצורך. ב-MVP לא נדרש.
  • HTTP/2 כברירת מחדל. Railway תומך. Multiplexing מקטין latency.
  • Brotli compression. ה-edge של Cloudflare דוחס responses אוטומטית.

9.4 איך אנחנו מגיעים לזה — Frontend

  5. שיפור: אינדקס נוסף → query rewrite → denormalization → cache (לפי סדר עלות)

המערכת תרגיש מהירה ב-MVP, ב-10 ארגונים, וב-100 ארגונים — כי הטכניקות הללו מובנות. אם בעתיד נצטרך לעבור ל-edge runtimes או ל-DB sharding, התשתית מאפשרת. אבל ב-MVP הקנה מידה הזה — Postgres אחד + Railway BE + Cloudflare CDN — הוא יותר ממספיק.
10 · MULTI-TENANCY

Multi-tenancy — שישה תפקידים, שלושה tiers

המודל הזה הוא הלב של ה-SaaS. שישה תפקידים (כולל Tenant ב-MVP — D.17). שלושה tiers של זהות. שני wrappers. RLS על הכל.

Multi-tenancy אינה רק "ב-DB יש org_id בכל טבלה." היא מודל מבני שמגדיר מי קיים, מי רואה מה, ואיך הקוד מוודא את זה. המודל הזה הוא ההבדל בין SaaS שניתן לסמוך עליו ובין SaaS עם cross-tenant leakage. אנחנו לוקחים את זה ברצינות מהיום הראשון.

10.1 ה-Tiers

החמשת תפקידים מאורגנים בשלושה tiers של זהות:

Tier 1: Organization UsersManager, Agent, Viewerusers + membershipsapp_userwithTenant(orgId, ...)
Tier 2: External EntitiesContractor, Tenant (דייר)contractors + shares · tenantsapp_userwithTenant(orgId, ...) + share/tenant scope resolution

⚠ Tenant (דייר) — תפקיד MVP, D.17+D.20
Tenant הוא ישות חיצונית ב-Tier 2 (כמו Contractor) אבל עם מודל scope משלו: דייר רואה רק את הרשומה של עצמו (הדירה שלו, סטטוס החתימה שלו, מסמכים אליו). טבלת זהות נפרדת tenants, התחברות ב-SMS OTP (ספק ישראלי — §6.6), ו-RLS policy ייעודי שמסנן ל-tenant_id של המבקש. דייר לעולם לא רואה דיירים אחרים, רשימות, או נתוני ארגון. ה-RLS לדייר מחמיר יותר מ-Contractor — אין JSONB permissions, פשוט "רק שלי".

הסיבה לחלוקה לשלושה tiers: מי לא צריך לראות מי. Provider Admin לא צריך להופיע ב-tenant audit logs ככה. Contractor לא צריך להופיע ב-users. כל tier הוא מודל זהות נפרד, עם wrapper משלו, עם DB role משלו (ב-tier 3).

10.2 התפקידים בפירוט

Tier 1.1 — Manager

מנהל פרויקטים בארגון לקוח. בעל ההרשאות הרחבות בארגון.

  • רואה: כל הפרויקטים בארגון; כל הדירות; כל הבעלים (PII); audit log של הארגון
  • פעולות: יצירת פרויקטים, ניהול בניינים, ניהול בעלים, הקצאת Agents (project_assignments), הזמנת Contractors (shares), כל פעולת CRUD
  • הקצאה: דרך membership עם role = 'manager'
  • במציאות עסקית: ראש פרויקט בחברת התחדשות. בדרך כלל 1-3 מנהלים בארגון.

Tier 1.2 — Agent

סוכן שמטפל בפרויקטים ספציפיים. רואה רק מה שהוקצה לו.

  • רואה: רק פרויקטים שב-project_assignments שלו; דירות בהם; בעלים שלהם
  • פעולות: CRUD על הדירות שלו, סטטוסים, notes, tasks, signatures. אינו יכול להקצות Agents אחרים או להזמין Contractors.
  • הקצאה: Membership עם role = 'agent' + Manager מקצה לפרויקטים דרך project_assignments
  • במציאות עסקית: "איש שטח" שעובד עם דיירים. בדרך כלל 5-20 בארגון. מטפל בכמה פרויקטים במקביל.

Tier 1.3 — Viewer

קריאה בלבד. רואה הכל בארגון, אינו יכול לכתוב.

  • רואה: כל הפרויקטים בארגון (כמו Manager)
  • פעולות: SELECT בלבד. שום INSERT/UPDATE/DELETE.
  • הקצאה: Membership עם role = 'viewer'
  • במציאות עסקית: בעלי מניות, חברי דירקטוריון, רואה חשבון פנימי. צריכים לראות, לא לעדכן.

Tier 2 — Contractor

ישות חיצונית (עו"ד, חברת הנדסה, קבלן) שמקבלת גישה לפרויקטים ספציפיים.

  • רואה: רק פרויקטים שיש להם share פעיל; ובתוכם, רק שדות שמוגדרים ב-share.permissions JSONB
  • פעולות: תלוי ב-share.permissions. בדרך כלל read; לפעמים upload documents
  • הקצאה: Manager יוצר contractor + share(project, contractor, permissions)
  • במציאות עסקית: "תזמין את עו"ד יוסי לראות חוזים בפרויקט X, אבל לא ת"ז של בעלים." הזמנת אורח עם הרשאות פרטניות.
  • טכני: מודל זהות נפרד מ-users (שולחים JWT עם contractorId + orgId). אינו ב-users table.

Tier 3 — Provider Admin

צוות EMAPP פנימי. הגישה היחידה שחוצה לקוחות. מבחינתית מבחינה מבנית.

  • רואה: כל הלקוחות (BYPASSRLS), אבל כל גישה audited
  • פעולות: SELECT רחב לתמיכה. UPDATE על מצומצם של טבלאות (אם נדרש). אין DELETE.
  • הקצאה: מבוצעת ידנית דרך bootstrap script + רישום ב-provider_users
  • הגנות נוספות: MFA חובה (schema-level NOT NULL), session 30 דקות, אין magic links
  • במציאות עסקית: 2-5 אנשי תמיכה ב-EMAPP. גישה לקוח-לקוח כשמתקבלת בקשת תמיכה. כל פעולה חייבת reason.

10.4 איך זה מתממש טכנית

שלוש שכבות של אכיפה. גם אם אחת תיכשל, השנייה והשלישית עוצרות:

  • App-level RBAC. בקוד השירות, if (user.role !== 'manager') throw ForbiddenError. ה-decision מבוסס על JWT claims.
  • RLS policies על כל טבלה. גם אם השירות שגוי, ה-DB מסנן ל-org_id = current_setting('app.organization_id')::uuid. אם RLS מתפעל, לא נראה דאטה של ארגון אחר.
  • DB GRANTs. אפילו אם RLS לא מוגדר נכון או נופל, ה-app_user role פשוט לא יכול לעשות UPDATE על audit_log, DELETE על provider_users, etc.

ראה Doc 04c §P1.11 (RLS Policies) ו-§P1.13 (withTenant + withProvider) למימוש המלא.

10.5 רב-ארגוניות (Multi-org users)

נקודה דקה אבל קריטית: משתמש יכול לשייך לכמה ארגונים. למשל, רואה חשבון שעובד עם 3 חברות התחדשות. ייצוג במודל:

  • users table אינו מכיל org_id. user הוא אדם, לא "אדם-בארגון".
  • memberships table הוא ה-M:N junction. שורה: (user_id, org_id, role, is_primary, accepted_at, revoked_at).
  • משתמש יכול להיות Manager ב-org A, Agent ב-org B, Viewer ב-org C — בו זמנית.
  • JWT נושא activeOrgId — איזה membership זה "הנוכחי". מעבר בין ארגונים = יצירת JWT חדש (endpoint נפרד).
  • RLS על users משתמש ב-EXISTS subquery: "user נראה אם יש לו membership ב-org הנוכחי שאינה revoked."

10.6 שמירת PII במודל

קישור בין הרשאות לבין PII:

  • Manager / Agent / Viewer: רואים PII (national_id, phone) של בעלים בארגונם. ה-decryption קורה ב-DB; ה-key הוא session-scoped.
  • Contractor: רואה PII רק אם share.permissions.tenants.fields.national_id = true. ה-app filter מסיר את ה-field לחלוטין מה-response אם false (absence pattern).
  • Provider Admin: יכול לראות PII דרך BYPASSRLS, אבל הגישה audited עם action_type = 'decrypt' ב-provider_audit_log. בנוסף, ה-internal tool של Provider Admin מציג רק 4 ספרות אחרונות כברירת מחדל; מציג מלא רק בלחיצה מפורשת.

11.3 ארבעה חוקים לכל אינטגרציה

כל אינטגרציה חדשה חייבת לעמוד בארבעה תנאים:

  1. Behind an interface. אם זה ספק שאפשרי להחליפו (email, SMS, storage, cache, realtime) — חייב interface. אם זה תשתית קריטית שאינה realistically replaceable (Postgres, GitHub) — לא חובה.
  2. Health check ב-startup. בעת הפעלת האפליקציה, כל interface מקבל קריאת healthCheck(). אם נופל — האפליקציה לא עולה. עדיף crash loop ב-deploy מאשר 500s לכל בקשה.
  3. Graceful degradation אם נופל. אם השירות נופל ב-runtime, מה קורה? Email נופל → log + Sentry, המשך פעולה. R2 נופל → upload נכשל, user מקבל error מובן. שני הכשלים אינם זהים.
  4. Audit אם רגישה. אינטגרציה ששולחת PII החוצה (email עם פרטי owner, למשל) — חייבת audit entry. אינטגרציה שרק עוקבת (Sentry) — לא חובה.

11.4 איך אינטגרציות מתחברות לקוד

הזרימה הסטנדרטית — דוגמה: שליחת magic link email:

flow: send magic link integration
// 1. Service consumes the interface (DI)
@Injectable()
export class AuthService {
  constructor(@Inject(EMAIL_PROVIDER) private email: IEmailProvider) {}

  async sendMagicLink(emailAddr: string, token: string) {
    // 2. Service calls interface, not implementation
    try {
      const result = await this.email.send({
        to: emailAddr,
        subject: 'התחברות ל-EMAPP',
        html: renderMagicLinkTemplate(token),
      });

      // 3. Success — log id for traceability
      logger.info({ msg: 'magic link sent', emailId: result.id });
    } catch (err) {
      // 4. Graceful failure — log + Sentry + propagate to caller
      logger.error({ msg: 'magic link failed', err });
      Sentry.captureException(err);
      throw new ServiceUnavailableError('email service unavailable');
    }
  }
}

// 5. The factory in providers.module.ts decides implementation
{
  provide: EMAIL_PROVIDER,
  useFactory: () => new ResendEmailProvider(new Resend(env.RESEND_API_KEY), env.EMAIL_FROM),
}

11.5 ניהול secrets ל-אינטגרציות

כל אינטגרציה דורשת API keys / credentials. הקפדה:

  • אף secret לא ב-git. .env ב-.gitignore. .env.example committed עם names ריקים.
  • כל הסודות ב-Railway env vars. Railway מצפין them at rest. Access logged.
  • Validation ב-startup. T3-env מוודא שכל env var נדרש קיים ובפורמט הנכון. אם חסר — האפליקציה לא עולה.
  • Rotation procedure (Doc 07 §14). אם API key חשוד נחשף, יש פרוצדורה מוגדרת לרוטציה.
  • Least privilege. Resend API key רק עם זכות "send"; R2 credentials רק עם זכות לבאקט הספציפי.

11.6 ניטור אינטגרציות

איך נדע שאינטגרציה נופלת:

  • Sentry alerts. Error spikes על שגיאות מ-Resend/R2/וכו'. notification לצוות.
  • Synthetic checks. Phase 2: בדיקות תקופתיות אם email נשלח, אם R2 נגיש.
  • Sentry Health. Sentry SDK עצמו מנטר מה משתבש בו (rare, אבל קורה).
  • Status pages. כל ספק יש לו status page (status.resend.com, status.cloudflare.com). מנוטרים ידנית כשמשהו נראה רע.
  • App-level health endpoint. GET /health מחזיר 200 רק אם כל ה-healthChecks עוברים. שימושי ל-Railway health checks.

11.7 הסיכון של תלות ב-ספק חיצוני

שאלה הוגנת: מה אם Resend ייסגר? מה אם Neon יעלה ב-10x? מה אם Cloudflare יתחיל ל-rate-limit אותנו?

התשובה שלנו מבוססת על שכבת ה-interfaces (Section 6):

  • החלפת ספק = ימים, לא חודשים. דוגמאות ב-§6.9
  • אין vendor lock-in מבני. ה-code לא יודע מי הספק; ה-factory decide.
  • Postgres הוא המעט-החלפי — אבל Postgres אינו ספק, הוא טכנולוגיה. Neon → RDS → CockroachDB כולם תומכים ב-Postgres dialect.
  • אנחנו לא משתמשים ב-features ספציפיים לספק. Neon branching נחמד אבל לא קריטי; R2 ללא egress fees נחמד אבל S3 גם אפשרי.

היחידה הקריטית: אובדן מפתחות הצפנה. אם Railway env vars נמחקים ואין גיבוי — PII אבוד לעולמים. ראה Doc 07 §14 לפרוצדורת הגיבוי.

✓ אינטגרציות הן הסכמה, לא ההתחייבות
בחרנו 5 ספקים מסוימים. הם הסכמה עכשווית, לא התחייבות לעולם. אם פעם נצטרך להחליף — יש לנו כלי. הקפדה על interface layer ועל ארבעת החוקים (§11.3) מבטיחה שאינטגרציה היא החלטה הפיכה.
12 · OBSERVABILITY

Observability — איך אנחנו רואים מה קורה

Logs, metrics, traces. הקצוות מהמשתמש ועד ה-DB. אם משהו נשבר — נדע מתי, איפה, ולמה.

Observability היא ההבדל בין צוות שיודע מה קורה במערכת ובין צוות שמנחש. ה-MVP שלנו מבוסס על Sentry בלבד — לא Datadog, לא New Relic. Sentry מספק error tracking + performance monitoring + release tracking ב-tier אחד, חינמי ל-Developer plan. כשהמערכת תגדל, נשקול הוספה (לא החלפה). כאן: מה אנחנו מתעדים, איך, ולמה.

12.1 שלושת עמודי ה-Observability

הגישה הסטנדרטית בתעשייה — שלוש שכבות, כל אחת עונה על שאלה שונה:

12.2 Logs — Pino בכל מקום

אנחנו משתמשים ב-Pino כ-logger הסטנדרטי. מהיר (אחד הכי מהירים ב-Node.js), structured JSON, ועם פיצ'רים של redaction לאוטומציה של הסתרת PII.

packages/api/src/logger.ts
import pino from 'pino';

export const logger = pino({
  level: process.env.LOG_LEVEL ?? 'info',

  // CRITICAL: redact PII automatically — even if a dev accidentally logs it
  redact: {
    paths: [
      '*.password', '*.password_hash',
      '*.national_id', '*.national_id_encrypted',
      '*.phone', '*.phone_encrypted',
      '*.signature_blob',
      '*.encryption_key', '*.hash_key',
      'req.headers.authorization', 'req.headers.cookie',
    ],
    censor: '[REDACTED]',
  },

  // Structured fields auto-added to every log
  base: {
    service: 'emapp-api',
    env: process.env.NODE_ENV,
  },
});

מה אנחנו לוגגים

  • כל request: method, path, statusCode, duration, userId, orgId (אבל לא תוכן ה-body)
  • כל error: message, stack, request context. גם נשלח ל-Sentry
  • חיבורי DB: חיבורים שנופלים, queries איטיים (> 100ms)
  • אינטגרציות חיצוניות: Resend send result, R2 operation outcome, withProvider entries
  • Auth events: login success, login failure, MFA challenge, session expiry
  • Sensitive events: בעת קריאת PII (PII access events) — log עם userId + apartmentId, לא PII עצמו

מה אנחנו לא לוגגים

  • PII (national_id, phone) - גם לא ב-error stack traces (Pino redact מסיר)
  • Passwords, password hashes, MFA secrets
  • Session tokens, JWT contents
  • Request bodies בשלמות (רק metadata על הקריאה)
  • Encryption keys

12.7 על-mode Debugging — איך פותרים אירוע

כשאלרט מגיע — הצוות יודע בדיוק מה לעשות. הזרימה:

  2. פותחים את ה-issue ב-Sentry — רואים stack trace, request context, user context.
  3. Trace ה-event שגרם — Sentry Tracing מציג מ-frontend ועד ה-DB.
  4. בודקים breadcrumbs (logs) — מה קרה לפני ה-error בו-זמן בו-session.

  6. אם נדרש — Production logs — Railway provides shell access; railway logs CLI command.
  7. Fix + deploy — PR, CI, merge. Sentry מקשר את ה-release ל-fix.
  8. Post-mortem — אם זה היה אירוע משמעותי, document ב-incidents/.

13 · PORTABILITY

שמונה חוקי הברזל ל-Portability

השמונה חוקים שמאפשרים החלפת ספק בימים, לא בחודשים. כל אחד מהם נשמר כקדוש.

בחירת Stack היא לרוב blocker בעתיד: "אנחנו לא יכולים לעבור ספק כי כל הקוד תלוי בהם." אנחנו לא רוצים את זה. שמונה חוקי הברזל הללו מבטיחים שהחלפת כל אחד מהספקים שבחרנו תהיה אפשרית — לא טריוויאלית, אבל אפשרית בימים. כל החלטה ארכיטקטונית עוברת דרכם.

13.1 שמונת החוקים

  • שכבת interface לכל תלות חיצונית. Email, Storage, SMS, Cache, Realtime, Encryption. אם זה ספק שאפשר להחליפו — חייב interface. ראה Section 6.
  • אין שימוש ב-features ייחודיים לספק (vendor-specific features). Neon branching נחמד; אנחנו לא בונים עליו business logic. R2 ללא egress fees חוסך כסף; אנחנו לא בונים על זה. Cloudflare Workers ייחודי; לכן לא משתמשים בו.
  • Postgres הוא Postgres. כל SQL שאנחנו כותבים תקף בכל Postgres 15+. בלי Neon-specific extensions שאינן זמינות במקום אחר.
  • S3-compatible API ל-storage. AWS SDK עובד עם R2 (Cloudflare), S3 (AWS), MinIO (self-hosted). שינוי endpoint = שורת קוד אחת.
  • SMTP / API-based email — לא ספק-לוקי. Resend, SES, SendGrid כולם מספקים HTTP API דומה. ה-interface שלנו נורמלי, לא חושף את ההבדלים.
  • Docker containers, לא serverless functions. Container יכול לרוץ ב-Railway, Fly.io, Render, AWS ECS, Google Cloud Run. Serverless functions תלויות בספק.
  • Standard protocols. HTTPS, JWT, OAuth/OIDC, SMTP. לא משתמשים בפרוטוקולים מסחריים סגורים.
  • Migrations versioned ב-code. Drizzle Kit migrations הם source of truth. אפשר להריץ אותם בכל DB Postgres-compatible — בלי תלות בכלי הספק.

    13.3 דוגמת מימוש: חוק 4 — S3-compatible

    איך החוק "S3-compatible storage" מתממש קונקרטית. ה-implementation אינה תלויה ב-Cloudflare:

    packages/db/src/providers/storage/r2.provider.ts (extracted from §6)
    import { S3Client, GetObjectCommand, PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';
import { IStorageProvider } from './storage.interface';

export class R2StorageProvider implements IStorageProvider {
  private client: S3Client;

  constructor(private bucket: string, accountId: string, accessKey: string, secretKey: string) {
    // THE ONLY R2-SPECIFIC LINE: the endpoint URL.
    // Change endpoint → works with S3, MinIO, Wasabi, Backblaze B2.
    this.client = new S3Client({
      region: 'auto',
      endpoint: `https://${accountId}.r2.cloudflarestorage.com`,
      credentials: { accessKeyId: accessKey, secretAccessKey: secretKey },
    });
  }

  async getUploadUrl(key: string, opts: UploadUrlOptions): Promise<string> {
    const cmd = new PutObjectCommand({
      Bucket: this.bucket,
      Key: key,
      ContentType: opts.contentType,
      ContentLength: opts.maxSizeBytes,
    });
    return getSignedUrl(this.client, cmd, { expiresIn: opts.ttlSeconds });
  }
  // ... getDownloadUrl, delete, healthCheck
}

// To switch to AWS S3, write S3StorageProvider with different endpoint.
// All other code identical. Service layer doesn't change.

    13.4 דוגמת מימוש: חוק 2 — אין vendor-specific

    דוגמה ל-החלטה שהפסיקה Vendor lock-in מראש: Cache layer.

    אפשר היה לבנות על Cloudflare Workers KV — fast edge cache, integrated עם Cloudflare. אבל:

    • Workers KV הוא Cloudflare-specific. שום ספק אחר לא מציע אותו exact API
    • אם פעם נצטרך להתרחק מ-Cloudflare — כל cache logic ידרוש rewrite
    • הפיצ'רים שלו (sub-1s globally consistent) אינם נחוצים ל-MVP שלנו

    במקום, בחרנו Postgres cache_kv ב-MVP → Upstash Redis ב-Phase 2. שניהם דרך ICacheProvider. אף אחד לא vendor-specific.

    13.8 תזכורת מ-Doc 07: למה זה קריטי לאבטחה

    אם פעם נצטרך להחליף ספק עקב אירוע אבטחה אצלו (data breach ב-Resend, פרצה ב-R2), הזמן הוא הקריטי. Portability ⇒ Resilience:

    • Resend חוו breach — אם אנחנו vendor-locked, נצטרך לחכות לתיקון שלהם. עם interface, אפשר לעבור ל-SES או SendGrid תוך יום.
    • R2 חוו אירוע — אפשר לעבור ל-S3 ב-שעות. files-בעלי ידרשו העברה אך זה ניהול ידני, לא rewrite קוד.
    • Neon חוו אירוע מערכתי — אפשר להעביר ל-RDS תוך 24-48 שעות. הסכמה זהה, ה-SQL זהה.
    ✓ פורטביליות = ביטוח אבטחה
    שמונת החוקים אינם רק על "לא להיות תקוע" עם ספק. הם תוכנית גיבוי אבטחתית: אם ספק חווה אירוע, יש לנו אופציה. הקפדה על 8 החוקים לאורך כל הפיתוח שווה חודשים של חופש מאוחר יותר.

    14.8 הסיכון של overprovisioning

    שדרוג מוקדם מדי הוא ההפך מסכנה — הוא בזבוז משאבים. עקרון: אנחנו לא משדרגים בגלל "מה אם", רק בגלל איתות מדיד.

    • "מה אם יבואו 50 לקוחות בבת אחת" — לא קורה בפועל. הצמיחה הדרגתית.
    • "Redis יהיה יותר מהיר" — תרצה לראות שה-cache_kv אמיתית בעיה לפני המעבר.
    • "Pusher יהיה real-time יותר טוב" — תרצה SSE קונקרטית להיות bottleneck.

    כל שדרוג מקדים = הוצאה חודשית מתמשכת + מורכבות תפעולית מוסיפה. אנחנו משלמים על תשתית שאנחנו צריכים עכשיו, לא על תשתית שאולי נצטרך בעוד שנה.

    ✓ צמיחה כספית מתוכננת
    העלות גדלה כמעט linear עם מספר הלקוחות. ב-3 לקוחות: $0-6/חודש. ב-10: $100-180. ב-50: $300-600. ב-100: $500-1000. זה אומר ש-cost-per-customer דווקא יורד ככל שגדלים — בזכות free tiers ו-bulk pricing.

    15.3 איך טבלה אופיינית נראית

    דוגמה — projects. כל הטבלאות עוקבות אחר אותו דפוס:

    projects table structure
    // All tables have:
id            uuid PK             // generated client-side
org_id        uuid FK             // → organizations(id), RESTRICT delete
created_at    timestamptz         // NOT NULL, default NOW()
updated_at    timestamptz         // NOT NULL, auto-update trigger

name          text                // "Renewal Tama 38 — Ben Yehuda 42"

USING (org_id = current_setting('app.organization_id', true)::uuid)

    15.4 דפוסים שמתחזרים בכל הסכמה

    כל הטבלאות הרב-לקוחיות עוקבות אחר אותם דפוסים:

    • UUID primary keys. נוצרים ב-client (gen_random_uuid()), לא serial. מאפשר לקוח לדעת ID לפני INSERT.
    • org_id ברוב הטבלאות. או דרך FK ישיר (rapid RLS) או דרך parent chain (ל-buildings, apartments). מנמק ב-Section 10.
    • Timestamps cluster. created_at + updated_at + archived_at (soft delete) — בכל טבלה.
    • FK עם RESTRICT/CASCADE מבחירה מודעת. organizations: RESTRICT (לא ניתן למחוק אם יש projects). apartments: CASCADE מ-buildings (מחיקת בניין → מחיקת דירות, אבל באמת רק soft delete).
    • Partial unique indexes. "unique active" — UNIQUE (cols) WHERE archived_at IS NULL. מאפשר ערכים כפולים בהיסטוריה.
    • Enums במקום text. סטטוסים מוגדרים כ-Postgres enum types; compile-time safety + small storage.
    • JSONB לפרטים גמישים. share.permissions, organizations.settings — עם Zod schema validation בקוד.

    15.5 PII בסכמה

    הטבלה היחידה שמחזיקה PII רגיש היא owners. הסכמה שלה:

    owners — the PII repository
    // Plaintext (low-medium sensitivity):
name                  text         // displayable; not search-sensitive
email                 citext NULL  // case-insensitive, plaintext

// CRITICAL: encrypted + HMAC for lookup
national_id_encrypted bytea NOT NULL  // pgp_sym_encrypt result
national_id_hash      text NOT NULL   // HMAC for indexed search

// CRITICAL: encrypted (nullable — optional field)
phone_encrypted       bytea NULL
phone_hash            text NULL

// Composite indexes for PII lookup:
INDEX idx_owners_org_natid_hash (org_id, national_id_hash)
INDEX idx_owners_org_phone_hash (org_id, phone_hash) WHERE phone_hash IS NOT NULL

// Unique active by national_id_hash per org:
UNIQUE (org_id, national_id_hash) WHERE archived_at IS NULL

    כל טבלה אחרת אינה מחזיקה PII רגיש. signatures מחזיקות חתימות ויזואליות (יחסית רגיש — encrypted), אבל לא ת"ז/טלפון.

    15.7 שדות שלא תראו בסכמה — בכוונה

    החלטות "מה לא להוסיף":

    • אין password_reset_token column. ה-token חי ב-cache (ICacheProvider), לא ב-DB
    • אין email_verified boolean ב-users. רק lastLoginAt — נקודת הוודאות הראשונית
    • אין session_id ב-users. Sessions ב-cache בלבד

    • אין is_admin ב-users. Provider tier הוא טבלה נפרדת — לא דגל

    15.8 איך הסכמה מתפתחת

    שינויים בסכמה הם זהירים. הזרימה:

    1. הצעה ב-PR — שני המפתחים סוקרים
    2. Drizzle Kit generates migration — לא ידני
    3. Migration runs locally — מאמתים שעובד על copy של data אמיתי
    4. CI runs migration from scratch — מאמת שלא שובר את ה-setup
    5. Production rollout — ב-night-time deploy אם משמעותי
    6. Rollback ready — אם משהו מתפוצץ, יש migration להפוך

    שינויים תוספתיים (הוספת column, חדש index) — קלים. שינויים מבניים (פיצול טבלה, שינוי FK) — דורשים תכנון. שינוי שמוחק נתונים — דורש review של שני המפתחים + Provider Admin approval.

    16.7 שורת הסיום

    הארכיטקטורה הזו אינה מורכבת בגלל שאנחנו חכמים. היא מורכבת בגלל שהבעיה היא מורכבת. אנחנו בונים SaaS שמטפל ב-PII רגיש (תעודות זהות), עם משתמשים מרובים בכמה תפקידים, עם שותפים חיצוניים שיש להם הרשאות פרטניות, עם צרכי תמיכה פנימיים, ועם דרישת אבטחה גבוהה.

    חמשת העקרונות (Section 2) הם המסנן. שלוש שכבות ההגנה (RLS + GRANTs + Encryption) הן ההגנה. שכבת ה-interfaces (Section 6) היא ה-resilience. שמונת חוקי ה-portability (Section 13) הם הביטוח. וה-18 הטבלאות (Section 15) הן ה-foundation שעליה הכל בנוי.
