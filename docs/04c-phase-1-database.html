01 · PHASE OVERVIEW

What This Phase Builds

The database foundation: schema, wrappers, policies, interfaces. Nothing more, nothing less.

Phase 1 produces the data layer of the application. By the end, the system can hold organizations, users, projects, apartments, owners, tasks, notifications, documents, signatures, audit entries — and every read or write is automatically scoped to the right tenant, every PII field is encrypted, and every external service interaction goes through an interface that can be swapped without changing consumer code. The application logic that uses this layer is Phase 2's problem; the foundation is this phase's deliverable.

1.1 Deliverables

At the end of Phase 1, the repository contains:

  • Migrations for all 18 tables, all RLS policies, all indexes, all DB roles. Idempotent. Versioned in Drizzle Kit. Runnable against a fresh Postgres in < 10 seconds.
  • Drizzle schema for every table. Type-safe. Re-exported from @emapp/db package. All relationships modelled explicitly.
  • Two DB roles: app_user (the connection role for normal app traffic, subject to RLS) and provider_app_role (the connection role for EMAPP team access, RLS bypass + audit).
  • Two access wrappers: withTenant(orgId, fn) for customer-facing requests, withProvider(providerUserId, reason, fn) for internal access. No other path to data exists in the codebase.
  • Interface layer for every external service: IEmailProvider, ISMSProvider, IStorageProvider, IEncryptionService, ICacheProvider, IRealtimeProvider. MVP implementations + stubs for future ones.
  • Test suite T1.x covering all critical security properties. T1.5 (RLS isolation) is the gate for any deployment.
  • Seed data for development and integration tests. Realistic fake organizations, projects, apartments.
  • Documentation embedded in the code: each table has a header comment explaining its purpose, each migration has a comment explaining why it exists.

1.2 What Phase 1 Does Not Include

To keep this phase focused, the following are out of scope (some are Phase 2, some are later):

  • HTTP API endpoints (Phase 2)
  • Authentication flow integration (Phase 2 — Better Auth setup)
  • Business logic services using the data layer (Phase 3)
  • Frontend integration (Phase 4)
  • Real-time SSE channels (Phase 6 — uses the schema established here, but adds the runtime)
  • Field tasks and recon (deferred to Phase 2 of the product roadmap)
  • Chat tables (Phase 2)
  • Tenant portal screens (Phase 8) — but the tenants identity table + tenant-scope RLS ARE in this phase (D.17+D.20)

The schema, however, anticipates these. Where they will need columns or relationships, the foundation accommodates them — but the tables are created when needed, not earlier.

    02 · WHY SO CRITICAL

    The Five Principles, Applied to the Database

    Every decision in this phase is filtered through SOLID, Security, Performance, Runtime, and Code efficiency.

    A database layer can be designed many ways. We have a specific way that flows from our five core principles. Understanding the principles is what lets the team make consistent decisions across tasks — and refuse the wrong decisions when shortcuts are tempting.

    2.1 SOLID Applied to the Database

    PrincipleHow it shapes Phase 1
    S — Single ResponsibilityEach table holds one entity. users doesn't hold project data. shares doesn't hold permission rules outside the JSONB column. Every column belongs to its table's natural concern.
    O — Open/ClosedProvider interfaces (IEmailProvider, etc.) are open for extension (new implementations) but closed for modification (interface contract is stable). Schema is open to additions (new tables, new columns) but closed to breaking changes (existing columns don't change semantics).
    L — Liskov SubstitutionIsraeliSMSProvider can substitute NoopSMSProvider (dev) or TwilioSmsProvider without changing consumers. R2 storage provider can substitute S3 storage provider. The interface contract is what matters; the implementation is replaceable.
    I — Interface SegregationInterfaces are narrow: IEmailProvider has send(), not sendAndTrack() + sendBulk() + parseInbox(). Consumers depend only on the operations they use.
    D — Dependency InversionService code depends on IEmailProvider, not on Resend directly. The wiring (NestJS providers) injects the concrete implementation. Service code is testable in isolation; mock implementations are trivial.

    2.2 Security First in the Database

    The database is where customer trust is technically realized. Security shapes every decision:

    • RLS on every multi-tenant table. Not opt-in. Not "we'll add it later." From day one, every table that holds tenant data has RLS enabled + FORCE.
    • Two roles, two access paths. app_user for customer requests (RLS enforced), provider_app_role for EMAPP team (RLS bypass + mandatory audit). Mixing them is structurally impossible.
    • PII encrypted at the column level. National ID and phone aren't "encrypted in transit" or "encrypted at rest by the cloud provider." They're encrypted by us, with our keys, in BYTEA columns. The cloud provider sees ciphertext.
    • Audit log is append-only at the DB level. Not "the app doesn't expose a delete endpoint." Actually no DELETE permission on the role. Provider tier can't erase its own audit.
    • Foreign keys enforce referential integrity. A project's org_id must reference a real organization. Cross-tenant references are structurally impossible.
    • Constraints encode business rules. Sum of ownership_pct per apartment = 100%. Apartment status transitions follow allowed paths. These aren't validations in app code that can be forgotten; they're database CHECK constraints.

    2.3 Performance: The DB Layer Sets the Ceiling

    API latency = framework overhead + business logic + DB latency. The first two are small constants. The third is the variable that determines whether the product feels fast or slow. We design the schema for performance:

    DecisionPerformance reason
    UUID primary keysGenerated client-side; no DB round-trip to get the ID before insert. Slightly larger than bigint but the trade-off is worth it for client-friendly IDs.
    Composite indexes on (org_id, common_filter)RLS subqueries match index prefix. Listing within org with filter is sub-millisecond.
    JSONB for share permissionsRead in single column access; no joins to permission table. Indexable with GIN if needed.
    Denormalized actor_email in audit_logQuerying audit doesn't require joining to users table. Trade-off: stale email if user changes it.
    Hash columns for PII lookupSearch by national_id_hash uses btree index. Decrypting per row would be O(n) full scan.
    Status as enum (not free text)Smaller storage, index-friendly, type-safe at app level.
    Connection pool with transaction-modeRLS SET LOCAL works correctly; connections reused safely; sub-millisecond connection acquisition.

    2.4 Runtime: Minimal Resource Footprint

    The database layer must be efficient in memory and CPU:

    • Connection pool size: 20 connections max per service. With 2 services (BE + Worker), 40 connections total. Neon Free supports 100; Launch supports 200. Plenty of headroom.
    • No ORM "magic" loading. Drizzle is closer to SQL than Prisma. Eager loading is explicit (with). Lazy loading doesn't exist — every query is intentional.
    • No N+1 queries. Lint rule enforces explicit join syntax for relationships. Code review catches the rest.
    • Pgcrypto runs in the database. No round-trip to app for encryption. CPU cost is on the DB, where it's small per-row.
    • Audit log writes inline. Same transaction as the action, ~0.5ms overhead. No separate audit service to maintain.

    2.5 Code Efficiency: Don't Repeat Yourself, But Don't Over-Abstract

    The schema is the source of truth. Code derives from it; type definitions are inferred from it:

    • Drizzle schemas in packages/db/src/schema/*.ts are the only place tables are defined
    • TypeScript types are inferred (InferModel, InferSelectModel) — never hand-written
    • Zod validators for API DTOs are derived from Drizzle schemas (drizzle-zod) where shapes match
    • Migrations are generated by Drizzle Kit from schema changes — not hand-written SQL
    • RLS policies live alongside their tables in dedicated migration files — readable as one unit
    • Test factories reuse Drizzle inserts; same shape as production code

    The principle: schema is declared once, used everywhere. A change to a column propagates to types, validators, factories — no five places to update.

    2.6 The Cost of These Principles

    Following the principles isn't free. The trade-offs we accept:

    CostWhat we gain
    ~5% query latency from RLS + withTenantCross-tenant isolation that survives any app-level bug
    ~10% schema complexity from provider tier separationProvider compromise can't quietly access customer data
    Extra DB columns for hash lookupsPII encryption without losing search capability
    Interface layer for every external serviceProvider swap in days instead of weeks
    More tables (18 vs minimal ~10)Cleaner separation; easier to reason about; queries are simpler
    More upfront design timeLess rework when assumptions change
    ✓ The principles are the project
    If anyone asks "why do we do it this way?", the answer is one of the five principles. If the answer can't be traced to a principle, the decision needs re-examining. Consistency comes from applying the same filter to every choice — not from following a static rulebook.
    03 · DATA MODEL OVERVIEW

    The Mental Model

    Eighteen tables organized into five zones, each with a coherent purpose. Understand the zones first; tables follow naturally.

    A schema with eighteen tables can feel overwhelming. The structure is simpler than the count suggests: tables cluster into five logical zones, and each zone has a coherent purpose. Within a zone, relationships are tight. Between zones, relationships are explicit and few. Once the zones are clear, the schema reads as a story instead of a list.

    3.1 The Five Zones

    Z1 · TENANCY
    Who exists, and where
    organizations · users · memberships
    The "who" of the system. Organizations are tenants. Users are people. Memberships connect them with roles. Users can belong to multiple orgs.
    Z2 · PROVIDER
    The EMAPP team's access
    provider_users · provider_audit_log
    A separate identity tier for support and operations. Audit-heavy, MFA mandatory. Bypasses RLS via a different DB role.
    Z3 · PROJECTS
    The work itself
    projects · buildings · apartments · owners · ownerships
    The hierarchy of urban renewal work. Project has buildings; buildings have apartments; apartments have owners; ownerships connect apartments to owners with percentages.
    Z4 · COLLABORATION
    Coordinating across actors
    contractors · shares · tasks · task_assignees · notifications · project_assignments
    External contractors with project-specific access. Tasks and calendar. In-app notifications. Agent-to-project assignments.
    Z5 · ARTIFACTS & HISTORY
    Documents and the record
    documents · signatures · notes · audit_log
    Files (metadata only, contents in R2). Signed contracts. Conversation/work notes. The audit trail of who did what when.

    3.2 The Tenant Boundary

    Every table belongs to one of three categories with respect to tenancy:

    CategoryTablesHow tenancy is enforced
    Tenant-scopedprojects, buildings, apartments, owners, ownerships, contractors, shares, tasks, task_assignees, notifications, project_assignments, documents, signatures, notes, audit_logRLS policy on each table. Filtered by current_setting('app.organization_id') either directly or via parent
    Multi-tenant (users)users (via memberships M:N)RLS uses EXISTS subquery on memberships — user visible if they have a membership in current org
    Tenancy itselforganizations, membershipsRLS: organizations visible if user has membership in it; memberships visible to user themselves
    Provider-onlyprovider_users, provider_audit_logapp_user role has NO access. provider_app_role only. Separate connection pool.

    3.3 The Dependency Graph

    Tables have foreign-key dependencies. The graph determines the order of migrations and creation:

    // Dependency graph — arrows point from child to parent (FK direction) organizations ▲ ├── memberships ────────→ users ├── projects │ ▲ │ ├── buildings │ │ ▲ │ │ └── apartments │ │ ▲ │ │ ├── owners ─ (belongs to apartment) │ │ └── ownerships ──→ owners │ ├── tasks ───→ users (creator) │ │ ▲ │ │ └── task_assignees ─→ users │ ├── project_assignments ─→ users │ ├── documents ─→ apartments (optional) │ │ ▲ │ │ └── signatures ─→ owners │ └── notes ──→ apartments (optional, or project-level) ├── contractors │ ▲ │ └── shares ──→ projects ├── notifications ──→ users └── audit_log ───→ users (actor) // Provider tier — separate hierarchy, no FK to tenant tables provider_users ▲ └── provider_audit_log

    3.4 Tenants and Users — The Subtle Part

    The relationship between users and organizations is the schema's trickiest detail. We model it as many-to-many:

    • users table has no org_id column. A user is a person, not a person-in-an-org.
    • memberships table is the M:N junction. Each row: (user_id, org_id, role, is_primary). A user can have multiple membership rows — multiple orgs.
    • JWT carries active_org_id. Determines which membership is "current." Switching is an explicit endpoint that issues a new JWT.
    • RLS on users uses EXISTS on memberships. User visible if they have a membership in the current org.

    Why this complexity? Many real users do work for more than one company (consultants, accountants, fractional executives). Pretending they don't would force account duplication, which leads to data quality issues and authentication confusion.

    3.5 The CTI Pattern for Owners (Future)

    Currently, owners stores all owner data in a single table. As the product expands, we may add specialized owner types (corporate owners, trustees, conservators). Without forethought, this becomes either a giant table with many nullable columns, or a JSON blob.

    The CTI (Class Table Inheritance) pattern is anticipated: a base owners table with common fields, and future specialized tables (corporate_owners, etc.) keyed by owner_id. This is not implemented in MVP — we have only individual owners. But the schema design doesn't preclude it. When the time comes, individual owner rows stay in owners; corporate ones get rows in owners + corporate_owners.

    3.9 Common Columns Across Tables

    Most tables share a common set of columns. We define them once via a helper and reuse:

    packages/db/src/schema/_common.ts
    import { uuid, timestamp, varchar } from 'drizzle-orm/pg-core';

// Common columns for every tenant-scoped table
export const commonColumns = () => ({
  id: uuid('id').primaryKey().defaultRandom(),
  createdAt: timestamp('created_at', { withTimezone: true })
    .notNull()
    .defaultNow(),
  updatedAt: timestamp('updated_at', { withTimezone: true })
    .notNull()
    .defaultNow(),
  archivedAt: timestamp('archived_at', { withTimezone: true }),
});

// For multi-tenant tables — also includes org_id
export const tenantColumns = () => ({
  ...commonColumns(),
  orgId: uuid('org_id')
    .notNull()
    .references(() => organizations.id, { onDelete: 'restrict' }),
});
    • id is always UUID v7 (generated as v4 for now; v7 in newer Postgres versions for time-ordering)
    • created_at and updated_at on every table; updated_at updated by a trigger (P1.10)
    • archived_at for soft deletion; presence means "archived"
    • org_id on tenant tables; FK with onDelete: 'restrict' — orgs can't be deleted if they have data

    3.10 The Schema as Documentation

    A well-designed schema explains the product. Reading our schema, a new developer should understand:

    • What entities exist (organizations, projects, apartments, etc.)
    • How they relate (project has buildings; apartment has owners)
    • What's important (encrypted fields signal sensitivity; FK with CASCADE/RESTRICT signal ownership)
    • What's deferred (no chat tables yet; provider tier exists separately)

    This is why we write headers on each schema file, why we annotate constraints with comments, why we use descriptive names. The schema isn't just data; it's the most enduring documentation of the product.

    💡 Read the schema before the code
    When onboarding a new developer or starting a new feature: read the relevant schema files first. They establish the domain model in five minutes — saving hours of confusion when reading service code that assumes the model.

    The Complete Inventory

    Every table, its purpose, its key columns, and its relationships. The reference map for everything that follows.

    This section is the catalog.     4.1 Zone 1 — Tenancy (3 tables)

    organizations

    The tenant entity. Every multi-tenant table eventually traces back to an organization.

    organizations id uuid PK name text NOT NULL slug text UNIQUE NOT NULL // URL-friendly identifier plan text NOT NULL DEFAULT 'pilot' settings jsonb DEFAULT '{}' // org-level config created_at timestamptz NOT NULL updated_at timestamptz NOT NULL archived_at timestamptz NULL INDEX idx_organizations_slug (slug) // RLS: visible if user has membership in this org
    • Slug uniqueness is global, not per-tenant — it's the public identifier.
    • Settings JSONB holds non-critical preferences (default language, timezone, etc.). Strict shape — validated by Zod at write time.
    • onDelete: 'restrict' on all child tables — an org can't be deleted while it has data. Soft delete only.

    users

    A person. Not an "employee of org X" — a person, potentially with memberships in multiple orgs.

    users id uuid PK email citext UNIQUE NOT NULL // case-insensitive name text NOT NULL password_hash text // nullable (magic-link-only users) avatar_color text NOT NULL DEFAULT '#0f766e' mfa_secret_encrypted bytea // nullable; TOTP if enrolled mfa_enabled_at timestamptz last_login_at timestamptz created_at timestamptz NOT NULL updated_at timestamptz NOT NULL archived_at timestamptz INDEX idx_users_email (email) // RLS: visible if user has membership in current org (EXISTS subquery)
    • No org_id column. Multi-org membership lives in memberships.
    • citext for email. Case-insensitive comparison without lowercase normalization in app code.
    • password_hash is nullable. Users authenticated only by magic link don't need passwords.
    • MFA secret is encrypted — same pattern as PII. Bytea + pgcrypto.

    memberships

    The M:N junction between users and organizations. Encodes role within the org.

    memberships id uuid PK user_id uuid NOT NULL → users(id) org_id uuid NOT NULL → organizations(id) role user_role NOT NULL // manager | agent | viewer is_primary boolean NOT NULL DEFAULT false // default org on login invited_by uuid → users(id) accepted_at timestamptz // null = pending invite revoked_at timestamptz // removed from org created_at timestamptz NOT NULL updated_at timestamptz NOT NULL UNIQUE (user_id, org_id) WHERE revoked_at IS NULL INDEX idx_memberships_user_active (user_id) WHERE revoked_at IS NULL INDEX idx_memberships_org_active (org_id) WHERE revoked_at IS NULL // RLS: visible if user is the actor OR org_id is current org
    • Partial unique index — a user can have one active membership per org, but historical revoked ones are allowed.
    • Soft revocation via revoked_at — preserves audit trail.
    • is_primary determines default org on login. Constraint at app layer: exactly one primary per user (would be DB constraint but easier in code).

    4.2 Zone 2 — Provider Tier (2 tables)

    provider_users

    The EMAPP team's identities. Separate from users by design — different security model, different DB role.

    provider_users id uuid PK email citext UNIQUE NOT NULL name text NOT NULL password_hash text NOT NULL // password mandatory (no magic links) role text NOT NULL DEFAULT 'admin' // future: support | billing | readonly mfa_secret_encrypted bytea NOT NULL // MFA MANDATORY — not nullable recovery_codes_hash jsonb NOT NULL // 8 hashed recovery codes last_login_at timestamptz disabled_at timestamptz // instant revocation created_at timestamptz NOT NULL updated_at timestamptz NOT NULL INDEX idx_provider_users_email (email) WHERE disabled_at IS NULL // NO RLS — only accessible via provider_app_role; app_user has no GRANT
    • MFA mandatory at schema level — mfa_secret_encrypted is NOT NULL. Cannot create a provider user without enrolling MFA.
    • No magic links — password is the only auth method; password_hash NOT NULL.
    • Disabled, not deleted — departed team members get disabled_at set; row remains for audit history.
    • app_user role has zero access — even SELECT is denied. Customer-facing code literally cannot see this table.

    provider_audit_log

    Append-only audit of every Provider tier action. Independent of customer-facing audit_log.

    provider_audit_log id uuid PK provider_user_id uuid NOT NULL → provider_users(id) reason text NOT NULL // MANDATORY per withProvider call action_type text NOT NULL // 'read' | 'write' | 'decrypt' | 'export' target_table text target_record_id uuid affected_orgs uuid[] // which tenants were touched ip inet NOT NULL user_agent text started_at timestamptz NOT NULL ended_at timestamptz // null = session in progress query_count integer DEFAULT 0 metadata jsonb DEFAULT '{}' INDEX idx_provider_audit_user_time (provider_user_id, started_at DESC) INDEX idx_provider_audit_affected_orgs (affected_orgs) // GIN // provider_app_role: INSERT + SELECT only — NO UPDATE, NO DELETE // app_user: ZERO access

    4.3 Zone 3 — Projects (5 tables)

    05 · PROVIDER TIER ARCHITECTURE

    A Separate Identity, A Separate Path

    The EMAPP team's access is structurally isolated from customer access. Not by convention — by Postgres roles and connection pools.

    Provider tier is the technical realization of a promise: "EMAPP team can help when needed, but cannot betray your trust without leaving evidence." The architecture has three layers — a separate identity table, a separate database role, and a separate access wrapper. Each one is necessary; together they make the promise enforceable.

    5.1 The Three-Layer Separation

  • Identity layer: provider_users table is separate from users. Provider Admins have entirely separate accounts — they cannot accidentally use customer-tier authentication for cross-tenant access.
  • Database role layer: provider_app_role is a separate Postgres role from app_user. The provider role bypasses RLS policies (because it must — its job is cross-tenant). The app_user role does not have this privilege.
  • Application wrapper layer: withProvider() is a separate function from withTenant(). It uses a separate connection pool (configured with provider_app_role credentials), enforces a mandatory reason parameter, and writes audit before the work begins.

    • 5.2 Why Not Just "Admin Flag" on Users?

    The obvious-but-wrong design: add a is_provider_admin column to users, write app code that handles "if admin, query without org filter." Why we reject this:

    • Bug surface. Every service method must remember to check the flag. One missing check = unaudited access. With separate roles, even a missing app-code check is caught by the database.
    • Audit risk. If the flag is in the same row as the user data, an attacker who modifies a user row could grant themselves admin. Separate tables + separate roles make privilege escalation structurally harder.
    • Operational confusion. Are Provider sessions subject to org-switching? Do they show up in customer audit logs? Mixing concerns leads to ambiguity. Separate tier means clear answers.
    • Different auth requirements. Provider Admins need MFA, short sessions, no magic links. Forcing these on regular users (or having "two policies in one table") is messy.
    • The trust narrative. Customer-facing security claims include "your data is structurally separated from other customers and from EMAPP's internal access." A flag column is harder to defend than two physically separate Postgres roles.

    5.3 The Database Role Separation

    Two Postgres roles are created at migration time:

    migrations/0001_roles.sql
    -- The customer-facing application role
CREATE ROLE app_user WITH LOGIN PASSWORD '<from env>';
GRANT CONNECT ON DATABASE emapp TO app_user;
GRANT USAGE ON SCHEMA public TO app_user;

-- The provider tier role — bypasses RLS via privilege
CREATE ROLE provider_app_role WITH LOGIN PASSWORD '<from env>';
GRANT CONNECT ON DATABASE emapp TO provider_app_role;
GRANT USAGE ON SCHEMA public TO provider_app_role;

-- BYPASSRLS attribute — provider role ignores RLS policies on tables.
-- FORCE policies still apply only to non-bypass roles.
ALTER ROLE provider_app_role BYPASSRLS;

    The BYPASSRLS attribute is the technical mechanism. Roles with this attribute see all rows regardless of RLS policies. Combined with FORCE ROW LEVEL SECURITY on tables, this means: app_user respects policies even if it owns the table; provider_app_role bypasses, but only because it has explicit BYPASSRLS privilege.

    5.4 The Connection Pool Separation

    Two separate pools, two separate connection strings:

    5.5 The Permission Grants

    Each role gets only the permissions it needs:

    migrations/0002_permissions.sql
    -- app_user has full DML on customer-facing tables (RLS enforced)
GRANT SELECT, INSERT, UPDATE, DELETE ON
  organizations, users, memberships, projects, buildings, apartments,

  notifications, project_assignments, documents, signatures, notes

-- app_user has NO access to provider tables
-- (no GRANT means no access)

-- provider_app_role has SELECT on customer tables (read for support)
GRANT SELECT ON
  organizations, users, memberships, projects, buildings, apartments,
  owners, ownerships, contractors, shares, tasks, task_assignees,
  notifications, project_assignments, documents, signatures, notes,
  audit_log
TO provider_app_role;

-- provider_app_role can UPDATE customer tables for support actions
-- (with audit — withProvider enforces this at app layer)
GRANT UPDATE ON
  organizations, users, memberships, projects, buildings, apartments,
  owners, contractors, shares, tasks, notifications
TO provider_app_role;

-- provider_app_role: SELECT + INSERT on provider tables, no UPDATE/DELETE
GRANT SELECT, INSERT ON provider_users, provider_audit_log TO provider_app_role;

-- Sequences (for serial IDs if any)
GRANT USAGE, SELECT ON ALL SEQUENCES IN SCHEMA public TO app_user, provider_app_role;

    Key properties:

    • app_user cannot UPDATE or DELETE audit_log (DB-level append-only)
    • app_user cannot access provider tables (no GRANT)
    • provider_app_role cannot UPDATE or DELETE audit_log or provider_audit_log (DB-level append-only)
    • provider_app_role cannot do destructive operations: no DELETE on customer tables. Destructive operations are explicit, separate, and gated.
    • Neither role is a superuser. Neither can ALTER TABLE, DROP, or modify RLS policies.

    5.6 The withProvider Contract

    Detail of the application-layer wrapper. See Doc 07 Section 8.3 for the security rationale; here is the implementation summary:

    packages/db/src/wrappers/with-provider.ts (sketch — full impl in Task P1.13)
    export async function withProvider<T>(
  providerUserId: string,
  reason: string,                       // MANDATORY — non-empty
  fn: (db: Database) => Promise<T>
): Promise<T> {
  // Defensive validation
  if (!isUuid(providerUserId)) throw new Error('invalid providerUserId');
  if (!reason || reason.length < 5) throw new Error('reason is required (min 5 chars)');

  // Use the provider pool — separate connection
  return providerPool.transaction(async (tx) => {
    // Session context for the provider role
    await tx.execute(sql`SET LOCAL app.provider_user_id = ${providerUserId}`);
    await tx.execute(sql`SET LOCAL app.access_reason = ${reason}`);

    // Write audit BEFORE the work — guarantees the access is recorded
    // even if the work fails. (Note: audit row commits/rolls back with tx,
    // but Sentry captures the failure independently.)
    const startTime = new Date();
    await tx.execute(sql`
      INSERT INTO provider_audit_log
        (provider_user_id, reason, action_type, started_at, ip, user_agent)
      VALUES
        (${providerUserId}, ${reason}, 'session', ${startTime},
         ${getRequestIp()}, ${getRequestUserAgent()})
    `);

    // Execute the user's code
    return fn(tx);
  });
}

    5.8 The Operational Reality

    How this looks in day-to-day operations:

    • Customer-facing API requests use db (the app_user pool), wrapped in withTenant(orgId, fn). RLS does its job. No audit overhead for routine actions.
    • Customer support tasks by EMAPP team members use a separate internal tool (Phase 2 — for MVP, this means using Drizzle Studio with provider credentials). Every action wrapped in withProvider(providerUserId, reason, fn). Reason is plain text, free-form, captured in audit.
    • Migrations run as the database owner (a third, separate role used only for DDL). Neither app_user nor provider_app_role can run migrations.
    • Backups run as a backup role, separate from both. Read-only access; cannot modify.

    5.9 The Cost of Provider Tier Separation

    Trade-offs we accept:

    • +2 tables (provider_users, provider_audit_log) — schema is larger
    • +1 DB role + 1 connection pool — slightly more operational complexity
    • +1 wrapper function (withProvider) — devs must know when to use which
    • Provider tooling requires extra work — can't just give Provider Admins admin URLs to customer features; we build internal tools that use withProvider

    In return:

    • Customer trust narrative is structural, not just policy
    • Insider misuse leaves evidence — audit log can't be erased by the actor
    • Compromised customer-tier credentials cannot escalate to provider access
    • Compromised provider-tier credentials are obvious (audit shows them) and limited (no DELETE)
    ⚠ The provider tier is the most sensitive surface
    A breach of provider tier credentials is catastrophically worse than a breach of any customer account. One compromised Provider Admin can access every customer. The MFA mandate, the short session TTL, the role separation, the audit log — these are not bureaucratic friction. They are the defense against a single-point catastrophe. Never weaken these requirements for convenience.
    06 · INTERFACE LAYER ARCHITECTURE

    SOLID Applied: Every External Service Has an Interface

    No service code talks directly to Resend, R2, Twilio, or any provider. They talk to interfaces. Implementations are swappable.

    The interface layer is what makes reversibility real. The decision "use Resend for email" becomes a configuration choice — not an architectural commitment. If Resend fails us, falls behind, or raises prices, the migration is a new implementation of the same interface, swapped in via dependency injection. Service code never knows. This is SOLID applied to external dependencies.

    6.2 The Interface Pattern

    Every external dependency follows the same five-part structure:

  • Interface (I<Name>) — the contract. Methods, parameters, return types. Lives in packages/db/src/providers/<area>/<name>.interface.ts.
  • Implementation(s) — concrete classes implementing the interface. One per provider (Resend, SES, etc.). MVP has one active; others may exist as stubs for testing or future use.
  • Factory or DI wiring — NestJS provider definition that maps interface to concrete implementation based on config.
  • Tests — interface contract tests run against ALL implementations to ensure they're truly substitutable.
  • Stub for testing — a FakeXProvider for unit tests that doesn't touch external services.

    The full pattern, applied to email:

    import { Resend } from 'resend';
import { IEmailProvider, EmailMessage, EmailDeliveryResult } from './email.interface';

export class ResendEmailProvider implements IEmailProvider {
  constructor(private client: Resend, private defaultFrom: string) {}

  async send(message: EmailMessage): Promise<EmailDeliveryResult> {
    try {
      const result = await this.client.emails.send({
        from: message.from ?? this.defaultFrom,
        to: message.to,
        subject: message.subject,
        html: message.html,
        text: message.text,
        tags: message.tags ? Object.entries(message.tags).map(([k, v]) => ({ name: k, value: v })) : undefined,
      });
      return { id: result.data?.id ?? '', status: 'sent' };
    } catch (error) {
      return { id: '', status: 'rejected', error: error.message };
    }
  }

  async healthCheck(): Promise<void> {
    // Resend has no health endpoint; verify API key with domain lookup
    await this.client.domains.list();
  }
}

    6.7 The NoopSMSProvider Detail

    This is the most unusual choice. Why a no-op SMS provider in MVP?

    • Tenant portal is Phase 2. SMS OTP is the primary tenant auth flow. We don't need SMS yet.
    • SMS provider choice is a decision we haven't made. Twilio is expensive for Israel ($0.10/SMS). Local Israeli vendors are cheaper but less polished. We want to delay choosing until we have data on volume.
    • But the AUTH FLOW needs an SMS provider object to compile. If we omit the entire SMS interface, the auth flow code gets ifdef-y ("if Phase 2 then call SMS"). That's worse.
    • NoopSMSProvider satisfies the interface. The auth flow compiles and runs end-to-end. It logs "would send SMS" with the recipient and code. Tests work; we know flow is correct.
    • Phase 2 swap is configuration. Replace NoopSMSProvider with TwilioSmsProvider in the module factory. Zero service code changes.

    6.8 The Cost of the Interface Layer

    Trade-offs:

    • +1 file per interface — the interface definition
    • +1-2 files per implementation — concrete + fake
    • ~30-50 extra lines of NestJS wiring — module providers, injection tokens
    • +1 step in mental model — "where is this implementation actually wired?"

    In return:

    • Service code is testable without external dependencies (use fake providers)
    • Provider swap is a configuration change, not a refactor
    • Contract is documented (the interface file IS the documentation)
    • New developers can read interfaces to understand what the system does
    • Future-proofing is structural, not promised in comments
    ✓ The reversibility insurance
    The interface layer is what makes our stack choices reversible. The decision "use Resend for email" is not architectural — it is configuration. When you read service code, you'll see IEmailProvider, not Resend. This is by design. The architecture survives provider changes; the providers serve the architecture.

    A note on the org_id question for buildings & apartments

    Buildings and apartments do not have a direct org_id column. Their tenancy is established via the FK chain: apartments → buildings → projects → organizations. This is a deliberate choice:

    • Pro: smaller rows, less denormalization risk. If a project moves between orgs (rare but possible), only the project row needs updating.
    • Pro: enforces consistency. No risk of "apartment has org_id A but its building has org_id B" — there's only one source of truth.
    • Con: RLS subquery cost. The policy must join through to check org_id. Mitigated by composite indexes on (project_id) and (building_id).

    For tables where direct org_id is preferred (owners, tasks, notifications, documents, signatures, notes, audit_log), denormalization is justified by query patterns — they don't reliably have a parent that owns them, or they need RLS to be especially fast.

    The sum=100 trigger

    Postgres CHECK constraints can't span rows; a trigger is the only way to enforce a multi-row invariant atomically:

    migrations/0003_owners.sql (appended)
    -- Enforce SUM(ownership_pct) per apartment = 100
-- This runs AFTER each INSERT/UPDATE/DELETE on ownerships.
-- If the sum is wrong, the transaction is rolled back.

CREATE OR REPLACE FUNCTION trigger_check_ownership_sum()
RETURNS TRIGGER AS $$
DECLARE
  v_apartment_id uuid;
  v_total numeric(7,2);
BEGIN
  -- Determine which apartment to check (works for INSERT/UPDATE/DELETE)
  IF TG_OP = 'DELETE' THEN
    v_apartment_id := OLD.apartment_id;
  ELSE
    v_apartment_id := NEW.apartment_id;
  END IF;

  -- Sum of active ownerships for this apartment
  SELECT COALESCE(SUM(ownership_pct), 0) INTO v_total
  FROM ownerships
  WHERE apartment_id = v_apartment_id
    AND ended_at IS NULL;

  -- If apartment has any owners, sum MUST equal 100
  -- If apartment has zero owners, that's also valid (new apartment, no owners assigned yet)
  IF v_total > 0 AND v_total <> 100 THEN
    RAISE EXCEPTION 'Sum of ownership percentages must equal 100 for apartment %, got %',
      v_apartment_id, v_total;
  END IF;

  RETURN NEW;
END;
$$ LANGUAGE plpgsql;

-- DEFERRABLE so a transaction can briefly have wrong sum during multi-row updates
-- (e.g., changing 50/50 to 60/40 requires two updates; check at commit)
CREATE CONSTRAINT TRIGGER trg_ownerships_sum_check
  AFTER INSERT OR UPDATE OR DELETE ON ownerships
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION trigger_check_ownership_sum();

    Key detail: DEFERRABLE INITIALLY DEFERRED. Without this, an update from "50%/50%" to "60%/40%" would temporarily have sum=110 between the two UPDATE statements, and the trigger would reject the first one. Deferred = checked only at COMMIT time, allowing valid multi-row updates.

    Inserting an owner with PII (the helper)

    Service code never writes PII directly. There's a helper that handles the encrypt + hash:

    packages/db/src/helpers/owners.ts
    import { sql } from 'drizzle-orm';
import { createHmac } from 'crypto';
import { env } from '../env';
import { Database } from '../client';

export interface CreateOwnerInput {
  orgId: string;
  name: string;
  email?: string;
  nationalId: string;     // plaintext — encrypted before storage
  phone?: string;         // plaintext — encrypted before storage
  notes?: string;
}

function hmac(input: string): string {
  return createHmac('sha256', Buffer.from(env.PII_HASH_KEY, 'base64'))
    .update(input, 'utf8')
    .digest('hex');
}

export async function createOwner(
  db: Database,
  input: CreateOwnerInput
): Promise<{ id: string }> {
  // Encryption happens IN the SQL — pgcrypto with the session-level key.
  // The plaintext nationalId/phone are sent as parameters; encrypted in-DB.
  const [row] = await db.execute(sql`
    INSERT INTO owners (
      id, org_id, name, email,
      national_id_encrypted, national_id_hash,
      phone_encrypted, phone_hash,
      notes
    ) VALUES (
      gen_random_uuid(),
      ${input.orgId},
      ${input.name},
      ${input.email ?? null},
      pgp_sym_encrypt(${input.nationalId}, current_setting('app.encryption_key')),
      ${hmac(input.nationalId)},
      ${input.phone ? sql`pgp_sym_encrypt(${input.phone}, current_setting('app.encryption_key'))` : sql`NULL`},
      ${input.phone ? hmac(input.phone) : null},
      ${input.notes ?? null}
    )
    RETURNING id
  `);

  return { id: row.id as string };
}

export async function findOwnerByNationalId(
  db: Database,
  orgId: string,
  nationalId: string
): Promise<Owner | null> {
  const [row] = await db.execute(sql`
    SELECT
      id, org_id, name, email,
      pgp_sym_decrypt(national_id_encrypted, current_setting('app.encryption_key')) AS national_id,
      CASE WHEN phone_encrypted IS NOT NULL
        THEN pgp_sym_decrypt(phone_encrypted, current_setting('app.encryption_key'))
        ELSE NULL
      END AS phone,
      notes, created_at, updated_at, archived_at
    FROM owners
    WHERE org_id = ${orgId}
      AND national_id_hash = ${hmac(nationalId)}
      AND archived_at IS NULL
    LIMIT 1
  `);
  return row ?? null;
}

    Resolving the active share

    Every Contractor request starts by resolving the share. The helper:

    packages/db/src/helpers/resolve-share.ts
    import { eq, and, isNull } from 'drizzle-orm';
import { Database } from '../client';
import { shares } from '../schema/collaboration';
import { sharePermissionsSchema } from '../schema/_share-permissions';

export async function resolveActiveShare(
  db: Database,
  projectId: string,
  contractorId: string
): Promise<Share | null> {
  const [share] = await db
    .select()
    .from(shares)
    .where(and(
      eq(shares.projectId, projectId),
      eq(shares.contractorId, contractorId),
      isNull(shares.revokedAt)
    ))
    .limit(1);

  if (!share) return null;

  // VALIDATE the JSONB at read time too — defends against corrupted rows
  const parsed = sharePermissionsSchema.safeParse(share.permissions);
  if (!parsed.success) {
    // Corrupted permissions → treat as no permissions (fail closed)
    logger.error({
      msg: 'share permissions failed schema validation — treating as no access',
      shareId: share.id,
      errors: parsed.error.flatten(),
    });
    return null;
  }

  return { ...share, permissions: parsed.data };
}

    Note the fail-closed pattern: if validation fails on a stored share (which could only happen via direct DB manipulation), we treat it as "no access" rather than letting it through. Defense in depth.

    Why notes uses polymorphic target (and trade-offs)

    The notes table has target_type + target_id instead of separate project_id, apartment_id, owner_id columns. The decision and its costs:

    • Pro: One table for all annotation needs. A new annotatable entity (e.g., "task") doesn't require schema migration — just a new value for target_type.
    • Pro: Common query patterns work. "Show me all notes for this apartment" is WHERE target_type='apartment' AND target_id=<id> — fast with the composite index.
    • Con: No FK constraint on target_id. The DB can't enforce "target_id is a valid apartment if target_type=apartment." Mitigation: application code never writes notes without confirming the target exists first.
    • Con: Orphan notes on deletion. If an apartment is hard-deleted, its notes become orphans. Mitigation: we soft-delete apartments; orphans are theoretical.

    The trade-off is fine for MVP. If we hit edge cases (e.g., orphans appear), the migration to separate tables is straightforward: project_notes, apartment_notes, owner_notes — each with proper FK.

    DB-level append-only permissions

    The schema is enforced by grants, not by policy. app_user has INSERT + SELECT but not UPDATE or DELETE:

    migrations/0006_audit_log.sql (appended)
    -- app_user can insert audit and read it. Cannot modify or delete.
GRANT SELECT, INSERT ON audit_log TO app_user;
REVOKE UPDATE, DELETE ON audit_log FROM app_user;

-- provider_app_role: SELECT (read for support) + INSERT (its own writes for system actions).
-- Still no UPDATE or DELETE — even provider tier cannot erase audit.
GRANT SELECT, INSERT ON audit_log TO provider_app_role;
REVOKE UPDATE, DELETE ON audit_log FROM provider_app_role;

    This is the structural guarantee. An attacker who fully compromises the app code still cannot delete audit entries — because the database role they're connected as doesn't have permission. The only path to delete is via a superuser running migrations, which is a documented, audited, two-person operation.

    Example: a service using AuditService

    The pattern looks like this in service code (full service code is Phase 2; this is illustrative):

    apps/api/src/shares/shares.service.ts (excerpt)
    @Injectable()
export class SharesService {
  constructor(
    private audit: AuditService,
  ) {}

  async revokeShare(orgId: string, shareId: string, reason: string) {
    return withTenant(orgId, async (db) => {
      // 1. Load the share (before-state)
      const [before] = await db.select().from(shares).where(eq(shares.id, shareId));
      if (!before) throw new NotFoundError('share');

      // 2. Perform the revocation
      const [after] = await db
        .update(shares)
        .set({ revokedAt: new Date(), revokedBy: this.audit.getContext().actorId })
        .where(eq(shares.id, shareId))
        .returning();

      // 3. Audit — same transaction
      await this.audit.log({
        orgId,
        action: 'share.revoked',
        targetTable: 'shares',
        targetId: shareId,
        before: { revokedAt: before.revokedAt },
        after: { revokedAt: after.revokedAt },
        metadata: { reason },
      }, db);

      return after;
    });
  }
}

    If the audit insert fails for any reason, the transaction rolls back — the share isn't revoked either. State changes and their audit entries are atomic.

    Verifying pgcrypto works at startup

    The app's startup procedure verifies that pgcrypto round-trips correctly with the configured keys. If misconfigured, the app fails fast:

    packages/db/src/startup-check.ts
    import { sql } from 'drizzle-orm';
import { db } from './client';
import { env } from './env';

export async function verifyEncryptionStartup() {
  const testPlaintext = '__startup_check__';

  // Test encryption + decryption round trip with the configured key
  const [{ decrypted }] = await db.execute(sql`
    SELECT pgp_sym_decrypt(
      pgp_sym_encrypt(${testPlaintext}, ${env.PII_ENCRYPTION_KEY}),
      ${env.PII_ENCRYPTION_KEY}
    ) AS decrypted
  `);

  if (decrypted !== testPlaintext) {
    throw new Error('pgcrypto round-trip failed — encryption key is misconfigured');
  }

  // Test HMAC determinism
  const [{ h1 }] = await db.execute(sql`
    SELECT encode(hmac(${testPlaintext}::bytea, ${env.PII_HASH_KEY}::bytea, 'sha256'), 'hex') AS h1
  `);
  const [{ h2 }] = await db.execute(sql`
    SELECT encode(hmac(${testPlaintext}::bytea, ${env.PII_HASH_KEY}::bytea, 'sha256'), 'hex') AS h2
  `);

  if (h1 !== h2) {
    throw new Error('HMAC determinism failed — hash key is misconfigured');
  }

  console.info('[startup] pgcrypto verified — encryption ready');
}

    Called from main.ts after the app boots but before it accepts requests. A misconfiguration is loud and immediate — never silent.

    A note on key storage in Neon

    The PII_ENCRYPTION_KEY and PII_HASH_KEY are stored as Railway environment variables (Section 14 of Doc 07 — Secret Rotation). They are NOT stored in:

    • The database itself (would defeat the purpose)
    • The code (any commit exposes them)
    • Application-level config files committed to git
    • Cloud Run/Render/Vercel public env (Railway has private env vars; verify same for any host)

    The keys are loaded from process.env at startup, validated by T3-env (Section P1.1), then passed via session-level SET LOCAL app.encryption_key inside withTenant transactions. They never appear in query logs because SET LOCAL is parameter-bound.

    Hebrew collation — sorting Israeli names correctly

    Without a Hebrew-aware collation, ORDER BY name sorts Hebrew text via byte order, which produces nonsense (אבי comes after תמר). The default Neon locale is en_US.UTF-8. We need an ICU collation to sort Hebrew text correctly in lists like "Owners by name" or "Tenants of a building".

    The extensions migration adds the collation:

  provider = icu,
  locale = 'he-IL-x-icu',
  deterministic = false
);

DO $$
DECLARE
  result text;
BEGIN
  SELECT string_agg(name, ',' ORDER BY name COLLATE he_il_icu)
    INTO result
    FROM (VALUES ('תמר'), ('אבי'), ('בן')) AS t(name);
  IF result <> 'אבי,בן,תמר' THEN
    RAISE EXCEPTION 'he_il_icu collation produced unexpected sort: %', result;

    RLS Policies — Apply to All Multi-Tenant Tables
    Owner: Backend Est: 1.5 days Depends on: P1.2-P1.9
    Why this task is critical

    Row-Level Security is the final, structural defense against cross-tenant data leakage. Every multi-tenant table needs it. One missing policy = one possible breach. A failure of this task makes T1.5 (the critical test) fail; deployments are blocked until fixed. See Doc 07 Section 10 for the full security rationale.

    The pattern: ENABLE + FORCE

    Every policy follows the same pattern: enable RLS, force it (so even the table owner respects it), then create the policy:

    RLS application pattern
    -- 1. Enable RLS on the table
ALTER TABLE <table> ENABLE ROW LEVEL SECURITY;

-- 2. FORCE — even the table owner is subject to policies
-- (provider_app_role bypasses via BYPASSRLS attribute, not via ownership)
ALTER TABLE <table> FORCE ROW LEVEL SECURITY;

-- 3. Create the isolation policy
CREATE POLICY tenant_isolation ON <table>
  USING (...)        -- filter for SELECT/UPDATE/DELETE
  WITH CHECK (...);  -- filter for INSERT/UPDATE (rows being written)

    Critical: the true in current_setting

    Every policy uses current_setting('app.organization_id', true) — the second argument being true. This is critical:

    • Without true: if the setting hasn't been set (i.e., withTenant was forgotten), Postgres raises an error: "unrecognized configuration parameter."
    • With true: returns NULL. The policy then evaluates to org_id = NULL, which is always FALSE in SQL. The query returns zero rows.

    The second behavior is what we want: a missing tenant context returns no rows, not an exception. This is the safe default — and it's what makes T1.5 Scenario 6 (no tenant context → 0 rows) pass.

    A note on policy performance

    Subquery policies (Template B) add per-query cost. Mitigations:

    • Indexes on the joined columns: buildings(project_id), apartments(building_id), ownerships(apartment_id)
    • Indexes on the org_id columns: projects(org_id)
    • The Postgres planner inlines policies into the query plan; well-indexed joins are sub-millisecond
    • For very hot paths, denormalize: if a deep table is queried heavily, add a direct org_id column (with FK + check trigger to maintain consistency)

    For our scale (MVP through 100 orgs), the joined policy approach is fine. We measure (P1.12 indexes), and if anything is slow we denormalize.

    Composite Indexes for Common Queries
    Owner: Backend Est: 0.5 day Depends on: P1.11
    Goal

    Most composite indexes were created alongside their tables in P1.2-P1.9. This task is the verification + filling in any indexes that weren't obvious until RLS policies are in place. RLS policies create implicit query patterns (every query becomes "filter by org_id AND something else"), and the indexes must support these patterns.

    The RLS index principle

    Every RLS policy adds an implicit filter to every query. The composite index must lead with the same column the RLS filters on. Specifically:

    • If RLS filters by org_id directly: index leads with org_id.
    • If RLS filters via parent (e.g., project_id IN (SELECT ... WHERE org_id = ...)): index on the FK column (project_id) is enough — the planner handles the join.
    • For partial unique indexes (e.g., "unique active membership"), the partial WHERE clause must match the typical query.

    Index maintenance considerations

    Indexes are not free:

    • Each INSERT/UPDATE/DELETE updates relevant indexes. More indexes = slower writes.

    Our index list is justified: every entry serves a known query pattern. We don't add indexes "just in case." If a new query appears that's slow, we add an index then — based on EXPLAIN data, not speculation.

    withTenant — the full implementation

    The wrapper that 99% of application code uses. Sets tenant context + encryption key, runs the callback in a transaction:

    packages/db/src/wrappers/with-tenant.ts
    import { sql } from 'drizzle-orm';
import { appPool } from '../client';
import { drizzle, NodePgDatabase } from 'drizzle-orm/node-postgres';
import { env } from '../env';
import * as schema from '../schema';

type TenantDatabase = NodePgDatabase<typeof schema>;

const UUID_REGEX = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

function isUuid(s: string): boolean {
  return typeof s === 'string' && UUID_REGEX.test(s);
}

/**
 * The only path to customer-facing data in the codebase.
 *
 * Sets app.organization_id (used by RLS policies) and app.encryption_key
 * (used by pgcrypto helpers) for the duration of a transaction.
 *
 * IMPORTANT:
 * - Direct use of `db` outside this wrapper is forbidden by ESLint rule.
 * - Both setting use SET LOCAL — scoped to this transaction only.
 * - On rollback (anything thrown inside fn), both contexts are discarded.
 */
export async function withTenant<T>(
  orgId: string,
  fn: (tx: TenantDatabase) => Promise<T>,
  options?: {
    userId?: string;   // optional — for policies that also filter by user
  }
): Promise<T> {
  // Defensive validation
  if (!isUuid(orgId)) {
    throw new Error('withTenant: orgId must be a valid UUID');
  }
  if (options?.userId && !isUuid(options.userId)) {
    throw new Error('withTenant: userId must be a valid UUID');
  }

  // Acquire a client from the pool — manual checkout for transaction
  const client = await appPool.connect();

  try {
    await client.query('BEGIN');

    // SET LOCAL — transaction-scoped, doesn't leak to next pooled request
    await client.query({
      text: 'SELECT set_config($1, $2, true)',
      values: ['app.organization_id', orgId],
    });

    // Encryption key — pgcrypto helpers read via current_setting
    await client.query({
      text: 'SELECT set_config($1, $2, true)',
      values: ['app.encryption_key', env.PII_ENCRYPTION_KEY],
    });

    // Optional user_id — for notifications RLS policy
    if (options?.userId) {
      await client.query({
        text: 'SELECT set_config($1, $2, true)',
        values: ['app.user_id', options.userId],
      });
    }

    // Wrap the pooled client in drizzle for the user's callback
    const tx = drizzle(client, { schema });

    const result = await fn(tx);

    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {});
    throw err;
  } finally {
    client.release();
  }
}

    Key implementation details:

    • Manual client checkout. We don't use Drizzle's db.transaction(...) helper because it doesn't give us a hook to run SET LOCAL before the user's callback. Manual BEGIN/COMMIT/ROLLBACK is explicit and predictable.
    • set_config(name, value, true) is the function-form equivalent of SET LOCAL. The third argument true means "local to current transaction" — same semantics as SET LOCAL, but works inside a prepared statement.
    • Parameter binding for the setting value. We pass the orgId and key as parameters, not interpolated into the SQL. This prevents log leakage (the value doesn't appear in query logs).
    • ROLLBACK on any throw. The .catch(() => {}) swallows secondary errors if ROLLBACK itself fails — the primary error is what matters.
    • client.release() in finally. Even if BEGIN, the work, or COMMIT throw, the client is returned to the pool. Connection leak is impossible.
    withProvider — the cross-tenant wrapper

    Mirror of withTenant for the EMAPP team. Uses the provider pool, requires a reason, writes audit before the work:

    import { sql } from 'drizzle-orm';
import { providerPool } from '../client';
import { drizzle, NodePgDatabase } from 'drizzle-orm/node-postgres';
import * as schema from '../schema';

type ProviderDatabase = NodePgDatabase<typeof schema>;

interface ProviderContext {
  ip?: string;
  userAgent?: string;
}

const UUID_REGEX = /^[0-9a-f]{8}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{4}-[0-9a-f]{12}$/i;

function isUuid(s: string): boolean {
  return typeof s === 'string' && UUID_REGEX.test(s);
}

/**
 * The path for Provider tier (EMAPP team) access to data.
 *
 * Uses the provider_app_role pool — bypasses RLS, can query across tenants.
 * EVERY call writes an audit_log entry BEFORE the work runs.
 *
 * MANDATORY:
 * - providerUserId must be a valid UUID
 * - reason must be a non-empty string (minimum 5 chars)
 *
 * The reason is the most important field — it answers
 * "why did this provider access customer data?" Forever.
 */
export async function withProvider<T>(
  providerUserId: string,
  reason: string,
  fn: (tx: ProviderDatabase) => Promise<T>,
  context?: ProviderContext
): Promise<T> {
  // Defensive validation
  if (!isUuid(providerUserId)) {
    throw new Error('withProvider: providerUserId must be a valid UUID');
  }
  if (!reason || reason.trim().length < 5) {
    throw new Error('withProvider: reason is required (minimum 5 chars)');
  }

  const client = await providerPool.connect();
  const startTime = new Date();

  try {
    await client.query('BEGIN');

    // Set provider context (separate session vars from withTenant)
    await client.query({
      text: 'SELECT set_config($1, $2, true)',
      values: ['app.provider_user_id', providerUserId],
    });
    await client.query({
      text: 'SELECT set_config($1, $2, true)',
      values: ['app.access_reason', reason.trim()],
    });

    // Audit BEFORE the work — same transaction.
    // If the work fails, audit is rolled back too. But the failed
    // ATTEMPT is captured by Sentry, separately.
    await client.query({
      text: `
        INSERT INTO provider_audit_log
          (provider_user_id, reason, action_type, started_at, ip, user_agent)
        VALUES
          ($1, $2, $3, $4, $5, $6)
      `,
      values: [
        providerUserId,
        reason.trim(),
        'session',
        startTime.toISOString(),
        context?.ip ?? null,
        context?.userAgent ?? null,
      ],
    });

    // Run the user's code
    const tx = drizzle(client, { schema });
    const result = await fn(tx);

    await client.query('COMMIT');
    return result;
  } catch (err) {
    await client.query('ROLLBACK').catch(() => {});

    // Capture failure context for Sentry — the attempt itself
    // is meaningful, even if no audit row was committed.
    Sentry.captureException(err, {
      tags: { providerAccess: 'failed' },
      extra: { providerUserId, reason },
    });

    throw err;
  } finally {
    client.release();
  }
}

    Why we don't use Drizzle's db.transaction()

    Drizzle provides db.transaction(async (tx) => { ... }). We could use it instead of manual BEGIN/COMMIT. We don't, for two reasons:

    • Setup ordering. Drizzle's transaction helper has no hook to run SET LOCAL before the user's callback. We'd have to call it as the first line of every callback — easily forgotten. Manual control means SET LOCAL is always executed, in the right place, before any application code.
    • Pool client identity. Drizzle's tx inside the callback might not be the same physical client as where we'd have run SET LOCAL. Manual checkout guarantees the same client is used throughout.

    The 10 extra lines of manual transaction code are worth the certainty.

    import { S3Client, GetObjectCommand, PutObjectCommand, DeleteObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';
import { IStorageProvider, UploadUrlOptions, DownloadUrlOptions } from './storage.interface';

export class R2StorageProvider implements IStorageProvider {
  private client: S3Client;

  constructor(private bucket: string, accountId: string, accessKey: string, secretKey: string) {
    // R2 is S3-compatible — pointed at Cloudflare endpoint
    this.client = new S3Client({
      region: 'auto',
      endpoint: `https://${accountId}.r2.cloudflarestorage.com`,
      credentials: { accessKeyId: accessKey, secretAccessKey: secretKey },
    });
  }

  async getUploadUrl(key: string, opts: UploadUrlOptions): Promise<string> {
    const cmd = new PutObjectCommand({
      Bucket: this.bucket,
      Key: key,
      ContentType: opts.contentType,
      ContentLength: opts.maxSizeBytes,
    });
    return getSignedUrl(this.client, cmd, { expiresIn: opts.ttlSeconds });
  }

  async getDownloadUrl(key: string, opts: DownloadUrlOptions): Promise<string> {
    const cmd = new GetObjectCommand({
      Bucket: this.bucket,
      Key: key,
      ResponseContentDisposition: opts.responseFilename
        ? `attachment; filename="${opts.responseFilename}"`
        : undefined,
    });
    return getSignedUrl(this.client, cmd, { expiresIn: opts.ttlSeconds });
  }

  async delete(key: string): Promise<void> {
    await this.client.send(new DeleteObjectCommand({ Bucket: this.bucket, Key: key }));
  }

  async healthCheck(): Promise<void> {
    // List one object as a connectivity test
    await this.client.send(new ListObjectsV2Command({ Bucket: this.bucket, MaxKeys: 1 }));
  }
}

    T.4 T1.5 — The Canonical RLS Isolation Test

    The most important test in the codebase. Defined in Doc 07 Section 10.6; restated here in the implementation context.

    Seven scenarios, all must pass:

    1. SELECT can't read across tenants
    2. SELECT by ID for another org returns 0 rows (no error, no leak)
    3. INSERT with another org's FK fails (WITH CHECK clause)
    4. UPDATE of another org's row is a no-op (affects 0 rows)
    5. DELETE of another org's row is a no-op
    6. No tenant context (forgotten withTenant) returns 0 rows everywhere
    7. Multi-org user only sees current org context

    T.10 What the Test Suite Cannot Catch

    Honest accounting of test suite limitations (also see Doc 07 Section 11.11):

    • Race conditions in concurrent updates. Tests run sequentially. Production has many concurrent users.
    • Performance regressions in specific data shapes. Test data is small; production data has skew.
    • Bugs that depend on production environment. Cloud-specific Postgres versions, network latency variations.
    • Business logic bugs. Tests verify the data layer is correct, not that the business rules are.
    • Schema drift between environments. If staging has a different schema than production, T1.x in CI won't catch it. Mitigation: migrations are versioned and replayed identically.
    ✓ The CI gate that protects production
    T1.5, T1.6, T1.7 are non-negotiable. A PR that breaks any of them cannot merge. The CI configuration enforces this — no human can "approve and merge" past it. The cost of running these tests on every push is ~30 seconds; the cost of letting them fail in production is incalculable. The math is obvious.
    P · CODE PATTERNS

    How Services Use Phase 1

    The recurring patterns that service code follows when consuming the data layer.

    Phase 2 builds service classes that use Phase 1's wrappers, helpers, and interfaces. The patterns are consistent — and consistency makes review easier, onboarding faster, bugs rarer. This section documents the patterns once so they don't need re-inventing per service.

    P.1 The Service Method Skeleton

    Every service method follows the same outline. Once you see one, the rest are familiar:

    Service method skeleton
    @Injectable()
export class ExampleService {
  constructor(
    private audit: AuditService,
    @Inject(EMAIL) private email: IEmailProvider,
  ) {}

  async doSomething(orgId: string, userId: string, input: SomeDto) {
    // 1. Open a tenant-scoped transaction
    return withTenant(orgId, async (tx) => {
      // 2. Read what you need to verify state
      const [existing] = await tx.select()
        .from(someTable)
        .where(eq(someTable.id, input.id));
      if (!existing) throw new NotFoundError();

      // 3. Check business-level permissions (beyond RBAC)
      if (existing.status === 'archived') {
        throw new ConflictError('cannot modify archived');
      }

      // 4. Perform the work
      const [updated] = await tx.update(someTable)
        .set({ ...input })
        .where(eq(someTable.id, input.id))
        .returning();

      // 5. Audit the change (same transaction)
      await this.audit.log({
        orgId,
        action: 'something.updated',
        targetTable: 'something',
        targetId: updated.id,
        before: { status: existing.status },
        after: { status: updated.status },
      }, tx);

      // 6. Side effects via interfaces (after audit, before return)
      await this.email.send({
        to: existing.notifyEmail,
        subject: 'Updated',
        text: 'Your record was updated.',
      });

      // 7. Return the result
      return updated;
    });
  }
}

    Steps 1, 5, and 7 are mechanical. Steps 2, 3, 4 are business logic. Step 6 (side effects) is the interesting one — it happens inside the transaction. If audit fails, the side effect is rolled back too. This means the email is sent only if the audit committed — never out of sync.

    P.2 The Side-Effect Question

    Step 6 above is subtle. Sending emails inside a transaction is risky:

    • Email send takes time. Holding a DB transaction for 1-2 seconds is bad — connections in the pool are scarce.
    • Email failure may roll back DB work. If Resend is down, the user's action gets undone. Sometimes that's right; sometimes not.
    • Idempotency is hard. If the transaction commits but the email retry fails, do we have a duplicate email later?

    Our rule: side effects that must succeed-or-revert run inside the transaction. Side effects that are best-effort run after.

    Pattern: best-effort side effect (after commit)
    async createShare(orgId: string, input: CreateShareDto) {
  const share = await withTenant(orgId, async (tx) => {
    const [created] = await tx.insert(shares).values(...).returning();
    await this.audit.log({ ... }, tx);
    return created;
  });
  // Transaction committed. Email is best-effort.
  // If it fails: log error, don't roll back the share.
  try {
    await this.email.send({
      to: input.contractorEmail,
      subject: 'You have access to a project',
      html: renderInviteEmail(share),
    });
  } catch (err) {
    logger.error({ msg: 'share invite email failed', shareId: share.id, err });
    // Future: queue retry; for MVP, log and move on
  }
  return share;
}

    P.3 The Manager / Agent / Contractor Pattern

    Many services need to handle three roles differently. Pattern: extract the role-specific query at the start:

    Pattern: role-aware data access
    async listProjects(orgId: string, user: AuthUser): Promise<Project[]> {
  return withTenant(orgId, async (tx) => {
    if (user.role === 'manager') {
      // Manager: all projects in org (RLS handles isolation)
      return tx.select().from(projects).where(isNull(projects.archivedAt));
    }

    if (user.role === 'agent') {
      // Agent: only assigned projects
      return tx
        .select({ project: projects })
        .from(projects)
        .innerJoin(projectAssignments, eq(projectAssignments.projectId, projects.id))
        .where(and(
          eq(projectAssignments.userId, user.id),
          isNull(projectAssignments.unassignedAt),
          isNull(projects.archivedAt),
        ))
        .then((rows) => rows.map((r) => r.project));
    }

    if (user.role === 'contractor') {
      // Contractor: only projects with active share
      return tx
        .select({ project: projects })
        .from(projects)
        .innerJoin(shares, eq(shares.projectId, projects.id))
        .where(and(
          eq(shares.contractorId, user.id),
          isNull(shares.revokedAt),
          isNull(projects.archivedAt),
        ))
        .then((rows) => rows.map((r) => r.project));
    }

    throw new ForbiddenError('role cannot list projects');
  });
}

    P.4 The "Find Or Throw 404" Pattern

    Repeated everywhere — extract to a helper:

    Pattern: find-or-404 helper
    async function findOrThrow<T>(
  promise: Promise<T | undefined>,
  entity: string
): Promise<T> {
  const result = await promise;
  if (!result) throw new NotFoundError(entity);
  return result;
}

// Usage:
const project = await findOrThrow(
  tx.query.projects.findFirst({ where: eq(projects.id, id) }),
  'project'
);

    Subtle but important: the 404 here doesn't distinguish "doesn't exist anywhere" from "exists but RLS filtered it." That's intentional — we don't leak existence across tenants. Doc 07 Section 7.8.

    P.5 The "Multi-Table Update" Pattern

    When an action touches multiple tables, all must be in one transaction. Pattern: use the SAME tx client:

    Pattern: multi-table update
    async assignTaskToUser(orgId: string, taskId: string, userId: string, byUserId: string) {
  return withTenant(orgId, async (tx) => {
    // 1. Verify task exists
    const task = await findOrThrow(
      tx.query.tasks.findFirst({ where: eq(tasks.id, taskId) }),
      'task'
    );

    // 2. Insert assignment (same tx)
    const [assignment] = await tx
      .insert(taskAssignees)
      .values({ taskId, userId, assignedBy: byUserId })
      .onConflictDoNothing()  // no-op if already assigned
      .returning();

    // 3. Insert notification for the assignee (same tx)
    await tx.insert(notifications).values({
      orgId,
      userId,
      type: 'task_assigned',
      title: 'Task assigned to you',
      body: task.title,
      link: `/tasks/${task.id}`,
    });

    // 4. Audit (same tx)
    await this.audit.log({
      orgId,
      action: 'task.assigned',
      targetTable: 'tasks',
      targetId: taskId,
      metadata: { assignedTo: userId, assignedBy: byUserId },
    }, tx);

    return assignment;
  });
}

    All four operations succeed-or-fail together. If the notification insert fails, the assignment isn't recorded either — no orphan state.

    P.6 The "Encrypt-or-Plaintext Field" Pattern

    Owners need a national_id (encrypted) and a name (plaintext). The helper handles both:

    Pattern: PII field handling
    async updateOwner(orgId: string, ownerId: string, input: UpdateOwnerDto) {
  return withTenant(orgId, async (tx) => {
    const existing = await findOrThrow(
      tx.query.owners.findFirst({ where: eq(owners.id, ownerId) }),
      'owner'
    );

    const updates: any = {};

    // Plaintext fields: just assign
    if (input.name !== undefined) updates.name = input.name;
    if (input.email !== undefined) updates.email = input.email;

    // Encrypted fields: use SQL helper (encrypt + hash)
    if (input.nationalId !== undefined) {
      await tx.execute(sql`
        UPDATE owners
        SET
          national_id_encrypted = pgp_sym_encrypt(${input.nationalId}, current_setting('app.encryption_key')),
          national_id_hash = ${this.encryption.hash(input.nationalId)},
          updated_at = NOW()
        WHERE id = ${ownerId}
      `);
    }

    // Plain fields go through Drizzle update
    if (Object.keys(updates).length > 0) {
      await tx.update(owners).set(updates).where(eq(owners.id, ownerId));
    }

    // Audit — careful not to include PII!
    await this.audit.log({
      orgId,
      action: 'owner.updated',
      targetTable: 'owners',
      targetId: ownerId,
      // before/after fields exclude national_id — never write PII to audit
      before: { name: existing.name, email: existing.email },
      after: { name: updates.name ?? existing.name, email: updates.email ?? existing.email },
    }, tx);
  });
}

    P.7 The "Read with Permissions Filter" Pattern

    When a Contractor reads, the response must be filtered by share.permissions. Pattern: fetch full, then filter:

    Pattern: contractor-filtered response
    async getApartmentForContractor(
  orgId: string, projectId: string, apartmentId: string, contractorId: string
) {
  return withTenant(orgId, async (tx) => {
    // 1. Resolve share (or 403)
    const share = await resolveActiveShare(tx, projectId, contractorId);
    if (!share) throw new ForbiddenError('no active share');

    // 2. Fetch the apartment with full owner data (RLS scopes to org)
    const apt = await findOrThrow(
      tx.query.apartments.findFirst({
        where: eq(apartments.id, apartmentId),
        with: { owners: { with: { owner: true } } },
      }),
      'apartment'
    );

    // 3. Filter response based on share permissions
    // (CRITICAL: hidden fields are ABSENT not null — see Doc 07 §7.4)
    return {
      id: apt.id,
      number: apt.number,
      status: share.permissions.overview.on ? apt.status : undefined,
      owners: share.permissions.tenants.on
        ? apt.owners.map((own) => filterTenantByPermissions(own.owner, share.permissions))
        : undefined,
    };
  });
}

    P.8 The Composition Pattern

    Larger workflows compose smaller services. Each service has its own withTenant; the outer service calls them sequentially:

    Pattern: composing services
    async createProjectWithBuildings(orgId: string, userId: string, input: CreateProjectDto) {
  // Outer withTenant — all sub-operations join this transaction
  return withTenant(orgId, async (tx) => {
    const project = await this.projectsService.createInternal(tx, orgId, userId, input.project);

    const buildings = [];
    for (const bldg of input.buildings) {
      const b = await this.buildingsService.createInternal(tx, project.id, bldg);
      buildings.push(b);
    }

    return { project, buildings };
  });
}

    Note: createInternal methods take a tx argument and don't open their own withTenant. They assume the caller has tenant context already. Public methods (without "Internal") open withTenant; internal methods join an existing transaction.

    P.9 The Anti-Patterns We Avoid

    • Multiple withTenant calls for one user action. Each opens a new transaction; intermediate failures leave partial state. Use one withTenant + composed internal methods.
    • Async work outside withTenant that uses tenant-scoped data. The data isn't filtered; risky.
    • Direct db.query.* in service code. ESLint catches this.
    • String-concatenating into SQL. Use Drizzle's sql tag with parameters.
    • Returning database rows directly to API consumers. Schema includes internal columns (e.g., national_id_hash) that shouldn't leak; map to a clean DTO.
    • Try-catching to ignore errors silently. Either retry, log explicitly, or let it propagate. Silent failures are the worst kind.
    • Putting PII in metadata JSONB. Same rules as audit — PII isn't allowed in metadata fields.
    💡 Patterns vs prescriptions
    These patterns are documented because they recur. Following them makes code review faster and bugs rarer. But they're not rigid prescriptions — if a specific case has a reason to diverge, document the reason. Patterns serve the codebase, not the other way around.
    ! · COMMON PITFALLS

    Mistakes We've Seen, and How to Avoid Them

    Mistakes that look fine in isolation but cause real bugs. Documented here so future developers don't repeat them.

    Every section above describes what we do. This section describes what we've seen go wrong — by us or by similar projects — and how to recognize the mistake before it costs a week of debugging. Read this section before writing any Phase 1 code, then re-read it before Phase 2.

    !.1 Forgetting withTenant

    The mistake:

    Anti-pattern
    // BAD — direct query, no tenant context
async getMyProjects() {
  return db.query.projects.findMany();
}

    What happens: No app.organization_id is set. RLS returns 0 rows (the policy condition evaluates to false). In dev with seeded data, this looks like "no projects found." Developer adds workarounds. Eventually, someone bypasses the wrapper to "fix it" — and now there's a real cross-tenant leak.

    The fix: ESLint rule blocks direct db.query.* in service files (P1.13). Even if the rule is somehow bypassed, the RLS policy still returns zero rows — fail-closed by design.

    !.2 Setting app.organization_id via SET (not SET LOCAL)

    The mistake:

    Anti-pattern
    // BAD — SET (without LOCAL) persists across the connection's lifetime
await client.query(`SET app.organization_id = '${orgId}'`);

    What happens: The setting persists on the pooled connection. The next request that grabs this connection inherits the previous tenant's context. This is a cross-tenant leak.

    The fix: Always use SET LOCAL (transaction-scoped). withTenant uses SELECT set_config(name, value, true) — the true means LOCAL. The setting dies with the transaction.

    !.3 String-Interpolating UUIDs into SQL

    The mistake:

    Anti-pattern
    // BAD — orgId could be malformed or malicious; lands in query logs
await tx.execute(sql.raw(`SET LOCAL app.organization_id = '${orgId}'`));

    What happens: If orgId is somehow malformed (e.g., contains a single quote), SQL injection becomes possible. Even without injection, the orgId appears in query logs and Sentry breadcrumbs.

    The fix: Always parameter-bind via set_config($1, $2, true). Drizzle's sql tag with template literal interpolation does this automatically, but sql.raw() does not — never use sql.raw() with user input.

    !.4 Encrypting in App Instead of SQL

    The mistake:

    Anti-pattern
    // BAD — encryption at app layer means plaintext crosses the wire to DB
const encrypted = aes256.encrypt(nationalId, key);
await tx.insert(owners).values({ nationalIdEncrypted: encrypted, ... });

    What happens: Two problems. First, the encryption key has to be in app memory, where it's more exposed than in the DB session. Second, encryption logic varies between languages and libraries — DBA tools, future Python/Go services, manual queries — all need to know the same scheme.

    The fix: Use pgp_sym_encrypt() in SQL, with the key as a session variable. Plaintext crosses the wire once (in the INSERT statement); everything stored and read is uniform. Single source of truth: pgcrypto.

    !.5 Forgetting FORCE ROW LEVEL SECURITY

    The mistake:

    Anti-pattern
    // BAD — ENABLE but no FORCE
ALTER TABLE projects ENABLE ROW LEVEL SECURITY;
CREATE POLICY tenant_isolation ON projects USING (...);

    What happens: Without FORCE, the table owner bypasses RLS. If the migration runs as the database owner (which it does), the policy works for app_user but not for the migration role. Worse: if anyone runs queries as superuser/owner, they see ALL data — even though the policy "is enabled."

    The fix: Always pair ENABLE + FORCE. The verify-rls.sql check in P1.11 catches missing FORCE.

    !.6 Sub-Query Policy Without an Index

    The mistake:

    Anti-pattern
    CREATE POLICY tenant_isolation ON apartments
  USING (
    project_id IN (
      SELECT id FROM projects
      WHERE org_id = current_setting('app.organization_id', true)::uuid
    )
  );

// BUT no index on projects(org_id)

    What happens: Every query against apartments runs a sub-query against projects. Without an index on projects(org_id), that's a full scan of projects. As projects grow, every single apartment query gets slower. By 100 orgs, the API feels broken.

    The fix: Every column referenced in an RLS policy must have an index. projects(org_id, id), buildings(project_id), apartments(building_id). The Postgres planner handles the rest.

    !.7 Confusing 403 and 404

    The mistake:

    Anti-pattern
    async getProject(orgId: string, projectId: string) {
  return withTenant(orgId, async (tx) => {
    const [proj] = await tx.select().from(projects).where(eq(projects.id, projectId));
    if (!proj) {
      // BAD — leaks existence
      if (await projectExistsAnywhere(projectId)) {
        throw new ForbiddenError('you cannot access this project');
      }
      throw new NotFoundError('project');
    }
    return proj;
  });
}

    What happens: An attacker can guess project IDs (UUIDs are random, but if leaked elsewhere, they're usable). Different responses for "doesn't exist" vs "exists but yours" reveal cross-tenant existence. They learn which IDs are valid in other tenants.

    The fix: Return 404 for both cases. If RLS returns no row, the resource is "not found" — period. Don't probe across tenants to give a more "helpful" error. See Doc 07 §7.8 for the full reasoning.

    !.8 Audit Inserts Outside the Transaction

    The mistake:

    Anti-pattern
    async revokeShare(orgId: string, shareId: string) {
  const updated = await withTenant(orgId, async (tx) => {
    return tx.update(shares).set({ revokedAt: new Date() }).where(...);
  });

  // BAD — audit insert is its own connection
  await auditService.log({ action: 'share.revoked', ... });

  return updated;
}

    What happens: The update commits. The audit insert opens a new connection (new transaction). If audit fails, the share is already revoked — but there's no record of who did it. The audit log is incomplete in exactly the cases that matter most.

    The fix: Audit happens inside the same withTenant transaction:

    Correct
    async revokeShare(orgId: string, shareId: string) {
  return withTenant(orgId, async (tx) => {
    const [updated] = await tx.update(shares)...returning();
    await this.audit.log({ action: 'share.revoked', ... }, tx);  // SAME tx
    return updated;
  });
}

    Atomicity is the contract: state change and its audit succeed together, or neither happens.

    !.9 Returning Database Rows Directly to API Consumers

    The mistake:

    Anti-pattern
    @Get(':id')
async getOwner(@Param('id') id: string) {
  return this.ownersService.findById(id);  // returns full Owner row
}

    What happens: The response includes nationalIdEncrypted (a BYTEA blob) and nationalIdHash (a hex string). These are internal artifacts — they shouldn't leave the backend. Worse, if a future column is added with sensitive data, the API silently exposes it.

    The fix: Map DB rows to DTOs explicitly. Service code returns DTOs, not Drizzle types:

    Correct
    export interface OwnerDto {
  id: string;
  name: string;
  email: string | null;
  nationalId: string;  // decrypted plaintext
  phone: string | null;
}

async findById(orgId: string, id: string): Promise<OwnerDto> {
  return withTenant(orgId, async (tx) => {
    const [row] = await tx.execute(sql`
      SELECT id, name, email,
             pgp_sym_decrypt(national_id_encrypted, current_setting('app.encryption_key')) AS national_id,
             CASE WHEN phone_encrypted IS NOT NULL
               THEN pgp_sym_decrypt(phone_encrypted, current_setting('app.encryption_key'))
               ELSE NULL END AS phone
      FROM owners WHERE id = ${id}
    `);
    if (!row) throw new NotFoundError('owner');
    return mapToOwnerDto(row);
  });
}

    !.10 Putting PII into metadata JSONB Fields

    The mistake:

    Anti-pattern
    await this.audit.log({
  orgId,
  action: 'owner.signed_contract',
  metadata: {
    // BAD — PII in audit_log metadata
    nationalId: '039284756',
    phone: '+972541234567',
  },
}, tx);

    What happens: The audit_log is now a parallel store of PII — but unencrypted. Audit logs are read by support, exported for customers, sometimes sent to monitoring. The PII protection of the owners table is undermined.

    The fix: Reference the entity by ID. The audit log says what happened, not which PII values. Anyone reading the audit and needing PII can look up the owner (with proper auth).

    Correct
    await this.audit.log({
  orgId,
  action: 'owner.signed_contract',
  targetTable: 'owners',
  targetId: ownerId,  // reference, not data
  metadata: { contractId, signatureMethod: 'in-person' },
}, tx);

    !.11 Closing a Transaction Without Releasing the Client

    The mistake:

    Anti-pattern
    const client = await pool.connect();
try {
  await client.query('BEGIN');
  // ... work ...
  await client.query('COMMIT');
} catch (err) {
  await client.query('ROLLBACK');
  throw err;
}
// BAD — no finally block; client never released

    What happens: On the happy path, you don't release the client. Eventually, the pool exhausts (20 connections, all checked out). New requests hang waiting. Production-impacting.

    The fix: Always finally { client.release() }. withTenant in P1.13 has this structure baked in.

    !.12 Trying to "Optimize" RLS Away

    The mistake: A senior developer profiles a slow query, sees the RLS subquery in the EXPLAIN plan, decides "I'll just add SET ROLE postgres for this hot path to skip RLS, since the app already filters."

    What happens: Now there's a hot path that bypasses the structural security. If the app filter has a bug — and app filters have bugs — there's no second layer to catch it. The whole defense-in-depth is gone for that endpoint.

    The fix: Never bypass RLS in customer-facing code. If RLS is too slow, fix the indexes or denormalize org_id onto the table. The structural defense is not optional. See Doc 07 §10 for the rationale.

    !.13 Soft-Deleting via DELETE Statement

    The mistake:

    Anti-pattern
    // BAD — actually deletes the row, not soft-deletes
await tx.delete(projects).where(eq(projects.id, id));

    What happens: CASCADE FKs kick in. Buildings, apartments, owners, documents, signatures, audit_log entries — all gone. Audit history evaporates exactly when you need it (after the deletion). If the deletion was a mistake, recovery requires restoring from backup.

    The fix: Soft delete is the default. Set archived_at = NOW(). Filter WHERE archived_at IS NULL in all queries. Hard delete is a separate, documented, audited procedure done by Provider Admin.

    !.14 Trusting req.body.org_id

    The mistake:

    Anti-pattern
    @Post()
async createProject(@Body() body: CreateProjectDto) {
  // BAD — body could specify any org_id
  return this.service.create(body.orgId, body);
}

    What happens: A Manager of org A sends { orgId: '<orgB-id>', name: 'evil' }. If the service code uses body.orgId instead of the authenticated user's org, it creates a project in org B. RLS WITH CHECK saves us in this case — but the attacker probes for similar bugs elsewhere.

    The fix: orgId always comes from the authenticated session (JWT active_org_id), never from the request body. Zod DTOs shouldn't even include orgId as a field — it's invisible to the request:

    Correct
    @Post()
async createProject(
  @Body() body: CreateProjectDto,
  @CurrentUser() user: AuthUser,
) {
  // orgId from JWT, NEVER from body
  return this.service.create(user.activeOrgId, user.id, body);
}

    !.15 The "It Works in Dev" Trap

    The mistake: Developer creates the migration, tests locally with one org and one user. Everything works. PR merged. T1.5 is skipped because "RLS works — I tested it."

    What happens: With one org, RLS can return all data and the developer can't tell. The bug surfaces in production when org #2 signs up and starts seeing org #1's data — or vice versa.

    The fix: T1.5 requires TWO test orgs. Every "isolation check" requires "data exists in both orgs; visible from one, not the other." The pattern is in the test factories. Don't shortcut.

    !.16 Skipping the Fake Providers for Tests

    The mistake: Service test uses the real ResendEmailProvider "because the fake doesn't exercise the integration."

    What happens: Tests hit the real Resend API. Tests are slow (network), flaky (Resend has hiccups), and either send real emails (annoying) or fail to send (timeouts). CI breaks intermittently.

    The fix: Unit tests use the Fake. Integration contract tests use Real, but only in dedicated integration runs (not on every PR). Two test types, two purposes — keep them separate.

    !.17 Forgetting the Pool Timeout

    The mistake: Pool config without statement_timeout. A bad query (missing WHERE, infinite loop in trigger) runs forever, holding the connection.

    What happens: Pool exhausts. New requests hang. The bad query keeps running, possibly until Neon kills the connection minutes later.

    The fix: statement_timeout: 30000 in pool config. After 30 seconds, Postgres cancels the query. The error propagates, the client is released, the pool recovers.

    !.18 Bonus: Things That Look Wrong But Are Right

    Quick reference for "the next developer might think this is a bug":

    • RLS policies use current_setting('...', true) with the true. Looks like a typo. It's not — it means "return NULL if not set" instead of erroring. Required for the failsafe behavior.
    • UUID validation in the wrappers (isUuid()). Looks redundant — Drizzle types should ensure it. But TypeScript types are erased at runtime; defensive validation catches malformed inputs.
    • provider_audit_log INSERT is in the same transaction as the work. Looks like it could roll back. Yes — and that's correct. Failed audit AND failed work are captured by Sentry separately.
    • Hidden fields are absent from response objects, not null. Looks like incomplete DTOs. Intentional — see Doc 07 §7.4.
    • Audit log fields denormalize actor_email. Looks like normalization violation. Intentional — query audit doesn't require joining users; users change emails over time and we want the historical value.
    • NoopSMSProvider is the MVP implementation. Looks broken. Intentional — see Section 6.7.

    →.6 The Long View

    Phase 1 takes about 8 working days for two part-time developers. That's not a lot — but it's the most important 8 days. Everything Phase 2+ does sits on what we built here. A bug in Phase 1 isn't a bug in one feature; it's a bug in every feature. A correct foundation isn't optional. It's the only foundation worth building.
