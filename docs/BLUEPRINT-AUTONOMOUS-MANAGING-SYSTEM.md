All five load-bearing claims are now ground-truth confirmed:

4. **Ledger one-shared-table touch**: `proposal_id` is `.notNull()` with FK + `onDelete:'restrict'`, and the key is deliberately NOT proposal_id — so making it nullable + adding a `cause` discriminator is the correct reuse-not-fork move and provably can't affect exactly-once.
5. **Documents P1 divergence**: `CockpitPulse`/`ProjectAttentionCard` are re-implemented as local functions in `documents-list.client.tsx` instead of importing from `board-primitives.tsx`.

# EMAPP → Smart Autonomous Managing System — The Single Blueprint

## 1. VERDICT

Today EMAPP is a **polite suggestion box**: a thin, single-axis recommender fleet (signature/owner only) where almost everything proposes and nothing auto-executes, sitting on top of well-built but disconnected feature-surfaces — and one of its headline numbers (the home signature KPI) is computed by a second, drifting query. The completed system becomes **smart + autonomous + managing** when it (a) **perceives every project across all axes** through ONE shared read-model, (b) **decides** what each project needs by mapping that perception to classified actions, (c) **acts** — silently auto-executing the safe/reversible/internal work and surfacing only genuine judgment calls for one-click confirm, (d) **chases every party** including the external parties (lawyer/appraiser/bank/surveyor) who are currently dead, unreachable silos, and (e) **anticipates** risk and **explains** legibly to a technophobe in plain Hebrew with no schema leaks. **The ONE architectural through-line:** a single **`ProjectPerception` object** (assembled only from existing canonical seams) feeds a **fleet of `IRecommender`s** whose every output passes **the one `classify()` boundary** and lands in the **Approval Inbox**, with **cross-party coordination** built by _wiring the already-built `decideExternalPartyAccess` resolver_ to a delivery path — **every stage extends a named seam; nothing is a second parallel implementation.**

**The two cross-cutting invariants that make it honest:**

- **Single source of truth by construction:** the home KPI becomes a _reduction_ of the same perception array the board renders (`Σ perception.signatures`), so they cannot drift — and a static CI ratchet bans any _second_ signature-count query.

# Adversarial Review — EMAPP Autonomous-Managing Blueprint

**Verdict on the blueprint as a document:** Unusually honest. I verified all five load-bearing claims against the actual code and every one holds (home divergence at `projects.service.ts:1404-1410`; the `autoExecute-ELIGIBLE but Phase-1 PROPOSES` comments; zero `recipient_*` columns in `external_share`; `outbound_ledger` idempotency key provably excludes `proposal_id`; `CockpitPulse`/`ProjectAttentionCard` re-implemented locally at `documents-list.client.tsx:327,356`). The seam-reuse discipline is real. But the blueprint has **one architectural hole it walks straight past, two slices that are mis-scoped as "buildable now," and a trust gap that no slice in the plan closes.** Prioritized below.

---

## P0 — Blocking. The plan is wrong here, not just incomplete.

### P0-1. The ACT leg (slice 1.2) crosses a layer boundary that doesn't exist. This is a hidden rewrite.

The blueprint's keystone — "add the auto-apply step in `runProposalProducerTick`: dispatch the SAME `executors[kind]`" — **cannot be built as written.** Ground truth:

- The `executors` map lives in `apps/api/src/modules/proposals/proposals.service.ts:105`, is a **NestJS `@Injectable`**, and its closures capture **constructor-injected services** (`SignatureRequestsService`, `TasksService`) plus `executeDocumentChase`.
- The producer (`runProposalProducerTick`) lives in `packages/db` / `packages/jobs` — the **worker layer**, which has no Nest DI container and cannot reach those services.

So "dispatch the SAME executors" is not a 3-foot reach; it requires either (a) extracting every executor into a DI-free, withTenant-pure function in `packages/db` that both the API approve-path and the worker call (a genuine refactor of the one path the blueprint elsewhere insists must never be touched twice), or (b) having the worker call back into the API over HTTP to "approve its own proposal." Option (b) is a second outbound-ish path and a security smell. Option (a) is correct **but it is the single largest piece of work in the plan and the blueprint budgets it as a one-liner.**

**Correction:** Re-scope 1.2 explicitly as "extract `KindExecutor`s into shared `packages/db` pure functions (`applyProposalEffect(tx, kind, proposal)`), keep `ProposalsService.approve` and the new producer auto-apply as two thin callers of the ONE extracted path." This is _more_ SOLID than the blueprint — but it is a Wave-1 slice of its own, with its own G-RT, and it must land **before** any recommender graduates. Mark it the true critical-path bottleneck, not 0.1.

### P0-2. The only auto-execute kinds that are safe to graduate are nearly worthless; the valuable ones can't graduate.

Walk the boundary against the proposed graduations:

- `signature_request.reissue` is classified `autoExecute`-eligible **but the actual executor is `reissueAndDeliver` — which SENDS** (governed outbound). The blueprint hand-waves this with "re-mint only; the _send_ stays a separate confirm," but **no such send-free executor exists** — `reissueExpired` (re-mint only) was deliberately replaced by `reissueAndDeliver` precisely because re-mint-without-send was "dead on arrival" (the executor comment says so). So to auto-execute reissue you must **re-split** the executor you just merged — re-introducing the dead-on-arrival half. That's a regression dressed as autonomy.
- `document.autofile`, `project.flagAtRisk`, `building.apartments.generate` (the genuinely safe new kinds) are real and fine — but they are **low-drama internal bookkeeping**. None of them is the thing a manager would notice or value.

**Net:** after 1.2 lands, the system still auto-executes ~nothing the manager cares about, and the inbox stays the product. That's acceptable as Phase-1 honesty, but the blueprint **oversells** it as turning a "suggestion box" into an "autonomous manager." It does not. Re-frame: the autonomy win in this plan is **better proposals across more axes**, not unattended action. Say that plainly so the owner isn't promised autonomy the boundary forbids.

### P0-3. `building.apartments.generate` as an `autoExecute` recommender contradicts slice 2.1.

The fleet table (§3) lists `building.apartments.generate` as **autoExecute** ("empty shells, no PII"). Slice 2.1 says generation is **deterministic, manager-confirmed, and explicitly does NOT go through classify()**. These are two different mechanisms for the same act. Auto-generating apartments from an inferred unit-count is _not_ obviously safe at scale — a wrong נסח-inferred count silently spawns/archives rows under hundreds of buildings, and "reversible by archive" is exactly the kind of mass mutation a technophobe can't audit. **Pick one:** it's a manager-confirmed action (2.1) OR an auto-executed recommender (§3) — not both. I'd kill the recommender row; keep it human-confirmed.

## P1 — Real, must-fix before merge, but the slice exists.

### P1-1. `attentionReasonToActionKind` as a total `Record<>` will not compile-check what the blueprint claims.

The blueprint sells the `Record<AttentionReason, AutonomyActionKind>` as a "compile-error if a reason has no classified action." True — but it gives a **false sense of safety**: many perception reasons (e.g. "at-risk", "ready-to-approve") map to actions that are `humanOnly` or `proposeConfirm`, and several map to **no action at all** (pure situational badges). Forcing every reason to name a kind will pressure an implementer to invent junk kinds just to satisfy the type. **Correction:** the map value must be `AutonomyActionKind | null` (null = perceive-only, no action), and the totality check stays. Otherwise the type system _encourages_ the exact "junk kind" sprawl the boundary table is meant to prevent.

### P1-2. Slice 0.1's "everything else is provably single-source" is overstated for residents.

The agent branch computes residents via `ownerships → apartments → buildings → project` with `ended_at IS NULL`; the manager branch is a bare `COUNT(DISTINCT owner_id) FROM ownerships WHERE ended_at IS NULL` — **org-wide, no archived-project exclusion, no building join.** The blueprint fixes the _signature_ count but treats residents as a trivial tag-along. It isn't: routing residents through the building-join will **change the displayed number** (drops owners in archived/terminal projects), which a technophobe will read as "the system lost my owners." That needs a one-line legibility note in the UI ("בעלים בפרויקטים פעילים") or it's a support ticket on day one. Add it to 0.1's DoD, don't bury it.

### P1-3. `outbound_ledger.proposal_id` nullable + `cause` is correct — but the blueprint omits the migration's hardest part.

Making `proposal_id` nullable is safe (key excludes it, verified). But the existing **`onDelete:'restrict'` FK and the `idx_outbound_ledger_org_proposal` index** assume a non-null proposal. A `party_request`-caused row with null `proposal_id` makes that index half-dead and the "did this proposal already send?" lookup ambiguous for party sends. The blueprint needs a **`cause`-aware lookup path** (the producer/governor must query by `(cause, party_request_id)` for party sends, not `proposal_id`), and a CHECK that exactly one of `proposal_id`/`party_request_id` is non-null per `cause`. That's a real schema-design slice, not an additive column. Buildable now — but spec it.

## P2 — Sequencing and scope corrections.

### P2-1. Wave 4 is gated harder than the blueprint admits — and its "buildable now" half is mostly inert.

The blueprint is honest that real sends are owner-gated, but it lists 4.2 (party token + write-back) as "**NOW**." A party **write-back endpoint that no party can authenticate to reach** (because OTP delivery is gated) is untestable end-to-end against a real recipient — you can only unit-test the guard. That's fine, but it means Wave 4's actual _value_ (two-way collaboration) is **100% behind the owner gate**, not partially. The plan should stop implying Wave 4 delivers collaboration; it delivers the _machinery_ for collaboration, all of which sits dark until the `recipient_opt_outs` registry (#512, confirmed unbuilt) + provider creds land. Given that, **Wave 4 is the lowest-ROI wave to build now** and should move _after_ Waves 2–3, not be presented as co-equal. The highest-leverage _reachable_ win is auto-data-in (Wave 2), because apartment-owners are the one party that can already self-act.

### P2-2. The critical-path claim "0.1 → 1.1 → 1.2 → everything" is wrong twice.

0.1 (home stat) blocks nothing downstream architecturally — perception (1.1) doesn't read the buggy home query; it _replaces_ it. 0.1 is a correctness fix that can run fully in parallel. The true serial spine is **1.1 (perception) → [P0-1 executor extraction] → 1.2 (graduation) → recommenders**. Put the executor extraction on the diagram; it's the real bottleneck.

## P3 — The trust question (the one that actually decides adoption).

**What single thing is still missing for a technophobe to trust the system to manage on his behalf?** Not in the plan, and it's the most important omission:

**An undo/inspect surface for what the system did on its own.** Every auto-executed effect is "reversible" in the engineer's sense (archive the task, re-scope the doc) — but there is **no manager-facing "the system did these N things for you today; here's how to undo any of them"** view. The blueprint's audit trail is `system-audit` rows the manager never sees. A non-technical manager will not trust _any_ unattended action — even safe ones — if he can't (a) see it happened, (b) understand it in one Hebrew sentence, and (c) reverse it in one click. **This is the missing capability that gates trust, and it's cheaper than Wave 4.** Add a Wave-1.5 slice: **"What I handled for you" ledger** (instrument-voice: "לפי הכללים שלך, סודרו 3 כפילויות מסמכים — לביטול, לחצו כאן"), reading the same `system-audit` rows, with a one-click reverse per auto-execute kind. Without this, the org-opt-in flags in 1.2 will **never get turned on**, and the entire ACT leg stays theoretical forever.

Secondary trust gaps the plan doesn't address:

- **Recommender loop/lie protection.** A recommender that re-detects the same condition after its proposal is rejected will re-propose forever (the dedup key releases on reject). The blueprint mentions TTL but no **"rejected → suppress for cadence window"** rule. A technophobe who rejects a chase and sees it reappear tomorrow concludes the system is broken. Add a `rejection cools the dedup key` rule to the producer contract.
- **No "why am I seeing this" provenance on proposals.** Perception evidence is PII-free counts/ids; the manager needs the _sentence_ ("3 בעלים לא חתמו 14 יום"), and the plan assumes `buildPulseSentence` covers it. Verify each new recommender emits a human reason string, not just a dedup key — make it a field in the `DetectedCondition` contract, gated in review.

## Bottom line — corrected priority order

1. **Re-scope P0-1 (executor extraction to `packages/db`) as the real Wave-1 keystone** — without it, the entire ACT leg is unbuildable as written.
2. **Add the "What I handled for you" undo/inspect ledger (P3)** — without it, autonomy never gets switched on, so everything else is dead weight.
3. **Ship 0.1 + 0.2 + 1.1 in parallel** (truth + speed + perception) — genuinely buildable, genuinely high-leverage, genuinely on-seam.
4. **Build Wave 2 (auto-data-in) before Wave 4** — it's the only high-value wave that's reachable without the owner gate.
5. **Fix the four spec bugs** (P0-3 double-mechanism, P1-1 nullable map, P1-2 residents legibility, P1-3 ledger CHECK + cause-lookup) inside their slices.
6. **Demote Wave 4 to "machinery, owner-gated, lowest ROI now"** and stop describing it as delivering collaboration.
7. **Stop claiming the plan makes EMAPP "autonomous-managing."** Honestly, it makes it a **far better proposal engine with multi-axis perception and a trustworthy undo surface.** Unattended action stays minimal by the boundary's own design — which is correct, and should be sold as the safety feature it is, not apologized for or oversold.
