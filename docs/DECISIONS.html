D.01 — Stack: Neon + Railway + Cloudflare + Resend + Sentry

  • Date: 2026-05 (v2 architecture)
  • Decision: MVP runs on Neon (Postgres), Railway (BE + Worker containers), Cloudflare (R2 storage + Pages hosting), Resend (email), Sentry (monitoring). GitHub for code + CI.
  • Alternatives: AWS (RDS+ECS+S3+SES), Vercel+Supabase, Koyeb (was in v1), Render, Fly.io.
  • Why: Lowest operational overhead for a 2-person team; generous free tiers ($0-6/mo at MVP scale); each service swappable via the interface layer (Doc 02 §6). Neon's branching is excellent for migration testing. Railway's container model fits BE+Worker cleanly.
  • Reversibility: Medium (interface layer protects app code; infra config would change).
  • Revisit trigger: ~50 paying orgs (cost), or a provider degrades materially.
  • Ref: Doc 02 §4

D.02 — ORM: Drizzle (not Prisma)

  • Date: 2026-05
  • Decision: Drizzle ORM for all DB access.
  • Alternatives: Prisma, Kysely, raw SQL with pg.
  • Why: Generates readable SQL (no opaque engine binary), no runtime query-engine overhead, native-feeling TypeScript types, migrations are owned files. Prisma's engine binary added edge-deploy complexity.
  • Reversibility: Hard (ORM switch = rewrite all queries).
  • Revisit trigger: Drizzle abandons maintenance, or a blocking bug with no workaround.
  • Ref: Doc 02 §4.3, Doc 04a §2.6 C.01

D.03 — Auth: Better Auth (not Clerk/Auth0)

  • Date: 2026-05
  • Decision: Better Auth, self-hosted in our codebase.
  • Alternatives: Clerk, Auth0, Lucia, hand-rolled.
  • Why: Full control over the auth flow + data; no per-MAU pricing that punishes growth; MFA, magic links, sessions all supported; PII stays in our DB (important for Israeli privacy posture).
  • Reversibility: Hard (auth touches every request path).
  • Revisit trigger: Enterprise SSO/SAML demand that Better Auth can't meet (Phase 2+).
  • Ref: Doc 02 §4.4, Doc 07 §6

D.04 — Cache: PostgresCacheProvider in MVP (not Redis)

  • Date: 2026-05
  • Decision: ICacheProvider implemented with a Postgres cache_kv table in MVP. Upstash Redis deferred to Growth.
  • Alternatives: Upstash Redis from day 1, self-hosted Redis, Memcached.
  • Why: Minimal Runtime principle — one fewer service. Postgres handles MVP cache load (~10k ops/sec) easily. Interface lets us swap to Upstash with no app-code change.
  • Reversibility: Easy (swap the ICacheProvider implementation).
  • Revisit trigger: ~10 paying orgs, or cache_kv p95 > 10ms.
  • Ref: Doc 02 §4.5, §14.4, Doc 04a §2.6 C.02

D.05 — Provider tier: separate DB role + table (not is_admin boolean)

  • Date: 2026-05
  • Decision: EMAPP-internal access is a structurally separate tier — provider_users table, provider_app_role DB role with BYPASSRLS, withProvider() wrapper, MFA mandatory, all access audited.
  • Alternatives: is_admin boolean on users; a "superadmin" org; impersonation.
  • Why: A boolean flag is one bug away from privilege escalation. Structural separation means a customer JWT can never reach provider data even if RBAC has a bug. Defense in depth.
  • Reversibility: Hard (schema + auth + RLS all depend on it).
  • Revisit trigger: Never (this is foundational).
  • Ref: Doc 02 §10, Doc 07 §11, Doc 04c P1.3, Doc 04a §2.6 C.03

D.06 — PII encryption: pgcrypto field-level (not disk-only)

  • Date: 2026-05
  • Decision: national_id and phone and signature_blob encrypted at the field level via pgcrypto, with a separate PII_HASH_KEY for HMAC search. Two distinct keys.
  • Alternatives: Disk encryption only (Neon default), app-level encryption, no encryption.
  • Why: Disk encryption doesn't protect against a leaked connection string. Field-level means a DB dump without the key is useless. HMAC enables search without decryption.
  • Reversibility: Hard (re-encryption ceremony required — Doc 07 §14).
  • Revisit trigger: Never routinely. Only on confirmed key compromise.
  • Ref: Doc 07 §5, §14, Doc 04c P1.5

D.07 — Soft delete: archivedAt (not deletedAt)

  • Date: 2026-05 (v2 rename)
  • Decision: Soft delete uses archived_at timestamp. UI verb is "ארכוב" (archive), never "מחיקה" (delete). Hard delete is a Provider-only audited operation.
  • Alternatives: deleted_at (v1 name), hard delete, status enum.
  • Why: "Archive" communicates recoverability to users; legal/audit requirements forbid true deletion of signature/owner data; the rename from v1 avoids the implication that data is gone.
  • Reversibility: Easy (it's a naming + UX convention).
  • Revisit trigger: Never expected.
  • Ref: Doc 04c §4, Doc 05 §16, Doc 06 §16

D.08 — Buildings/Owners: single table with enum (not CTI)

  • Date: 2026-05 (v2 simplification)
  • Decision: One buildings table with a type enum; one owners table with a type discriminated union. No Class-Table-Inheritance child tables.
  • Alternatives: v1's CTI (residential_buildings / mixed_use_buildings / commercial_buildings; individual_owners / company_owners / inheritance_owners).
  • Why: CTI added join complexity and bug surface for marginal modeling benefit at MVP scale. Single table + enum + Zod discriminated union is simpler and faster.
  • Reversibility: Medium (could split later if a type's fields diverge significantly).
  • Revisit trigger: A building/owner type accumulates many type-specific columns.
  • Ref: Doc 04c §4, Doc 06 §16.1

D.09 — RLS: ENABLE + FORCE on all multi-tenant tables

  • Date: 2026-05
  • Decision: Every multi-tenant table has ENABLE ROW LEVEL SECURITY + FORCE ROW LEVEL SECURITY. app_user is not the table owner. Org context set via SET LOCAL app.organization_id.
  • Alternatives: App-level WHERE filters, separate schema per tenant, separate DB per tenant.
  • Why: RLS is enforced by Postgres even if app code has a bug. FORCE ensures it applies even to the table owner. The single highest-leverage tenant-isolation control.
  • Reversibility: Hard (the entire tenancy model depends on it).
  • Revisit trigger: Never (foundational). Tested by T1.5 (CI gate).
  • Ref: Doc 07 §10, Doc 04c P1.11

D.10 — API versioning: /api/v1/ from day 1

  • Date: 2026-05

  • Alternatives: Unversioned /api/, header-based versioning, no versioning.
  • Why: Retrofitting a version prefix later is a breaking change for every client. The cost now is one line (app.setGlobalPrefix('api/v1')).
  • Reversibility: Hard once clients exist (that's the point of doing it now).
  • Revisit trigger: Never reverse. v2 prefix added when a true breaking change is unavoidable.
  • Ref: Doc 06 §5.1

D.12 — Signature format: SVG, encrypted, inline (not R2)

  • Date: 2026-05
  • Decision: Signatures captured as SVG, encrypted with pgcrypto (same PII_ENCRYPTION_KEY), stored inline as bytea in signatures. 50KB max. Plus a documentHash (SHA-256) for tamper detection.
  • Alternatives: PNG, raw points; storage in R2; unencrypted.
  • Why: SVG is vector (scales for print), small (~5-15KB). Inline keeps the encryption story identical to other PII and avoids a second round-trip for small, tightly-coupled data.
  • Reversibility: Medium (format column allows future PNG; storage move is a migration).
  • Revisit trigger: If wet-ink scan upload is needed (would add PNG/JPG path).
  • Ref: Doc 04c P1.8

D.21 — Auth architecture: full ownership (argon2id + domain-DB sessions), Better Auth removed as orchestrator

  • Date: 2026-05-18
  • Decision: Own the entire authentication stack. Password hashing via argon2id (OWASP params). Credentials, sessions and refresh tokens live in the domain database (RLS-aware), not in a separate Better Auth store. Signup is a single atomic transaction (org + user + membership + credential + audit) via the audited withProvider bootstrap. Refresh tokens are stored hashed (SHA-256) with rotation-on-use and reuse-detection (replay ⇒ revoke all sessions + audit). Better Auth is removed from the request path (it was used only for password hashing behind a custom JWT + manual-refresh hybrid). The locked stack entry "Auth: Better Auth" (CLAUDE.md) is hereby superseded by this decision.
  • Alternatives: (a) Keep Better Auth, full adoption — rejected: its HTTP/session model does not satisfy the locked wire contract (stateless JWT with mandated claims, opaque hashed refresh in a sessions table, {data} envelope, /api/v1 prefix, RLS via withTenant), and the domain bootstrap would still span its store + ours non-atomically. (b) Patch the hybrid per-finding — rejected: orphaned-account / non-atomic-signup / plaintext-refresh / logout-not-revoking are all symptoms of the two-store hybrid; point fixes are plasters that retain the unsafe topology.
  • Why: A single store + single transaction makes the orphaned-account class of bug structurally impossible rather than "fixed". It is the only option that satisfies auth invariant #1 (atomic signup). The surface lost from Better Auth is password hashing only — replaced by a vetted argon2id library. For a 2-dev team facing security review (ISO 27001 A.8.5/A.8.24/A.8.25/A.8.26), a fully-understood auth module is more defensible than a library fighting the spec contract.
  • Risk & acceptance: Hand-written auth carries hand-rolled-auth risk. Contained by: black-box invariant contract suite written before the code; @security-reviewer on the diff pre-commit; argon2id not hand-rolled; rate-limit/lockout at the framework layer. Residual risk accepted by the product owner on this date as the lower-risk path versus shipping the broken hybrid.
  • Reversibility: Hard. Auth touches schema, sessions, and every guarded route. Treated as a one-way door — hence this record + Gate 6.
  • Revisit trigger: A managed auth provider (WorkOS/Auth0) is adopted org-wide, or the contract invariants change materially.
  • Ref: Doc 07 §6, Doc 08, GATES.md (Gate 6), Phase 2 audit + black-box conformance (PROGRESS.md)

D.22 — Production security-design hardening backlog (interim risk acceptance + remediation plan)

  • Date: 2026-05-18
  • Decision: A principal-level design review (docs-only) found four DESIGN-level gaps that are NOT code bugs and that a reckless mid-hardening rebuild would only turn into plasters. They are formally ACCEPTED as interim MVP risk with a dated remediation plan, per ISO 27001 risk-treatment governance, rather than rebuilt now:
    1. (A) Encryption-key blast radius. PII_ENCRYPTION_KEY is injected as a readable GUC (SET LOCAL app.encryption_key) on every withTenant tx and is process-resident. An app-level compromise (SQLi defeating Drizzle params, errant RAISE, current_setting readback) exposes the key for ALL tenants — the "DB dump is useless" claim holds only for cold-leak, NOT app-compromise. Remediation (own workstream, before enterprise/BYOK or first external pentest): move decrypt into an explicit-GRANT SQL function so the key is never a readable GUC; design envelope encryption / per-tenant DEK. Interim control: Drizzle parameterization everywhere (enforced), no raw SQL in app code (ESLint), key never logged (pino redaction).
    2. (B) Audit log not tamper-evident. Append-only via withheld DELETE grant stops the app role only; anyone with the Neon connection string / console can DDL. Not STRIDE-R / ISO-repudiation grade. Remediation: hash-chain rows + periodic external WORM mirror (later phase). Interim: the "cannot erase their tracks" claim is hereby DOWNGRADED to "the application cannot erase tracks"; infra-level access is covered by Neon access control + Infisical.
    3. (D) Neon connection/pooling model undecided. SET LOCAL×2–3 round-trips/request + scale-to-zero on the login path; ~100 req/s ceiling at the guessed 20-conn direct pool. Remediation (before Gate 5): pin pooled-transaction (PgBouncer) vs direct, validate SET LOCAL-in-tx under it, size the pool against measured concurrency. Tracked as a Gate-5 pre-launch checklist item.
    4. (F) No server-side idempotency key on legally-weighty POSTs. /auth/signup is effectively idempotent on the unique email + anti-enum neutral duplicate path + tight throttle (acceptable). /signatures (Phase 5, not yet built) MUST get an idempotency key — recorded here as a hard Phase-5 requirement so a network partition cannot double-sign.
    (C) secrets-model doc contradiction and (E) D.21 doc-incoherence were NOT deferred — they were FIXED 2026-05-18: Doc 07 §5.5/§15 reconciled to Infisical-only; D.21 propagated to CLAUDE.md + Doc 07 §6.2/§6.3 banner.
  • Why: ISO 27001 does not require zero risk — it requires every risk identified, owned, treated or consciously accepted with a plan. Rebuilding Phase-1 pgcrypto / audit tamper-evidence inside Phase-2 hardening would be high-blast-radius scope creep and itself the "plaster" anti-pattern. Documented acceptance + dated plan is the correct, defensible posture.
  • Risk & acceptance: Product owner accepts A, B, D, F as interim MVP risk on 2026-05-18; none is a launch blocker for a 0–100-org pilot, ALL are pre-scale / pre-enterprise / pre-external-pentest blockers and are now tracked.
  • Reversibility: Each remediation is its own gated workstream; this entry is the tracking anchor.
  • Revisit trigger: first enterprise/BYOK demand, first external pentest, >100 orgs, or Gate 5 (pre-launch) — whichever first.
  • Ref: Principal design critique (PROGRESS.md), Doc 02 §5.4/§8, Doc 07 §5/§8, Doc 08 §5, GATES.md (Gate 5)

D.24 — High-scale stance for the multi-tenant data path (governed, no stack/schema deviation)

  • Date: 2026-05-18
  • Decision: The locked architecture (NestJS+Fastify, Drizzle, Postgres+RLS on Neon, withTenant/withProvider) is the scale-correct design for many tenants; scaling levers are config/infra + index discipline, NOT rewrites. Priority order: (1) point DATABASE_URL at the Neon connection pooler in transaction mode — withTenant is pooler-safe by construction (SET LOCAL ROLE app_user + set_config(..., true) are transaction-scoped, reset at COMMIT, never leak across pooled sessions); (2) every RLS predicate and every list query's parent-FK filter + keyset order (created_at, id) MUST be backed by a matching composite/partial index — enforced per Phase-3 slice; (3) keyset cursor pagination only (never offset) — already the standard (shared common/keyset-cursor.ts); (4) keep withTenant round-trips minimal (GUCs already batched into one set_config). Read replicas (Neon) for read-heavy reporting endpoints and cache_kv for hot, tenant-scoped, low-churn reads with explicit per-tenant invalidation are deliberately DEFERRED — added measurement-driven, never speculatively (cache without correct invalidation is a multi-tenant security bug).
  • EXPLAIN discipline: a dev-only helper to inspect query plans is sanctioned; query-plan assertions are NOT wired as a CI gate — plans are non-deterministic on a fresh CI DB with no statistics, so a plan-shape assertion would flake (a plaster, contra ISO test-stability). Index discipline is enforced by review per slice instead.
  • Alternatives: (a) denormalize org_id onto child tables to flatten via-parent RLS — REJECTED: locked-schema change (Gate 2); via-parent RLS + service parent-FK filter + indexes is sufficient and is the sanctioned pattern. (b) Redis/alternative cache or ORM/DB swap — REJECTED: locked stack (CLAUDE.md). (c) Shard-by-org / Citus — out of scope; single-DB + RLS scales to the MVP+ horizon; revisit only on measured ceiling.
  • Why: ~99% of the throughput/latency gain at "many customers" comes from transaction-mode pooling (multiplexes thousands of tenants onto few connections) + correct indexes — both zero-architecture-risk and within the locked stack. Anything beyond is premature without a real load profile (minimal-runtime / ISO).
  • Reversibility: Trivial — pooler is a DATABASE_URL swap (Infisical); replicas/cache are additive later.
  • Revisit trigger: measured connection saturation, RLS subquery hot-spots in pg_stat_statements, or a read-replica-worthy reporting load.
  • Ref: Phase 3 (docs/03 §7), withTenant wrapper, PROGRESS.md scale note, user directive 2026-05-18 ("must be efficient + support high scale").

D.25 — Ownership composition is ATOMIC per apartment (set-replace), mandated by the locked Phase-1 sum trigger

  • Date: 2026-05-18
  • Decision: Phase-1 migration 0002 defines trg_ownerships_sum_check — a CONSTRAINT TRIGGER ... DEFERRABLE INITIALLY DEFERRED that, at COMMIT, requires SUM(ownership_pct) over an apartment's ACTIVE ownerships (ended_at IS NULL) to be 0 or exactly 100. Because every withTenant call is its own transaction, a standalone per-row add/patch/delete can never satisfy "=100" and always rolls back. Therefore the Slice-5 write API is a single atomic full-set replace: PUT /api/v1/apartments/:apartmentId/ownerships with { owners: [...] } that must be empty (clear all) or sum to exactly 100; the service ends all current active ownerships and inserts the new set in ONE tx so the deferred trigger sees a legal end-state. Reads unchanged: GET …/ownerships (active, cursor) and GET …/owners (masked owner + share, docs/09 §3.13). The in-app Zod refine + service guard produce a clean 400 ownership_sum_invalid; the trigger raise is the authoritative backstop and is also mapped to 400 (never 500).
  • Alternatives: (a) per-row POST/PATCH/DELETE as docs/09 §3.13 literally implies — REJECTED: physically impossible against the locked deferred trigger across separate transactions (proved: a lone 50% insert → COMMIT raise → 500). (b) Make the trigger non-deferred / relax to "≤100" — REJECTED: that is a locked Phase-1 schema change (Gate 2) and weakens a data-integrity invariant. (c) Multi-row within one request but keeping "add one" semantics — still cannot reach 100 incrementally; the set-replace is the only coherent model. We conform TO the locked invariant; docs/09 §3.13's per-row shape is recorded doc-drift, NOT a schema deviation.
  • Why: matches the real-world act ("declare who owns this apartment, totalling 100%"), is the only model the locked trigger permits, and keeps the invariant strong (ISO data-integrity).

D.29 — pg pool resilience: process must survive idle/blip disconnects (per-client guard + keepAlive + silent backstop + Sentry observability)

  • Date: 2026-05-20 (PRs #15 + #16; packages/db/src/client.ts).
  • Decision: Every pg.Pool in the API (pool, providerPool) is hardened with FOUR coupled levers, none of which may be removed in isolation: (a) Per-client 'error' guard attached on pool.on('connect') — every checked-out client carries an 'error' listener for its full lifetime; without it a Neon idle drop / network blip on an in-flight client emits 'error' on the pg.Client with no listener → Node treats it as uncaught → process exit 1. The pool-level pool.on('error') only sees idle clients (via pg-pool's makeIdleListener re-emit) — it does NOT cover the checked-out path. (b) keepAlive: true + keepAliveInitialDelayMillis: 10_000 — keepAlive alone is useless because the Node socket default is the OS default (~7200s on Linux), much longer than any Neon idle cutoff; 10s starts probing well inside every realistic idle window so dead sockets are detected proactively, not on the next acquire. (c) allowExitOnIdle: false — explicit (even though it is the pg default) so a future pg default flip cannot silently let the long-lived API exit on an empty pool. (d) Silent pool 'error' backstop — the per-client guard is the SINGLE source of truth (logs + observer notify); the pool listener is registered but writes nothing, because pg-pool re-emits idle client errors to pool.emit('error') ON TOP of the per-client event. Removing the pool listener reintroduces the same unhandled-'error' crash class for idle drops; without dedup, every idle drop produced two log lines and (with observability) two notifications. Dedup contract is pinned by pool-resilience.spec.ts ("idle drop produces EXACTLY one log line"). On top of the guard, an injectable observer (setPoolErrorObserver in @emapp/db; apps/api/src/instrument.ts wires a Sentry breadcrumb, category="db.pool", level="warning") emits a chronic-rate signal for ops without changing the resilience behaviour. Observer exceptions are swallowed — a broken observer must never weaken the guard.
  • PII / security: Only err.message is forwarded to stderr and observer. err.stack is NOT forwarded (async frames can carry call-site context that has not been audited for PII). Empirically verified: pg auth failures (wrong password / user) surface via pool.connect() rejection, NOT via the Client 'error' event — the guard never sees them, so the DB username never reaches stderr or Sentry. Client 'error' events from pg are exclusively connection/protocol-level (terminated socket, SSL handshake) and never carry query text or row data.
  • DO NOT REMOVE (regression guards on these are pinned by tests): the per-client listener, the silent pool listener, the three pool defaults (keepAlive, keepAliveInitialDelayMillis, allowExitOnIdle), and the observer try/catch. packages/db/test/pool-resilience.spec.ts + pool-error-guard.spec.ts together pin all of these — 14 tests, including a real-pg integration test that emits "Connection terminated unexpectedly" on a real checked-out pg.Client and asserts the process survives + the pool serves SELECT 1 afterward.

The fix is invariant infrastructure (no domain change) and the observability hook turns "API mysteriously restarted" into a Sentry breadcrumb stream that lets ops detect chronic Neon instability or network degradation BEFORE users feel it.
  • Reversibility: Low. Removing any of the four levers reintroduces the crash class. The observer hook is reversible (no-op when unset).

D.34 — Phase 6 Excel import: layered mapping architecture (Strategy + Chain)

Date: 2026-05-21. Phase: 6 S7. Status: RECORDED (Layer 1 shipped; Layers 2 + 3 deferred to Phase 7+ behind a stable seam).

Decision: column-name → canonical-field resolution in the Excel import pipeline is implemented as a Strategy + Chain of Responsibility behind a single interface IMappingResolver in apps/worker/src/mapping/mapping-resolver.ts. The handler holds a MappingResolverChain (composition) and consumes one method (resolve(headers): {kind:'resolved'|'unknown'|'reject', …}). Three concrete strategies, layered in priority order:

  1. Layer 1 — LegacyAliasResolver (shipped, S7). Wraps today's deterministic resolveMapping() (the Hebrew/English alias table that has powered S4+S5 since Phase 6 began). resolved on full alias match (5 canonical fields bound), unknown on incomplete mapping (recoverable — Layer 2/3 may resolve), reject on duplicate alias (malformed input — fail loud, NOT recoverable). Zero behaviour change vs S6 for files that match canonical aliases (~80%+ of real-world urban-renewal Excel files per Lidor's customer onboarding signal).
  2. Layer 2 — TemplateResolver (deferred to Phase 7+, blocked by S8). Implements IMappingResolver against the new mapping_templates table (migration 0028). Algorithm: compute fingerprint (sha256 of normalised headers, lowercase + trimmed + sorted), look up SELECT mapping FROM mapping_templates WHERE org_id = current_setting('app.organization_id')::uuid AND fingerprint = $1 AND archived_at IS NULL LIMIT 1 (RLS isolates by org), return {kind:'resolved', source:'template'} if found, {kind:'unknown'} otherwise. Composes IN FRONT of Layer 1 in production main.ts once S8 ships (so a saved template wins over a generic alias guess for that customer's exact column shape).
  3. Layer 3 — AgentResolver (deferred to Phase 7+). Implements IMappingResolver by calling an LLM with a HEADERS-ONLY payload (no data rows ever — PII never crosses the LLM boundary; the agent sees column names, never owner data). Returns {kind:'resolved', source:'agent', mapping, confidence: 0–100}; a threshold guard (e.g. confidence < 70 → {kind:'unknown'}) defers low-confidence guesses to the wizard rather than persisting a wrong mapping. Hard contracts: (a) payload is headers-only, enforced at the AgentResolver boundary, never the handler's job to police; (b) any agent-resolved mapping that successfully imports MUST also INSERT into mapping_templates with source='agent' + confidence set, so a manager can audit/approve the agent's choice retroactively; (c) LLM provider DPA must be signed before this layer is enabled (Gate-5 obligation).

Chain semantics (pinned in MappingResolverChain + 8 unit tests in mapping-resolver.spec.ts):

  • First non-unknown result wins — earlier resolvers can short-circuit later ones. Production composition is [TemplateResolver, LegacyAliasResolver, AgentResolver] (template > deterministic > agent — give the manager's own saved mapping priority over a fresh guess).
  • reject from ANY link HALTS the chain — later resolvers do NOT get to override. Malformed input (duplicate alias) fails loud regardless of how many strategies are stacked.
  • All-unknown → final {kind:'unknown'} → handler transitions parsing → awaiting_mapping + writes import.awaiting_mapping audit row (resolver name + header_count, PII-free), commits and returns cleanly (no pg-boss retry storm). The row sits ready for the wizard (S8) to supply a mapping out-of-band.

Why this design (not alternatives):

  • Customer-onboarding signal Lidor surfaced 2026-05-21: "מה לגבי ייבוא של אקסל, בסוף אני אצטרך נורמליזציה מבוססת agent בגלל שכל אקסל יכול להיות בנוי שונה." Real Israeli urban-renewal contractors have wildly variant Excel shapes — bank exports, lawyer spreadsheets, hand-maintained sheets in 5+ regional naming conventions. The deterministic alias table can't cover the long tail; eventually an LLM normaliser is required. The seam must exist BEFORE the agent does, so the agent slots in by composition (not by handler edits).
  • Why not a single "smart" resolver: mixing deterministic + template + LLM logic in one class violates SRP, makes the agent dependency mandatory (raises infra cost + DPA scope before it's needed), and tangles confidence handling. Three classes × one interface = three independently testable units, each with a clean failure mode.
  • Why awaiting_mapping instead of failed on Layer-1 miss (the v3-pre-S7 behaviour): a "failed" row gives the manager no recovery path — they see "your file is wrong" and either give up or fight the support team. awaiting_mapping + the wizard means the same file becomes recoverable in 30 seconds. Customer-onboarding UX is a Phase 6 requirement, not Phase 7+.
  • Why mapping_templates stores fingerprints not raw headers: sha256 of normalised headers gives O(1) lookup, doesn't leak header text to a future agent diffing the table for sensitive column names (defense-in-depth — even though headers themselves are not PII, header SHAPES sometimes encode customer trade secrets), and lets us index a partial UNIQUE without bloating btree pages with long composite text. The full headers ARE stored in the mapping jsonb for audit/debug, just not the index key.
  • Why source enum + confidence + approval pair (CHECK constraints on the table): ISO A.18.1.4 (PII data creation logging) — every template that materialises customer data must be traceable to a human approver (manual: by the manager; agent: explicitly approved by a manager after review). The CHECK constraints make this structurally impossible to bypass.

D.35 — Phase 4 FE topology: Cloudflare Pages reverse-proxy → private Railway API (same-origin /api/v1/*), hostOnly cookies

Decision: The FE on app.emapp.io (Cloudflare Pages) routes all /api/v1/* calls through a Next.js Route Handler at apps/web/src/app/api/[...path]/route.ts that proxies to the private Railway API URL (API_BACKEND_URL, server-only Infisical secret). The API has NO public DNS — its only ingress is the Pages Function. Auth cookies stay hostOnly (no Domain= attribute, matching the existing COOKIE_BASE in auth.service.ts line ~59).

Why this over the obvious alternative (api.emapp.io public subdomain + CORS):

  1. Cookie security. Same-origin = hostOnly cookies. A future api.emapp.io subdomain takeover (CNAME dangling on an old CDN, an SRE who forgets to remove a Cloudflare DNS record) cannot read sessions issued to app.emapp.io because the cookie is bound to the exact host. With a Domain=emapp.io cookie, ANY *.emapp.io subdomain can read it — a structural Sev1 waiting for a misconfiguration.
  2. No CORS. Same origin means no preflight OPTIONS roundtrip on every state-changing request (saves ~30–50ms p50 from Israeli users hitting EU edge). Eliminates an entire class of "I added a new endpoint and forgot the CORS allowlist" bugs.
  3. No public attack surface for the API. Railway internal URL only — Bots, scanners, and credential-stuffing tooling cannot reach /api/v1/auth/login directly. Cloudflare WAF + Pages DDoS sits in front; the throttler (D.30) and lockout become defense-in-depth, not the only line.
  4. Israeli user latency. Cloudflare's TLV PoP terminates the connection; the proxy hop to Railway-eu is one east-west call inside the same provider region. Net: faster than a direct browser→Railway round trip from Israel today (which goes browser→Frankfurt→Railway).

What changed (v8.5):

  • New: apps/web/src/app/api/[...path]/route.ts — Next.js Route Handler that proxies all verbs (GET/POST/PUT/PATCH/DELETE/HEAD/OPTIONS), forwards cookies + body + safe headers, strips Host/X-Forwarded-*/CF-* (rebuilds X-Forwarded-For from CF-Connecting-IP so backend logs see the real client), passes Set-Cookie back unmodified (critical for the refresh-token rotation flow). SSE-safe (streams response body, no buffering).
  • Changed: apps/web/src/lib/api-client.ts now calls /api/v1/* (no NEXT_PUBLIC_API_URL, no absolute base). credentials: 'same-origin' (strictest setting that still ships cookies). The old NEXT_PUBLIC_API_URL is intentionally NOT read — a future hand adding it would break the cookie model silently.
  • Verified: auth.service.ts COOKIE_BASE has no domain field — hostOnly by default. Refresh + access cookies are already path-scoped to /api/v1/auth/refresh and / respectively, which the same-origin model preserves unchanged.
  • Required env (Cloudflare Pages): API_BACKEND_URL — full URL to the private Railway API (e.g. https://emapp-api.railway.internal). MUST NOT be prefixed NEXT_PUBLIC_ (would leak it to the browser bundle).

Alternatives considered & rejected:

  • (B) Public api.emapp.io + CORS + Domain=.emapp.io cookies. Easier wiring, but: subdomain-takeover blast radius covers auth; CORS preflight on every write; API has public ingress (every WAF / Bot Management decision becomes a separate config plane). The user explicitly weighed security vs latency and chose A.
  • (C) Cloudflare Workers as proxy (instead of Next Route Handler). More code to maintain (separate worker repo or wrangler config); Next.js already has the request/response primitives we need and ships on Pages natively.
  • (D) Direct browser → Railway, no proxy. Requires public API DNS, CORS, and breaks the hostOnly-cookie model. Same downsides as B without the CDN benefit.

Reversibility: HIGH. To flip to topology B in the future: (1) deploy backend at api.emapp.io with public DNS; (2) delete apps/web/src/app/api/[...path]/route.ts; (3) change api-client.ts back to process.env.NEXT_PUBLIC_API_URL; (4) add domain: '.emapp.io' to COOKIE_BASE; (5) re-add CORS allowlist in main.ts. ~30 minutes total. The Route Handler is a pure addition; no schema, no migrations, no contract changes.

Trade-offs accepted:

  • Cold-start of the Route Handler. Pages Functions warm in milliseconds; the proxy adds ~5–15ms over a direct call. Negligible vs the round-trip savings (no CORS preflight on writes).
  • Pages Function size budget. The Cloudflare 1 MB limit per function. The handler is ~5 KB; comfortable.
  • SSE buffering. Pages defaults to buffering; the API's X-Accel-Buffering: no header (already set in the imports SSE controller) disables it. Verified pre-merge against the live SSE endpoint.
  • WebSocket support. Out of scope for MVP. If we ever need WS, a Cloudflare Worker upgrade-handler is the standard path; not blocked by this decision.

CSP / CSRF posture (decided alongside D.35):

  • CSRF: Same-origin + SameSite=Lax (already set in COOKIE_BASE) blocks cross-site form-POST CSRF for cookie-bearing requests. No CSRF tokens needed in MVP. Provider Admin paths additionally require a tier-3 JWT in the Authorization header (D.29) — a CSRF cannot mint that.
  • CSP: Helmet's default plus a strict connect-src 'self' (since all API calls are same-origin now). img-src + style-src stay as Helmet defaults. Re-evaluate when we add Sentry browser SDK (needs connect-src for ingest) and PostHog if we land P.01.

D.36 — v8.5 phase-transition audit protocol (separate from code-quality audit)

Decision: Introduce a distinct "phase-transition audit" run BEFORE handing a phase to the next downstream consumer (FE consuming BE, BE consuming DB, worker consuming queue, etc.). This is in addition to the existing 3-axis code-quality audit (SOLID / Security / Perf) that runs per slice.

Why: Lesson from Phase 6 → Phase 4 handoff. The v7 + v8 + v8 P0 closeout passes all verified code-quality of the just-shipped code. They did NOT verify "is the next layer's consumer set up to actually consume this surface." Concrete gaps caught only at v8.5 (after user pushed back "why so many gaps?"):

  • Contract suite green vs an API that didn't have THROTTLE_TEST_BYPASS set → silent 429s on first run.
  • FE topology (cookies, CORS, hostOnly) was unspecified — a wrong default would force a rewrite at Phase 4 mid-stream.
  • R2 dev creds had been pasted in chat → compromised, but rotation was nobody's task on the ledger.
  • The cancel() path didn't purge bytes — visible only by reading the "is the FE going to call this?" question, not the "does this code work?" question.

Protocol: Before opening the phase-N PR, run a phase-transition pass that answers, for the immediate downstream consumer:

  1. Does the consumer have everything it needs to call this surface in dev (env vars, secrets, fixtures, contract suite, test bypass flags)?
  2. Does the consumer's deployment topology (cookies / CSRF / CORS / CSP / proxy / DNS) match what the producer assumes?
  3. For every state the producer can leave the system in (terminal states, error states, async deferrals), has the consumer's path been verified end-to-end with real producer code (not mocks)?
  4. For every external dependency rotated, leaked, or about-to-be-rotated (R2 keys, Resend keys, PII keys, JWT secrets), is the rotation tracked in a named task with an owner?
  5. For every "best-effort" or "swallowed-failure" path the producer ships, is there a sweeper / retry / alert that owns the failure?

Cross-confirmation rule: A phase-transition gap surfaced by ≥2 fresh-eyes agents is P0 for the transition (cannot ship the phase). A gap surfaced by 1 agent + a concrete reproducible incident is P0. A single-agent observation with no incident is HIGH (must have a tracked closure plan, not necessarily a fix in this PR).

Reversibility: Process change only — costs one agent-pass per phase boundary. No code or schema impact. If the process feels like overkill after 2–3 phase boundaries, drop it; nothing depends on it structurally.

D.41 — Calendar attendees: separate task_external_attendees from task_assignees

Date: 2026-05-27 · Status: Locked (authorized inline at the B.S1 GO answer Q3, formalised here on B.S5).

Decision: Calendar attendees on a task (D.38 — owners/tenants invited to the ICS event) live in a NEW table task_external_attendees (task_id FK → tasks, owner_id FK → owners, ics_sent_at, ics_cancelled_at, UNIQUE on (task_id, owner_id)). This is structurally separate from the pre-existing task_assignees (which links task_id + user_id, used by Manager/Agent task assignment).

Alternatives: (a) Extend task_assignees with a nullable owner_id + polymorphic discriminator — REJECTED: conflates two distinct semantics (the actor who does the task vs the invitee who receives an ICS), forces every task_assignees consumer to add discriminator-aware logic, and loses the tier-audit signal (Tier-1 user assignment vs Tier-2 external invitation). (b) Use a single shared "any actor" table with two nullable FKs — same issue, plus a CHECK constraint enforcing exactly-one-FK that adds insert-time overhead.

Why: The split matches the real-world act ("Manager assigns Agent to do the task" is distinct from "Manager invites Tenant to attend the meeting"), keeps each table's CRUD path linear, and preserves the audit trail per-tier. The cost is one extra table — paid once at migration time, zero ongoing complexity for either consumer.

Idempotency-aware columns (ics_sent_at / ics_cancelled_at) are NOT cosmetic: B.S7 Resend integration uses them to avoid double-sending if the BE crashes between sending the ICS and writing the audit row, and to track per-attendee delivery status for the future audit view.

RLS: Template B (via parent) per D.24 + 0011 — task_external_attendees has no org_id direct; the policy joins through tasks.org_id (single-hop chain). GRANT: SELECT + INSERT + UPDATE for app_user, no DELETE (soft-cancel via ics_cancelled_at; forensic posture matches task_assignees, mapping_templates, import_jobs).

Reversibility: High. DROP TABLE task_external_attendees in a single reverse migration; no data migration of the separate table required because task_assignees is unaffected and external-attendee data is purely additive.

Revisit trigger: A real product need for "an Agent who is ALSO an invited attendee" (vs. just an assignee) — at that point we'd add an also_invited boolean to task_assignees rather than merge tables.

D.42 — Phase-7 export PDF stack: playwright-core + base64-embedded Heebo woff2 (V11 B.S9)

Date: 2026-05-27 · Scope: V11 Phase 7 export (project → PDF). NOT a closure of P.02 (which is about Phase-5 contract signing); the two paths share lessons but the contract stack is decided later.

What: The Phase-7 PDF renderer (apps/api/src/modules/export/pdf-export.service.ts) uses playwright-core to drive headless Chromium against an HTML template with Heebo woff2 fonts base64-embedded as @font-face data: URLs.

Why playwright-core (not puppeteer, which the master plan literally names): apps/web already installs Chromium via pnpm --filter @emapp/web test:e2e:install to ~/.cache/ms-playwright/. playwright-core is the just-the-JS-API package (~5 MB) and discovers the same shared binary. Puppeteer would pull a duplicate ~300 MB Chromium for no benefit. Explicitly authorized by the user via in-chat question during B.S9 ("puppeteer-core + reuse playwright's Chromium" → realized as playwright-core with one fewer npm dep).

Why base64-embedded Heebo: Avoids Google Fonts fetch at render time (would (a) leak the render to Google, (b) add latency, (c) break in air-gapped Railway). @fontsource/heebo npm package supplies a stable, version-pinned woff2; we embed Hebrew 400/700 + Latin 400/700 (~80 KB total). Resulting PDF is fully self-contained — recipients with no Heebo install still see the document exactly as the manager rendered it.

Critical fix during dev: page.setContent(html, { waitUntil: 'load' }) alone is NOT enough — Chromium emits PDFs with fallback Arial glyphs until document.fonts.ready resolves. Always pair with await page.evaluate(() => document.fonts.ready) before page.pdf(). (Discovered via B.S9 visual smoke — see memory/feedback_visual_smoke_gap.md.)

Webpack externals quirk: webpack-node-externals doesn't catch playwright-core under pnpm's symlinked node_modules layout — playwright internals get inlined into dist/main.js and crash at runtime on dynamic require('./package.json'). Fixed in apps/api/webpack.config.js with an explicit externals entry (defensive entry for exceljs against the same quirk).

Implication for P.02 (Phase-5 contract PDFs): The playwright-core + Heebo stack is a known-good baseline; P.02 may adopt it directly or evaluate @react-pdf/renderer as an alternative if contracts need stricter layout control. NOT a forced decision either way — P.02 stays open.

D.44 — Optimistic locking on PATCH deferred to V12 (Wave-4 M-7)

Date: 2026-05-28 · Source: 2026-05-27 Manager-BE errors audit, finding M-7.

Question: should mutate endpoints accept If-Unmodified-Since or expectedUpdatedAt and 409 on mismatch? Today: every PATCH is last-write-wins. Two managers editing the same project simultaneously → the second commit silently overwrites the first.

Decision: Defer to V12. No DB column, no controller annotation, no FE plumbing. Document the gap in this entry so a future agent doesn't re-discover it cold.

Why defer:

  • No concrete user-pain report — the SMB target (1–10 active projects, 1–3 managers per org) has very low edit-collision probability in practice.
  • Atomicity (not consistency) is already enforced where it matters: ownerships.replaceSet wraps the full set-replace in one tx + a sum-to-100 trigger, so concurrent writers serialize correctly on the row lock; projects.create + signature_requests.create + documents.create all have their own pessimistic guards (UNIQUE indexes, atomic state flips).
  • Adding a global version column to every mutable table is a cross-cutting migration that touches ~10 tables + ~10 controllers + the FE. Wrong time before MVP launch.

Alternatives considered:

  • (A) Per-resource opt-in — add the precondition only on resources where a real collision is reported. Pro: pay-as-you-go. Con: we never get coverage; the audit will keep re-flagging it.
  • (B) Global version column + interceptor — uniform pattern across all mutable tables, one migration. Pro: complete. Con: ~10-day cross-cutting churn for an unsubstantiated risk.

Revisit trigger: first user-pain report of "I edited X and my change disappeared", OR Phase-2 enterprise tier (5+ managers per org). At that point (B) becomes the right answer; the migration can be additive (default version=0, gradually enforce per resource).
